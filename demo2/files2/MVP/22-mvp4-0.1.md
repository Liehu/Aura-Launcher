是的。**如果把 `Effect` 设计成一组固定的 `ActionKind`，插件最终一定会被 Host 的 Effect 枚举卡死。**

但这不是“ActionEngine 统一执行”本身的问题，而是 **Effect 抽象层级选错了**。

真正应该冻结的不是：

```text
Effect = Copy | Paste | Open | Execute | ...
```

而是：

> **Effect 是一个“可授权、可验证、可执行的副作用请求”协议；具体 Effect 的语义可以由 Host、Plugin、未来 Workflow Runtime 等不同 Executor 提供。**

这样既保留你现在的单一执行闸门，又不会把插件能力限制在 `system.*`。

---

# 1. 先区分三个东西

你现在其实混合了：

```text
Action
Effect
Executor
```

建议彻底拆开。

### Action

回答：

> 用户/系统想做什么？

例如：

```text
Open Terminal Here
Copy Path
Translate Selection
Compress Files
Export as PDF
```

### Effect

回答：

> 执行这个 Action 需要产生什么副作用？

例如：

```text
clipboard.write
file.move
network.request
plugin.invoke
process.spawn
document.transform
```

### Executor

回答：

> 谁真正执行这个 Effect？

例如：

```text
SystemExecutor
PluginExecutor
NetworkExecutor
WorkflowExecutor
```

所以：

```text
Action ≠ Effect ≠ Executor
```

---

# 2. 现在的 `ActionKind` 不应该继续承担 Effect 的职责

目前你有：

```text
ActionKind::Copy
ActionKind::Paste
ActionKind::Open
ActionKind::Reveal
ActionKind::OpenTerminalHere
ActionKind::Execute
```

这个设计对 MVP3.x 很合适，因为你需要建立第一个可控闭环。

但到了 MVP4，我不建议继续：

```rust
enum ActionKind {
    Copy,
    Paste,
    Open,
    ...
    PluginFooExport,
    PluginBarTranslate,
    ...
}
```

否则会出现典型问题：

> 每增加一个插件能力，都要修改 Host 的核心枚举。

这就意味着你的插件系统实际上不是 extensible。

---

# 3. 更合理的抽象：Effect Descriptor

建议把 Effect 抽象成一个数据对象：

```rust
pub struct EffectRequest {
    pub effect_type: EffectType,
    pub input: Value,
    pub capability: CapabilityId,
    pub target: EffectTarget,
    pub context: ExecutionContext,
}
```

其中：

```text
effect_type
```

不是 Rust enum，而是稳定字符串：

```text
system.clipboard.write
system.process.spawn
system.file.move

plugin.foo.export
plugin.foo.translate
plugin.foo.compress
```

也就是：

```text
EffectType = namespaced string
```

---

# 4. 关键点：Effect Type 应该是开放命名空间

你现在已经有：

```text
system.*
plugin.*
```

可以继续演化成：

```text
system.*
plugin.<plugin_id>.*
workflow.*
```

甚至未来：

```text
mcp.<server_id>.*
```

但是这里我反而建议：

**不要让 `workflow.*`、`ai.*` 成为真正 Effect Domain。**

更合理：

```text
system.*
plugin.<id>.*
```

是实际 Effect。

而：

```text
workflow
ai
mcp
```

属于 Producer / Orchestrator / Adapter。

---

# 5. 于是 Plugin 能力不再受限于 Host 已知 Effect

举个你以后真正会遇到的插件：

### PDF 工具插件

插件提供：

```text
plugin.pdf.merge
plugin.pdf.split
plugin.pdf.compress
plugin.pdf.extract_text
plugin.pdf.ocr
```

Host 根本不需要知道这些具体语义。

Host 只需要知道：

```text
effect_type starts with plugin.pdf.
```

然后交给：

```text
PluginBroker
```

执行。

---

# 6. 这时 ActionResolver 也不需要理解每个插件 Effect

当前：

```text
ActionResolver
    ↓
ActionKind
    ↓
ActionEngine
```

未来应该变成：

```text
ActionResolver
    ↓
ResolvedAction
    ↓
EffectRequest
    ↓
ActionEngine
    ↓
EffectRouter
       ├── system
       └── plugin
```

也就是：

```text
                  ActionEngine
                       │
                 EffectRequest
                       │
                 EffectRouter
                  /          \
                 /            \
        SystemExecutor    PluginExecutor
                               │
                         PluginBroker
```

这样 ActionEngine 只负责**执行生命周期**，而不是理解所有 Effect 的业务语义。

---

# 7. ActionEngine 也不要知道插件业务

这是很重要的一个边界。

比如：

```text
plugin.image.remove_background
```

ActionEngine 不应该有：

```rust
match action.effect_type {
    "plugin.image.remove_background" => ...
}
```

它最多只判断：

```text
namespace = plugin.image
```

然后：

```text
router.resolve(...)
```

这会让 Host 变成一个真正的扩展运行时，而不是插件功能注册表。

---

# 8. Effect 能力应该抽象成“Capability + Effect Type”

这里是避免失控的关键。

不要：

```text
plugin.foo.export
```

自动拥有任何东西。

而是：

```text
Effect Type:
plugin.foo.export

Required Capabilities:
filesystem.read
filesystem.write
plugin.invoke
```

于是：

```text
                    Effect
                      │
                      ▼
              RequiredCapabilities
                      │
                      ▼
                 Policy Check
                      │
            ┌─────────┴─────────┐
            ▼                   ▼
         Allowed              Denied
            │
            ▼
         Executor
```

这样插件可以无限扩展 Effect Type，而 Host 仍然保持权限边界。

---

# 9. 更进一步：Capability 不应该等于 Effect

这是未来非常重要的抽象。

例如：

```text
plugin.pdf.export
```

可能要求：

```text
filesystem.read
filesystem.write
```

但：

```text
plugin.pdf.ocr
```

可能要求：

```text
filesystem.read
network.connect
```

而：

```text
plugin.pdf.preview
```

可能只要求：

```text
filesystem.read
```

所以：

```text
Capability
    ↓
描述允许使用哪些资源

Effect Type
    ↓
描述具体做什么
```

二者是不同维度。

---

# 10. 我建议再抽象一个 `EffectProvider`

这可能是整个系统以后最重要的接口。

```rust
trait EffectProvider {
    fn can_handle(
        &self,
        effect_type: &EffectType
    ) -> bool;

    fn describe(
        &self,
        effect_type: &EffectType
    ) -> EffectDescription;

    fn execute(
        &self,
        request: EffectRequest,
        ctx: &ExecutionContext
    ) -> EffectResult;
}
```

然后：

```text
SystemEffectProvider
PluginEffectProvider
```

都实现它。

---

# 11. Plugin 本身就变成 EffectProvider

对于 Plugin：

```text
Plugin Manifest
        │
        ▼
Effect declarations
        │
        ▼
PluginEffectProvider
        │
        ▼
PluginBroker
        │
        ▼
plugin process
```

插件只需要声明：

```json
{
  "effects": [
    {
      "type": "plugin.pdf.merge",
      "capabilities": [
        "filesystem.read",
        "filesystem.write"
      ]
    }
  ]
}
```

Host 不需要理解：

```text
merge
```

究竟是什么意思。

---

# 12. 但这里有一个安全问题：不能让插件自由定义 Capability

例如不能：

```json
{
  "effect": "plugin.foo.delete_everything",
  "capabilities": [
    "admin.unrestricted"
  ]
}
```

然后 Host：

```text
“manifest 说需要 admin，那就给 admin”
```

所以必须分层：

```text
Plugin declares requested capabilities
                ↓
Host policy
                ↓
Granted capabilities
```

即：

```text
Requested != Granted
```

你现有模型正好可以继续扩展。

---

# 13. Effect Description 应该做成能力契约

我建议未来 Effect Descriptor 大概长这样：

```json
{
  "type": "plugin.pdf.compress",
  "version": 1,
  "input_schema": {
    "type": "object",
    "fields": {
      "input": "path",
      "output": "path",
      "level": "u8"
    }
  },
  "requires": [
    "filesystem.read",
    "filesystem.write"
  ],
  "confirmation": "optional",
  "context": {
    "location": true
  }
}
```

注意这里：

**Host 不需要理解 `compress` 的业务含义。**

它只需要理解：

```text
type
schema
requires
confirmation
context
```

这些是 Runtime-level metadata。

---

# 14. 这其实就是“Declarative Effect Contract”

你前面做的 Action Contract 本质上已经走在这条路上。

可以继续演化成：

```text
ActionDescriptor
       │
       └── declares intent

EffectDescriptor
       │
       └── declares side effect contract

EffectRequest
       │
       └── actual invocation

EffectExecutor
       │
       └── actual implementation
```

这四层特别干净。

---

# 15. Action 和 Effect 可以是 1:N

这一点非常关键。

例如：

```text
Action:
"Publish PDF"
```

实际上可能需要：

```text
Effect #1
plugin.pdf.render
Effect #2
system.file.write
Effect #3
plugin.cloud.upload
```

所以不要设计：

```text
Action -> one Effect
```

应该允许：

```text
Action
  ↓
EffectPlan
  ↓
EffectInvocation[]
```

但这里 **Workflow** 和普通 Action 要区分。

---

# 16. 我建议 ActionEngine 内部引入 `EffectPlan`

例如：

```text
ResolvedAction
      ↓
EffectPlan
      ├── EffectInvocation #1
      ├── EffectInvocation #2
      └── EffectInvocation #3
```

于是：

```text
ActionEngine
    ↓
validate plan
    ↓
execute effects
    ↓
aggregate result
```

这会为未来 Workflow 铺路。

---

# 17. 但是不要让插件直接提交任意 EffectPlan

例如：

```text
Plugin
 ↓
EffectPlan [
  system.execute,
  filesystem.write,
  network.connect
]
```

然后 Host 全盘执行。

这实际上又回到了“插件拥有执行引擎”。

正确的是：

```text
Plugin Action
    ↓
Plugin declares Effect contract
    ↓
Host resolves
    ↓
Host creates Resolved EffectPlan
    ↓
ActionEngine
```

换句话说：

> **Plugin 可以声明它希望产生什么 Effect，但最终 EffectPlan 必须由 Host 解析出来。**

# 19. 一个非常有价值的抽象：Effect ≠ OS Effect

当前你的命名容易让人理解成：

```text
Effect = OS 副作用
```

实际上应该定义：

> **Effect = 系统承诺提供的副作用执行能力。**

那么：

```text
system.clipboard.write
```

只是其中一种。

而：

```text
plugin.pdf.compress
```

同样是 Effect。

这就能保证：

```text
Effect Engine
```

不是：

```text
OS API wrapper
```

而是：

```text
Side-effect execution runtime
```

# 21. 最终的能力空间应该是“开放的”

而不是：

```text
┌────────────────────────────┐
│ Host knows all Effects     │
│                            │
│ Copy                       │
│ Paste                      │
│ Open                       │
│ Execute                    │
│ ...                        │
└────────────────────────────┘
```

应该变成：

```text
                 Effect Namespace
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
     system.*      plugin.foo.*   plugin.bar.*
        │              │              │
   Host executor   Plugin executor Plugin executor
```

Host 只定义：

```text
Namespace semantics
Capability semantics
Execution lifecycle
Security policy
Timeout
Error model
Audit
Context binding
```

而不定义：

```text
所有具体业务功能
```

这就是插件可扩展性的关键。

---

# 22. 但我不建议无限开放 `system.*`

这里需要一个明确的边界：

```text
plugin.<id>.*
```

应该是开放扩展命名空间。

而：

```text
system.*
```

应该是 **Host-owned closed namespace**。

例如：

```text
system.clipboard.write
system.clipboard.read
system.process.launch
system.file.move
system.window.focus
system.shell.execute
```

这些由 Host 定义、Host 实现、Host 管理权限。

插件不能定义：

```text
system.plugin_magic.*
```

否则系统安全边界就会退化。

# 23. Plugin Effect 与 Plugin RPC 的关系

最终：

```text
plugin.foo.compress
```

并不是：

```text
RPC method = plugin.foo.compress
```

建议实际上：

```text
EffectType:
plugin.foo.compress

RPC:
execute_effect
```

也就是说 RPC 是固定协议：

```json
{
  "method": "execute_effect",
  "params": {
    "execution_id": "e-100",
    "effect_type": "plugin.foo.compress",
    "input": {...}
  }
}
```

这样 Plugin Contract 不需要因为插件增加新 Effect 就变版本。

这非常重要。

# 26. Effect Capability 还可以进一步分层

这是后面安全系统很有价值的一步：

```text

        ↓
Operation Capability
        ↓

```

例如：

```text

        ↓

        ↓
```

甚至可以做到：


> `plugin.* = Plugin RPC Action`

而是：

> **`plugin.*` = Plugin-owned Effect namespace.**

然后：

```text
       ↓

       ↓

       ↓

       ↓
```

这比“Plugin Action RPC”这个命名其实更精确。

# 28. 最终我建议冻结一个新的四层模型

### Intent Layer

```text
Command
ActionDescriptor
ActionProposal
```

回答：

> 想做什么？

### Resolution Layer

```text
ActionResolver
CapabilityPolicy
ContextPolicy
ConfirmationPolicy
```

回答：

> 现在允许做吗？

### Effect Layer

```text
EffectDescriptor
EffectInvocation
EffectPlan
```

回答：

> 需要产生什么副作用？

### Execution Layer

```text
ActionEngine
EffectRouter
EffectProvider
SystemExecutor

```

回答：

> 谁实际做？

完整关系：

```text
      INTENT
         │
         ▼

         │
         ▼
    ResolvedAction
         │
         ▼
     EffectPlan
         │
         ▼
   ┌───────────────┐
   │ ActionEngine  │
   └───────┬───────┘

 system.*       plugin.*
    │               │

    │               │
```

## 我认为这会比当前模型更适合作为 MVP4 的基础

**不要把 `ActionEngine` 变成“所有功能的巨大 switch”。**

应该让它成为：

> **统一的执行生命周期与安全边界。**

而真正的能力空间由：

```text
EffectType
+
EffectDescriptor
+
EffectProvider
+
Capability
```

共同定义。

这样：

```text
Host
```

控制安全、生命周期和系统能力；

```text
Plugin
```

可以无限增加自己的 `plugin.<id>.*` Effect；

```text
AI / Workflow / MCP
```

可以产生 Proposal，但不能跳过 Resolver / ActionEngine；

最终仍然只有一个副作用入口：

```text
ActionEngine
```

这实际上解决了你担心的核心矛盾：

**“统一执行”与“插件无限扩展能力”并不冲突；真正需要统一的是执行协议、策略和生命周期，而不是 Effect 的具体语义。**

我建议下一步把这个模型正式落实成 **ADR-0014 的修正版 + `EFFECT-CONTRACT-v0.1`**，尤其先冻结 `EffectDescriptor / EffectInvocation / EffectPlan / EffectProvider / Capability scope / execute_effect RPC` 六个核心接口。
