### 1. `ActionProposal` 做成结构性信任边界，是很好的决定

你没有采用：

```text id="3rxq9v"

  + confirmed
  + trust_level
```

再依靠：

而是直接让类型不存在这些字段：

```text id="l96qdb"
ActionProposal {
    provider_id
```

于是：

```text id="yi5d3g"

   ↓

   ↓
ActionProposal
```

模型输出的：

```text id="85qf7z"

confirmed
granted_capabilities
trust_level
resolved_action
effect
```

根本无法进入 Proposal 模型。

这是比“再写一个 if 检查”更强的边界，因为它已经从业务规则变成了**数据模型约束**。

## 2. `ActionPlanner` 的抽象层级现在很合适

```text id="7sbw1x"
trait ActionPlanner {
    plan(input, catalog) -> Vec<ActionProposal>
}
```

这个接口有三个很好的限制：

```text id="wq0cek"
Planner
  ├── 不监听 Context
  ├── 不拥有 Effect
  └── 不进入 ActionEngine
```

因此以后：

```text id="8qd2mk"
KeywordPlanner
LLMPlanner
RemotePlanner
```

都是同一类 Producer。

Core 不需要：

```rust id="1m2yyu"
if ai_enabled { ... }
```

这正好证明了你之前的架构目标：

> **AI 是 Producer，而不是 Runtime。**

# 7. 现在唯一需要提前想清楚的，是 MCP Tool → ActionProposal 的身份问题

AI Planner 目前有：

```text id="7kdwzh"

action_id
input
```

MCP Adapter 也必须提供这四项。

但是 MCP 自己的：

```text id="5jgyx4"
server_id
tool_name
```

不能直接冒充 Launcher 的：

```text id="ProviderId
CommandId
ActionId
```

建议将来明确：

```text id="1nkk4t"
MCP identity
   ↓
MCP Adapter assigned provider identity
   ↓
Command / Action namespace
```

仍然由 Host 负责最终 Provider identity。

否则 MCP 会重新打开你已经在 MVP4.0 解决过的 provider spoofing 问题。

# 8. AI Planner 还有一个很好的结果：`catalog` 应该继续保持只读

你现在：


其中 `catalog` 是只读的。

建议长期保持：

```text id="6gjeqf"

    ↓

    ↓
```

```text id="tfj6lc"

    ↓
```

如果未来 AI 想“创建一个临时能力”，应该另设计 Capability/Provider registration 机制，**不要污染 Planner**。
