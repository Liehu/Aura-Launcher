### 我建议 MVP3.2 先冻结一个核心状态机

3.1 已经有：

```text
ActionDescriptor
      ↓
ActionResolver
      ↓
Ready / Disabled / Hidden / Invalid
      ↓
ActionPresentation
      ↓
ActionPanel
      ↓
ActionEngine
      ↓
Effect
```

3.2 可以扩展成：

```text
                  ┌───────────────┐
                  │ ActionDeclared│
                  └───────┬───────┘
                          ↓
                    ActionResolver
                          │
             ┌────────────┼────────────┐
             ↓            ↓            ↓
          Hidden       Disabled      Ready
                                       │
                              ┌────────┴────────┐
                              ↓                 ↓
                          Shortcut         User Execute
                              │                 │
                              └────────┬────────┘
                                       ↓
                                Confirmation?
                                │           │
                               No          Yes
                                │           ↓
                                │      ConfirmPending
                                │           │
                                │      Confirmed
                                │           │
                                └─────┬─────┘
                                      ↓
                                ActionEngine
                                      ↓
                                    Effect
                                      ↓
                                   Result
```

然后 Context Refresh 独立作用于 Resolver：

```text
ContextSnapshot(t0)
       ↓
   Resolver
       ↓
ActionResolution
       │
       │ ContextChanged
       ↓
ContextSnapshot(t1)
       ↓
  re-resolve
       ↓
ActionPresentation'
```

这里有一个很重要的边界：**Context Refresh 不应该由 ActionPanel 自己解释和处理。** Panel 仍然只是消费新的 Presentation。

## 3.2-A Shortcut

重点不是“给 Action 加一个快捷键”，而是建立稳定的：

```text
shortcut → action_id
```

映射。

建议最终语义：

```text
Ctrl+Shift+C
      ↓
selected command
      ↓
action_id
      ↓
ActionEngine
```

而不是：

```text
Ctrl+Shift+C
      ↓
直接调用 clipboard API
```

这样 INV-037 继续成立。

同时需要解决两个问题：

```text
Shortcut collision
Shortcut applicability
```

例如同一个面板中的两个 Action 声明同一快捷键时，必须有确定规则，而不是由 Slint 控件顺序碰巧决定。

---

## 3.2-B Confirmation

这里建议**不要把 `confirmation` 简单变成 UI Boolean**。

更合理的是：

```text
ActionDescriptor.confirmation
          ↓
ActionResolver
          ↓
ExecutionPolicy
          ↓
ConfirmationRequired
```

也就是 Confirmation 属于**执行策略**，不是 Presentation 属性。

这样未来可以自然扩展：

```text
confirmation:
  required
  message
  destructive
```

而 UI 只负责：

```text
ConfirmationRequired
      ↓
显示确认
      ↓
Confirm / Cancel
```

真正的 Effect 仍旧只能由：

```text
ActionEngine
```

触发。

尤其要保持你 3.1 已经冻结的语义：

> **Effect 一旦提交，Esc 不负责取消 Effect。**

---

## 3.2-C Context-aware Refresh

这是 MVP3.2 中架构价值最高的一项。

建议明确区分三个时刻：

```text
T0 = Command resolve
T1 = ActionPanel open
T2 = Action execute
```

Context 可能在任何阶段变化。

因此需要定义：

```text
ContextSnapshot.version
```

或者等价的 generation：

```text
context_generation = 42
```

然后 ActionResolution 携带：

```text
resolved_context_generation = 42
```

执行时发现：

```text
current_context_generation != resolved_context_generation
```

就可以：

```text
re-resolve
```

这能避免非常典型的 TOCTOU 问题：

```text
用户看到：
Open Terminal Here
        ↓
用户切换 Explorer 文件夹
        ↓
Enter
        ↓
仍然对旧目录执行
```

这正是 Context-aware Action 生命周期真正需要解决的问题。

# `system.paste` 可以这样定位

建议把它作为第一个新的 Host-owned Effect：

```text
system.copy
system.open
system.reveal
system.open_terminal_here
system.execute
        │
        └── existing
          
system.paste
        └── MVP3.2 candidate
```

但不要把：

```text
system.paste
```

实现成一个“ActionPanel 特殊按钮”。

应该继续走：

```text
ActionDescriptor
      ↓
ActionResolver
      ↓
ResolvedAction
      ↓
ActionEngine
      ↓
system.paste Effect
```

这样它会成为一个很好的架构验证点：

```text
Native Action UI
        +
Shortcut
        +
Confirmation
        +
Context
        +
new System Effect
```

### 关键新增 invariants

建议至少考虑：

```text
INV-040
Shortcut execution resolves to stable action_id.

INV-041
Shortcut dispatch never bypasses ActionEngine.

INV-042
Confirmation is an execution-policy state, not a UI-only flag.

INV-043
A confirmed Action still executes only through ActionEngine.

INV-044
Action resolution is bound to a ContextSnapshot/version.

INV-045
Stale context resolution cannot silently execute against a changed context.

INV-046
Context refresh is owned by Core/Resolver, not ActionPanel.

INV-047
system.paste is a normal Host-owned Effect and follows the same ActionEngine path.
```

这样进入 MVP3.2 后，重点就不是继续堆 UI，而是把 **Action 从“静态可执行描述”正式升级成具有 Shortcut → Confirmation → Context → Execution 生命周期的系统对象**。

**MVP3.1 已经可以视为稳定基线；MVP3.2 的核心目标则应明确为：`Action Lifecycle`，而不是“再加几个 Action 功能”。**
