# MVP4.4 / v0.2 Backlog

MVP4.3 已经完成封版，因此 v0.2 最重要的原则不是“继续堆功能”，而是：

> **在不破坏 MVP4.3 Authority Model、Provider/Producer/Executor 边界和现有 Contract 的前提下，扩大能力面。**

我建议把 MVP4.4 定义为一个 **Capability Expansion Release**，同时把纯视觉工作单独归入 v0.2 Visual Polish。

---

# 1. v0.2 总体路线

```text
MVP4.3
    │
    ├── Architecture FROZEN
    ├── Security FROZEN
    ├── Workflow Contract FROZEN
    ├── Action Contract FROZEN
    └── MCP Core FROZEN
             │
             ▼
        MVP4.4 / v0.2
             │
      ┌──────┼────────┬──────────┐
      │      │        │          │

      │      │        │          │
      ▼      ▼        ▼          ▼
   Remote  Agent    Advanced   Polish
   MCP     Planning  Runtime   Visual
```

建议不要把这四条线全部同时推进。

# 5. MVP4.4-C — Persistent MCP Session

这是一个很值得做、但应该与 v0.1 runtime 模型隔离的优化。

当前：

```text id="mcp-current"
execute
 ↓
spawn
 ↓
call
 ↓
shutdown
```

v0.2：

```text id="mcp-session"
McpSessionManager
        │
        ├── calc
        ├── github
        └── filesystem
```

生命周期：

```text
Stopped
  ↓
Starting
  ↓
Ready
  ↓
Idle
  ↓
Running
  ↓
Idle
  ↓
Stopping
```

---

## C1 Session Policy

不要默认全部 persistent。

配置：

```toml id="session-config"
[[mcp.servers]]
id = "github"
session = "persistent"
```

支持：

```text
ephemeral
persistent
```

---

## C2 Crash Isolation

persistent server crash：

```text
McpSession
   ↓
Crashed
   ↓
cleanup
   ↓
optional restart
```

重要：

```text
old execution_id
≠
new execution_id
```

不得复用旧 execution attempt。

---

## C3 Session Security

Session 只保存：

```text
transport state
protocol state
process state
```

不能保存：

```text
authorization grant
confirmation
ResolvedAction
Workflow approval
```

# 8. Agent 安全边界

必须保持：

```text id="agent-authority"
Agent
 X → capability grant
 X → confirmation
 X → raw Effect
 X → McpExecutor
 X → PluginBroker
```

Agent loop：

```text
MAX_STEPS
MAX_EXECUTIONS
MAX_RUNTIME
MAX_RETRIES
```

全部 bounded。

否则容易变成：

```text
LLM
 ↓
tool
 ↓
LLM
 ↓
tool
 ↓
infinite loop
```

# 9. MVP4.4-F — Workflow v0.2

当前 Workflow v0.1 是：




```text

  - id: search

```

但变量解析应位于：

```text

```

```text

```

---

## F2 Conditions

```text

```

```text

   ↓

   ↓

```

但：

```text

```

本身不是 Effect。

# 22. 我建议 MVP4.4 P0 先锁这四项

如果只考虑**工程收益 / 架构风险**：

### P0-1 RuntimeSupervisor

因为 Plugin + MCP 已经出现明显的：

```text
spawn
timeout
shutdown
reap
```

重复。

### P0-2 Streamable HTTP

MCP 从本地工具真正进入远程工具生态的必要条件。

### P0-3 MCP Auth

否则 HTTP MCP 很难成为真正可用的 production capability。

### P0-4 LLM Planner

因为现有：

```text
KeywordPlanner
```

已经把 Proposal → Workflow 架构验证完成，现在是自然的能力升级点。

# 24. v0.2 Backlog 的 Contract 规则

以后每个新功能都必须回答四个问题：

```text
1. Is it Data?
2. Is it Proposal?
3. Is it Resolution?
4. Is it Effect?
```

如果一个新模块回答不清楚：

> “它究竟在哪一层？”

就不要开始实现。

再加一个硬规则：

```text
New Producer
    → Proposal only

New Executor
    → Effect only

New Metadata
    → cannot increase authority
```

这样 v0.2 才不会重新破坏 MVP4.3 已经建立的边界。

# 26. 最重要的“禁止事项”

MVP4.4 期间建议永久禁止以下演化：

```text id="forbidden"
❌ MCP → ActionEngine direct call
❌ AI → Effect direct call
❌ Agent → McpExecutor direct call
❌ Workflow → Executor direct call
❌ Provider → Executor direct call

❌ MCP-specific WorkflowAction
❌ MCP-specific ActionProposal
❌ AI-specific Effect
❌ Protocol version in domain
❌ Transport type in Workflow
❌ metadata → capability grant
❌ confidence → authorization

❌ UI Dashboard化
❌ Plugin/MCP authority合并
❌ 为便利而绕过 Resolver
```

## MVP4.4 的核心方向

MVP4.3 解决的是：

> **“外部能力能否安全进入 Launcher 的统一执行模型？”**

答案已经是肯定的。

MVP4.4 应该解决：

> **“统一执行模型能否承载更多真实生产能力，而不牺牲原来的低内存、低延迟、可验证安全边界？”**

因此我建议下一阶段正式从：

```text
MVP4.3
Integration + Security
```

切换到：

```text
MVP4.4
Runtime Foundation + Remote Capability + AI
```

并把 **RuntimeSupervisor → Streamable HTTP/Auth → LLM Planner → Agent/Workflow v0.2 → Visual Polish** 作为主线。
