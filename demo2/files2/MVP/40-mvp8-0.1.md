# MVP4.3 MCP Adapter v0.1

**Status:** FROZEN
**Date:** 2026-09-05
**Depends on:** Action Contract v0.1 / Workflow Contract v0.1 / AI Planner v0.1 / Plugin Contract v0.1 / UI Contract v0.1

---

## 1. 目标

MVP4.3 的目标：

> 将 MCP Server 暴露的 `tools` 转换为 Launcher 内部的 `ActionProposal`，并复用既有 Workflow / ActionResolver / ActionEngine / PluginBroker 执行链。

MCP Adapter 本身：

* 不执行 Effect；
* 不调用 `ActionEngine`；
* 不获取 `ResolvedAction`；
* 不持有 capability grant；
* 不直接访问 PluginBroker；
* 不绕过 Workflow；
* 不成为新的 Effect Gateway。

核心数据流：

```text
MCP Server
    │
    ▼
MCP Client / Transport
    │
    ▼
MCP Adapter
    │
    ├── Tool Catalog
    ├── Tool Identity
    ├── Input Schema
    └── Tool Metadata
    │
    ▼
MCP Tool Invocation
    │
    ▼
ActionProposal
    │
    ▼
Workflow
    │
    ▼
ReferenceResolver
    │
    ▼
ActionResolver
    │
    ▼
ActionEngine
    │
    ▼
Effect
```

# 2. MCP 版本策略

当前 MCP 已于 **2026-07-28** 发布新的规范版本，其核心发生了重大变化：协议核心转向无状态请求/响应模型，并引入可缓存的列表结果、HTTP Header 路由以及新的授权模型。

因此 MVP4.3 不应该把传输层、session 生命周期直接写死在 Launcher Core。

采用：

```text
launcher-mcp
    │
    ├── protocol
    ├── transport
    ├── catalog
    ├── adapter
    └── invocation
```

内部统一抽象：

```rust
trait McpTransport {
    async fn initialize(...) -> Result<...>;
    async fn list_tools(...) -> Result<ToolCatalog>;
    async fn call_tool(...) -> Result<ToolResult>;
}
```

具体 stdio / HTTP / Streamable HTTP 等 transport 属于 Adapter 实现细节。

MVP4.3 第一阶段建议：

```text
stdio      REQUIRED
HTTP       ARCHITECTURE RESERVED
remote auth RESERVED
```

不要为了支持所有 MCP transport 把 Core API 固定住。

# 5. MCP Tool → Launcher Identity

MCP Tool 的原始身份：

```text
server_id + tool_name
```

Launcher 内部需要稳定身份：

```text
mcp.<server_id>.<tool_name>
```

但是：

> 外部 MCP 名称绝不能直接成为 Launcher 的 authority identity。

规范化：

```rust
struct McpToolIdentity {
    server_id: McpServerId,
    tool_name: String,
}
```

展示层可以生成：

```text
provider_id = "mcp:<server_id>"
command_id  = "<tool_name>"
action_id   = "invoke"
```

例如：

```text
server_id = "github"
tool_name = "search_repositories"
```

变成：

```text
provider_id = "mcp:github"
command_id  = "search_repositories"
action_id   = "invoke"
```

稳定 Route Identity：

```text
(
    provider_id,
    command_id,
    action_id
)
```

# 6. 为什么 action_id 固定为 invoke

MCP Tool 本质上已经是“可调用能力”。

因此 MVP4.3 不应人为生成：

```text
copy
open
execute
preview
...
```

一个 MCP Tool 对应：

```text
Command
    └── Action(invoke)
```

例如：

```text
GitHub Search
    provider = mcp:github
    command  = search_repositories

    actions:
      invoke
```

Descriptor：

```json
{
  "id": "invoke",
  "title": "Run",
  "type": "plugin.mcp.invoke",
  "input": {
    ...
  }
}
```

但注意：

`plugin.mcp.invoke` 只是 presentation/dispatch classification。

长期应继续服从：

```text
effect_type = "plugin.<namespace>..."
```

而不是扩张 `ActionKind`。

# 8. ActionProposal

MCP Adapter 最终只能生成现有：

```rust
ActionProposal {
    provider_id,
    command_id,
    action_id,
    input,
}
```

不得扩展：

```text
authorization
confirmed
granted_capabilities
trust_level
resolved_action
effect
```

MCP 不得携带 authority。

例如：

```json
{
  "provider_id": "mcp:github",
  "command_id": "create_issue",
  "action_id": "invoke",
  "input": {
    "repository": "foo/bar",
    "title": "test"
  }
}
```

这是合法 Proposal。

下面这种必须拒绝/丢弃：

```json
{
  "provider_id": "mcp:github",
  "command_id": "create_issue",
  "action_id": "invoke",

  "authorized": true,
  "confirmed": true,
  "granted_capabilities": [
    "network.connect"
  ]
}
```

原因与 MVP4.2 AI Planner 完全相同：

> Producer 只能提出意图，不能声明权限。

# 9. MCP Tool Input Schema

MCP Tool 定义可以携带 JSON Schema。

2026-07-28 规范继续强化 Tools，并允许完整 JSON Schema 2020-12。

因此 Adapter 保留：

```rust
input_schema: JsonSchema
```

但：

```text
Schema ≠ Authorization
Schema ≠ Capability
Schema ≠ Effect Policy
```

Schema 只负责：

```text
shape validation
type validation
required field validation
```

最终仍由 ActionResolver / Engine 执行权链决定是否允许执行。

# 10. MCP Tool Catalog

维护：

```rust
struct McpCatalog {
    servers: HashMap<McpServerId, McpServer>,
}

struct McpServer {
    id: McpServerId,
    name: String,
    tools: Vec<McpTool>,
}

struct McpTool {
    identity: McpToolIdentity,
    title: Option<String>,
    description: Option<String>,
    input_schema: JsonSchema,
    annotations: McpToolAnnotations,
}
```

MCP `tools/list` 可以携带缓存信息，因此 Catalog 层允许缓存，但必须遵守服务端提供的缓存语义。

建议分为：

```text
Discovery Cache
    ↓
MCP Catalog
    ↓
Command projection
```

而不是每次用户搜索都重新调用 MCP Server。


# 13. Empty Query Discovery

这是 MVP4.3 的关键补齐项。

此前 Workflow / AI 已经留下：

```text

```

的 TODO。

MVP4.3 应正式解决：

```text
Provider.search("")
```

例如：

```text

    ↓
```

```text
Current Popup Results
       ↓
Fresh Provider Query("")
       ↓
exact provider_id + command_id
```

而不再依赖 AI 当前临时的 live snapshot。

# 15. Effect Ownership

MCP Server 是外部能力提供者，因此：

```text
plugin.mcp.invoke
```

属于 Plugin Effect Execution Domain。

执行链：

```text
ActionEngine
    │
    ▼
Effect::PluginInvoked
    │
    ▼
Core::execute_plugin_action()
    │
    ▼
MCP Executor
    │
    ▼
MCP Client
    │
    ▼
MCP Server
```

注意：

```text
MCP Adapter != MCP Executor
```

Adapter：

```text
Tool → Proposal
```

Executor：

```text
Resolved Effect → MCP call
```

这两个组件必须分开。

```rust
trait McpExecutor {
```

# 17. execution_id

保持 MVP4.0/4.1：

```text
one Effect attempt
    =
one execution_id
```

因此：

```text
WorkflowRun
    │
    └── StepRun
          │
          └── attempt
                │
                └── execution_id
```

MCP 请求应携带：

```text
execution_id
```

作为内部 correlation identity。

MCP Server 不需要理解 Launcher 的 execution semantics。

# 18. MCP Failure Mapping

MCP Adapter/Executor 的原始错误必须归一化到既有 FailureClass。

建议：

| MCP Error                    | Workflow FailureClass |
| ---------------------------- | --------------------- |
| invalid arguments            | InvalidInput          |
| unknown tool                 | CommandNotFound       |
| server unavailable           | PluginUnavailable     |
| connection timeout           | Timeout               |
| tool execution error         | BusinessError         |
| malformed protocol response  | ProtocolViolation     |
| process crash                | ProtocolViolation     |
| local capability restriction | CapabilityDenied      |

Workflow 不允许自行判断 MCP 原始 error string。

统一：

```text
McpError
   ↓
Failure Classifier
   ↓
FailureClass
```

这与现有 Plugin error mapping 保持一致。

# 19. Confirmation

MCP Tool annotations 可以提供风险相关提示，但这些只能作为 metadata，不能直接赋予或取消 Launcher authorization。MCP 官方也明确将 tool annotations 定位为行为/风险提示，而非权限本身。

因此：

```text
MCP annotation
      ↓
metadata / hint
      ↓
Policy
      ↓
ActionResolver
```

不能：

```text
destructiveHint=true
    ↓
自动拒绝

readOnlyHint=true
    ↓
自动允许
```

是否 Confirmation：

```text
ActionDescriptor.confirmation
       +
local policy
       +
required capability
```

统一由既有 Resolver 决定。

# 20. Capability

MVP4.3 不新增 MCP 专属 capability 模型。

例如 MCP Tool 需要访问网络：

```text
network.connect
```

仍然由 Launcher 自己的 capability policy 判断。

MCP Server 声明：

```text
networkRequired = true
```

不等于：

```text
Launcher grants network.connect
```

原则：

```text
External Metadata
        ↓
Policy Input
        ↓
ActionResolver
        ↓
Allowed / Denied
```

# 29. Security Boundary

MCP Server 必须被视为：

```text
UNTRUSTED EXTERNAL PROVIDER
```

不能把：

```text
tool.description
tool.name
server.instructions
tool.annotations
```

视为可信 authority。

特别是 server-provided instructions 必须保持为普通数据；不要让它直接修改：

```text
system policy
capabilities
permissions
confirmation
```

MCP 官方近期也持续强化 server instructions、tool annotations 与授权安全模型，这进一步说明 Adapter 应把这些内容当作输入，而不是授权来源。

# 30. Protocol Isolation

MCP protocol types 不直接进入：

```text

launcher-workflow
```

必须经过：

```text
MCP Protocol DTO
      ↓

      ↓
Launcher Domain Projection
```

例如：

```text

      ↓
McpTool
      ↓

```

避免未来 MCP protocol change 污染整个 Workspace。

# 34. ADR

新增：

```text
ADR-0017 MCP Adapter as Proposal Producer
```

核心决策：

```text
MCP = Producer
```

而不是：

```text
MCP = Execution Framework
```

ADR 应明确记录：

```text
MCP → ActionProposal
MCP ≠ ActionEngine
MCP ≠ EffectGateway
```
