有。整体上这份已经可以称为 **FROZEN v0.1**，主架构没有倒退，但我看到 **4 个值得在真正开工前修掉的问题，其中 2 个是实际语义缺口，2 个是容易导致后续实现分叉的问题**。

我直接按严重程度说。

## 1. 【必须修】`Inline(ActionDescriptor)` 与 `WorkflowStep.input` 存在“双重输入源”

当前定义是：

```text
WorkflowStep {
    step_id
    action: WorkflowAction
    input: Value
    failure_policy
}

WorkflowAction {
    Reference(ActionReference)
    Inline(ActionDescriptor)
}
```

而 `ActionDescriptor` 本身已经包含 `input`。

因此 Inline 时会出现：

```text
Inline(ActionDescriptor.input)
+
WorkflowStep.input
```

例如：

```json
{
  "action": {
    "Inline": {
      "id": "copy",
      "type": "system.copy",
      "input": {"text": "A"}
    }
  },
  "input": {
    "text": "B"
  }
}
```

到底执行 A 还是 B，目前契约没有答案。

这不是小问题，因为以后：

```text
Workflow → ActionInvocation → Resolver
```

到底拿哪个 input，会变成实现者自行解释。

### 我建议直接冻结成：

**`WorkflowStep.input` 是唯一执行输入。**

因此：

```rust
struct WorkflowStep {
    step_id: StepId,
    action: WorkflowAction,
    input: Value,
    failure_policy: StepFailurePolicy,
}
```

同时规定：

```text
Reference
    → ActionDescriptor 由 ReferenceResolver 找到
    → 使用 WorkflowStep.input

Inline
    → ActionDescriptor 只提供 action metadata
    → 使用 WorkflowStep.input 覆盖 descriptor.input
```

更干净的做法甚至是把 `ActionDescriptor.input` 理解成**声明/默认输入**，而 Workflow invocation input 是最终输入。

必须明确一个规则，例如：

> `ActionInvocation.input` is authoritative for execution. Persisted descriptor input MUST NOT create a second input source.

否则以后 AI/MCP 复用 `ActionInvocation` 时还会再次遇到这个问题。

# 2. 【必须修】R1 的 Fresh Provider Query 目前与现有 Plugin Query Contract 有潜在接口错位

文件现在写的是：

```text
Fresh Provider Query：
按指定 provider_id 获取新 Command 集合
不是重新执行用户搜索词
按 (provider_id, command.id) 精确匹配
```



这个语义本身正确，但需要确认一个实际问题：

**当前 Plugin Contract 的 `query` 本质上是搜索接口，而不是 `get_command_by_id()` / `list_commands()` 接口。**

如果它仍然要求：

```text
query(text, limit)
```

那么：

```text
ActionReference(command_id = "foo")
```

执行时拿什么 `text` 去 fresh query？

如果传：

```text
text = ""
```

那么必须明确规定：

> 空 query 是 provider command discovery，而不是普通搜索。

否则 Runner 只能：

```text
“先随便搜”
```

然后希望目标 command 恰好出现在结果里，这与 R1 的：

> 按 `(provider_id, command.id)` 精确匹配

并不完全等价。

### 建议冻结一个非常小的语义

不要新增新的 RPC。

直接定义：

```text
Fresh Provider Query
    provider_id = referenced provider
    text = ""
    limit = provider-defined / bounded discovery limit
```

并规定：

> 对 Reference Resolution 而言，Provider 的 empty-text query 必须返回其可发布 Command 集合的发现结果。

如果当前 Provider/Plugin Contract 无法保证这一点，那么真正应该增加的不是 Workflow API，而是一个独立的：

```text
resolve_commands / list_commands
```

机制。

**我更倾向于先采用 empty query discovery，避免为一个 Workflow Resolution 问题提前扩大 Plugin Contract。**

# 3. 【应该修】`Inline(ActionDescriptor)` 的“Host-owned”约束还不够机器可验证

契约写的是：

```text
Inline(ActionDescriptor)
/// Host-owned 内联声明
```



但这里还没有明确：

```text
Inline
→ 只能 system.*
```

否则未来一个实现者完全可能写：

```text
Inline(
    ActionDescriptor {
        type = "plugin.com.example.foo.delete"
    }
)
```

这时候它到底：

```text
allowed?
provider identity 从哪里来？
plugin ownership 怎么验证？
```

又会重新打开 MVP4.0 已经解决的身份边界。

### 我建议直接加规则：

```text
WorkflowAction::Inline
    → MUST be Host-owned system.* ActionDescriptor

plugin.* MUST use Reference(ActionReference)
```

这样：

```text
Reference
    → Provider-owned / Plugin-owned Command

Inline
    → Host-owned system.*
```

语义非常漂亮：

```text
Reference = external capability reference
Inline    = Host-native declarative action
```

而不是两种任意 Action 输入形式。

# 4. 【建议冻结】`CommandNotFound` 与 `PluginUnavailable` 的边界要再明确一次

现在 Failure Classification 已经很好：

```text
PluginUnavailable
    Spawn / 未安装

CommandNotFound
    ReferenceResolver
```



但存在一个边界情况：

```text
provider 存在
   ↓
fresh query
   ↓
provider 返回成功
   ↓
目标 command 不存在
```

这是：

```text
CommandNotFound
```

没问题。

但是：

```text
provider 存在
   ↓
无法启动 plugin
```

应该：

```text
PluginUnavailable
```

这个也明确了。

真正需要补的是：

```text
provider 查询成功
但返回 malformed command
```

到底：

```text
InvalidInput
```

还是：

```text
ProtocolViolation
```

按照你 MVP4.0 已有语义，我建议：

```text
malformed Provider/Plugin response
→ ProtocolViolation
```

不要让 Workflow 把“Provider 返回坏数据”当成 CommandNotFound。

# 5. 状态机本身没有大问题

这部分我认为是正确的。

Run：

```text
Created
 → Queued
 → Running
 → Paused(ConfirmationRequired)
 → Succeeded / Failed / Cancelled
```

并且明确：

> 没有 run-level Retrying。

这是对的。

Step：

```text
Pending
 → Resolving
 → Resolved
 → WaitingForConfirmation
 → Executing
 → Complete / Failed / Skipped
```

而：

```text
stale / retry
    ↓
Resolving
```



也正确。

尤其 `Resolving` 可重入这一点，为未来 AI/MCP 保留得很好。

# 6. `resolved_context_generation` 的语义现在也是一致的

已经明确：

> 最近一次成功解析所依据的 generation。

因此：

```text
Resolving
    ↓
Resolved
    ↓
resolved_context_generation = N
```

如果：

```text
current_context_generation != N
```

回：

```text
Resolving
```

而不是拿旧的 `ResolvedAction` 继续执行。

这一点没有问题。

# 7. `WorkflowRun` 序列化设计正确，但有一个隐含前提

文件明确写了：

```text
Serializable != Resumable
```

而且只冻结 stable serializable representation，不冻结 SQLite/File/Memory。

这是合理的。

但是 `StepRun` 里：

```text
last_execution_id
attempt
status
```

都意味着未来“reload”之后能够知道：

```text
这个步骤之前发生过 execution attempt
```

这没问题。

但不能让 reload 后自动推断：

```text
Executing
→ Effect 一定没完成
→ 自动 Retry
```

因为你已经冻结了：

```text
at-least-once
```

以及：

```text
Timeout ≠ Effect 未发生
```

所以 **自动恢复**必须等以后专门定义，不应该隐含在 `serialize/reload` 里面。

目前文档实际上已经通过 `Serializable ≠ Resumable` 把这个危险挡住了。

# 8. 我认为还有一个非常值得现在补的东西：Step ID 的唯一性

当前：

```text
WorkflowDefinition
    steps: Vec<WorkflowStep>
```

但没有显式写：

```text
step_id unique within definition
```

后面的：

```text
StepRun.step_id
current_step
workflow_run → step_id
```

都依赖它。

所以建议加：

> `step_id` MUST be unique within a `WorkflowDefinition`.

这是非常简单的 invariant，却能避免以后状态映射出现隐蔽错误。

---

# 9. 当前 Contract 我会建议最终只做 4 个很小的 Addendum

不需要推翻现在的设计：

```text
WF-A1
WorkflowStep.input is the authoritative ActionInvocation input.

WF-A2
WorkflowAction::Inline MUST reference Host-owned system.* actions;
plugin.* MUST use Reference.

WF-A3
Fresh Provider Query semantics are explicitly defined
(empty-query discovery or equivalent provider command enumeration).

WF-A4
step_id MUST be unique within WorkflowDefinition.
```

再补一个错误分类：

```text
Malformed provider command response
→ ProtocolViolation
```

即可。

# 最终评价

**没有需要重做的架构问题。**

现在的模型已经基本形成：

```text
WorkflowDefinition
      ↓
WorkflowRun
      ↓
StepRun
      ↓
ActionInvocation
      ↓
ReferenceResolver
      ↓
ActionDescriptor
      ↓
ActionResolver
      ↓
ResolvedAction
      ↓
ActionEngine
      ↓
Effect
```

其中最关键的保护链也完整：

```text
持久化的是 Reference / Inline Declaration
              ↓
执行前重新寻找
              ↓
执行前重新 Resolve
              ↓
重新检查 Context / Capability / Policy / Confirmation
              ↓
ActionEngine
```

这已经符合你此前冻结的 **INV-049/050** 目标。

**所以我的判断是：`WORKFLOW-CONTRACT-v0.1` 可以继续保持 FROZEN，不需要重新开评审；只建议做上面 4 个微修订，尤其优先解决 `Inline + input` 和 `Fresh Query` 两处真实语义缺口。**

修完这几个点，就很适合正式进入 **MVP4.1 implementation**，而且此时已经具备我们前面说的条件：**实现 Workflow Runner 之前不需要再碰 Plugin / ActionEngine 架构。**
