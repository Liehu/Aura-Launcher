# MVP3.1 — Native Action UI

这一阶段的目标非常明确：

> **把已经冻结的 `Command Contract + Action Contract` 从“数据/解析模型”变成真实可用的原生交互。**

核心闭环：

```text
Context
   ↓
Provider
   ↓
Command
   ↓
ActionDescriptor
   ↓
ActionResolver
   ↓
ResolvedAction / Hidden / Disabled
   ↓
Native Action Panel
   ↓
ActionEngine
   ↓
Effect
```

当前架构已经把 UI、Action Engine、Core 分开；Action Engine 是 Effect 的唯一入口，符合继续扩展的基础。

---

# 2. MVP3.1 第一原则：UI 不是 Action 的解释器

这一点非常重要。

UI 不应该知道：

```text
system.copy_to_clipboard
system.open
system.execute
```

具体是什么意思。

UI 只认识：

```text
ActionPresentation
```

例如：

```rust
struct ActionPresentation {
    id: ActionId,
    title: String,
    subtitle: Option<String>,
    enabled: bool,
    shortcut: Option<Shortcut>,
}
```

而：

```text
ActionDescriptor
```

和：

```text
ResolvedAction
```

全部由 Domain / Action 层处理。

---

# 3. 推荐增加一个 Presentation Model

我建议不要直接：

```text
ActionDescriptor → Slint
```

而是：

```text
ActionDescriptor
       ↓
ActionResolver
       ↓
ActionResolution
       ↓
ActionPresentation
       ↓
Slint
```

例如：

```rust
enum ActionPresentationState {
    Ready,
    Disabled(DenyReason),
    Hidden,
}
```

然后：

```rust
struct ActionPresentation {
    id: ActionId,
    title: String,
    subtitle: Option<String>,
    state: ActionPresentationState,
}
```

这让 UI 完全不知道：

```text
Capability
ActionKind
ContextSnapshot
```

的内部细节。

---

# 4. Action Panel 不应成为新的业务层

推荐：

```text
launcher-action
    ActionResolver
    ActionEngine

launcher-ui
    ActionPanelModel
    ActionPanel

launcher-core
    Command selection
```

不要：

```text
launcher-ui
    resolve_action()
    validate_capability()
    execute_effect()
```

你现在的架构已经把 Action Engine 单独拿出来，继续保持这个边界更重要。

# 6. Primary Action 的呈现

按照你已经冻结的规则：

```text
first Ready action
    ↓
primary
```

UI 不重新判断 primary。

也就是说 Core/Resolver 给 UI 的已经是：

```text
ActionViewModel {
    primary: ...
    secondary: [...]
}
```

这样 UI 只是呈现。

---

# 7. Disabled Action 的处理

这里必须严格区分：

```text
Resolution:
    Disabled
```

和：

```text
Presentation:
    灰掉 / 显示原因 / 隐藏
```

Contract 已经规定：

> CapabilityDenied 是 Execution state，不是 Presentation。

所以 MVP3.1 可以选择：

```text
Copy
   🔒 clipboard permission required
```

而不是让 Action Contract 强制定义具体 UI。

推荐初版：

```text
Disabled action:
- visible
- non-selectable
- optional denial reason
```

但是：

```text
Unknown secondary
```

仍然：

```text
Hidden
```

这两个不要混。

---

# 8. Primary 被拒绝时的情况

按照你现在的规则：

```text
Copy → denied
Insert → ready
History → ready
```

则：

```text
Insert = primary
History = secondary
```

因此：

```text
Enter → Insert
```

UI 根本不需要知道 Copy 曾经存在。

但 Action Panel 如果需要展示 denied action，可以展示：

```text
Copy        🔒
Insert      Enter
History
```

这就是一个很好的产品行为。

---

# 9. 一个关键原则：UI 必须保存 ID，而不是对象索引

你之前已经解决过 `last_results` 不同步的问题。

MVP3.1 不要再出现这种状态：

```text
selected_index = 2
```

然后执行：

```text
actions[2]
```

推荐：

```text
selected_command_id
selected_action_id
```

流程：

```text
User selects Action
       ↓
action_id
       ↓
ActionResolver / Action lookup
       ↓
ResolvedAction
       ↓
ActionEngine
```

这样排序和 UI 重绘不会破坏执行对象。

# 10. Action Panel 的状态机

建议直接做成状态机：

```text
Hidden
  │
  │ open
  ▼
Opening
  │
  ▼
Visible
  │
  ├── select action
  │
  ├── Enter
  │
  └── Esc
  │
  ▼
Executing
  │
  ├── Success
  ├── Failure
  └── Denied
  │
  ▼
Closed / Updated
```

建议尤其定义：

```text
Visible + Esc
    → close panel, stay launcher

Visible + Enter
    → execute selected action

Executing + Esc
    → UI may close, effect continues / cancellation policy TBD
```

最后这一条要先确定。

MVP3.1 我建议：

> **Action 已提交执行后，Esc 不取消 Effect。**

因为现有 Action Engine 目前不是 cancellation-oriented。

---

# 11. Action Execution 结果必须有统一 UI 映射

Action Engine：

```text
Success
CapabilityDenied
InvalidInput
UnknownActionType
ConfirmationRequired
EffectFailed
```

MVP3.1 映射：

| ActionResult         | UI                               |
| -------------------- | -------------------------------- |
| Success              | close / success                  |
| CapabilityDenied     | show denial                      |
| InvalidInput         | show error                       |
| UnknownActionType    | should normally never be visible |
| ConfirmationRequired | reserved                         |
| EffectFailed         | show error                       |

特别是：

> `UnknownActionType` 正常情况下不应该出现在可执行 UI 中。

因为 Resolver 已经是 trust boundary。

如果还能进入 UI execution，应该视为 bug。

# 15. 建议加入 Action Panel 性能指标



# 20. 我建议 MVP3.1 新增 4 个 Invariant

```text
INV-035
UI MUST identify commands/actions by stable IDs,
never by display text or positional index.

INV-036
UI MUST NOT resolve ActionDescriptor or perform
capability checks itself.

INV-037
ActionPanel MUST NOT execute Effects directly;
all execution MUST pass through ActionEngine.

INV-038
An ActionResolver result marked Hidden MUST NOT
be executable through the UI.
```

再加一个我认为很有价值的：

```text
INV-039
Unknown or invalid secondary actions MUST NOT
alter the validity of their containing Command.
```

你现在已有 fault-containment 原则，这里只是把 Native UI 层也覆盖进去。




即使现在存在于 schema：

