进入 **MVP4.4 P0**。建议不要把 4 个 P0 同时开工，而是先冻结 **P0-A Runtime Foundation**，因为它会直接影响后面的 Persistent MCP、Plugin Runtime、Streamable HTTP、Agent Runtime。

## MVP4.4 P0 总体顺序

```text
P0
│
├── P0-A RuntimeSupervisor        ← 先做
│      │
│      ├── Plugin process runtime
│      └── MCP process runtime
│
├── P0-B Streamable HTTP
│      │
│      └── RuntimeSupervisor 可复用
│
├── P0-C MCP Auth
│      │
│      └── HTTP transport
│
└── P0-D LLM Planner
       │
       └── ActionProposal
```

我建议现在正式进入：

# P0-A — RuntimeSupervisor

核心目标：

> **把 PluginBroker / McpExecutor 目前重复的 spawn、读写、timeout、shutdown、crash、process-tree cleanup 能力抽成统一运行时基础设施，但绝不合并 Plugin/MCP 的协议与业务语义。**

---

# 1. 新架构

现在大致是：

```text
PluginBroker
 ├── spawn
 ├── reader
 ├── timeout
 ├── shutdown
 └── reap

McpExecutor
 ├── spawn
 ├── reader
 ├── timeout
 ├── shutdown
 └── reap
```

P0-A 后：

```text
                RuntimeSupervisor
                       │
        ┌──────────────┼──────────────┐
        │              │              │
 ProcessLauncher  ProcessIO     ProcessReaper
        │              │              │
        └──────────────┼──────────────┘
                       │
             RuntimeHandle / Process
                  ┌────┴────┐
                  │         │
             PluginBroker  McpExecutor
                  │         │
             Plugin proto  MCP proto
```

核心原则：

```text
RuntimeSupervisor
    = HOW to run

PluginBroker / McpExecutor
    = WHAT protocol means
```

---

# 2. Crate 放在哪里

建议新增：

```text
crates/
└── launcher-runtime/
    ├── Cargo.toml
    └── src/
        ├── lib.rs
        ├── error.rs
        ├── config.rs
        ├── launcher.rs
        ├── process.rs
        ├── io.rs
        ├── lifecycle.rs
        ├── supervisor.rs
        └── tests/
```

依赖：

```text
launcher-runtime
    ↓
standard library / minimal Windows APIs
```

**不要依赖：**

```text
launcher-mcp
launcher-plugin-host
launcher-workflow
launcher-ui
```

这样基础设施不会反向依赖业务层。

---

# 3. 为什么不是直接把它塞进 `launcher-plugin-host`

因为以后：

```text
Plugin
MCP
future external runtime
```

都会需要：

```text
spawn
kill
timeout
reap
```

所以：

```text
launcher-plugin-host
```

不是合适的 ownership。

应该：

```text
launcher-runtime
       ↑
 ┌─────┴─────┐
 │           │
Plugin      MCP
```

---

# 4. Runtime API

建议 API 极小。

```rust
pub struct LaunchSpec {
    pub program: PathBuf,
    pub args: Vec<OsString>,
    pub env: Vec<(OsString, OsString)>,
    pub working_dir: Option<PathBuf>,
}
```

运行：

```rust
pub trait RuntimeSupervisor {
    fn spawn(&self, spec: LaunchSpec) -> Result<RuntimeHandle, RuntimeError>;
}
```

Handle：

```rust
pub struct RuntimeHandle {
    pub id: RuntimeId,
}
```

不要让：

```text
PluginBroker
McpExecutor
```

直接拥有：

```text
Child
stdin
stdout
stderr
```

都交给 runtime boundary。

---

# 5. Runtime ID 与 Execution ID 必须分开

这是 P0 的重要语义：

```text
RuntimeId
    = process/runtime instance

ExecutionId
    = one Effect execution attempt
```

例如：

```text
Runtime:
    r-17

Execution:
    e-42

Execution:
    e-43
```

可能：

```text
persistent runtime
r-17
    ├── e-42
    ├── e-43
    └── e-44
```

也可能：

```text
ephemeral
r-18 → e-45 → shutdown
r-19 → e-46 → shutdown
```

两者绝不能合并。

---

# 6. Lifecycle

统一：

```text
Created
   ↓
Starting
   ↓
Running
   ↓
Stopping
   ↓
Stopped
```

异常：

```text
Running
   ↓
Crashed
   ↓
Stopped
```

不要让 RuntimeSupervisor 理解：

```text
BusinessError
CapabilityDenied
CommandNotFound
```

它只知道：

```text
process exited
timeout
transport broken
shutdown
```

---

# 7. Plugin / MCP 错误不能在 Runtime 层分类

例如 Runtime：

```text
child exited 1
```

只能告诉上层：

```text
ProcessExited {
    exit_code: Some(1)
}
```

然后：

```text
McpExecutor
    ↓
McpError::...
    ↓
FailureClass
```

Plugin：

```text
PluginBroker
    ↓
PluginError
```

这样：

```text
runtime
    ≠
protocol semantic
```

仍然干净。

---

# 8. Timeout

RuntimeSupervisor 应提供：

```rust
pub struct RuntimeLimits {
    pub startup_timeout: Duration,
    pub io_timeout: Duration,
    pub shutdown_grace: Duration,
    pub max_stdout_frame: usize,
    pub max_stderr_bytes: usize,
}
```

但是注意：

```text
Runtime timeout
```

与：

```text
Workflow timeout/retry policy
```

不是一个概念。

Runtime：

> “这个 process / IO 操作超时了。”

Workflow：

> “这个失败应该 Retry 还是 Stop？”

---

# 9. Shutdown

统一：

```text
request stop
    ↓
grace period
    ↓
terminate
    ↓
kill process tree
    ↓
wait
    ↓
reap
```

现有 Plugin contract 的：

```text
200ms graceful shutdown
```

可以继续作为默认。

但建议变成：

```text
RuntimeLimits.shutdown_grace
```

而不是 RuntimeSupervisor 硬编码。

---

# 10. Windows Job Object

你之前已有：

```text
CREATE_SUSPENDED
    ↓
AssignProcessToJobObject
    ↓
ResumeThread
```

这个能力应该迁入：

```text
launcher-runtime
```

形成：

```text
spawn
  ↓
CREATE_SUSPENDED
  ↓
create job
  ↓
assign process
  ↓
resume
```

最终保证：

```text
root process
    └── descendants
          └── descendants
```

都属于 runtime process tree。

因此：

```text
kill runtime
```

可以真正：

```text
kill process tree
```

---

# 11. stdout/stderr 管理

Runtime 层统一提供：

```rust
RuntimeIo {
    stdin,
    stdout,
    stderr,
}
```

但：

```text
stdout
```

仍然是协议数据。

```text
stderr
```

仍然是 diagnostics。

Runtime 不知道：

```text
JSON-RPC
NDJSON
Plugin protocol
MCP protocol
```

它只负责 bytes / lines / bounded stream。

---

# 12. 一个关键设计：不要让 RuntimeSupervisor 自动解析 NDJSON

错误：

```text
RuntimeSupervisor
    ↓
JSON parser
```

正确：

```text
RuntimeSupervisor
    ↓
bounded byte/frame transport
    ↓
Protocol-specific parser
```

否则：

```text
launcher-runtime
```

会开始变成：

```text
generic protocol engine
```

最后 Plugin/MCP 又重新耦合。

---

# 13. Persistent Runtime 要从现在开始预留

虽然 P0-A 不一定马上实现 persistent session，但 API 不要设计死成：

```rust
spawn() -> run once -> destroy
```

应该支持：

```text
RuntimeHandle
    ↓
send/read
    ↓
multiple logical operations
    ↓
shutdown
```

这样以后：

```text
Persistent MCP
Persistent Plugin
```

都能复用。

---

# 14. Ephemeral Runtime

当前 MVP4.3 可以直接映射：

```text
McpExecutor
    ↓
RuntimeSupervisor.spawn()
    ↓
call
    ↓
shutdown
```

所以迁移之后行为完全不变：

```text
spawn → call → shutdown
```

只是：

```text
spawn / cleanup
```

从 executor 中抽出来。

---

# 15. Persistent Runtime

v0.2 后：

```text
RuntimeManager
    │
    ├── ephemeral
    │
    └── persistent
```

例如：

```text
MCP github
    runtime r-1
       ├── call #1
       ├── call #2
       └── call #3
```

而：

```text
Plugin calculator
    runtime r-2
```

完全独立。

# 16. Runtime Resource Limits

统一支持：

```text
max_processes
max_runtime_instances
max_stdout_frame
max_stderr_bytes
startup_timeout
io_timeout
shutdown_timeout
```

不要现在支持：

```text
CPU quota
RAM quota
network quota
disk quota
```

这些需要更深的 Windows Job Object policy，不属于 P0-A。

# 17. Runtime Security Boundary

必须冻结：

```text
RuntimeSupervisor
    X capability grant
    X ActionResolver
    X Effect creation
    X Workflow
    X MCP protocol
    X Plugin protocol
```

它只接受：

```text
LaunchSpec
```

如果未来 LaunchSpec 被滥用，需要：

```text
caller
```

负责 authority。

因此：

```text
ActionEngine
   ↓
Effect
   ↓
Executor
   ↓
RuntimeSupervisor
```

而不是：

```text
RuntimeSupervisor
   ↓
“我看到这个 process 可以运行，所以允许它”
```

# 20. RuntimeSupervisor 的一个重要限制

**不要马上抽象成“万能 Executor Framework”。**

不要：

```text
RuntimeSupervisor
├── plugin
├── mcp
├── system
├── workflow
├── shell
└── everything
```

它只是：

```text
External Process Runtime
```

更加准确的名字甚至可以考虑：

```text
ExternalProcessRuntime
```

如果后续发现系统只有“管理外部进程”这一种共性，那么这个名字比：

```text
RuntimeSupervisor
```

更不容易膨胀。

如果你希望保留 Supervisor 语义，则：

```text
launcher-runtime
```

可以公开：

```text
ProcessSupervisor
```

内部再实现。

# 23. P0 全路线

P0-A 完成后继续：

```text id="p0-sequence"
P0-A RuntimeSupervisor
        ↓
P0-B Streamable HTTP
        ↓
P0-C MCP Auth
        ↓
P0-D LLM Planner
```

其中 **P0-A 是基础设施重构**，所以它完成后建议重新建立一个新的 regression baseline：

```text
MVP4.4-P0-A baseline
```

包括：

```text
tests
memory
CPU
MCP spawn latency
Plugin spawn latency
process cleanup
```

特别是你的产品核心之一是 **runtime-on-demand + low memory**。因此 RuntimeSupervisor 虽然是架构重构，但必须证明没有把：

```text
12.x MB idle
```

或者 popup latency baseline 悄悄拉高。

**现在就进入 P0-A，而不是同时开 Streamable HTTP。** 先把外部进程生命周期统一这一块稳定下来，后面的 Persistent MCP 和 HTTP/Auth 都会更容易控制边界。
