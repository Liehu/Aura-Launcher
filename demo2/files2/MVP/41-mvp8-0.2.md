# Phase 5：Action Projection

## 5.1 MCP Tool → Command → Action

现在 Phase 4 已经产生：

```text

action_id   = invoke
```

Phase 5 只是把当前：

```text

    ↓

```

变成真正的 ActionDescriptor。

建议冻结：

```rust
ActionDescriptor {
    id: "invoke",
    title: Some("Run"),
    type: "plugin.mcp.invoke",
    input: tool_input,
    requires: vec!["mcp.invoke"],
    confirmation: ...,
    shortcut: None,
}
```

其中：

```text
type = plugin.mcp.invoke
```

只是 Action semantic routing identity。

**不要创建：**

```rust
ActionKind::McpInvoke
```

也不要：

```rust
ActionKind::McpReadFile
ActionKind::McpSearch
ActionKind::McpGitHub
```

## 5.2 `mcp.invoke` capability

这里建议修正之前一个容易混淆的地方。

不要让 MCP action：

```text
requires = ["plugin.invoke"]
```

因为：

```text
plugin.invoke
```

代表 Plugin Action namespace 的执行能力，而：

```text
mcp.invoke
```

代表 MCP Tool execution capability。

它们使用同一个 Capability Model，但不是同一个 capability。

所以：

```text
Capability System
├── plugin.invoke
├── mcp.invoke
├── network.connect
├── shell.execute
└── ...
```

而不是建立第二套：

```text
McpCapabilitySystem
```

### authority 来源

`mcp.invoke` 不得来自：

```text
Tool.annotations
Tool.description
Tool.inputSchema
Server instructions
```

只能来自：

```text
Host configuration / policy
```

因此：

```text
MCP metadata
      X
      │
      │ 不能授予
      ▼
mcp.invoke

Host policy
      │
      ▼
mcp.invoke
```

这与之前 `plugin.invoke` 的“隐式 execution capability”理念一致，只是 ownership domain 不同。


原因很简单：

不能混在一起。

# 6.1 Executor interface

推荐：

```rust
#[async_trait]
pub trait McpExecutor {
    async fn execute(
        &self,
        input: McpInvokeInput,
        execution_id: &ExecutionId,
    ) -> Result<McpToolResult, McpExecutionError>;
}
```

这里不传：

```text
ActionDescriptor
ResolvedAction
ActionProposal
WorkflowRun
UI state
```

因为 Executor 不应该知道上游编排模型。

---

# 6.2 Executor 做什么

严格限制：

```text
McpExecutor
├── validate input
├── locate configured server
├── locate transport
├── call tools/call
├── timeout
├── classify transport/protocol/tool result
└── return execution result
```

不负责：

```text
authorization
capability grant
confirmation
workflow retry
action resolution
UI state
```

---

# 6.3 `execution_id`

调用：

```text
ActionEngine
      ↓
execution_id = e-123
      ↓
McpExecutor
      ↓
MCP transport
```

MCP executor 必须把这个作为**内部 correlation ID**保留。

但是不要强塞到 MCP tool arguments：

```json
{
  "execution_id": "e-123"
}
```

这是错误的。

Tool arguments 必须严格对应 MCP Tool schema。

---

# 6.4 Result

MCP Tool Result 建议保持两层：

```rust
struct McpToolResult {
    content: Vec<McpContent>,
    structured_content: Option<Value>,
    is_error: bool,
}
```

然后 Core 再统一转成：

```text
EffectResult / PluginResult / ActionExecutionResult
```

不要让 UI 直接消费 MCP protocol DTO。

---

# 6.5 `isError` 不等于 ProtocolViolation

这是 Phase 6 最重要的错误语义。

例如服务器正常返回：

```json
{
    "isError": true,
    "content": [...]
}
```

这表示：

```text
MCP call succeeded at protocol level
Tool business execution failed
```

应该：

```text
BusinessError
```

而不是：

```text
ProtocolViolation
```

而下面这种才是：

```text
invalid JSON
unexpected response id
malformed envelope
missing required protocol field
```

→ `ProtocolViolation`


# 7.3 推荐增加 Executor Registry

这里就是我不建议再说“Core 完全零代码”的地方。

```rust

```

Registry：

```text

├── system executor
├── PluginBroker
└── McpExecutor
```

路由：

```text

       │
       ▼

       │
 ┌─────┼─────────────┐

        │             │
        ▼             ▼

```

这样你现有：

```text

ActionEngine
WorkflowRunner
AI Planner
```

都不用知道 MCP。

这是真正意义上的：

> **Core execution semantics zero-change。**

只是 Assembly 增加一个 executor registration。

## 一个需要同步修正的规格项

你之前的 MVP4.3 文档里有：

> “MCP = Producer”
> “`plugin.mcp.invoke` = Effect route”

这两点继续成立。

但现在最好把中间层正式写成：

```text
MCP Provider
    = Discovery / Proposal Producer

MCP Executor
    = Effect Executor

MCP Server
    = External Untrusted Capability Provider
```

三者不要再用一个泛化的 `McpAdapter` 名字覆盖，否则 Phase 6 开始职责会重新混淆。

另外，当前 MCP 正式规范已经是 **2026-07-28**，新规范取消了 `initialize/initialized` handshake 和 session，改为无状态请求，并增加 `server/discover`；你当前 Phase 1–4 的 `2025-06-18` transport 可以作为兼容 profile，但 **Phase 5–7 不应让执行层依赖这个旧 lifecycle**。([blog.modelcontextprotocol.io][1])

**因此现在可以直接实现 Phase 5 → Phase 6 → Phase 7，且不需要改 Workflow、AI Planner、UI Contract。**
