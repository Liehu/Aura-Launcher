# 一、最重要：你现在其实同时存在 4 个版本概念

当前已经有：

```text
schema_version
version
api_version
protocol_version
```

这四个一定要在 Contract 中彻底区分，否则以后 Agent 很容易把它们混起来。

我建议正式定义：

```text
schema_version
    ↓
plugin.json 文件格式版本

version
    ↓
插件自身版本，例如 1.3.0

api_version
    ↓
Plugin API / SDK Contract 版本

protocol_version
    ↓
IPC wire protocol 版本
```

例如：

```json
{
  "schema_version": 1,
  "version": "1.3.0",
  "api_version": "0.1",
  "runtime": {
    "type": "process"
  }
}
```

然后 initialize：

```json
{
  "protocol_version": "0.1",
  "plugin_id": "com.example.calculator"
}
```

这里：

```text
schema_version
```

和：

```text
protocol_version
```

绝对不要混成一个东西。

我建议把这一条直接加入 `INVARIANTS`：

```text
INV-013:
Schema version, plugin version, API version and wire protocol
version MUST remain semantically distinct.
```

这是可以的。

这样不会出现：

# 四、现在的 query_id 设计非常关键，但还有一个边界需要补

你现在：

```text
q-<seq>
```

非常好。

它实际上已经解决了我们之前讨论的：

```text
Q101
Q102
Q103
Q104
```

乱序结果污染 UI 的问题。

但是 Contract 必须明确：

> **Host 是否允许同一 Plugin 同时存在多个 in-flight query？**

我建议 MVP 直接定义：

```text
MVP:
一个 Plugin Host instance 最多 1 个 in-flight query
```

这样：

```text
query q-101
    ↓
running
    ↓
query q-102
```

要么：

```text

```

要么：

```text
reject / supersede q-101
```

否则 Plugin 作者可能写：

```text
async task A
async task B
async task C
```

然后 host 同时等待。

现在已经有：

```text
query_id
```

但要把并发语义正式冻结。

# 六、你现在“裸数组兼容”这个点，建议再严格一点

仍然可以被接受，那么：

否则兼容逻辑可能永久存在。

# 七、建议增加“Protocol State Machine”

现在已经有：


非常适合直接冻结成：

```text
┌──────────────┐

┌──────────────┐
│   Spawned    │
└──────┬───────┘
       ▼

└──────┬───────┘
       │ success
       ▼
┌──────────────┐
│    Ready     │◄─────────────┐
```
