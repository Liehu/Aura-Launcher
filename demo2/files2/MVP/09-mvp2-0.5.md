## 一、我认为 MVP2.1 可以正式验收

目前已经验证了 4 个核心架构假设。

### 1. Context 确实可以成为独立基础设施

你没有把 Explorer 逻辑直接塞进 UI 或 Provider，而是：

```text
launcher-context
    ↓
ContextSnapshot
```

再通过：

```text
ContextHandle
```

交给 Core。

这证明了以后可以自然扩展：

```text
Explorer
VS Code
Terminal
Chrome
7-Zip
Office
```

而不需要修改 Launcher 主体结构。

### 2. Context-aware Provider 的模型成立

这点非常重要。

你现在已经证明：

```text

    ↓
Quick Switch
```

而：

```text
非空 query
    ↓
Context command
    ↓
正常 ranking
```

可以共存。

所以以后没有必要把：

```text
Quick Switch
普通搜索
Context Search
```

做成三个独立系统。

统一成：

```text
Provider
   ↓
Command
   ↓
Ranking
```

是正确方向。

# 二、你修掉的两个 bug 其实非常有价值

我特别注意到这两个问题。

### capture 时序

你发现：

> **capture 必须在 show 之前**

这个其实是一个非常典型的 Launcher 架构问题：

```text
Ctrl+Space
    ↓
Show Launcher
    ↓
Launcher 获取前台窗口
```

这时候前台已经被 Launcher 抢走了。

正确：

```text
Ctrl+Space
    ↓
Capture Context
    ↓
Show Launcher
```

这个经验建议永久写进 Architecture Invariant。

例如：

```text
INV-012:
Context capture triggered by launcher invocation
MUST occur before launcher popup activation/focus acquisition.
```

以后 Agent 改热键链路时就不会重新踩坑。

---

### `last_results` 不同步

这个 bug 更值得记录。

你的 UI：

```text
显示 Quick Switch
```

但：

```text
last_results
```

没有同步。

于是：

```text
用户看到 A
    ↓
Enter
    ↓
Action lookup
    ↓
找不到 A
```

这种 bug 很容易发生在：

```text
UI state
vs
Core state
```

之间。

我建议未来把架构进一步规定为：

> **UI 不应该拥有“可执行结果”的第二份真相。**

更理想的模型是：

```text
SearchResultSet
      │
      ├── render
      │
      └── execute(id)
```

也就是说：

```text
UI
```

只保存：

```text
selected_command_id
```

真正 Command/Action 定义仍然由 Core/ActionEngine 管。

这是后面非常值得做的一次小重构，可以避免：

```text
results
last_results
displayed_results
provider_results
```

多个状态源逐渐漂移。

                    │

# 七、Quick Switch 15 条这个限制很好，但需要解释“为什么”

你现在：

> Quick Switch 插入序、有界 15 条。

这在 MVP 阶段很好。

但建议记录为：

```text
QUICK_SWITCH_MAX_RESULTS = 15
```

并说明：

> **这是 UX/latency 上限，不是 Provider API 限制。**

否则以后 Agent 很容易误解：

```text
Context Provider
只能返回 15 个
```

最终造成：

```text
ContextProvider API
```

被产品行为绑死。

正确应该：

```text
Provider
    ↓
up to N
    ↓
Core/Ranking/Presentation
    ↓
15 displayed
```

# 十一、还有一个很值得做的架构测试：Context Failure Matrix

你现在 Context 是 best-effort，这个原则很好：

> COM 失败 → 空结果，绝不 panic。



但下一步建议把它系统化：

| 场景                   | Expected Context |
| -------------------- | ---------------- |
| Explorer 正常          | folder           |
| 多 Explorer           | foreground 对应窗口  |
| 非 Explorer           | app only         |
| Explorer COM failure | best effort      |
| Explorer closing     | empty/previous?  |
| UWP 文件管理器            | TBD              |
| Desktop              | TBD              |
| Save/Open dialog     | TBD              |
| 权限异常                 | best effort      |

尤其：

> **Context failure 不得影响 Launcher 本身。**

这应该作为正式 invariant。
