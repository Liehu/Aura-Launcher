对，这个修改我赞成，而且我认为它应该成为 **Visual Design Spec v0.1 的核心交互原则之一**。

你描述的其实不是“窗口高度可变”这么简单，而是：

> **Launcher 是 Progressive Disclosure（渐进展开）的瞬时界面：打开时只有搜索入口；只有用户产生输入或明确进入下一层，才按需显示结果、Action、Confirmation、Workflow 等内容。**

这比我们之前“Ctrl+Space 后直接显示 Search + Results + Context”的模型更接近 Wox / Flow / Raycast 这类启动器的实际体验，也更符合你要的“常驻但极轻”。

---

# 1. 我建议把默认启动状态改掉

之前：

```text
Ctrl+Space
    ↓
┌────────────────────────┐
│ Search                 │
├────────────────────────┤
│ Results                │
│ Results                │
│ Results                │
├────────────────────────┤
│ Context / Actions      │
└────────────────────────┘
```

现在改成：

```text
Ctrl+Space
    ↓
┌────────────────────────┐
│ 🔎 Search...            │
└────────────────────────┘
```

**只有一个 Search Box。**

此时：

```text
Results = Hidden
Context = Hidden
Action = Hidden
Status = Hidden
```

这应该成为：

```text
Main.Empty / Initial
```

而不是之前意义上的 `Main.Empty`。

---

# 2. 用户开始输入后，结果区域才出现

例如用户输入：

```text
chr
```

然后：

```text
┌──────────────────────────────────┐
│ 🔎 chr                           │
├──────────────────────────────────┤
│ ▸ Google Chrome                  │
│   Chromium                       │
│   Chrome Profile Manager        │
│   chrome.svg                    │
└──────────────────────────────────┘
```

这时候：

```text
Search = Visible
Results = Visible
Context = Optional
Status = Optional
```

高度根据：

```text
Search
+
N × ResultRow
+
optional footer
```

动态计算。

---

# 3. 这会自然解决你刚才问的“尺寸应该怎么定义”

现在不需要纠结：

```text
600 × 420
```

还是：

```text
620 × 400
```

因为实际模型变成：

```text
Window Width = stable / bounded
Window Height = content-driven
```

### Initial

```text
36px Search
+ padding
≈ 60–72px
```

### Search

```text
36px Search
+ 6 × 44px Result
+ footer
≈ 350–400px
```

### Action

```text
40px Search/header
+ N × 40px Action
≈ 280–400px
```

### Confirmation

```text
Search/Header
+ confirmation body
≈ 260–320px
```

### Workflow

```text
Header
+ N × 36px Step
+ status
≈ 300–500px
```

也就是说：

> **窗口大小由当前 UI state 的内容决定。**

这比“统一固定 420px”合理得多。

---

# 4. 我建议四个 Mode 的展开策略

虽然 UI Contract 仍然是：

```text
Main
Action
Workflow
```

以及：

```text
Action.ConfirmationPending
```

但是视觉上可以进一步定义：

```text
Main.Initial
Main.Searching
Main.Results
Action
Workflow
```

注意：

`Main.Initial` 仍然属于 Main，不新增顶层 Mode。

---

# 5. Main.Initial

Ctrl+Space：

```text
┌──────────────────────────────────────┐
│ 🔎 Search...                         │
└──────────────────────────────────────┘
```

要求：

```text
Search focused
No result area
No footer
No empty-state text
```

这点非常重要。

**不要显示：**

```text
No results
Type something...
Press...
```

因为用户还什么都没做。

Launcher 应该非常安静。

---

# 6. Main + 有输入但暂时没有结果

比如：

```text
xyz123
```

没有结果：

```text
┌──────────────────────────────────────┐
│ 🔎 xyz123                            │
├──────────────────────────────────────┤
│                                      │
│             No results               │
│                                      │
└──────────────────────────────────────┘
```

这里才出现：

```text
No results
```

这是与：

```text
Initial
```

完全不同的状态。

---

# 7. Searching 状态怎么表现

不建议：

```text
┌───────────────────────────────┐
│ 🔎 chrome                      │
│                               │
│         Loading...             │
│                               │
└───────────────────────────────┘
```

应该尽可能保持：

```text
┌───────────────────────────────┐
│ 🔎 chrome             ⌛      │
├───────────────────────────────┤
│ ▸ Google Chrome               │
│   Chromium                    │
└───────────────────────────────┘
```

或者如果搜索结果尚未到达：

```text
┌───────────────────────────────┐
│ 🔎 chrome                     │
├───────────────────────────────┤
│ ⌛ Searching                  │
└───────────────────────────────┘
```

但这个状态应该非常短暂。

---

# 8. Context 也应该按需显示

这个很重要。

之前：

```text
Ctrl+Space
→ 📁 Documents
```

我现在建议改成：

```text
Initial
→ 不显示

有结果
→ 如果 Context 对结果有价值，可以显示

Action
→ 隐藏

Workflow
→ 隐藏
```

比如：

```text
┌──────────────────────────────────┐
│ 🔎 terminal                      │
├──────────────────────────────────┤
│ ▸ Open Terminal Here             │
│   Windows Terminal               │
│   cmd                            │
├──────────────────────────────────┤
│ 📁 Documents       Ctrl+↓ Actions│
└──────────────────────────────────┘
```

这样 Context 是：

> **辅助解释信息**

而不是永久 UI chrome。

---

# 9. Action Panel 应该是“局部展开”

用户：

```text
Ctrl+↓
```

从：

```text
Main
```

变成：

```text
Action
```

窗口高度重新计算。

例如：

```text
┌──────────────────────────────────┐
│ Calculator                       │
├──────────────────────────────────┤
│ ▸ Copy result             Enter  │
│   Paste result           Ctrl+V  │
│   Open history                  │
│   Execute                       │
└──────────────────────────────────┘
```

这里搜索框甚至可以消失。

这样比：

```text
Search
Result
Action
```

全部同时存在更干净。

# 10. 这也是我建议的视觉层级

Main：

```text
Search
 ↓
Results
```

Action：

```text
Command identity
 ↓
Actions
```

Workflow：

```text
Workflow identity
 ↓
Steps
```

Confirmation：

```text
Action identity
 ↓
Confirmation
```

而不是：

```text
Search
+ Result
+ Action
+ Context
+ Workflow
+ Status
```

全部叠加。

这就是你说的：

> **按需显示。**

---

# 11. Workflow 也应该按需进入

比如：

```text
Run Example Workflow
```

然后 Launcher：

```text
┌────────────────────────────────────┐
│ Organize Downloads                 │
├────────────────────────────────────┤
│ ✓ Scan files                       │
│ ✓ Classify files                   │
│ ● Move files                       │
│ ○ Generate report                  │
├────────────────────────────────────┤
│ ● Running                          │
└────────────────────────────────────┘
```

Workflow Mode 不需要：

```text
Search Box
Context Footer
Action Panel
```

---

# 12. Confirmation 也应该局部占据空间

而不是弹出第二窗口。

例如：

```text
┌────────────────────────────────────┐
│ Calculator                        │
├────────────────────────────────────┤
│ ⚠ Confirm action                   │
│                                    │
│ Paste result at cursor?            │
│                                    │
│ Enter Confirm       Esc Cancel     │
└────────────────────────────────────┘
```

整个 Launcher 依旧只有一个 Window。

---

# 13. 这样 Launcher 的窗口高度就自然形成一个“离散状态”

可以把高度分成：

```text
H0 = Search only
H1 = Search + Results
H2 = Search + Results + Footer
H3 = Action
H4 = Confirmation
H5 = Workflow
```

而不是：

```text
Height = arbitrary number
```

这会让动画与布局更加稳定。

---

# 14. 我甚至建议不要让 Window Height 连续动画变化

例如：

```text
60px
 ↓
150px
 ↓
300px
```

连续平滑展开容易产生：

* 视觉拖沓
* 布局频繁重算
* 低端机器感觉明显
* 输入/选择焦点可能变化

更推荐：

```text
Initial
    ↓
Results
```

进行一次快速 resize / layout transition。

例如：

```text
80–120ms
ease-out
```

这和你目前 Visual Spec 的 motion 原则一致。

---

# 15. Width 可以基本稳定，Height 动态

这个组合我最推荐：

```text
Width
    620px default
    bounded 480–960

Height
    content-driven
```

原因是：

> 用户的视觉定位依赖稳定宽度，而内容数量更多地影响高度。

这也是 Flow / Wox 那类 Launcher 最合理的尺寸模型之一。

---

# 16. Search Box 应该是唯一常驻视觉锚点

这一条我建议直接加入 Visual Design Spec：

> **Search Box is the only persistent content element across Launcher modes, unless the current transient mode intentionally replaces it.**

也就是说：

### Main

```text
Search
+
Results
```

### Action

```text
Command / Action
```

Search 可以隐藏。

### Confirmation

```text
Action / Confirmation
```

### Workflow

```text
Workflow
```

因此：

```text
“Search Box 常驻”
```

在产品交互上更准确地表述为：

> **Search Box 是 Launcher 的入口与默认初始视图。**

而不是：

> 所有 Mode 永远显示 Search Box。

---

# 17. 我建议把“按需出现”定义成一条正式规则

### Progressive Disclosure

```text
UI must reveal only information necessary
for the current interaction stage.
```

对应：

```text
Ctrl+Space
    ↓
Search only

Input
    ↓
Results

Select
    ↓
Action affordance

Ctrl+↓
    ↓
Actions

Confirmation required
    ↓
Confirmation

Workflow running
    ↓
Workflow Runtime
```

这个原则非常符合 Launcher，而不是普通桌面应用。

---

# 18. 这对内存也有帮助

虽然真正的内存收益不会特别巨大，但架构上非常干净：

Initial：

```text
SearchBox
```

不需要：

```text
ResultRow × 8
ActionRow × N
WorkflowStep × N
```

全部同时存在。

尤其以后你支持：

```text
Preview
rich metadata
plugin UI
```

时，按需创建/加载 UI subtree 会更有价值。

这也符合你项目的核心约束——低内存、常驻后台；当前架构本身就是软件渲染、隐藏窗口常驻，而且空闲 Private 已经压到约 12.6 MB。

---

# 19. 这里我建议进一步调整我们的 Slint 架构

不要：

```text
LauncherWindow
├── Search
├── Results
├── ActionPanel
├── Confirmation
├── Workflow
└── ...
```

全部常驻并通过：

```text
visible = false
```

隐藏。

更推荐：

```text
LauncherWindow
└── ModeHost
    ├── MainView
    ├── ActionView
    └── WorkflowView
```

根据 Mode：

```text
Main
    → MainView

Action
    → ActionView

Workflow
    → WorkflowView
```

Confirmation：

```text
ActionView
└── ConfirmationView
```

这样生命周期更明确。

不过是否真的动态创建组件，取决于 Slint 当前组件模型；**概念层必须先这样设计，避免所有 Mode 永久占据视觉/布局空间。**

---

# 20. MainView 也建议继续细分

```text
MainView
├── SearchBox           always
├── ResultList          conditional
├── EmptyState          conditional
└── ContextFooter       conditional
```

逻辑：

```text
query == ""
    → Search only

query != "" && searching
    → Search + Searching

query != "" && results > 0
    → Search + Results

query != "" && results == 0 && no_error
    → Search + Empty

query != "" && error
    → Search + Error
```

这样 UI 状态本身就非常清楚。

---

# 21. 最终我会把 Visual Design Spec 的 Window Section 改成这样

## Window Size Model

```text
Width:
    Default 620px
    Min 480px
    Max 960px

Height:
    Content-driven
```

## Initial Size

```text
Search only
```

## Height Formula

```text
H =
    vertical_padding
  + search_or_mode_header
  + content_height
  + optional_status
  + optional_context
  + bottom_padding
```

## Visibility

```text
Search         Main: always
Results        query-dependent
Context        relevance-dependent
Action         mode-dependent
Confirmation   transient
Workflow       mode-dependent
Status         state-dependent
```

---

# 22. 这样与 Flow / Wox 的关系也更准确

我们的目标不是复制：

```text
Flow:
大量 Settings
```

或者：

```text
Wox:
大量 Preview / Layout
```

而是吸收它们背后的基本原则：

```text
Stable width
+
Content-driven height
+
Configurable density
+
Dynamic result count
+
Progressive disclosure
```

再结合你自己的：

```text
Native
Low-memory
Minimal
Keyboard-first
```

最终就是：

```text
Ctrl+Space
     ↓
┌──────────────────┐
│ 🔎               │  ← 极小初始面
└──────────────────┘
        ↓ typing
┌────────────────────────┐
│ 🔎 chrome              │
├────────────────────────┤
│ ▸ Chrome               │
│   Chromium             │
│   ...                  │
└────────────────────────┘
        ↓ Ctrl+↓
┌────────────────────────┐
│ Calculator             │
├────────────────────────┤
│ ▸ Copy            Enter│
│   Paste          Ctrl+V│
│   History              │
└────────────────────────┘
```

这其实比我们上一版 Visual Design Spec 的固定 `600×420` 方向更成熟。

## 我建议现在正式修改 Visual Design Spec 的两处核心定义

把：

> `Window = 600 × 420`

改为：

> **`Width = 620px baseline; Height = content-driven`**

同时新增：

> **Progressive Disclosure：Ctrl+Space 初始只显示 Search Box；Result / Context / Action / Confirmation / Workflow 按当前交互阶段按需呈现。**

这两条一旦确定，后面的 Slint Layout、Animation、Performance Benchmark 都会因此变得更合理。
