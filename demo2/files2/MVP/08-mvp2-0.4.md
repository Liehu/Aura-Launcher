这版已经很接近可以冻结了。不过我会做一个**非常关键的技术纠正 + 5 个规范层面的微调**。其中第一条很重要，建议一定改。

## 1. 最重要：`T1 + T2` 不是 T3 的“上界”

你现在写：

> 当前以 T1+T2 作为进程内上界代理

这个表述需要改。

根据你的定义：

```text
T1:
hotkey recv → show request submitted

T2:
show request → show() return

T3:
physical key → first visible frame
```

因此：

```text
T1 + T2
```

代表的是：

```text
physical key
   ↓
OS dispatch
   ↓
hotkey recv
   ↓
show()
return
```

而真正：

```text
first visible frame
```

还在后面：

```text
render
→ compositor
→ present
→ display
```

所以严格来说：

> **T1 + T2 是“达到 show() 返回”的进程内延迟，不是 T3 的上界。**

在理想的单调时间线上，它更接近：

```text
T3 ≥ T1 + T2 + T0
```

当然 T0 本身又是进程外的 OS 调度部分。

因此建议把这句话改成：

> `T1 + T2` 用于描述应用内部从热键接收到 `show()` 返回的延迟，仅作为 T3 的**不完整内部代理/下界参考**，不代表实际 first-frame latency，也不得作为 T3 的上界。

这是这份方法学里我认为唯一一个需要明确修正的概念。

# 2. Cold Popup 的 `≤35ms` 要明确百分位

现在：

```text
Cold Popup
T1 + T2
目标 ≤35ms
```

但下面又规定：

```text
P50/P95 为门禁
```

Agent 会问：

> 35ms 是 P50 还是 P95？

应该直接写：

```text
Cold Popup
P95(T1+T2) ≤ 35 ms
```

Warm Popup：

```text
P50 ≤ 5 ms
P95 ≤ 10 ms
```

Query：

```text
App Search P95 ≤ 10 ms
File Search P95 ≤ 50 ms
```

Enter：

```text
P95 ≤ 50 ms
```

这样所有预算完全统一。

# 3. `T1` 和 `T2` 不应该本身成为 UX Gate

你现在 P0 UX：

```text
T1 / T2 → T3
```

我建议稍微调整优先级。

因为：

```text
T1 = 0.16ms
T2 = 20.2ms
```

这些是**诊断指标**。

真正的产品门禁应该：

```text
Cold Popup P95
Warm Popup P95
Query P95
Enter P95
```

也就是说：

```text
User-facing SLO
    ↓
Cold/Warm Popup
Query
Action

Diagnostic breakdown
    ↓
T1
T2
T3
```

推荐改成：

```text
P0 UX
    Cold Popup
    Warm Popup
    Query → Result
    Enter → Effect

P1 Diagnostic
    T1
    T2
    T3
```

T3 虽然是用户感知指标，但现在尚未自动化，所以现阶段其实也是 **P2 measurement**。

---

# 4. `T3` 不一定需要“高速摄像”

你现在写：

```text
T3:
ETW / 高速摄像
```

这个方向可以，但我建议不要在规范里把实现手段绑定死。

改成：

```text
T3 = Physical Input → First Presented Frame

Measurement:
- ETW / PresentMon / compatible frame-present instrumentation
- high-speed camera as external validation
```

也就是：

> **定义是 First Presented Frame，不定义工具。**

以后你找到更好的 Windows frame timing 方法，不需要修改性能规范。

高速摄像反而比较适合做一次：

```text
instrumentation validation
```

而不是长期 benchmark。

# 5. P95 的 sample size = 50，我建议提高

现在：

```text
每桶 50 轮
```

对：

```text
average
P50
```

还能用。

但你现在已经把：

```text
P95
```

定义为正式性能门禁。

50 个样本的 P95 实际上只有最末尾的少数几个样本贡献非常大，容易受到 Windows scheduler、Defender、background task 等噪声影响。

我建议：

```text
Fast benchmark:
    50 warm-up
    200 measured

Latency CI benchmark:
    1000 measured

P99/Max:
    1000+
```

没必要所有 benchmark 都跑 1000 次。

可以定义：

```text
Microbenchmark:
    N = 50/100

Latency gate:
    N ≥ 200

Tail analysis:
    N ≥ 1000
```

这样比较合理。

# 6. `P50/P95 为门禁`，但 regression threshold 应该明确应用于谁

你现在写：

```text
relative >10%
AND absolute >100µs
→ fail
```

很好。

但建议明确：

```text
Regression Gate applies to:
    P50 and P95

Does not apply to:
    P99
    Max
```

然后：

```text
Budget Gate
```

和：

```text
Regression Gate
```

也最好区分。

例如：

```text
Baseline Regression:
    current > baseline × 1.10
    AND
    current - baseline > 100µs

Absolute SLO:
    current P95 > budget
```

因为这是两个完全不同的问题。

例如：

```text
baseline = 1ms
current = 1.2ms
budget = 10ms
```

虽然：

```text
+20%
```

应该触发 regression warning/fail。

即便还远低于绝对预算。

反过来：

```text
baseline = 9ms
current = 9.5ms
budget = 10ms
```

可能没有 regression，但已经需要关注长期趋势。

这两种 Gate 不要混在一起。

# 7. Soak verdict 建议从“三选一字符串”改成结构化结果

你现在：

```text
verdict:
    staircase_suspected
    final_within_20pct
    slope_under_1kb_per_op
```

实际上这三个条件不是 mutually exclusive。

例如：

```text
staircase_suspected = false
final_within_20pct = true
slope_under_1kb = true
```

完全可以同时成立。

所以更适合：

```json
{
  "verdict": {
    "pass": true,
    "staircase_suspected": false,
    "final_within_20pct": true,
    "slope_within_threshold": true
  }
}
```

这会非常适合 Agent。

---

# 8. `slope_under_1kb_per_op` 仍然建议不要做统一阈值

这一点和你前面的版本一样，我还是建议改。

因为：

```text
1KB/op × 100000 query
= 100MB
```

对 query soak 来说显然不能接受。

但：

```text
1KB/op × 1000 plugin cycle
= 1MB
```

可能又没那么严重。

所以：

```text
slope_threshold
```

最好按 scenario 配置。

甚至可以更简单：

```text
global:
    slope is diagnostic only

gate:
    last-third retention
    staircase detection
    peak-to-final
```

这比人为设：

```text
1kb/op
```

更稳妥。

---

# 9. `peak_to_final_bytes` 很好，但最好增加 ratio

你现在：

```text
peak_to_final_bytes
```

是：

```text
peak - final
```

建议同时保存：

```text
peak_to_final_bytes
peak_to_final_ratio
```

例如：

```json
{
  "peak_private_bytes": 80000000,
  "final_private_bytes": 13000000,
  "peak_to_final_bytes": 67000000,
  "peak_to_final_ratio": 0.1625
}
```

这样未来 Agent 很容易分析：

```text
16% retained
```

比直接看数字更直观。

# 10. 还有一个特别适合你的 benchmark：Popup State

你现在已经有：

```text
Cold Popup
Warm Popup
```

建议补一个状态：

```text
Warm Visible Idle
```

也就是：

```text
Ctrl+Space
 ↓
Popup visible
 ↓
30s 什么都不操作
```

测：

```text
Private Bytes
CPU
```

因为你的软件是 launcher，不是普通窗口。

真正长期运行时可能是：

```text
Hidden Idle
```

但用户也可能：

```text
Popup Open
10~30 seconds
```

然后决定执行什么。

所以：

```text
Hidden Idle
Visible Idle
Searching
Plugin Running
```

这四个状态以后都应该有 memory/CPU baseline。
