# MVP4.3 Phase 11 — Compatibility Matrix

Phase 11 应和前面的 Phase 10 明确区分：

> **Phase 10 验证“攻击者穿不过来”；Phase 11 验证“现实世界的 MCP Server/SDK 能不能正常接进来”。**

当前正式 MCP 规范已经是 **2026-07-28**。它是一次 breaking revision：取消 `initialize/initialized` 与协议级 session，引入无状态请求、`server/discover`、HTTP header routing、可缓存 list 结果，以及新的 MRTR/extension 模型。旧的 `2025-06-18` 实现不能简单宣称“兼容当前 MCP”。([Model Context Protocol Blog][1])

因此 Phase 11 不应该直接覆盖现在的实现，而应该建立 **Compatibility Profile Matrix**。

---

# 1. Phase 11 最终目标

```text id="phase11-goal"
                 MCP Ecosystem
                      │
        ┌─────────────┼─────────────┐
        │             │             │
  Legacy Profile   Current        Future
   2025-06-18      2026-07-28      ext/*
        │             │             │
        └─────────────┼─────────────┘
                      ▼
               launcher-mcp
                      │
                      ▼
                 Normalized
                 Tool Model
                      │
                      ▼
              Existing Authority
                  Pipeline
```

也就是说：

> **协议兼容性被隔离在 `launcher-mcp`，不能污染 Launcher Domain / Workflow / AI / Action。**

---

# 2. 先修正一个重要版本定位

你当前实现：

```text
MCP_PROTOCOL_VERSION = "2025-06-18"
```

Phase 11 不建议把它简单升级为：

```text
MCP_PROTOCOL_VERSION = "2026-07-28"
```

因为这不是一个字符串替换。

2026-07-28 已经取消：

```text
initialize
notifications/initialized
Mcp-Session-Id
```

请求变成 self-describing，并通过 `_meta` 携带客户端信息/能力；另外新增 `server/discover`。([Model Context Protocol Blog][1])

所以应该正式引入：

```text id="profiles"
McpProtocolProfile
├── V2025_06_18
└── V2026_07_28
```

未来：

```text
V2027_...
```

继续追加，而不是修改已有枚举含义。

---

# 3. Compatibility Profile

建议：

```rust id="profile"
enum McpProtocolProfile {
    V2025_06_18,
    V2026_07_28,
}
```

但不要让这个 enum 出现在：

```text
launcher-domain
launcher-workflow
launcher-action
```

只存在：

```text
launcher-mcp::protocol
launcher-mcp::transport
```

# 4. Matrix 第一维：Protocol Version

| Profile    | initialize |   session | tools/list | tools/call | server/discover |
| ---------- | ---------: | --------: | ---------: | ---------: | --------------: |
| 2025-06-18 |          ✅ |    legacy |          ✅ |          ✅ |               ❌ |
| 2026-07-28 |          ❌ | stateless |          ✅ |          ✅ |      ✅ optional |
| Unknown    |          ❌ |         ❌ |          ❌ |          ❌ |               ❌ |

当前 2025 profile 保留兼容即可。

2026 profile 要按正式规范实现无状态模型。([Model Context Protocol Blog][1])

---

# 5. Matrix 第二维：Transport

Phase 11 建议：

| Transport       |                Status |
| --------------- | --------------------: |
| stdio           |            ✅ REQUIRED |
| Streamable HTTP |           🟡 Phase 11 |
| legacy HTTP+SSE | 🟡 compatibility-only |
| WebSocket       |                     ❌ |
| custom          |                     ❌ |

当前官方已经把旧 HTTP+SSE 视为 deprecated，并推荐新的 Streamable HTTP/stateless 模型。([Model Context Protocol Blog][1])

所以 Phase 11 的核心不是支持所有旧 transport，而是：

```text
2025 stdio
2026 stdio
2026 Streamable HTTP
```

先形成最有价值的矩阵。

建议结构：

```text id="transport-tree"
launcher-mcp/
├── protocol/

│   └── v2026_07_28/
│
├── transport/

│   └── streamable_http.rs
│
├── compatibility/

│   ├── negotiation.rs
│   └── matrix.rs
```

核心：

```text id="adapter-boundary"
MCP Wire
   ↓
Protocol Profile
   ↓
Normalized MCP DTO
   ↓
McpTool
```

后面的：

```text
McpProvider
ActionCatalog
Workflow
AI
ActionEngine
```

全部只消费 normalized DTO。

# 7. 2025 Profile

保持现有实现。

验证：

```text id="old-profile"
spawn
  ↓
initialize
  ↓
initialized
  ↓
tools/list
  ↓
tools/call
  ↓
shutdown
```

所有 Phase 1–10 安全测试继续跑。

因此：

> **2025 compatibility profile 必须保持现有 329 个安全/功能测试全绿。**

不能因为增加 2026 profile 而回归旧 profile。

# 8. 2026 Profile

2026 profile 的 stdio 请求应该不再：

```text id="new-profile"
initialize
initialized
```

而是：

```text id="stateless"
tools/list
tools/call
```

每个请求自描述。

2026-07-28 官方定义了：

* protocol version
* client info
* client capabilities

通过请求 `_meta` 传递，而不再依靠初始化 handshake。([Model Context Protocol Blog][1])

---

# 9. `server/discover`

2026 profile 增加：

```text id="discover"
server/discover
```

因此建议：

```rust
trait McpTransport {
    fn discover_server(...) -> Result<...>;
    fn list_tools(...) -> Result<...>;
    fn call_tool(...) -> Result<...>;
}
```

但不要让 `McpProvider` 直接调用：

```text
server/discover
```

仍然：

```text
McpTransport
    ↓
McpCatalog
```

Provider 只看：

```text
McpCatalogSnapshot
```

这样协议变化不会传播。

---

# 10. 2026 `tools/list` Cache

当前正式规范给 `tools/list` 增加：

```text
ttlMs
cacheScope
```

用于决定列表缓存时间和缓存范围。([Model Context Protocol Blog][1])

所以 Phase 11 建议把现在的：

```rust
McpCatalogSnapshot
```

扩成：

```rust
struct McpCatalogSnapshot {
    tools: Vec<McpTool>,
    fetched_at: Instant,
    cache: CacheMetadata,
}
```

例如：

```rust
struct CacheMetadata {
    ttl_ms: Option<u64>,
    scope: CacheScope,
}
```

但是：

```text
CacheMetadata
```

不得进入：

```text
ActionProposal
WorkflowStep
Effect
```

它只是 Discovery cache metadata。

---

# 11. Deterministic Tool Ordering

2026-07-28 的 list responses 强调 deterministic order。([Model Context Protocol Blog][1])

因此增加：

```text id="order"
MCP-COMPAT-ORDER-001
```

要求：

同一个 Server + 同一个 catalog state：

```text
tools/list
→
same logical order
```

如果 Server 顺序不稳定：

```text
McpCatalog
    ↓
deterministic normalization
```

但不要改变 Tool identity。

---

# 12. JSON Schema Compatibility

2026-07-28 已经把 Tool Schema 提升到完整 JSON Schema 2020-12：

```text id="schema"
oneOf
anyOf
allOf
if/then/else
$ref
$defs
```

并允许 `structuredContent` 成为任意 JSON value；规范同时要求不要自动 dereference 外部 `$ref`，并对 schema depth / validation time 做限制。([Model Context Protocol Blog][2])

这应该成为 Phase 11 的重点矩阵：

| Schema           |              Legacy |                2026 |
| ---------------- | ------------------: | ------------------: |
| object           |                   ✅ |                   ✅ |
| required         |                   ✅ |                   ✅ |
| oneOf            |               basic |                   ✅ |
| anyOf            |               basic |                   ✅ |
| allOf            |               basic |                   ✅ |
| `$defs`          |                  🟡 |                   ✅ |
| `$ref` internal  |                  🟡 |                   ✅ |
| recursive `$ref` | safely reject/bound | safely reject/bound |
| external `$ref`  |              reject |              reject |
| deep schema      |             bounded |             bounded |

# 13. `structuredContent`

当前 Phase 6 已经有：

```text
structuredContent: Option<Value>
```

这一点非常好。

Phase 11 再验证：

```text id="structured"
null
string
number
boolean
array
object
```

都能被 protocol layer 正确保留。

并且：

```text id="no-exec"
structuredContent
      ↓
AI context / result data
```

绝不能：

```text
structuredContent
      ↓
automatic action
```

这一点与 Phase 10 AI security 直接连接。

# 15. Error Code Compatibility

Phase 10 已经发现：

```text id="existing-error"
-32601 → CommandNotFound
```

Phase 11 要建立完整标准错误矩阵。

尤其官方 2026-07-28 把 resource-not-found 从 MCP custom `-32002` 调整为 JSON-RPC `-32602 Invalid Params`。([Model Context Protocol Blog][2])

虽然你现在只实现 Tools，但建议建立：

```text id="error-matrix"
MCP / JSON-RPC code
        ↓
McpError
        ↓
FailureClass
```

而不要：

```text
Workflow
    ↓
match -32601
```

# 16. Streamable HTTP

Phase 11 可以开始支持：

```text id="http"
Streamable HTTP
```

但必须单独 crate/module：

```text
launcher-mcp
└── transport
    ├── stdio.rs
    └── streamable_http.rs
```

不能让：

```text
launcher-core
```

依赖 HTTP implementation。

---

# 17. HTTP 2026 Routing Headers

官方 2026-07-28 要求 Streamable HTTP 使用：

```text id="headers"
MCP-Protocol-Version
Mcp-Method
Mcp-Name
```

并要求 header 与 JSON body 保持一致。([Model Context Protocol Blog][1])

例如：

```text id="header-mismatch"
Header:
Mcp-Name: search

Body:
params.name = delete
```

必须：

```text id="header-fail"
ProtocolViolation / HeaderMismatch
```

不能相信其中一个。

---

# 19. HTTP Authentication

Phase 11 **只设计，不强制实现完整 OAuth**，除非你决定现在正式支持 remote MCP。

如果进入 implementation：

```text
OAuth 2.0
OIDC
CIMD
issuer validation
credential binding
```

必须独立：

```text
launcher-mcp::auth
```

不要：

```text
launcher-domain::Auth
```

2026-07-28 已强化 issuer (`iss`) 校验，并要求凭据绑定 issuer；Dynamic Client Registration 正式进入 deprecation path，推荐 Client ID Metadata Documents。([Model Context Protocol Blog][1])

# 20. stdio 与 HTTP 不应该共享 session state

这是新规范特别值得利用的地方。

当前 stdio：

```text
spawn
initialize
call
shutdown
```

2026 HTTP：

```text
request
→
response
```

不要为了抽象复用而制造：

```rust
McpSession
```

成为 Core 长生命周期对象。

建议：

```text id="session"
Legacy transport:
    compatibility session internal

Modern transport:
    stateless request

Application:
    no protocol session dependency
```

这与官方 2026-07-28 的无状态设计一致。([Model Context Protocol Blog][1])

# 21. MCP Apps / Tasks 不纳入本阶段执行范围

2026-07-28 同时正式引入 MCP Apps，并把 Tasks 放到 extension。([Model Context Protocol Blog][2])

```text
Tools            ✅
Resources        ❌
Prompts          ❌
Tasks            ❌
MCP Apps         ❌
Sampling         ❌
Elicitation      ❌
```

但 compatibility matrix 要记录：

```text
recognized extension
    → safely ignored / unsupported
```

不能：

```text
unknown extension
    → protocol crash
```

# 26. Compatibility Contract

建议冻结：

```text id="compat-contract"
MCP Compatibility Contract v0.1

1. Wire differences are isolated to launcher-mcp.
2. Normalized McpTool is protocol-version independent.
3. Provider does not inspect protocol version.
4. Workflow does not inspect protocol version.
5. ActionResolver does not inspect protocol version.
6. AI Planner does not inspect protocol version.
7. Effect Executor consumes normalized invocation.
8. Unsupported extension never grants authority.
9. Unknown protocol feature fails closed or is ignored according to profile.
10. Security invariants from Phase 10 hold for every profile.
```

# 27. 最重要的 Cross-Profile Test

同一个 Tool：

```text id="cross-profile"
evaluate(expression)
```

分别来自：

```text
2025-06-18 stdio
2026-07-28 stdio
2026-07-28 HTTP
```

最终必须得到完全一致的 normalized representation：

```rust id="normalized"
McpTool {
    server_id,
    tool_name,
    input_schema,
    annotations,
}
```

然后：

```text
same ActionCatalogItem
same ActionProposal
same Workflow Reference
same ActionResolver behavior
same Effect type
same FailureClass semantics
```

也就是说：

```text id="cross-profile-flow"
2025 wire ──────┐
                │
2026 stdio ─────┼──→ Normalized MCP Tool
                │
2026 HTTP ──────┘
                         │
                         ▼
                identical Launcher behavior
```

**这是 Phase 11 最有价值的一条测试。**

# 31. Phase 11 的最终架构目标

完成后应该是：

```text id="final-compat"
                 MCP Wire Formats
                       │
        ┌──────────────┼───────────────┐
        │              │               │
   2025 stdio    2026 stdio     2026 HTTP
        │              │               │
        └──────────────┼───────────────┘
                       ▼
              Protocol Adapter
                       │
                       ▼
              Normalized McpTool
                       │
          ┌────────────┴────────────┐
          │                         │
      McpProvider              McpExecutor
          │                         │
          ▼                         ▼
    ActionCatalog                Effect
          │                         │
          └──────────┬──────────────┘
                     ▼
             Existing Launcher
                 Contracts
```

最终应满足：

> **MCP 版本可以换，Transport 可以换，SDK 可以换，但 `ActionProposal`、`WorkflowAction::Reference`、`ActionResolver`、`ActionEngine` 和 authority model 都不需要知道 MCP 发生了什么变化。**

这才是 Phase 11 的兼容性目标。

### 当前路线

```text
Phase 1–9   功能闭环       ✅
Phase 10    Security       ✅
Phase 11    Compatibility  → current
Phase 12    Release Gate   → final
```

还有一个实际工程建议：**Phase 11 不要一次性把 2026-07-28 的所有新特性都实现。** 当前正式规范已经把 Tasks、MCP Apps、MRTR、HTTP routing、authorization 等拆成多个不同复杂度的问题；先完成 **2025 compatibility + 2026 stateless Tools + Streamable HTTP + real SDK interoperability**，再把 Tasks/MCP Apps 保留为 extension backlog，会更符合你目前已经冻结的最小 authority surface。([Model Context Protocol Blog][2])
