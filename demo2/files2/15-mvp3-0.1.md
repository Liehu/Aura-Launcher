这两份设计稿已经进入了一个比较关键的阶段：**Plugin Protocol 已冻结，现在 Domain Contract 开始承担真正的产品架构责任。**

整体方向我认可，但我建议 **现在不要直接进入实现**。这次和前面的 Protocol 不同，`Command` / `Action` 一旦冻结，后面 UI、Context、Workflow、AI、MCP 都会反向依赖它，修改成本会明显上升。

我的结论是：

> **ACTION-CONTRACT-v0.1：方向正确，但有 6 个地方需要在冻结前解决。**
> **COMMAND-CONTRACT-v0.1：整体成熟，但有 5 个地方建议调整。**
> 两者合起来后，建议再增加一层非常薄的 **Command/Action lifecycle semantics**，然后再进入 calculator-plus 实现。

# 一、先看整体模型：现在已经基本正确

你现在的目标链：

```text
Plugin
  ↓
Command
  ↓
ActionDescriptor
  ↓
Capability
  ↓
Action Engine
  ↓
Effect
```

这是我比较认可的最终方向。

而且你明确：

```text
UI Schema
    不属于 Command Contract
```

这是正确的。

因此未来应该是：

```text
                   Command
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
       UI Host                 Actions
                                  │
                           Capability Check
                                  │
                             Action Engine
                                  │
                                Effect
```

这样不会让插件 API 被 UI 技术绑死。

# 二、ACTION-CONTRACT：第一个需要修改的是 `type`

你现在：

```json
{
  "id": "copy",
  "title": "Copy",
  "type": "system.copy_to_clipboard",
  "input": {
    "text": "80"
  }
}
```

这个方向对。

但：

```text
system.*
plugin.<id>.*
```

这里存在一个需要尽早解决的问题：

## `plugin.<id>.*` 到底是谁执行？

你目前定义：

```text
system.*
    → Host Action Engine

plugin.<id>.*
    → callback plugin.action RPC
```

那么最终其实存在两种 Action：

```text
Host Action
Plugin Action
```

它们虽然都叫 Action，但信任模型完全不一样。

我建议在 Contract 中正式定义：

```text
Action Execution Domain

system.*
    = Host-owned Effect

plugin.*
    = Plugin-owned Effect
```

然后明确：

```text
plugin.<id>.*
```

永远不能绕过：

```text
Host validation
Capability
Process isolation
```

即：

```text
Plugin Action
   ↓
Plugin Action RPC
```

仍然必须由 Host Broker 控制。

否则以后有人可能理解成：

```text
plugin action
   ↓
plugin 自己执行任意代码
```

那就会重新绕过你的 Action Engine。

# 三、Action 的 `input` 现在定义得太自由

你现在：

```json
"input": {
  "text": "80"
}
```

这个对于 MVP 很方便。

但后面很容易演化成：

```json
"input": {
  "x": ...
}
```

完全没有 schema。

最终：

```text
system.copy_to_clipboard
system.open
system.reveal
system.execute
```

每个 Action 都自己解释 input。

这会让 Action Contract 很快腐化。

我建议现在不需要做完整 JSON Schema，但至少定义：

```text
ActionType
    ↓
Action Input Schema
```

例如：

```text
system.copy_to_clipboard
    input:
        text: string

system.open
    input:
        target: string

system.reveal
    input:
        path: string

system.open_terminal_here
    input:
        path: string
```

可以先在规范中用表格定义，而不是增加复杂协议。

这样 Host 的：

```rust
ActionEngine
```

才能稳定映射：

```text
type → validate(input) → Effect
```

# 四、Action ID 和 Action Type 必须明确区别

现在有：

```json
"id": "copy",
"type": "system.copy_to_clipboard"
```

这两个字段的关系建议冻结为：

```text
id
    = Command 内局部稳定标识

type
    = 全局 Action semantics
```

也就是说：

```text
id = copy
```

可以在不同 Command 里重复。

例如：

```text
calc.result → copy
git.commit  → copy
file        → copy
```

但是：

```text
type = system.copy_to_clipboard
```

语义一致。

这非常好。

建议加一句：

> `Action.id` 在所属 Command 内必须唯一，不要求跨 Command 全局唯一。

# 五、`requires` 与 Manifest capability 的三层关系需要再明确

现在：

```text
Action.requires = ["clipboard.write"]
```

然后：

```text
Manifest
    ↓
Requested

User
    ↓
Granted

Broker
    ↓
Enforced
```

这个模型是对的。

但是还有一个重要问题：

### Action 要求的 capability 能不能超过 Manifest？

比如：

```text
Manifest:
[]

Action:
requires = ["clipboard.write"]
```

你现在：

> Action 丢弃。

这个是正确的。

但需要明确：

> **Action `requires[]` 是 Manifest requested capability 的子集。**

也就是：

```text
Action.requires ⊆ Manifest.capabilities
```

而不是：

```text
Action.requires
    → 自己申请 capability
```

否则就形成：

```text
Plugin Manifest 没声明
        ↓
Action 临时声明
        ↓
偷偷扩大权限
```

这违反你现在已经建立的 Capability 模型。

建议直接写成一个 invariant。

# 六、CapabilityDenied 不应该成为 JSON-RPC 错误

这是我认为 ACTION-CONTRACT 里最值得现在区分的一件事。

你写：

```text
未授予
→ DENY (-32001 CapabilityDenied)
```

但是这个 Action 并不是 Plugin RPC 出错。

而是：

```text
Host intentionally denied execution
```

如果直接把：

```text
-32001
```

作为 Plugin protocol error 返回，语义会混乱。

更合理：

```text
Plugin Protocol Error
    ↓
Plugin ↔ Host RPC

Action Execution Result
    ↓
Action Engine
    ├── Success
    ├── CapabilityDenied
    ├── InvalidInput
    ├── UnknownActionType
    ├── ConfirmationRequired
    └── EffectFailed
```

也就是说：

> **`CapabilityDenied` 属于 Action Engine Result，不一定属于 Plugin RPC Error。**

尤其以后：

```text
AI → Command → Action
```

AI 也可能触发：

```text
CapabilityDenied
```

那显然不能再叫 Plugin RPC error。

这条我强烈建议调整。

# 七、Unknown Action Type 的行为，我建议不是“拒绝执行”这么简单

你现在：

> unknown type → deterministic rejection

对。

但需要规定：

```text
Command 本身是否保留？
```

例如：

```json
{
  "title": "Foo",
  "actions": [
    {
      "id": "open",
      "type": "plugin.foo.magic"
    }
  ]
}
```

如果 Host 不支持：

```text
Command
```

应该：

```text
保留 Command
隐藏这个 Action
```

而不是：

```text
整个 Command 丢掉
```

除非：

```text
primary action
```

不存在合法 action。

我建议：

```text
Unknown secondary action
    → drop action

Unknown primary action
    → command remains but becomes non-executable
    OR fallback next valid action

Command itself invalid
    → drop command
```

否则一个插件多放一个未知 secondary action，就可能导致整个结果消失。

# 八、`actions[0] = primary` 目前有一点过度依赖数组位置

你写：

```text
actions[0] = primary
actions[1..] = secondary
```

MVP 很简单。

但我建议现在就改成显式字段：

```json
{
  "id": "copy",
  "role": "primary"
}
```

或者：

```json
"primary_action": "copy",
"actions": [...]
```

我更推荐：

```json
{
  "actions": [
    {
      "id": "copy",
      "role": "primary"
    },
    {
      "id": "insert",
      "role": "secondary"
    }
  ]
}
```

原因是以后：

```text
AI-generated actions
Dynamic actions
Disabled actions
Context actions
```

都可能发生。

单纯：

```text
index 0
```

很脆弱。

如果你想保持 MVP 简洁，也可以不改 schema，而把：

> **“第一个合法 Action 为 primary”**

写进规则。

这样至少不是简单的“数组第一项就是主动作”。

# 九、COMMAND-CONTRACT：`score` 我建议继续保持 hint，但加范围

你现在：

```json
"score": 0.0
```

并说：

> Host 可忽略。

这个设计对。

但是建议直接规定：

```text
score ∈ [0, 1]
```

或者：

```text
score ∈ [-∞,+∞]
```

二选一。

我更推荐：

```text
score ∈ [0, 1]
```

这样不同插件作者容易理解。

而 Core 最终：

```text
final_score =
    lexical
  + plugin_hint * weight
  + type_prior
  + frequency
  + recency
  + context
```

插件不能直接控制排名。

# 十、`provider_id` 不应该让 Plugin 自己随意返回

你现在：

```json
"provider_id": "plugin:com.example.calculator"
```

这个其实属于：

> **Host metadata**

而不是 Plugin command semantics。

如果插件自己写：

```text
provider_id = "plugin:foo"
```

Host 可能被污染。

建议：

```text
plugin_id
```

来自 Manifest / Host identity。

Host 在接收到 Command 后自己生成：

```text
provider_id = plugin:<manifest.id>
```

插件无需提供。

如果你现在的 domain model 已经要求这个字段，可以：

```text
plugin-side:
    optional / ignored

host:
    authoritative
```

这是非常值得现在修正的地方。

# 十一、`Command.id` 的“稳定唯一”需要进一步定义生命周期

你现在规定：

> 同一逻辑结果跨 query 不变。

非常重要。

但：

```text

```

这种简单插件比较容易。

例如 GitHub：


可以：

```text

```

但有些动态结果：


建议定义：

> `Command.id` 应表示**资源身份或逻辑动作身份**，而不是当前搜索实例身份。

例如：

```text

file:C:\a\b.txt
app:{known-id}
```

而不是：

```text

```

否则 Action Panel / history / cache / keyboard selection 都会受到影响。

# 十七、我建议新增一个“Action Resolution”阶段

现在执行链：

```text
Plugin
→ ActionDescriptor
→ Host validation
→ Capability check
→ Action Engine
→ Effect
```

我建议更精确：

```text
Plugin
    ↓
Command
    ↓
ActionDescriptor
    ↓
Action Resolution
    ├── type resolution
    ├── input validation
    ├── context eligibility
    ├── capability validation
    └── confirmation policy
    ↓
ResolvedAction
    ↓
Action Engine
    ↓
Effect
```

这样：

```text
ActionDescriptor
```

是**不可信声明**。

而：

```text
ResolvedAction
```

才是 Action Engine 可以接受的内部对象。

这是一个很漂亮的安全边界。

---

# 十八、这样 Host 内部 API 可以非常干净

例如：

```rust
trait ActionResolver {
    fn resolve(
        &self,
        command: &Command,
        action: &ActionDescriptor,
        ctx: &ContextSnapshot,
    ) -> ActionResolution;
}
```

结果：

```rust
enum ActionResolution {
    Ready(ResolvedAction),
    Hidden(HideReason),
    Disabled(DenyReason),
    Invalid(InvalidReason),
}
```

然后：

```rust
trait ActionEngine {
    fn execute(&self, action: ResolvedAction) -> ActionResult;
}
```

这样就非常清楚：

```text
Untrusted Descriptor
         ↓
      Resolver
         ↓
Trusted ResolvedAction
         ↓
    ActionEngine
```

我非常推荐采用这个模型。

---

# 十九、这也能解决“Unknown Action Type”的问题


```text

 ↓
```


这样 Action Engine 就能保持：

# 最后的判断

这两个 Proposed Contract **已经足够接近冻结，但我建议暂缓一次实现，先把上述几个语义钉死**。

最关键的不是字段，而是这四个边界：

```text
                    UNTRUSTED
                       │
                       ▼
Plugin Command / ActionDescriptor
                       │
                       ▼
                 ActionResolver
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        Context     Capability    Input
        Check         Check       Check
          └────────────┼────────────┘
                       ▼
                 ResolvedAction
                       │
                       ▼
                 Action Engine
                       │
                       ▼
                     Effect
```

以及：

```text
Command.id
    = logical identity

Action.id
    = local stable identity

Action.type
    = execution semantics

provider_id
    = Host authority

requires_context
    = eligibility

requires
    = capability requirement
```

**这几个概念一旦冻结，后面的 UI Schema、Workflow、AI、MCP 基本都可以建立在这套模型上，而不必再次改 Command/Action 的核心语义。**

所以我现在建议把这两个文档标记成：

```text
COMMAND-CONTRACT-v0.1
Status: Proposed — Revision 2

ACTION-CONTRACT-v0.1
Status: Proposed — Revision 2
```

完成上面这些语义修订后，再让 Agent 实现 `calculator-plus`。**这一轮最重要的不是写代码，而是确保 Action Engine 拿到的永远是 `ResolvedAction`，而不是插件随手构造的 `ActionDescriptor`。** 这是我认为这套 Launcher 从“插件系统”走向“可组合 Command Platform”最关键的一条架构边界。
