# P2.3-E — Security / Trust Boundary Closure

进入 **P2.3-E**。

这一批的目标不是“再增加安全功能”，而是对 1.0 当前已经冻结的执行链、权限边界、外部输入和恢复机制进行一次**最终安全收口**：

> **证明任何不可信输入都不能提升权限；任何未授权对象都不能进入 Effect；任何身份都不能被下游重铸；任何异常路径都不能绕过 Resolver / ActionEngine。**

本批次完成后，P2.3 才进入最后的 **UI / Interaction QA** 与 **Release Candidate** 阶段。

# 2. E1 — Security Contract Freeze

首先正式冻结：

```text
Security Boundary v1.0
```

核心原则只有三层：

```text
Authority

```

---

## 2.1 Authority

唯一执行权限路径：

```text
Producer
   ↓
ActionResolver
   ↓
launcher-action
 ├─ validate()
 └─ execute()
   ↓
Effect Executor
```

其中：

> `launcher-action` = ActionEngine。

禁止新增任何绕行执行入口：

```text
Core → PluginHost
Core → MCP
Workflow → Effect
Agent → Effect
UI → Effect
Provider → Effect
```

均属于架构违规。

---

# 3. E2 — Trust Boundary Inventory

将所有外部/不可信输入列出来。

| 来源                | 信任等级            | 可能影响            | 禁止                   |
| ----------------- | --------------- | --------------- | -------------------- |
| User Query        | Untrusted       | Search          | Authority            |
| Search Candidate  | Untrusted       | UI/Ranking      | Authority            |
| Plugin Manifest   | Untrusted       | Metadata        | Capability Grant     |
| Plugin Output     | Untrusted       | Observation     | Authority            |
| MCP Server        | Untrusted       | Tool Result     | Capability           |
| MCP Tool Metadata | Untrusted       | Catalog         | Execution Authority  |
| AI Output         | Untrusted       | Proposal        | Effect               |
| Workflow Input    | User-controlled | Variables/Input | Policy Bypass        |
| Config            | Semi-trusted    | Configuration   | Arbitrary execution  |
| IPC Payload       | Untrusted       | Commands        | Authority escalation |
| File Metadata     | Untrusted       | Search/Icon     | Code execution       |

核心原则：

> **Metadata 可以改变“看到什么”，不能改变“允许做什么”。**

# 6. E5 — Plugin Security Audit

Plugin 是本地最主要的不可信执行边界。

---

## 6.1 Manifest

Manifest 可以声明：

```text
commands
actions
capabilities requested
metadata
```

但不能：

```text
grant itself capability
```

例如：

```text
requires = ["filesystem.write"]
```

不等于：

```text
approved = true
```

---

## 6.2 Plugin Output

Plugin 返回：

```text
title
subtitle
action
metadata
```

均视为不可信。

特别检查：

```text
plugin output
→ action.requires
```

不能导致：

```text
capability auto grant
```

---

## 6.3 Disabled Plugin

```text
disabled
→ no candidate
→ no execution
```

---

## 6.4 Quarantined Plugin

```text
quarantined
→ no candidate
→ no execution
```

---

## 6.5 Plugin Namespace

继续保持：

```text
plugin.<id>.*
```

只有对应 plugin 自己拥有的 command/action namespace 可以被绑定。

禁止：

```text
plugin-a
  ↓
plugin-b action
```

或者：

```text
plugin output
  ↓
system.shutdown
```

这种 namespace confusion。

---

# 7. E6 — MCP Security Audit

MCP 必须继续维持：

```text
server_id
tool_name
```

双重身份绑定。

---

## E6-001 Tool Substitution

正常：

```text
server-A
tool-X
```

攻击：

```text
server-A
tool-Y
```

使用原来的 identity：

```text
reject
```

---

## E6-002 Server Substitution

```text
server-A/tool-X
```

替换成：

```text
server-B/tool-X
```

必须：

```text
ProtocolViolation
```

不能变成：

```text
CommandNotFound
```

然后被错误处理成 retry / success。

---

## E6-003 Tool Metadata Injection

MCP server 返回：

```json
{
  "name": "dangerous-tool",
  "description": "...",
  "requires": ["admin"]
}
```

不得因此自动增加：

```text
Capability
```

---

## E6-004 Arguments

继续保持：

```text
bounded
strict
typed
```

当前既有：

```text
256 KB arguments
```

继续作为输入上限之一。

---

# 8. E7 — Workflow Security Audit

Workflow 是编排层，不是权限层。

必须继续满足：

```text
Workflow
 ↓
Reference / Input
 ↓
ActionResolver
 ↓
ActionEngine
```

禁止：

```text
Workflow
 ↓
Effect
```

---

## 8.1 Identity Binding

特别测试：

```text
server_id
tool_name
```

不能来自用户模板动态替换后改变原始 identity。

也就是说：

```text
identity fields
```

必须保持静态绑定。

---

## 8.2 Output Injection

假设 Step 1 返回：

```text
{
    "server_id": "evil-server"
}
```

然后 OutputBinding：

```text
variables.server_id = step1.server_id
```

不能让 Step 2 把：

```text
server_id
```

替换进入受保护 identity。

---

## 8.3 Expression

继续验证：

```text
max_expr_depth = 32
```

不能通过：

```text
((((((((...
```

耗尽 parser stack / CPU。

Runtime 本身不提供业务权限。


## 10.1 Runtime Isolation

检查：

```text
Runtime-A
Runtime-B
```

```text

```

## 10.2 Process Cleanup

异常：

```text

```

最终：


> 被终止的 Runtime 不会继续以隐藏子进程形式执行。


# 12. E11 — Input / Resource Limits

1.0 必须有统一的**边界资源预算**。

至少冻结：

```text
Query length
Result count
Provider result count
Manifest size
Plugin output size
MCP message size
MCP argument size
Workflow variables
Workflow expression depth
Workflow steps
Agent turns
Agent proposals
Icon size
Cache item size
```

已有 Workflow：

```text
max_steps = 1000
max_vars = 256
max_var_bytes = 1 MiB
max_expr_depth = 32
```

MCP：

```text
arguments ≤ 256 KiB
```

继续保留。

---

# 13. DoS 防护原则

目标不是做企业级 sandbox，而是防止意外/恶意输入把 Launcher 拖死。

例如：

```text
巨大 MCP response
巨大 plugin result
巨大 workflow variable
巨大 search query
大量 provider candidates
大量 icon requests
```

最终必须：

```text
Bounded
Reject
Truncate according to contract
or isolate
```

而不是：

```text
Unbounded allocation
```
