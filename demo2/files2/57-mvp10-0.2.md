## P1-B：Persistent MCP / Plugin Protocol State

P1-B 正式启动。基于已经冻结的 **P0-A Runtime Persistence + P1-A RuntimeManager**，本阶段不再扩展进程管理，而是补齐：

> **Persistent Runtime 之上的 Protocol Session 生命周期、状态机、恢复与失效语义。**

核心边界继续保持：

```text
RuntimeManager
    “保留哪个进程实例”

ProcessSupervisor
    “如何启动 / 停止 / 回收进程”

ProcessSession
    “当前进程如何读写”

ProtocolSession
    “当前进程上的协议会话处于什么状态”
```

其中：

```text
Process Runtime ≠ Protocol Session ≠ Execution
```

三者必须是三个独立 identity / lifecycle。

---

# 1. P1-B 目标

P1-B 完成后，应支持：

```text
Persistent Runtime
        │
        ▼
Protocol Session
        │
        ├── establish
        ├── ready
        ├── use
        ├── invalidate
        ├── reconnect / reinitialize
        └── close
```

并允许：

```text
同一个 Runtime
    ├── Session S1
    ├── Session S1 持续复用
    │
    └── S1 失效
         ↓
        Session S2
```

同时严格禁止：

```text
Session recovery
    ↓
automatic replay
    ↓
old Execution
```

---

# 2. P1-B 非目标

本阶段明确不做：

```text
❌ Workflow v0.2
❌ Agent
❌ Task
❌ Execution replay
❌ exactly-once
❌ 并行 protocol operation
❌ Runtime CPU/RAM quota
❌ sandbox
❌ 多租户
❌ MCP Resources / Prompts 扩展
❌ MCP Apps
❌ Tasks
```

P1-B 也不重新设计 `RuntimeManager`。

# 3. 核心对象模型

建议新增协议层对象：

```rust
ProtocolSessionId
ProtocolSessionState
ProtocolSessionKey
ProtocolSession
```

### 3.1 ProtocolSessionId

```rust
pub struct ProtocolSessionId(/* opaque */);
```

要求：

```text
ProtocolSessionId != RuntimeId
ProtocolSessionId != ExecutionId
```

不得通过类型别名偷换。

---

# 4. ProtocolSessionKey

建议：

```rust
pub struct ProtocolSessionKey {
    pub namespace: String,
    pub endpoint_id: String,
    pub profile: ProtocolProfile,
}
```

例如：

```text
mcp / calc / V2025_06_18
mcp / calc / V2026_07_28
plugin / foo / default
```

重点：

> Session 复用必须由 **完整协议身份** 决定，而不是只看 RuntimeKey。

这样可以防止：

```text
same process
+ different protocol profile
→ accidental session reuse
```

# 5. MCP Session 状态机

建议先把状态压缩到真正必要的范围：

```text
                  ┌─────────────┐
                  │     New     │
                  └──────┬──────┘
                         │ establish
                         ▼
                 ┌───────────────┐
                 │ Initializing  │
                 └──────┬────────┘
                        │ success
                        ▼
                 ┌───────────────┐
                 │     Ready     │
                 └───┬───────┬───┘
                     │       │
             invalidate      │ close
                     │       │
                     ▼       ▼
               ┌─────────┐  Closed
               │ Invalid │
               └────┬────┘
                    │ re-establish
                    ▼
                 Initializing
```

失败情况：

```text
New
 ↓
Initializing
 ↓
Failed
```

而 `Failed` 不等于 Runtime 已经死亡。

---

# 6. 最关键的生命周期约束

### Runtime 活着，但 Session 已失效

合法：

```text
Runtime R1
MCP Session S1 = Invalid
```

然后：

```text
R1
 ↓
new MCP session
 ↓
S2
```

所以：

```text
R1 == R1
S1 != S2
```

---

### Runtime 崩溃

例如：

```text
R1 + S1
     ↓
process crash
```

结果：

```text
R1 dead
S1 dead
Ecurrent failed
```

P1-A 可以：

```text
R1 → R2
```

P1-B 可以：

```text
R2 → S2
```

但是：

```text
Ecurrent ≠ replay(Ecurrent)
```

新 Execution 才能使用 `S2`。

---

# 7. Session 与 Runtime 的关系

推荐明确存：

```rust
pub struct ProtocolSession {
    pub session_id: ProtocolSessionId,
    pub runtime_id: RuntimeId,
    pub key: ProtocolSessionKey,
    pub state: ProtocolSessionState,
    pub created_at: Instant,
    pub last_activity_at: Instant,
}
```

但是：

> **ProtocolSession 不拥有 ProcessSession。**

它只保存关联关系：

```text
ProtocolSession
      │
      └── runtime_id
              │
              ▼
        RuntimeManager
              │
              ▼
        ProcessSession
```

生命周期所有权仍然属于 Runtime 层。

---

# 8. Persistent MCP Executor 的新结构

P1-A 当前已经存在：

```text
McpExecutor
 └── runtime registry
```

P1-B 不应把大量 protocol state 继续塞进这个 registry。

建议变成：

```text
McpExecutor
 ├── RuntimeRegistry
 │
 └── SessionRegistry
```

关系：

```text
RuntimeKey
   │
   ▼
RuntimeId
   │
   └──── ProtocolSessionKey
                 │
                 ▼
          ProtocolSessionId
```

---

# 9. Session 建立流程

一次新的 persistent MCP operation：

```text
ActionEngine
   ↓
Effect
   ↓
McpExecutor
   ↓
resolve RuntimeKey
   ↓
RuntimeManager.use_runtime()
   ↓
lookup ProtocolSession
   │
   ├── Ready
   │      ↓
   │    use
   │
   ├── New / Invalid
   │      ↓
   │    establish
   │      ↓
   │    initialize
   │      ↓
   │    Ready
   │
   └── Failed
          ↓
        recreate
```

这里必须保证：

```text
session establishment
≠ execution retry
```

---

# 10. Execution 与 Session 的严格关系

每一次 Action execution：

```text
Execution E17
    ↓
Runtime R4
    ↓
Session S8
```

下一次：

```text
Execution E18
    ↓
Runtime R4
    ↓
Session S8
```

这是正常复用。

但是：

```text
E17
 ↓
protocol failure
 ↓
S8 invalid
 ↓
S9 established
```

只能：

```text
E18 → S9
```

不能：

```text
E17 → S9 → retry
```

---

# 11. Protocol Operation Lock

P1-A 已经规定：

> 一个 Runtime 同时只能有一个 protocol operation。

P1-B 建议把这个语义提升到 Session：

```text
ProtocolSession.acquire_operation()
```

结果：

```rust
Ready
Busy
Invalid
Closed
```

禁止内部 queue：

```text
operation 1
operation 2
operation 3
```

不能变成：

```text
queue
 ├── op2
 └── op3
```

而是：

```text
op1 → running
op2 → Busy
op3 → Busy
```

这样才能继续保持 v0.1 的 bounded semantics。

---

# 12. Initialize 的幂等策略

这是 P1-B 一个必须明确冻结的问题。

对于：

```text
Persistent Runtime R1
Session S1 = Ready
```

第二次执行不能再次无条件：

```text
initialize
```

而应该：

```text
lookup S1
 ↓
Ready
 ↓
reuse
```

只有：

```text
S1 Invalid
```

才：

```text
initialize new S2
```

因此：

```text
initialize count:
first operation  = 1
second operation = 1
third operation  = 1
```

而不是：

```text
1
2
3
```

---

# 13. Session invalidation

建议把 protocol failure 分类映射到 session 生命周期。

| MCP 层事件                   | Session | Runtime      |
| ------------------------- | ------- | ------------ |
| 正常 tool result            | Ready   | Alive        |
| JSON-RPC business error   | Ready   | Alive        |
| InvalidInput              | Ready   | Alive        |
| CommandNotFound           | Ready   | Alive        |
| ProtocolViolation         | Invalid | 通常 Alive     |
| malformed server envelope | Invalid | 通常 Alive     |
| EOF                       | Invalid | Dead/Unknown |
| process crash             | Invalid | Dead         |
| runtime killed            | Invalid | Dead         |
| explicit shutdown         | Closed  | Dead         |

这里要特别保留一个原则：

> **Protocol failure 不自动等价于 Runtime failure。**

否则一个错误响应就会不必要地杀掉整个 persistent runtime。

---

# 14. Plugin Persistent Session

Plugin 也使用同一个抽象，但不要为 Plugin/MCP 再复制两套 runtime machinery。

目标：

```text
PluginBroker
     │
     ▼
RuntimeManager
     │
     ▼
PluginProtocolSession
```

不过如果 Plugin 当前协议没有明确 session semantics，不要为了“统一”强行制造虚假的 protocol state。

因此建议：

```text
MCP
→ ProtocolSession first-class

Plugin
→ 只有存在真实协议 session 时才实例化
```

而不是：

```text
every persistent plugin
→ fake session
```

---

# 15. Session Persistence 的实际含义

必须冻结这个定义：

> **P1-B 的 persistence 指 protocol session 可附着在 persistent runtime 上持续存在，而不是将 session 永久写盘。**

即：

```text
process memory
    +
session memory
```

目前不做：

```text
SQLite persistence
disk checkpoint
session serialization
session restore after machine reboot
```

因此：

```text
application restart
→ Runtime gone
→ Session gone
```

这是正确行为。

---

# 16. Idle Cleanup

P1-A：

```text
RuntimeManager.sweep_idle()
```

P1-B 必须增加顺序约束：

```text
idle runtime
 ↓
Session close / protocol cleanup
 ↓
Runtime release
 ↓
Process termination
```

禁止：

```text
kill runtime first
 ↓
leave session registry dangling
```

所以建议：

```rust
ProtocolSessionRegistry::close_for_runtime(runtime_id)
```

由上层 protocol executor 处理协议语义关闭。

RuntimeManager 只负责：

```text
“这个 runtime 要结束了”
```

不负责：

```text
“怎么发送 MCP shutdown”
```

---

# 17. Crash Recovery

完整生命周期应该是：

```text
R1 alive
  │
  └── S1 Ready
        │
       E10
        │
        ▼
    process crash
        │
        ├── E10 = failed
        ├── S1 = invalid
        └── R1 = dead
                 │
                 ▼
             RuntimeManager
                 │
              restart
                 │
                 ▼
                R2
                 │
                 ▼
                S2
                 │
                 ▼
             E11 (new)
```

绝对禁止：

```text
E10
 ↓
R2
 ↓
S2
 ↓
replay E10
```

# 18. Session Identity Binding

建议冻结：

```text
SessionKey
    ↓
RuntimeKey
```

必须存在一致性检查。

例如：

```text
Session S1
    runtime_id = R1
    server_id  = calc
```

不得出现：

```text
S1
 → R1
 → server_id = another-server
```

也不得利用 session registry 跨 server lookup：

```text
calc
 ↓
reuse session of git
```

所以应该保留此前的 server/profile isolation。

# 20. P1-B 建议新增 API

概念层：

```rust
pub trait ProtocolSessionManager {
    fn get(
        &self,
        key: &ProtocolSessionKey,
    ) -> Option<ProtocolSessionId>;

    fn establish(
        &mut self,
        key: ProtocolSessionKey,
        runtime_id: RuntimeId,
    ) -> Result<ProtocolSessionId, SessionError>;

    fn invalidate(
        &mut self,
        session_id: &ProtocolSessionId,
    );

    fn close_for_runtime(
        &mut self,
        runtime_id: &RuntimeId,
    );

    fn state(
        &self,
        session_id: &ProtocolSessionId,
    ) -> Option<ProtocolSessionState>;
}
```

但这里的 `establish()` **不应执行 MCP initialize 本身**。

建议分开：

```text
SessionManager
    → state / identity / lifecycle

McpProtocolClient
    → initialize / tools/list / tools/call
```

这是本阶段非常重要的职责分离。

## P1-B 冻结后的架构

最终希望形成：

```text
                         ┌──────────────────┐
                         │   ActionEngine   │
                         └────────┬─────────┘
                                  │
                               Effect
                                  │
                 ┌────────────────┴────────────────┐
                 │                                 │
                 ▼                                 ▼
            McpExecutor                       PluginBroker
                 │                                 │
          ProtocolSession                     ProtocolSession*
                 │                                 │
             SessionRegistry                  SessionRegistry*
                 │                                 │
             RuntimeKey                         RuntimeKey
                 │                                 │
                 └──────────────┬──────────────────┘
                                ▼
                         RuntimeManager
                                │
                         ProcessSupervisor
                                │
                         ProcessSession
```

`*` 仅在 Plugin 本身确实存在需要持久化的协议会话语义时启用。

### P1-B 最终边界

可以把整个阶段压缩成一句冻结规则：

> **P1-A 决定“进程实例是否继续存在”，P1-B 决定“该进程上的协议会话是否继续有效”；任何 Session 恢复都只能服务于新的 Execution，不能恢复或重放旧 Execution。**

这条规则应成为 P1-B 的主验收标准。
