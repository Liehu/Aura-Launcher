这份 **Review 24 → APPROVE WITH REVISIONS** 的修改方向是对的。四个 R1–R4 解决的都是实际架构缺口，而不是文案优化；m1–m5 则把 v0.1 的边界进一步收紧。按你的冻结路径，**MVP4.1 可以在这些修订完成后正式冻结为 `FROZEN v0.1`**。

## 一、四个 R 的处理结论

### R1：Resolution Source 必须冻结

这是此前草案最大的实际缺口。

现在执行链应该明确为：

```text
ActionReference
      │
      ├── ① 当前 Popup Session results
      │
      └── ② Provider fresh query
                │
                ▼
       (provider_id, command.id)
                │
         ┌──────┴──────┐
         ▼             ▼
      Found          Not Found
         │             │
         ▼             ▼
    re-resolve     CommandNotFound
```

关键点是：

```text
WorkflowDefinition
    ≠
Command Registry
```

也：

```text
WorkflowDefinition
    ≠
cached ActionDescriptor
```

因此 `ActionReference` 是**逻辑引用**，不是物化对象。

建议把 R1 的失败语义冻结成：

```text
CommandNotFound → Stop
```

并明确：

> Fresh query 不是“重新搜索用户当前输入”，而是针对指定 `provider_id` 获取新的 Command 集合，再按 `(provider_id, command.id)` 精确匹配。

这样可以避免 Workflow 执行时因为搜索词、排序、score 变化而找不到原 Command。

# 二、R2：`WorkflowAction` 双态是正确修复

最终模型：

```rust
enum WorkflowAction {
    Reference(ActionReference),
    Inline(ActionDescriptor),
}
```

这解决了 `system.*` 没有 `provider/command/action` 三元组的问题，同时没有产生第二执行通道。

完整路径：

```text
Reference
   ↓
resolve reference source
   ↓
ActionDescriptor
   ↓
Resolver

Inline
   ↓
ActionDescriptor
   ↓
Resolver
```

所以二者最终汇聚：

```text
WorkflowAction
      ↓
ActionDescriptor
      ↓
ActionResolver
      ↓
ResolvedAction
      ↓
ActionEngine
```

这是正确的。

### 一个建议性的契约措辞

`Inline(ActionDescriptor)` 应明确：

> Inline descriptor is a persisted declaration, not a trusted resolved executable object.

尤其不要让 `Inline` 在持久化之后变成：

```text
“已经允许执行的 system.copy”
```

它仍然是输入。

# 三、R3：Failure Taxonomy 现在完整了

最终建议冻结成 **8 类**：

| 分类                  | 来源                         | 默认策略                   |
| ------------------- | -------------------------- | ---------------------- |
| `CapabilityDenied`  | Resolver                   | Stop                   |
| `InvalidInput`      | Resolver                   | Stop                   |
| `UnknownActionType` | Resolver                   | Stop / 归类 InvalidInput |
| `StaleContext`      | Context check              | Re-resolve             |
| `Timeout`           | Plugin/Executor            | Retry                  |
| `BusinessError`     | Plugin ActionFailed        | Policy                 |
| `ProtocolViolation` | Malformed / Crashed        | Stop                   |
| `PluginUnavailable` | Spawn / not installed      | Retry → Stop           |
| `CommandNotFound`   | Workflow resolution source | Stop                   |

这里实际上你已经指出一个重要问题：

> `UnknownActionType` 到底作为独立分类，还是规范化成 `InvalidInput`？

我建议 **契约层只保留 `InvalidInput` 作为 Workflow failure class**，而在内部诊断/错误模型里保留：

```text
UnknownActionType
```

作为具体 reason。

即：

```text
ResolverError::UnknownActionType
        ↓
WorkflowFailure::InvalidInput
```

这样 Workflow 不需要理解 ActionResolver 内部的所有错误细节。

同理：

```text
PluginError::Malformed
PluginError::Crashed
```

统一归：

```text
ProtocolViolation
```

而：

```text
PluginError::Spawn
```

归：

```text
PluginUnavailable
```

这就形成了真正的：

```text
Plugin / Resolver native errors
          ↓
Workflow Failure Classification
          ↓
Failure Policy
```

而不是 Workflow 自己猜错误类型。

# 四、R4：Confirmation 的处理方式应该冻结为 Pause

R4 是必要修复。

最终建议：

```text
ResolvedAction
    │
    ▼
ConfirmationRequired
    │
    ▼
WorkflowRun
Paused(ConfirmationRequired)
    │
    │ originating UI session
    ▼
User confirms
    │
    ▼
Re-resolve
    │
    ▼
ActionEngine
```

这里特别重要的是：

### Confirmation 不属于 Workflow 持久化状态中的授权事实

不能保存：

```text
confirmed = true
```

然后日后继续运行。

可以保存：

```text
Paused(ConfirmationRequired)
```

因为它表达的是：

> 此步骤等待一个新的外部确认事件。

而不是：

> 用户曾经授权过这个 Action。

确认恢复后也应该：

```text
resume
 ↓
re-resolve
 ↓
ActionEngine
```

不能：

```text
resume
 ↓
execute previously resolved action
```

这与 INV-050 / INV-048 完全一致。

---

# 五、m1：删除 Run-level `Retrying`

同意。

最终应该：

```text
WorkflowRun
    Running
       │
       ├── Step retry
       │       ↓
       │   StepRetrying
       │       ↓
       │   StepResolving
       │
       └── next step
```

而不是：

```text
WorkflowRun
   ↓
Retrying
```

因为 Retry 是 **Step execution policy**，不是 WorkflowRun 的业务状态。

这能明显减少：

```text
Run state × Step state
```

的组合爆炸。

# 六、m2：`ActionInvocation` 去掉 Workflow 绑定

这个修改很重要，而且会直接帮助 MVP4.2/MCP。

最终：

```rust
struct ActionInvocation {
    action: ActionReference,
    input: Value,
    resolved_context_generation: Option<u64>,
    attempt: u32,
}
```

而：

```text
StepRun
   └── invocation_id
```

负责建立 Workflow 关系。

未来：

```text
Workflow
AI
MCP
```

全部可以复用：

```text
ActionInvocation
```

而不会产生：

```text
WorkflowActionInvocation
AIActionInvocation
MCPActionInvocation
```

这种类型裂变。

# 八、m4：`WorkflowRun 可序列化` 是正确粒度

这里不应该冻结：

```text
SQLite
```

甚至也不应该冻结：

```text
JSON file
```

只冻结：

> `WorkflowRun` MUST have a stable serializable representation.

这样将来可以：

```text
SQLite
File
Memory
Remote Store
```

而不会破坏 Contract。

但要进一步区分：

```text
Serializable
≠
Resumable
```

Workflow v0.1 可以要求：

```text
Run serializable
```

但不一定要求：

```text
任意崩溃后自动恢复到中断点
```

后者应该属于运行时实现能力。

# 九、m5：术语统一

建议直接统一：

```text
resolved_context_generation
```

然后只出现这一种名字。

不要同时存在：

```text
observed_context_generation
resolved_context_generation
context_generation_at_observation
```

因为它们会让后续代码把：

```text
“我看到的 Context”
```

和：

```text
“我最终解析出来所依据的 Context”
```

混在一起。

在你当前语义里，真正需要保存的是：

> **该 ActionInvocation 最近一次成功解析时所依据的 Context generation。**

因此：

```text
resolved_context_generation
```

最准确。

# 十、我建议把 `WorkflowAction` 最终定义成这样

这是 R2 完成后的核心类型：

```rust
enum WorkflowAction {
    /// Resolve through current command source.
    Reference(ActionReference),

    /// Host-owned inline action declaration.
    /// Never treated as trusted/executable state.
    Inline(ActionDescriptor),
}
```

然后：

```text
WorkflowAction
       │
       ▼
Action Source Resolution
       │
       ▼
ActionDescriptor
       │
       ▼
ActionResolver
       │
       ▼
ResolvedAction
       │
       ▼
ActionEngine
```

两条路径最终完全汇聚。

# 十一、Resolution Source 最好也抽象成一个明确的 Resolver 子步骤

不要让 Workflow Runner 自己写：

```text
if popup_results.contains(...)
else provider.query(...)
```

否则 Workflow Runner 又开始理解 Provider/Search 细节。

建议：

```text
WorkflowActionResolver
```

或者：

```text
ActionReferenceResolver
```

负责：

```text
Reference
    ↓
Popup Session
    ↓
Fresh Provider Query
    ↓
CommandNotFound
```

最终：

```text
ActionReference
      ↓
ReferenceResolver
      ↓
ActionDescriptor
      ↓
ActionResolver
      ↓
ResolvedAction
```

这样职责非常清楚：

| Resolver            | 解决什么             |
| ------------------- | ---------------- |
| `ReferenceResolver` | **在哪里找到 Action** |
| `ActionResolver`    | **当前是否允许执行**     |

不要把两个问题混在一起。

# 十三、最终建议的 MVP4.1 冻结原则

我会把这 10 条作为 `ADR-0015` 的核心：

```text
WF-001  Workflow is orchestration only.

WF-002  WorkflowDefinition persists logical Action references/proposals,
        never ResolvedAction.

WF-003  WorkflowRun contains execution state, not executable Effects.

WF-004  ActionInvocation is producer-agnostic and carries no Workflow identity.

WF-005  ActionInvocation is re-resolved immediately before execution.

WF-006  ActionReference resolution uses:
        Popup Session Results → Fresh Provider Query.

WF-007  Inline ActionDescriptor is untrusted and is re-resolved.

WF-008  Workflow has no Capability Authority and no Effect Gateway.

WF-009  Retry creates a new execution_id and is Step-scoped.

WF-010  Confirmation pauses the Run and can only be resumed by the
        originating UI session; resume requires re-resolution.
```

另外将：

```text
CommandNotFound
PluginUnavailable
PluginCrashed
```

正式加入 failure classification，而不是散落在 Runner 的错误分支里。

## 结论

这次 R1–R4 实际把 MVP4.1 从一个“看起来合理的 Workflow 模型”提升成了**可以真正冻结的 Runtime Contract**。

尤其三个修订非常关键：

```text
R1
ActionReference
    ↓
明确 Resolution Source

R2
WorkflowAction
    ↓
Reference / Inline 双态

R3
Native errors
    ↓
统一 Failure Classification

R4
ConfirmationRequired
    ↓
Paused
    ↓
UI resume
    ↓
Re-resolution
```

因此现在可以进入你提出的冻结路径：

```text
ADR-0015 Workflow Orchestration
        +
WORKFLOW-CONTRACT-v0.1
        +
Workflow State Machine
        +
Failure Policy Matrix
        +
INV-049/050 生效
        +
INV-052~057
```

**冻结后再实现代码。**

而实现顺序我会严格按：

```text
1. domain types
2. reference resolution
3. failure classification
4. workflow runner state machine
5. calculator-plus mixed Reference + Inline workflow
6. CAT-WF-001~012
```

推进，暂时不引入 DAG、条件、循环、并行、Rollback、AI、MCP 或新的 Effect Domain。
