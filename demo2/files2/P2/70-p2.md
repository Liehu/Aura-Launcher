# P2.1：Search + Incremental Index + Application Identity

这一阶段建议正式定义为 **Launcher Core 2.0 Foundation**，目标不是再增加搜索类型，而是把目前已经存在的：

```text
App Provider
File Provider
Folder Provider
Plugin Provider
History
Ranking
Action
```

统一成一个真正可扩展的 **Retrieval → Identity → Ranking → Result** 管线。

核心目标：

> **启动快、查询快、结果不重复、文件库持续新鲜、应用不会重复、History/Context 后续可以无痛叠加。**

---

# 1. P2.1 最终目标

完成后，搜索主链应该冻结为：

```text
User Query
    │
    ▼
Query Parser / Intent
    │
    ▼
Provider Retrieval
    │
    ├── Apps
    ├── Files
    ├── Folders
    ├── Plugins
    ├── Commands
    └── System
    │
    ▼
Candidate Normalization
    │
    ▼
Canonical Identity
    │
    ▼
Deduplication
    │
    ▼
Feature Extraction
    │
    ▼
Global Ranking
    │
    ├── lexical
    ├── type
    ├── history
    ├── recency
    └── context
    │
    ▼
Top-K
    │
    ▼
SearchResult
```

与此同时：

```text
Filesystem
    ↓
Watcher
    ↓
Incremental Index Queue
    ↓
Indexer
    ↓
SQLite
    ↓
File Search
```

应用：

```text
Start Menu / Registry / MSIX / Portable
    ↓
Application Discovery
    ↓
Application Identity
    ↓
Application Record
    ↓
Search
```

---

# 2. P2.1 的三个真正核心

这次不要把三部分当成三个独立 feature。

应该建立：

```text
Search
   ↕
Index
   ↕
Identity
```

三者之间的契约。

因为：

### Search 需要 Identity

解决：

```text
Chrome
Chrome.lnk
chrome.exe
```

是不是同一个结果。

### Index 需要 Identity

解决：

```text
rename
delete
shortcut
duplicate
```

如何更新已有对象。

### History 需要 Identity

解决：

```text
“Chrome 被打开了 57 次”
```

究竟记录在：

```text
Chrome.lnk
```

还是：

```text
chrome.exe
```

上。

所以：

> **P2.1 最值得提前冻结的是 Identity，而不是某个具体搜索算法。**

# 4. P2.1-A：统一 Search Pipeline

目前最应该避免的是：

```text
AppProvider
  → 自己排序

FileProvider
  → 自己排序

PluginProvider
  → 自己排序
```

应该统一成：

```text
Provider
    → Retrieval
    → raw candidates

SearchCoordinator
    → normalize
    → identity
    → dedup
    → ranking
```

---

# 5. Provider 的职责重新冻结

Provider 只负责：

> **“把可能相关的候选项找出来。”**

不负责：

```text
history
context
final ranking
UI ordering
```

例如：

```rust
pub trait SearchProvider {
    fn retrieve(
        &self,
        query: &SearchQuery,
        budget: &RetrievalBudget,
    ) -> Vec<SearchCandidate>;
}
```

不再强调：

```rust
search() -> already-final-results
```

---

# 6. Retrieval 与 Ranking 必须分离

推荐：

```text
Retrieval
    = recall

Ranking
    = precision
```

例如：

```text
query = "chrome"
```

Provider 找：

```text
Chrome
Chrome.lnk
chrome.exe
Chrome uninstall
Google Chrome
Chromium
```

然后：

```text
Identity
Dedup
Ranking
```

最终只显示：

```text
Google Chrome
```

# 7. Retrieval Budget

之前 `MAX_FILE_HITS = 100` 是一个合理临时修复，但现在应该正式抽象：

```rust
pub struct RetrievalBudget {
    pub max_candidates: usize,
    pub max_scan_time: Duration,
}
```

Provider：

```text
Apps      → 100
Files     → 100
Plugins   → 50
Commands  → 50
```

这些是：

```text
retrieval budget
```

而不是：

```text
final result count
```

# 8. Result Limit 与 Candidate Limit 必须分开

例如：

```text
result_limit = 12
```

绝对不能意味着：

```text
provider only returns 12
```

而应该：

```text
provider
 → <= retrieval budget

global rank
 → top 12
```

最终：

```text
Retrieval
100
 ↓
Identity
 ↓
Dedup
 ↓
Ranking
 ↓
Top 12
```

建议正式冻结：

```rust
pub struct SearchQuery {
    pub raw: String,
```

```rust
pub enum QueryIntent {

    Url,
```

> Intent 只影响排序，不默认过滤 Provider。

# 10. Query Normalization

建议至少：

```text

tokenization
```

```text
原始 Query

```

例如：

```text

```

最终：

```text

```

# 11. 不要过度处理 Unicode

P2.1 不建议马上引入复杂：


```text

Unicode-safe
```

以后可以作为独立 Search Enhancement。

# 13. SearchIdentity

这是 P2.1 最重要的新类型之一。

建议：

```rust
pub enum SearchIdentity {
    Application(ApplicationId),
    File(FileId),
    Folder(FolderId),
    Command(CommandId),
    PluginCommand(PluginCommandId),
    System(SystemObjectId),

```

第一阶段可以内部用稳定 String/Hash 实现，但对外建立 typed abstraction。

# 14. FileId

不要简单：

```text
file.id = database row id
```

因为 SQLite rowid 会因 rebuild 改变。

更合理：

```text
FileIdentity
    = normalized absolute path
```

第一版可以：

```rust
pub struct FileId(pub String);
```

内部 canonical form：

```text
volume
+
normalized absolute path
```

以后再升级为：

```text
volume serial
+
file id
```

也不影响上层 API。

---

# 15. FolderId

同理：

```text
FolderId
    = normalized absolute path
```

例如：

```text
D:\Projects\Foo
```

统一 canonical：

```text
d:\projects\foo
```

但注意：

> **大小写规范化不能改变 Windows 实际路径语义。**

它只用于 identity comparison。

---

# 16. ApplicationId

应用不能再使用：

```text
display_name + executable path
```

直接作为 identity。

建议优先级：

```text
MSIX / AppUserModelID
    ↓
registered application identity
    ↓
normalized executable identity
    ↓
portable application canonical path
```

因此：

```rust
pub struct ApplicationId(pub String);
```

内部 canonical form 可以是：

```text
msix:<package family / app id>
appx:<AUMID>
exe:<normalized executable>
portable:<normalized executable>
```

# 17. Shortcut Identity

`.lnk`：

```text
Shortcut
```

不是最终的 ApplicationIdentity。

建议：

```text

├── shortcut_path
├── target_path
├── arguments
├── working_directory
└── application_id?
```

例如：

```text

   ↓

   ↓
```

所以 Search 最终可以：

```text

ApplicationIdentity(Chrome)
```

不要：




# 28. File Index v2


继续保留。

---

# 29. 为什么需要 normalized_path

避免：

```text
D:\Foo\Bar.txt
d:\foo\bar.txt
```

被认为不同。

也避免：

```text
D:\Foo\.\Bar.txt
```

之类 identity 问题。

但是：

> 不要把 canonicalization 做成会访问磁盘的 `realpath`。

否则 Junction / symlink 又会引入新的 traversal。

只做 lexical normalization。


```rust
pub trait FileWatcher {
```

```text

```

# 32. Change Event

统一：

```rust
pub enum FileChange {
    Created(PathBuf),
    Modified(PathBuf),
    Deleted(PathBuf),
    Renamed {
        old: PathBuf,
        new: PathBuf,
    },

```

# 33. Watcher 不等于 Indexer

非常重要：

```text
Watcher
    = 我观察到发生了什么

Indexer
    = 我如何更新数据库
```

所以：

```text
Watcher
 ↓
bounded queue
 ↓
coalescer
 ↓
Indexer
```

---

# 34. Coalescer

实际 Windows 文件操作经常出现：

```text
create
modify
modify
modify
rename
modify
```

不能：

```text
6 DB updates
```

而应该：

```text
events
 ↓
coalesce(path)
 ↓
final state
 ↓
one DB transaction
```

---

# 35. Coalesce 规则

例如：

```text
Created(A)
Modified(A)
Modified(A)
```

变为：

```text
Created(A)
```

例如：

```text
Created(A)
Deleted(A)
```

可以直接：

```text
No-op
```

例如：

```text
Created(A)
Renamed(A → B)
```

变为：

```text
Created(B)
```

例如：

```text
Modified(A)
Deleted(A)
```

变为：

```text
Deleted(A)
```

---

# 36. Rename 必须保持 Identity

对于：

```text
A.txt
→
B.txt
```

建议：

```text
FileId A
→
FileId B
```

是否视为同一个对象，需要分两个概念：

```text
Path Identity
File Object Identity
```

P2.1 可以先：

```text
SearchIdentity = path-based
```

未来再引入 Windows file ID。

不要现在就复杂化。

# 37. Watcher Overflow

`ReadDirectoryChangesW` 可能 overflow。

必须定义：

```text
ERROR_NOTIFY_ENUM_DIR
```

或者 buffer overflow：

```text
WatcherOverflow
```

发生时：

```text
Watcher
 ↓
Overflow
 ↓
mark root Dirty
 ↓
background subtree rescan
```

而不是：

```text
restart launcher
```

---

# 38. Dirty Root

建议：

```rust
pub struct DirtyRoot {
    pub root: PathBuf,
    pub reason: DirtyReason,
}
```

例如：

```text
Overflow
MissedEvents
WatchFailure
ManualRepair
```

然后：

```text
Dirty
 ↓
rescan only that root
```

不是：

```text
full disk rebuild
```

---

# 39. Index Queue 必须 bounded

与整个项目的设计保持一致：

```rust
pub struct IndexQueue {
    capacity: usize,
}
```

例如：

```text
10,000 events
```

满了之后：

```text
drop/coalesce
→ mark root dirty
```

而不是：

```text
unbounded VecDeque
```

否则几十万文件大规模变化时会爆内存。

---

# 40. Index Update Transaction

一个批次：

```text
events
 ↓
resolve filesystem state
 ↓
BEGIN
 ↓
upsert/delete
 ↓
COMMIT
```

失败：

```text
rollback
```

不要半写。

---

# 41. File disappearance

例如：

```text
watch says Modified(A)
```

但实际：

```text
A no longer exists
```

不要认为是 error。

应该：

```text
SELECT
if missing
→ DELETE
```

因为事件和磁盘状态之间存在 race。

---

# 42. Watcher 与 Full Rebuild 并发

必须禁止：

```text
rebuild
+
incremental updates
```

同时修改同一 index。

推荐：

```text
IndexCoordinator
   ├── rebuild lock
   └── incremental queue
```

状态：

```text
Idle
Rebuilding
Updating
Repairing
```

---

# 43. Rebuild 期间事件怎么办

这是一个非常重要的设计问题。

如果：

```text
Full rebuild
```

运行 30 秒：

期间发生：

```text
create A
delete B
rename C
```

不能直接丢掉。

推荐：

```text
Rebuild starts
 ↓
Watcher keeps collecting
 ↓
Rebuild commits snapshot
 ↓
Replay/coalesce events collected during rebuild
 ↓
Index becomes current
```

最终：

```text
index generation N
→
incremental events
→
generation N+1
```

# 47. Search Freshness 不是绝对一致

这里建议明确：

> File Search 是 **eventually consistent**。

可能：

```text
文件刚创建
→
100–500ms 后才出现
```

这是可接受的。

但：

```text
文件刚删除
→
旧结果还能永远存在
```

是不允许的。

# 48. Search Result Cache

P2.1 可以做非常小的 query cache：

```text
recent query
→
results
```

例如：

```text
max 32 queries
```

但是：

> Index change 后 cache 必须失效或按 generation invalidation。

建议：

```text
cache key:
normalized query + index generation
```

这样不用复杂 invalidation。

# 50. Ranking 顺序

建议：

```text
Canonicalize
 ↓
Dedup
 ↓
Base lexical score
 ↓
Type prior
 ↓
History
 ↓
Context
 ↓
Final sort
 ↓
Top-K
```

这样：

```text

```

不会把：


# 51. Ranking Stability

对于相同：

```text

index
history
context
```

必须：

```text
same result order
```

所以最终 sort 需要：

```text
score DESC

```

作为 deterministic tie-breaker。

# 54. Context Ranking

你已有：

```text
launcher-context
```

P2.1 先只做：

```text
context boost
```

不要改变搜索语义。


```text

```

适当提升。


仍然能够搜索到。

# 55. Application Ranking

应用应该具有：

```text
type_prior = high
```

但不要：

```text
Application always > File
```

例如：

```text
query = "report.pdf"
```

文件应该优先。

因此：

```text

```

必须是有限 boost。
