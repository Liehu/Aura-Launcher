# P2.3-F — UI / Interaction QA

进入 **P2.3-F**。

前面的：

```text
P2.3-A  Architecture       ✅
P2.3-B  Product E2E         ✅
P2.3-C  Reliability         ✅
P2.3-D  Performance         ✅
P2.3-E  Security            ✅
```

已经把后台能力基本锁定。F 的目标是最后验证：

> **用户通过键盘、鼠标、不同 DPI 和不同运行状态，能否稳定、可预测地完成 Launcher 的核心操作。**

这里尤其要坚持一个原则：

> **F 是 UI/交互验证批，不借机修改 Action、Resolver、Runtime、MCP、Workflow 的基础契约。**

# 2. F1 — UI Contract Re-audit

先重新检查当前 UI 契约，不新增 API。

目前冻结的核心模型应继续保持：

```text
UiMode
├─ Main
├─ Action
└─ Workflow

Confirmation
└─ Action child state

Agent
└─ not a top-level mode
```

UI 角色：

```text
Present
Select
Navigate
Invoke
Confirm
Observe
```

UI 不应该拥有：

```text
Effect
Capability
Resolver internals
ActionEngine internals
Runtime
MCP transport
PluginHost
```






```text

```

# 7. F4 — Selection / Invocation

测试：

```text
Result
 ↓
Select
 ↓
Enter
```

必须保证 Enter 对应的是：

```text
currently selected candidate
```

而不是：

```text
previous result
stale result
previous query
```

特别覆盖：

```text
query supersession
cache hit
provider completion race
```

例如：

```text
Query A
 ↓
slow provider

Query B
 ↓
fast provider
```

最终：

```text
Query B
```

的结果必须完全覆盖 A 的 UI 状态。

A 的 late response 不得重新污染 UI。

---

# 8. Primary Action UX

当前规则：

```text
first Ready action
```

如果第一个 Action：

```text
Disabled
```

则：

```text
next Ready action
```

成为 Primary。

F 要从用户视角验证：

```text
Action menu
```

显示出来的 primary action 与实际：

```text
Enter
```

行为一致。

不能出现：

```text
UI says Action A
Enter actually executes Action B
```

# 9. F5 — Confirmation UX

Confirmation 属于：

```text
Action
```

而不是：

```text
独立 top-level mode
```

因此 UI flow：

```text
Main
 ↓
Action
 ↓
Confirmation
 ↓
Confirm / Cancel
```

---

## Confirmation 必须显示

至少：

```text
action title
target
consequence / relevant description
confirm
cancel
```

但不要暴露内部：

```text
Effect
Capability
RuntimeId
ExecutionId
MCP Session internals
```

---

# 10. Stale Confirmation

这是安全 + UI 的交叉验证。

场景：

```text
Action A selected
 ↓
Confirmation displayed
 ↓
context/action changes
```

然后：

```text
Confirm
```

必须：

```text
reject stale action
```

不能：

```text
old confirmation
→ executes new / replaced target
```

这直接对应之前：

```text
INV-AUTH-004
```

# 13. Toast / Notification Contract

Toast 必须严格使用 whitelist。

不要让 backend error：

```text
raw error string
```

直接进入 UI。

应该：

```text
Internal Error
 ↓
classified UI event
 ↓
approved presentation
```

避免：

```text
MCP error:
server_id=...
raw JSON...
stack trace...
```

直接弹给用户。

# 24. F 测试必须覆盖的核心竞态

P2.3-F 最值得关注的不是普通“按钮能不能点”，而是下面这些竞态：

```text
Query A
 ↓
Provider A pending
 ↓
Query B
 ↓
Provider B complete
 ↓
UI displays B
 ↓
Provider A complete
 ↓
MUST NOT overwrite B
```

以及：

```text
Action selected
 ↓
confirmation shown
 ↓
action/context stale
 ↓
Confirm
 ↓
MUST reject stale
```

还有：

```text
popup close
 ↓
late provider result
 ↓
MUST NOT resurrect popup/UI state
```

以及：

```text
workflow pause
 ↓
late action completion
 ↓
MUST update correct run/step only
```

这些测试价值高于单纯增加几十个 VR baseline。

到这里：


此时 Launcher 的核心逻辑、异常行为、性能、安全和交互都已经有独立闭环。

下一阶段 **P2.3-G** 不再验证“程序功能是否能运行”，而是验证：

```text
安装
 ↓
运行
 ↓
产生用户数据
 ↓
升级
 ↓
迁移
 ↓
恢复
 ↓
卸载
 ↓
重新安装
```

整个生命周期是否不会破坏用户数据和运行状态。

**P2.3-F 的实施起点建议先锁 `UI-001 ~ UI-020` 的 Keyboard / Focus / Race 三类测试，再做 DPI 与 VR-016~020。** 这样能优先抓出真正影响 Launcher 交互正确性的状态机问题，而不是先花大量时间重新生成截图。
