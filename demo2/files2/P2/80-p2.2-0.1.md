# Launcher 1.0：从基础设施转向产品能力

P2.1-B/C/D/E 完成后，基础数据链已经比较完整：

```text
File Index
Application Catalog
      ↓
SearchCoordinator
      ↓
Ranking
      ↓
ActionResolver
      ↓
launcher-action
      ↓
Execution
```

接下来不建议把五项能力并行推进。它们之间存在明显依赖关系。

我建议把 **Launcher 1.0** 冻结为下面 5 个产品批次：

```text
P2.2-A  Favorites / Pinning
          ↓
P2.2-B  Query Cache
          ↓
P2.2-C  Context-aware Ranking
          ↓
P2.2-D  Plugin Ecosystem Management
          ↓
P2.2-E  Installer / Upgrade / Recovery
```

其中 A～C 属于**核心 Launcher UX**，D 属于**生态能力**，E 属于**产品交付与生命周期**。

---

# P2.2-A — Favorites / Pinning

这是下一步最应该先做的。

原因很直接：

> Favorites 是最确定、最容易验证、对搜索 Ranking 又有明确价值的用户意图信号。

它不依赖 AI，也不需要复杂模型。

---

## 1. 用户模型

建议区分三个概念：

```text
Favorite
Pinned
Recent
```

不要把它们混成一个 `usage_score`。

### Favorite

用户明确标记：

> “我希望这个东西始终容易找到。”

### Pin

用户明确要求：

> “在某个固定位置显示。”

例如：

```text
Launcher home
Favorites section
```

### Recent

系统自动生成：

```text
recent usage
```

---

# 2. Favorites 数据模型

建议：

```rust
pub struct Favorite {
    pub identity: SearchIdentity,
    pub created_at: Timestamp,
    pub order: u32,
    pub title_override: Option<String>,
}
```

关键是：

> Favorite 绑定 **semantic identity**，而不是 Provider item id。

因此：

```text
StartMenu/Chrome.lnk
Registry/chrome.exe
```

即使来源变化：

```text
Favorite → Chrome ApplicationIdentity
```

仍然有效。

---

# 3. Pin 不应该等价于 Favorite

建议：

```rust
pub enum PinLocation {
    Home,
}
```

以后再扩展：

```text
Context
Category
QuickPanel
```

但 1.0 先只有：

```text
Home
```

这样不会把 Pinning 做成一个布局系统。

---

# 4. Favorite 的生命周期

```text
Application exists
       │
       ▼
Favorite
       │
       ├── source changed
       │
       ├── path changed
       │
       └── app temporarily unavailable
```

Favorite 不应该立即删除。

例如：

```text
D:\Portable\Foo\foo.exe
```

U 盘拔出：

```text
ApplicationState = Unavailable
```

Favorite 仍存在。

U 盘重新插入：

```text
identity reappears
        ↓
Favorite automatically reconnects
```

---

# 5. Favorite 不产生执行权

这一条继续保持：

```text
Favorite
   ↓
SearchIdentity
   ↓
Live Catalog resolution
   ↓
SearchResult
   ↓
ActionResolver
   ↓
ActionEngine
```

不能：

```text
Favorite
   ↓
stored Action
   ↓
execute
```

否则 stale action 就有安全问题。

---

# 6. Pin UI

主 Launcher 可以增加：

```text
┌─────────────────────────────┐
│ Search                      │
├─────────────────────────────┤
│ Favorites                   │
│                             │
│ Chrome    VS Code    Git    │
│                             │
├─────────────────────────────┤
│ Results                     │
│ ...                         │
└─────────────────────────────┘
```

但不要创建一个新的 UI Mode。

继续：

```text
UiMode::Main
```

Favorites 只是 Main Mode 的一个结果区域。

---

# 7. Favorite Ranking

Favorite 应该是一个强 signal：

```text
score =
    text relevance
  + provider score
  + history
  + context
  + favorite boost
```

但是：

> Favorite 不能违反 query relevance 的基本约束。

例如：

```text
query = "excel"
```

不能因为：

```text
Favorite = Chrome
```

就把 Chrome 排到 Excel 前面。

因此 Favorite 更适合：

```text
strong secondary boost
```

而不是：

```text
absolute priority
```

---

# 8. Favorite 操作

建议 Action：

```text
system.favorite.add
system.favorite.remove
system.favorite.move
```

但这些仍然必须经过：

```text
ActionResolver
↓
launcher-action
```

不要让 UI 直接修改数据库。

---

# 9. Favorites Storage

SQLite：

```text
favorites
----------------------
identity_key PK
created_at
order_index
title_override
```

因为当前已经有 SQLite，可以直接扩展。

# P2.2-B — Query Cache

Favorites 完成后再做 Query Cache。

因为现在：

```text
IndexGeneration
ApplicationCatalogGeneration
SearchCoordinator
```

都已经成熟。

---

## 11. Cache Key

不要简单：

```text
cache["chrome"]
```

而应该至少：

```rust
pub struct SearchCacheKey {
    pub query: String,
    pub mode: SearchMode,

    pub file_generation: IndexGeneration,
    pub application_generation: ApplicationCatalogGeneration,

    pub context_generation: ContextGeneration,
}
```

未来才不会出现：

```text
index changed
but old result returned
```

---

# 12. Cache Value

缓存：

```text
SearchSnapshot
```

而不是：

```text
live Action
```

例如：

```rust
pub struct CachedSearch {
    pub results: Vec<SearchResultSnapshot>,
    pub created_at: Timestamp,
}
```

Action 在真正 invoke 时仍然重新：

```text
resolve
validate
execute
```

---

# 13. Query Cache 只缓存 Search

不能缓存：

```text
Effect
ResolvedAction
ExecutionResult
```

所以：

```text
Cache
   ↓
SearchResult
```

到这里为止。

---

# 14. L1 / L2

第一版：

```text
L1 memory cache
```

足够。

不要马上做磁盘 Query Cache。

Launcher 典型 query：

```text
chrome
code
calc
notepad
```

生命周期很短，磁盘持久化收益有限，却会引入：

```text
invalidation
schema migration
IO
corruption
```

---

# 15. Negative Cache

可以考虑：

```text
"foobar123"
```

短时间重复查询。

但是只允许：

```text
very short TTL
```

例如：

```text
100~500ms
```

具体值让 benchmark 决定。

不要长期缓存：

```text
No Result
```

因为 catalog 可能刚刚更新。

---

# 16. Query Cache 验收

```text
CACHE-001 cache hit
CACHE-002 cache miss
CACHE-003 generation invalidation
CACHE-004 context invalidation
CACHE-005 stale result rejection
CACHE-006 negative cache
CACHE-007 bounded memory
CACHE-008 rapid query supersession
CACHE-009 cache never contains executable authority
CACHE-010 benchmark improves warm TTFR
```

# P2.2-C — Context-aware Ranking

这是从“Launcher 工具”进入“智能 Launcher”的第一步。

但我建议仍然完全不引入 AI。

---

# 17. Context Model

当前已经有：

```text
SearchContextSnapshot
```

现在正式加入 ranking features：

```rust
pub struct ContextSignals {
    pub current_folder: Option<FileIdentity>,
    pub foreground_application: Option<ApplicationIdentity>,
    pub time_bucket: TimeBucket,
    pub launcher_source: LauncherInvocationSource,
}
```

---

# 18. Context 只产生 Score

严格：

```text
Context
   ↓
ContextSignals
   ↓
Ranking
```

不允许：

```text
Context
   ↓
Action authorization
```

---

# 19. Current Folder Ranking

例如用户当前在：

```text
D:\Projects\Launcher
```

搜索：

```text
cargo
```

那么：

```text
D:\Projects\Launcher\.cargo
D:\Projects\Launcher\target
```

可以获得少量 context boost。

但不能让：

```text
D:\Windows\System32\cargo.exe
```

因为“更近”而完全消失。

---

# 20. Foreground Application Context

例如当前：

```text
VS Code
```

用户输入：

```text
git
```

可以适当提升：

```text
Git Bash
Git GUI
Git commands
```

不过第一版建议只使用：

```text
foreground app identity
```

不做：

```text
window title semantic parsing
clipboard inspection
document content
```

---

# 21. Context Weight

继续统一走：

```text
RankingWeights
```

新增：

```rust
pub struct ContextRankingWeights {
    pub foreground_app: f32,
    pub current_folder: f32,
    pub time_bucket: f32,
}
```

不要把：

```text
+17
+32
+44
```

散落在 Provider 里。

---

# 22. 用户控制

必须有：

```text
Settings
  → Context-aware ranking
       On / Off
```

这是一个全局 feature flag。

关闭后：

```text
context weight = 0
```

而不是：

```text
Context provider disappears
```

---

# 23. Context Privacy

Context ranking 要遵循：

> 尽可能只保存抽象 identity，不保存用户活动内容。

例如保存：

```text
foreground application identity
```

而不是：

```text
完整窗口标题
完整文档内容
完整路径历史
```

这样后续即使加入 telemetry 或同步，也不会把隐私模型搞复杂。

---

# 24. Context Learning

这一批先不做 ML。

可以做：

```text
deterministic weighted signals
```

未来才考虑：

```text
online learning
bandit
embedding
neural ranking
```

---

# P2.2-D — Plugin Ecosystem Management

到这里才进入插件生态。

现在 Plugin Runtime 已经存在：

```text
Plugin Manifest
PluginBroker
Plugin Host
Capability
ExecutionId
```

缺的是：

> **用户如何安装、启用、禁用、更新和诊断插件。**

---

# 25. Plugin Registry

建立：

```text
PluginRegistry
```

统一管理：

```text
Installed
Enabled
Disabled
Broken
Quarantined
```

---

# 26. Plugin Lifecycle

```text
Discovered
   ↓
Validated
   ↓
Installed
   ↓
Enabled
   ↓
Running
```

失败：

```text
Validated
   ↓
Broken
```

或者：

```text
Running
   ↓
Crash
   ↓
Quarantined
```

---

# 27. Plugin Manifest

现有 Manifest 已经是 authority boundary。

P2.2-D 不允许插件通过更新 manifest：

```text
自动增加 Capability
```

必须：

```text
manifest requested capabilities
        ↓
host policy
        ↓
approved capabilities
```

---

# 28. Plugin Installation

第一版建议支持：

```text
Local Package
```

而不是：

```text
Marketplace
```

例如：

```text
plugin.zip
```

或者正式 package format：

```text
.plugin
```

---

# 29. Package Layout

建议：

```text
plugin-package/
├── manifest.json
├── plugin.exe
├── resources/
└── checksums/
```

安装到：

```text
%LOCALAPPDATA%\Launcher\Plugins\<plugin-id>\
```

---

# 30. Plugin ID

Plugin identity：

```text
namespace + plugin_id
```

必须：

```text
stable
case-normalized
validated
```

不能因为 display name 改变而改变 plugin identity。

---

# 31. Plugin Updates

更新不是：

```text
overwrite files
```

应该：

```text
v1
 ↓
stage v2
 ↓
validate
 ↓
switch
 ↓
v1 retained for rollback
```

这和 Launcher 本身的升级机制可以共享设计思想。

---

# 32. Plugin Rollback

如果：

```text
v2 startup crash
```

则：

```text
v2
 ↓
quarantine
 ↓
rollback v1
```

而不是：

```text
plugin unavailable forever
```

---

# 33. Plugin Quarantine

连续 crash：

```text
0
1
2
3
```

超过 policy：

```text
Quarantined
```

并禁止自动 restart。

---

# 34. Plugin Management UI

建议 Settings 中：

```text
Plugins

┌─────────────────────────────┐
│ Git Tools                   │
│ v1.4.0   Enabled            │
│ capabilities: ...           │
├─────────────────────────────┤
│ PDF Tools                   │
│ v2.1.0   Disabled           │
│                             │
├─────────────────────────────┤
│ Install Plugin              │
└─────────────────────────────┘
```

不需要新增：

```text
Plugin Mode
```

---

# 35. Plugin Diagnostics

需要显示：

```text
Plugin
Version
State
Last start
Last crash
Restart count
Requested capabilities
Granted capabilities
```

但：

```text
capability granted
```

必须展示为 host policy 的结果。

不能写成：

```text
plugin requests = plugin owns
```

---

# 36. Plugin Marketplace Deferred

Launcher 1.0：

```text
Local installation ✅
Management ✅
Update ✅
Rollback ✅

Marketplace ❌
Cloud account ❌
Auto-discovery internet ❌
```

这样可以先把安全边界跑通。

# P2.2-E — Windows Installer / Upgrade / Recovery

最后做交付能力。

这是 Launcher 从：

```text
developer build
```

变成：

```text
real Windows product
```

的关键一步。

---

# 37. 安装包模型

建议先选择：

```text
Per-user installation
```

原因：

```text
no admin requirement
simple update
isolated user state
```

系统级安装以后再考虑。

---

# 38. 安装与 Data 必须分离

这是必须冻结的：

```text
Program Files
    = binaries

%LOCALAPPDATA%\Launcher
    = mutable data
```

包括：

```text
Config
Database
Index
Catalog
Plugin
Icon Cache
Logs
```

不能把：

```text
database
plugins
icons
```

放进：

```text
Program Files
```

---

# 39. Configuration 与 Installation 分离

升级：

```text
Launcher.exe v1
    ↓
Launcher.exe v2
```

不应该影响：

```text
Favorites
History
Plugins
Index
Settings
```

---

# 40. Upgrade Strategy

推荐：

```text
Current
   ↓
Download / stage
   ↓
Verify
   ↓
Close Launcher
   ↓
Install new version
   ↓
Start
   ↓
Health check
```

---

# 41. Upgrade Rollback

启动 v2：

```text
health check
```

失败：

```text
rollback v1
```

不能让用户：

```text
Launcher unavailable
```

---

# 42. Single Instance 与 Upgrade

之前已经修复：

```text
CreateMutex lifetime
```

Launcher 1.0 要把它正式纳入 upgrade contract：

```text
normal launch
    ↓
single instance

installer/updater
    ↓
controlled shutdown
    ↓
upgrade
    ↓
restart
```

不能由 updater 强行：

```text
TerminateProcess
```

否则 index/catalog transaction 和 plugin host 会变得危险。

---

# 43. Crash Recovery

启动时检查：

```text
last shutdown state
```

例如：

```text
Clean
Crashed
UpgradeInterrupted
RecoveryRequired
```

---

# 44. Crash Recovery 不应该恢复 Action

这是非常重要的一条：

```text
Crash
   ↓
recover state
```

只能恢复：

```text
Index
Catalog
Config
Plugin state
UI preferences
```

绝不能自动恢复：

```text
previous Action
Workflow execution
Plugin Effect
MCP tool call
```

也就是：

> **Crash recovery ≠ Action replay**

和前面的：

```text
ExecutionId
RuntimeId
ProtocolSessionId
```

规则完全一致。

---

# 45. Index Recovery

如果 Launcher crash：

```text
SQLite
```

应依赖 WAL / transaction integrity 恢复到：

```text
last committed generation
```

启动后：

```text
File Index
    ↓
Watcher restart
    ↓
reconciliation
```

---

# 46. Plugin Recovery

如果：

```text
Plugin Host crashed
```

不能让整个 Launcher crash。

应：

```text
PluginHost crash
    ↓
Broker detects
    ↓
runtime policy
    ↓
bounded restart
    ↓
plugin unavailable
```

这与已经实现的 Runtime Policy 一致。

```text

❌ Cloud Sync
❌ Marketplace
❌ ML ranking
❌ Embedding search
```
