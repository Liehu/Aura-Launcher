# 1. `not_discard_other_results`：建议正式升级成硬不变量

这个测试：

```text
MCP provider unavailable
        ↓
Search
        ↓
healthy provider results survive
+
provider failure reported
```

我认为应该正式写入：

```text
INV-SEARCH-004

Failure or unavailability of one provider MUST NOT suppress successful
results from unrelated providers.
```

而且还应该区分三种情况：

```text
Provider A = success
Provider B = unavailable
Provider C = success
```

结果：

```text
A + C remain
B failure = diagnostics
```

如果用户查询明确针对 B：

```text
mcp:foo ...
```

才允许表现成：

```text
targeted provider unavailable
```

而不是静默返回空结果。

这条对以后：

```text
MCP
Plugin
File Index
```

都非常重要。

---

# 2. Windows Path Identity 这批补得很好

你现在明确：

```text
\\?\C:\Foo
≡
C:\Foo
```

以及：

```text
\\?\UNC\server\share\foo
≡
\\server\share\foo
```

同时：

```text
\\server\share\foo
≠
C:\foo
```

以及：

```text
C:\Foo\
≡
C:\Foo
```

这些正是后面 Watcher 最容易出问题的地方。

尤其：

```text
\\?\UNC\
```

如果没有现在固定，很容易以后出现：

```text
Watcher path
    ≠
SQLite indexed path
    ≠
SearchIdentity
```

导致：

```text
delete
rename
history
dedup
```

全部异常。

---

# 3. 建议再冻结一个非常重要的规则

目前你已经覆盖：

```text
prefix
UNC
separator
trailing slash
..
```

建议再明确：

```text
Device / Volume namespaces
```

至少先定义：

```text
\\.\...
```

**默认不作为普通 FileId 输入。**

也就是说：

```text
\\.\PhysicalDrive0
```

这类路径不应该进入普通文件搜索 identity。

否则：

```text
FileId
```

与普通 filesystem path 的语义会混在一起。

这不要求现在实现，只要写成：

```text
unsupported / non-filesystem identity
```

即可。

---

# 4. Path Identity 不应做“真实路径解析”

你目前一直坚持：

```text
lexical normalization
```

这是正确的。

继续禁止：

```text
realpath
canonicalize
resolve junction
follow symlink
```

在：

```text
normalize_path_identity()
```

内部出现。

最终：

```text
Path identity
    = lexical identity

Filesystem identity
    = actual object state
```

二者要保持概念分离。

建议最终：

```rust
pub struct ApplicationRecord {
```

现在：


以后：

自然可以追加。

这样你以后可以判断：

```text

```

与：

```text
all sources disappeared
```

完全是两种情况。

# 6. 建议补 `primary_source`

现在你说：

> 主来源不变。

那就最好显式建模：

```rust
pub struct ApplicationRecord {
    pub primary_source: ApplicationSource,

```

而不要依赖：


作为隐式主来源。

因为以后 merge 顺序改变：


会影响 UI。

# 7. `IndexGeneration`：现在预留是对的

这个设计我继续支持：

```text
index_meta.generation
```

首建：

```text
0
```

每完成一次 rebuild：

```text
0 → 1
1 → 2
...
```

但这里建议明确一个关键语义：

> **Generation 表示“已提交的索引版本”，不是“rebuild 已开始”。**

所以：

```text
rebuild begins
generation = 42
```

应该保持：

```text
42
```

直到：

```text
rebuild successfully commits
```

再：

```text
42 → 43
```

失败：

```text
generation stays 42
```

这样将来：

```text
Search cache key = query + generation
```

才可靠。

---

# 8. Generation 与增量更新的关系

未来 P2.1-B：

```text
event batch
→ transaction
→ commit
→ generation++
```

不要：

```text
every file event
→ generation++
```

否则：

```text
1000 file modifications
```

会得到：

```text
generation +1000
```

没有意义。

正确：

```text
coalesced batch
→ one commit
→ one generation increment
```

# 11. Application Identity 还有一个要提前冻结的边界

**IdentityResolver 必须是 pure / no-effect。**



建议加：

```text

Identity resolution MUST NOT produce or execute Effects.
```

这会和你现有 architecture 非常一致。

# 15. Bounded Queue

一定要保持：

```text

```

建议：


队列满：


# 17. Coalescer 要按 Identity 而不是字符串简单合并

一旦 Path Identity 已经规范化：


```text

```

```text

```

应该调用：

```text

```

否则：


还是会存在。

# 18. Rebuild + Watcher

下一阶段必须一起考虑：

```text

+

```

推荐：

```text

        ↓

        ↓
Rebuild active?
   ├── yes → retain/coalesce
   └── no  → update
```

Rebuild 完成：

```text

 ↓

```

否则 rebuild 过程中发生的变更会丢。

# 19. Overflow Recovery


