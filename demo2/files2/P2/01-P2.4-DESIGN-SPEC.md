# Aura-Launcher P2.4 — Design Specification v0.1

> Status: PROPOSED  
> Baseline: Launcher 1.0 RC1  
> Platform: Windows-first  
> Development mode: Agentic Coding

## 1. Purpose

P2.4 is **Post-1.0 Foundation Closure**. It closes platform foundations required by 2.x without introducing P2.5+ product capabilities.

### In scope

- P2.4-0 Baseline / documentation closure
- P2.4-A Application Catalog 2.0
- P2.4-B File Index Maintenance 2.0
- P2.4-C Plugin Control Plane 2.0
- P2.4-D Plugin SDK / CLI
- P2.4-E Plugin Development Diagnostics
- P2.4-F Release Gate / documentation freeze

### Explicitly out of scope

- Query Intent / AI Query Understanding
- Personal Ranking / Ranking Explainability
- Search Contract v2 full redesign
- Workflow Editor
- DAG / Parallel / Join
- Durable Workflow
- Agent Productization
- Marketplace
- Cloud Sync / Multi-device
- Enterprise

## 2. Frozen architecture

```text
Producer
  ↓ ActionProposal / ActionDescriptor
ActionResolver
  ↓
launcher-action::validate()
  ↓
launcher-action::execute()
  ↓
Effect
```

Only `launcher-action` owns execution authority.

Search, Cache, Favorites, Context, Catalog metadata, Plugin metadata, MCP metadata and AI output are data/signals only.

### Frozen identity/generation rules

- `ExecutionId`, `RuntimeId`, `ProtocolSessionId` are distinct namespaces.
- `IndexGeneration` advances only after successful index commit.
- `CatalogGeneration` advances only after successful catalog reconcile commit.
- Plugin lifecycle state is not runtime state.
- Identity normalization is deterministic and side-effect free.
- Cache keys must include every generation that can invalidate the result.

## 3. P2.4 work breakdown

```text
P2.4-0
   ↓
┌─────────────┬─────────────┬─────────────┐
P2.4-A        P2.4-B        P2.4-C
   └─────────────┬─────────────┘
                 ↓
              P2.4-D
                 ↓
              P2.4-E
                 ↓
              P2.4-F
```

A/B/C may run in parallel after P2.4-0. D depends on Plugin contract/lifecycle decisions from C. E depends on D's executable lifecycle. F depends on all release-facing tasks.

# 4. P2.4-A — Application Catalog 2.0

## Objective

Turn the existing persistent `catalog.db` into a durable, authoritative application catalog without rewriting stable discovery implementations.

### 4.1 Source model

```text
Start Menu
Registry / Uninstall
Packaged / AUMID
App Paths
Portable Roots
      ↓
ApplicationDiscovery
      ↓
ApplicationObservation
      ↓
ApplicationCatalogCoordinator
      ↓
catalog.db
      ↓
CatalogProvider
      ↓
Search
```

### 4.2 ApplicationObservation

Minimum logical fields:

```rust
ApplicationObservation {
    source_id,
    source_kind,
    identity_hint,
    display_name,
    launch_target,
    package_identity,
    aumid,
    app_path,
    icon_identity,
    metadata,
    observed_at,
}
```

Observation is untrusted data and is not executable authority.

### 4.3 Canonical identity

Identity precedence:

1. Stable packaged identity / AUMID when available.
2. Canonical normalized Win32 executable target.
3. Canonical App Paths target.
4. Portable executable target.
5. Fallback source-scoped identity only when no stronger identity exists.

Identity resolution must be pure and must not touch disk.

### 4.4 Catalog lifecycle

```text
Observed
  ↓
Normalized
  ↓
Merged
  ↓
Ready
  ├── Stale
  ├── Broken
  └── Removed
```

`Stale` and `Broken` are metadata states. They must never silently grant or retain execution authority.

### 4.5 Reconciliation

Reconcile requirements:

- one writer
- single transaction
- deterministic ordering
- delete missing observations
- preserve stable identity where possible
- generation +1 only after commit
- failed reconcile does not advance generation
- previous committed catalog remains queryable on failure

### 4.6 Search integration

The application search path must read the catalog through a provider abstraction. Discovery is responsible for producing observations; search is not allowed to rediscover applications synchronously.

# 5. P2.4-B — File Index Maintenance 2.0

## Objective

Turn the current incremental index into a self-healing, long-running subsystem.

### 5.1 Root lifecycle

```text
Configured
  ↓
Available
  ↓
Watching
  ├── Event → Verify → ApplyBatch
  ├── Overflow → DirtyRoot → Rescan
  ├── WatcherFailure → ReRegister
  └── RootMissing → Unavailable
                         ↓
                      Reappeared
                         ↓
                       Rescan
```

### 5.2 Hard rules

- Event queue is bounded.
- Overflow never triggers unbounded memory growth.
- Rescan is bounded to affected roots/subtrees.
- Reparse points are not followed unless explicitly approved by a future ADR.
- Events are hints; filesystem re-stat is authoritative.
- Index generation advances only after successful commit.
- Existing committed index remains searchable during maintenance.

### 5.3 Health model

Required observable fields:

```text
health
generation
indexed_entries
pending_events
dirty_roots
watcher_count
last_success
last_failure
recovery_count
```

Health diagnostics must not change execution behavior.

# 6. P2.4-C — Plugin Control Plane 2.0

## Objective

Separate plugin installation identity, trust, capability decisions, lifecycle state and runtime state.

### 6.1 State layers

```text
Plugin Identity
      +
Installation Revision
      +
Trust State
      +
Capability Decision
      +
Lifecycle State
      +
Runtime State
```

Runtime State is ephemeral. Registry state is persistent.

### 6.2 Trust states

Minimum:

```text
Unknown
Known
Trusted
Disabled
Quarantined
```

These are not mutually exclusive implementation flags; the canonical state model must define legal combinations.

### 6.3 Capability decisions

```text
unset
allow
deny
```

Manifest requests are data. `unset` must fail closed for protected capabilities.

### 6.4 Quarantine

Protocol-level failures may trigger quarantine. Business errors must not be conflated with protocol failures.

Quarantine:

- is persistent
- blocks discovery and execution
- preserves failure history
- can only be cleared by an explicit recovery/update/administrative operation defined by contract

### 6.5 Recovery

Preferred recovery order:

```text
validate current DB
  ↓
restore last known-good backup
  ↓
quarantine corrupt artifact
  ↓
rebuild
```

Security-sensitive decisions must not silently reset to permissive defaults when a valid backup exists.

# 7. P2.4-D — Plugin SDK / CLI

## Objective

Make plugin development independent from host internals.

### CLI

```text
launcher-plugin init
launcher-plugin validate
launcher-plugin build
launcher-plugin package
launcher-plugin install
launcher-plugin uninstall
launcher-plugin run
launcher-plugin inspect
```

### SDK boundary

Plugin code may depend on:

- Rust `launcher-plugin-api`
- Python public SDK

Plugin code may not depend on:

- `launcher-plugin-host`
- `launcher-core`
- `launcher-action`
- internal runtime types

### Package

Package must contain:

```text
manifest
runtime metadata
entrypoint
optional assets
contract version
```

Package validation must be deterministic and fail closed.

# 8. P2.4-E — Plugin Development Diagnostics

Required capabilities:

- development mode
- request/response logging
- query_id correlation
- runtime_id correlation
- protocol_session_id correlation
- elapsed time
- frame size
- result count
- timeout/crash/malformed/flood classification
- diagnostic snapshot
- replayable test input

Diagnostics never grant capability and never bypass ActionResolver.

---

# 9. P2.4-F — Release Closure

P2.4 is complete only when:

- all task gates pass
- no frozen contract is silently changed
- documentation uses the same release baseline
- release gate is reproducible
- all deferred items are documented
- all benchmark-impact claims are measured or explicitly justified

## 10. ADR requirements

ADR required before changing:

- Plugin Contract version
- Command/Action contract
- Catalog identity semantics
- Index generation semantics
- Process boundaries
- Runtime dispatch
- Persistent DB schema semantics
- Capability semantics
- Package format
