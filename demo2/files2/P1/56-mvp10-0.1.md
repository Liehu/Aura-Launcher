> **让这些能力从“一次性执行”升级为“持续运行、状态编排和多步自主操作”。**

我建议把 P1 固定为下面五阶段：

# P1-A — Runtime Persistence Foundation

## 1. 目标

把 P0-A 的：

```text id="runtime-model"
ephemeral process
    ↓
spawn
    ↓
call
    ↓
shutdown
```

扩展为：

```text id="persistent-runtime"
runtime instance
    ↓
Ready
    ↓
multiple executions
    ↓
Idle
    ↓
shutdown
```

但：

> **Persistent Runtime 不是 Persistent Authorization。**

必须继续保持：

```text id="authority-separation"
Runtime state
    ≠
Capability
    ≠
Confirmation
    ≠
ResolvedAction
    ≠
Workflow approval
```

---

# 2. 核心架构

```text id="p1a-architecture"
                    Effect Executor
                          │
                 ┌────────┴────────┐
                 ▼                 ▼
            PluginBroker       McpExecutor
                 │                 │
                 └────────┬────────┘
                          ▼
                  ProcessSupervisor
                          │
                   RuntimeManager
                          │
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
         r-001          r-002          r-003
        Plugin A        MCP GitHub     MCP Calc
```

新的：

```text id="runtime-manager"
RuntimeManager
```

负责：

```text
runtime lifecycle
runtime lookup
persistent/ephemeral policy
idle cleanup
restart
```

而：

```text id="launcher-runtime"
ProcessSupervisor
```

仍然只负责：

```text process mechanics
```

---

# 3. Runtime 层次必须分清

建议形成三层：

```text id="runtime-layers"
RuntimeManager
    │
    ├── RuntimePolicy
    │
    ▼
ProcessSupervisor
    │
    ▼
ProcessSession
```

职责：

### RuntimeManager

```text
“应该保留哪个 runtime？”
```

### ProcessSupervisor

```text
“怎么启动/停止/回收 process？”
```

### ProcessSession

```text
“这个 process 当前怎么读写？”
```

不要让 `ProcessSession` 决定 persistent policy。

---

# 4. Runtime Mode

```rust id="runtime-mode"
enum RuntimeMode {
    Ephemeral,
    Persistent,
}
```

不要扩展：

```text
Warm
Hot
Daemon
Background
Pinned
```

这些以后再考虑。

当前只需要：

```text
Ephemeral
Persistent
```

---

# 5. Persistent Runtime Identity

继续：

```text id="runtime-id"
RuntimeId = r-N
```

一个 persistent runtime：

```text id="persistent-instance"
r-17
```

可以执行：

```text
e-100
e-101
e-102
```

而：

```text id="exec-id"
ExecutionId
```

仍然：

```text
one attempt = one ID
```

绝不能：

```text id="bad-reuse"
runtime_id == execution_id
```

---

# 6. Runtime Key

RuntimeManager 不应仅：

```text id="bad-key"
provider_id
```

作为 key。

建议：

```rust id="runtime-key"
struct RuntimeKey {
    namespace: RuntimeNamespace,
    server_or_plugin_id: String,
    profile: Option<String>,
}
```

例如：

```text id="runtime-key-examples"
plugin / calculator
mcp / github / 2026-07-28
mcp / calc / 2026-07-28
```

目的：

> 同一逻辑 capability 可以有稳定 runtime owner，但不同 profile/instance 不会意外复用。

---

# 7. Persistent Runtime 不等于 MCP Session

这是 P1-A 最重要的概念之一。

```text id="runtime-vs-session"
Process Runtime
    = OS process lifetime

MCP Session
    = protocol semantics
```

未来可能：

```text id="mcp-future"
persistent process
+
stateless MCP protocol
```

也可能：

```text id="mcp-legacy"
persistent process
+
legacy MCP session
```

所以 RuntimeManager **不能**把：

```text process alive
```

解释成：

```text protocol session alive
```

这条必须写进 architecture invariant。

---

# 8. Plugin 也统一

Plugin：

```text id="plugin-persistent"
PluginBroker
    ↓
RuntimeManager
    ↓
Persistent runtime
```

MCP：

```text id="mcp-persistent"
McpExecutor
    ↓
RuntimeManager
    ↓
Persistent runtime
```

但：

```text id="protocol-separation"
Plugin protocol
MCP protocol
```

完全独立。

---

# 9. Idle Timeout

Persistent runtime 必须有：

```rust id="idle-policy"
struct RuntimePolicy {
    idle_timeout: Option<Duration>,
}
```

例如：

```text
persistent
idle 30min
→ shutdown
```

但注意：

```text id="runtime-idle"
idle runtime
```

不能影响：

```text workflow run
agent run
pending action
confirmation
```

也就是说：

```text id="no-shutdown-active"
active execution
    ↓
runtime cannot be reclaimed
```

---

# 10. Runtime Keepalive

不要添加：

```text id="bad-keepalive"
ping forever
```

P1-A 默认：

```text id="keepalive"
no synthetic keepalive
```

除非协议层需要。

原因：

```text
keepalive
    ↓
CPU
network
process lifetime
```

全部与 Launcher “runtime-on-demand” 原则冲突。

---

# 11. Restart Policy

建议：

```rust id="restart"
enum RestartPolicy {
    Never,
    OnCrash,
    OnFailure,
}
```

但第一版只实现：

```text id="p1a-policy"
Never
OnCrash
```

`OnFailure` 不建议现在做，因为：

```text business failure
```

不等于：

```text runtime failure
```

否则：

```text tool returns isError=true
```

可能导致：

```text restart process
```

这是错误语义。

---

# 12. Crash Recovery

Persistent runtime：

```text id="crash-recovery"
Running
   ↓
Crashed
   ↓
cleanup
   ↓
RestartPolicy
   ↓
Starting
   ↓
Running
```

但：

```text id="no-replay"
crashed runtime
    ≠
automatic execution replay
```

例如：

```text id="execution-crash"
e-42
   ↓
process crashes
```

RuntimeManager 可以：

```text restart r-7
```

但不能自行：

```text retry e-42
```

Workflow 才决定 retry。

---

# 13. Execution Recovery Boundary

这是 Agent/Workflow 前必须冻结的：

```text id="recovery-boundary"
Runtime
    ↓
process recovered

Execution
    ↓
still failed/unknown
```

特别是：

```text id="at-least-once"
Timeout
Crash
Connection lost
```

都不能被 Runtime 自动认定：

```text “Effect definitely didn't happen”
```

否则会破坏之前的 at-least-once semantics。

建议：


```text id="mcp-exec-flow"

 ↓
RuntimeHandle
 ↓
```


# 17. Runtime Lifecycle

建议：

```text id="runtime-lifecycle"
Created
   ↓
Starting
   ↓
Ready
   ↓
Running
   ↓
Idle
   │
   ├── execution
   │      ↓
   │    Running
   │
   ├── idle timeout
   │      ↓
   │   Stopping
   │
   └── crash

        Crashed
          ↓
        Restart / Stopped
```

这与 P0 的：

```text id="p0-life"
Created
Starting
Running
Stopping
Stopped
```

是扩展关系，不是完全重做。

# 18. Concurrency

Persistent runtime 最容易出现的新问题：

```text id="concurrency-problem"
execution A
execution B
execution C
      ↓
same process
```

P1-A 必须明确：

> **默认一个 RuntimeHandle 同一时间只允许一个 protocol operation。**

因此：

```text id="serialized"
r-1
 ├── e-1
 ├── e-2
```

必须：

```text
e-1 complete
    ↓
e-2
```

而不是：

```text
e-1 ──────┐
e-2 ──────┼→ same stdin/stdout
```

否则 JSON-RPC correlation/failure isolation 会复杂很多。

并发 runtime：

```text id="parallel-runtimes"
r-1 → execution A
r-2 → execution B
```

可以。

---

# 19. Queue Policy

如果 runtime 正忙：

```text id="busy"
r-1 = Running
new execution
```

P1-A 第一版建议：

```text id="queue-policy"
reject busy
```

而不是：

```text
internal unbounded queue
```

原因是：

```text
unbounded queue
    ↓
memory DoS
```

如果未来 Workflow/Agent 确实需要排队，再引入明确：

```text bounded queue
```

---

# 20. Persistent Runtime Security

新增不变量：

### `INV-RUNTIME-001`

> Runtime persistence MUST NOT grant execution authority.

### `INV-RUNTIME-002`

> Runtime recovery MUST NOT replay an execution automatically.

### `INV-RUNTIME-003`

> A RuntimeId MUST NOT be used as an ExecutionId.

### `INV-RUNTIME-004`

> A persistent runtime MUST serialize protocol operations unless the protocol explicitly supports concurrency.

### `INV-RUNTIME-005`

> Runtime cleanup MUST terminate the complete process tree.

# 21. Runtime Resource Limits

Persistent runtime必须进一步限制：

```text id="limits"

max_runtime_idle
max_restart_count
restart_backoff
max_stderr
max_stdout
```

例如：

```text id="bouned-restart"
crash
 ↓
restart
 ↓
crash
 ↓
restart
 ↓
limit
 ↓
Stopped
```

不能：

```text id="restart-loop"
crash → restart → crash → restart → ∞
```

# 22. Exponential Backoff

建议：

```text id="backoff"
restart 1 → 100ms
restart 2 → 500ms
restart 3 → 2s
restart 4 → stop
```

具体数值以后通过配置确定。

核心不是数字，而是：

```text id="bounded"
restart attempts bounded
```

# 28. Memory Policy

这是你的 Launcher 特别重要的一项。

如果：

```text id="persistent"
5 MCP servers
+
5 plugins
```

全部驻留：

```text id="bad-memory"
idle memory
    ↑↑↑
```

那么 Persistent Runtime 就违背产品原则。

建议建立：

```text id="runtime-budget"
max_persistent_runtimes = configurable
```

以及：

```text
LRU-ish idle reclamation
```

但第一版不要做复杂 global LRU。

优先：

```text id="simple-budget"
explicit idle timeout
max persistent count
```

### 一个必须保持的顺序关系

```text id="p1-order"
Runtime Persistence
        ↓
Workflow State
        ↓
Agent State
```

不要反过来。

因为 Agent 最终一定需要：

```text AgentRun
AgentStep
Observation
Proposal
Execution
Retry
Replan
```

如果底层 runtime/session 的生命周期还没稳定，Agent 很容易把：

```text runtime state
workflow state
agent state
execution state
```

全部揉到一起。

**P1 当前正式进入 P1-A。完成 P1-A 后再进入 Persistent MCP / Plugin，而不是提前做 Agent。**
