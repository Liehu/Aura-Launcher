
# Effect 抽象现在也应该正式“脱离 enum 思维”

你增加的 INV-051 很关键。

当前：

```text id="6k6e1k"
Effect::PluginInvoked
```

应该理解为：

> **Execution Domain / Routing Classification**

而不是：

> Plugin Action 的业务类型。

长期模型：

```rust
struct Effect {
    effect_type: EffectType,
    input: Value,
    target: EffectTarget,
    context: ExecutionContext,
}
```

其中：

```text
effect_type = "plugin.com.example.calc.echo"
```

而不是：

```rust
enum Effect {
    PluginCalculatorEcho,
    PluginPdfCompress,
    PluginOcr,
}
```

这样未来新增插件能力不会触碰 Core 的业务枚举，也不会导致：

```text
新增插件能力
    ↓
修改 launcher-domain
    ↓
修改 ActionResolver
    ↓
修改 ActionEngine
    ↓
重新发布 Host
```

而是：

```text
新增插件 Effect
    ↓
Manifest + Plugin
```

Host 只需要理解通用的执行协议。

# execution_id 的分层也已经正确

现在建议把整个生命周期理解成：

```text id="2f4j4q"
WorkflowRun
   │
   ├── step-1
   │     └── execution-101
   │
   ├── step-2
   │     └── execution-102
   │
   └── step-3
         └── execution-103
```

协议层：

```text
execution_id = e-101
```

只表达：

> 一次最终 Effect execution attempt。

而不是 Workflow identity，也不是 Action identity。

这会让未来失败重试时尤其干净：

```text id="o8kz4n"
step-2
 ├─ execution-102 → timeout
 └─ execution-103 → retry success
```

而不需要篡改原来的 `execution_id` 语义。

# Context generation 的三层边界也建议保持原样

现在已经明确：

```text id="ip9k6v"
① Generation Check
        ↓
② Preconditions
        ↓
③ Actual Effect
```

三个阶段的责任不同：

### Generation Check

检查：

> 我是不是还在之前看到的那个 Context？

### Preconditions

检查：

> 当前真实世界是否仍满足执行要求？

例如：

```text
file exists
window exists
target writable
plugin alive
```

### Effect

最后才真正：

```text
write
move
execute
paste
plugin action
```

因此：

```text
generation == current
```

不能被错误解释为：

```text
“执行一定安全/一定成功”
```

这一点对以后 Workflow 和 AI 尤其重要。

# INV-049 / INV-050 是 Workflow 阶段非常好的“反提前实现”护栏

目前只记录：

```text id="8t6jnn"
INV-049
Workflow persists Action references/proposals,
not ResolvedAction.

INV-050
ActionInvocation must be re-resolved before execution.
```

这是正确的。

因为现在如果提前实现 Workflow，很容易产生：

```text
Workflow
   ↓
ResolvedAction
   ↓
保存
```

然后隔一段时间：

```text
执行旧 ResolvedAction
```

这样会绕开你刚刚建立的：

```text
Context
Capability
Policy
Confirmation
```

重新解析。

你现在选择**只冻结约束、不提前实现**，比现在继续抽象 `WorkflowDefinition` 的具体结构更稳。

# 下一阶段的评审重点已经可以非常集中

MVP4.1 不需要重新讨论 Plugin。

它只需要回答五个问题：

```text id="oq6ecv"
1. WorkflowDefinition
   “我要编排什么？”

2. WorkflowRun
   “这一轮实际运行到哪里？”

3. ActionInvocation
   “某一个步骤到底要调用哪个 Action？”

4. Failure Policy
   “一个步骤失败以后怎么办？”

5. Re-resolution
   “为什么这个步骤执行前仍然有效？”
```

其中我认为 **Failure Policy** 会是 MVP4.1 最容易低估的部分。

至少需要在设计阶段区分：

```text
Continue
Stop
Retry
Skip
Abort
```

以及：

```text
EffectFailed
Timeout
CapabilityDenied
StaleContext
InvalidInput
PluginUnavailable
```

这些错误不能全部简单归类为 `failed = true`。

例如：

```text
CapabilityDenied
→ 通常 Stop

StaleContext
→ 可能 Re-resolve

Plugin Timeout
→ 可能 Retry

Business Error
→ 视 Workflow policy 决定

Protocol Violation
→ 通常 Stop
```

但**这些现在先不要实现**，留给 MVP4.1 设计评审即可。
