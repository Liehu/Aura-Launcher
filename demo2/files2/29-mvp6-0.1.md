下面这份可以直接作为 **Review 25 — Launcher UX Architecture Review** 的评审稿。它以目前已经冻结的 Command / Action / Context / Workflow / AI 语义为约束，不重新打开 Core 架构。

# Review 25 — Launcher UX Architecture Review

**Scope**

```text
Search
  → Context
  → Command
  → Action
  → Confirmation
  → Workflow
  → AI Proposal
  → Runtime Status / Error
```

**Status:** Proposed
**Goal:** Freeze launcher UI information architecture and interaction semantics before further UI implementation.

---

# 1. Review Objective

本次不是视觉设计评审，而是：

> **确定已经冻结的 Core 生命周期如何映射为稳定、可理解、可操作的 Launcher UX。**

UI 必须继续遵守：

```text
UI ≠ ActionResolver
UI ≠ Capability Authority
UI ≠ Effect Executor
UI ≠ Workflow Engine
UI ≠ AI Planner
```

UI 的职责只有：

```text
Present
Select
Invoke
Confirm
Observe
Navigate
```

所有业务语义继续来自 Core。

---

# 2. Global UX Model

Launcher UI 的完整用户模型：

```text
                  ┌─────────────┐
                  │   Hotkey    │
                  └──────┬──────┘
                         ↓
                 ┌─────────────┐
                 │ Search Input│
                 └──────┬──────┘
                         ↓
                 ┌─────────────┐
                 │ Result List │
                 └──────┬──────┘
                         ↓
                  Selected Command
                         │
              ┌──────────┼──────────┐
              ↓          ↓          ↓
           Context     Action     Shortcut
              │          │          │
              └──────────┼──────────┘
                         ↓
                  Action Execution
                         │
              ┌──────────┼──────────┐
              ↓          ↓          ↓
          Confirmation  Success    Failure
              │                     │
              ↓                     ↓
            Execute             Status/Error
                         │
                         ▼
                    Workflow
                         │
                 ┌───────┴────────┐
                 ↓                ↓
             Running            Paused
                 │                │
                 └───────┬────────┘
                         ↓
                     Result

AI Proposal enters the same Action path,
never a parallel execution path.
```

---

# 3. Primary UX Principle

Launcher 的核心界面不是“应用主页”，而是：

> **一个围绕当前 Context 进行 Command Discovery 和 Action Execution 的瞬时工作空间。**

因此默认 UX 应保持：

```text
Open
  ↓
Search / discover
  ↓
Select
  ↓
Execute
  ↓
Close
```

而不是：

```text
Open
  ↓
Navigate multiple pages
  ↓
Configure
  ↓
Confirm
  ↓
Execute
```

复杂状态只在确有必要时占用 UI。

---

# 4. Search

## 4.1 Search Box

搜索框是 Launcher 的视觉和交互锚点。

建议始终明确三个状态：

```text
Normal
Searching
No Results
```

但不要把：

```text
Searching
```

做成大型 loading screen。

Launcher 应保持：

```text
Input
↓
partial results
↓
updated results
```

而不是：

```text
Input
↓
Loading...
↓
Results
```

---

## 4.2 Search Results

Result Row 至少包含：

```text
Icon
Title
Secondary description
Provider/source hint
Optional shortcut
```

但不要直接向用户暴露：

```text
provider_id
command_id
action_id
capability
context_generation
```

这些属于内部 identity。

UI 保存：

```text
selected_command_id
```

而不是：

```text
selected_index
```

继续遵守 INV-035。

---

# 5. Context

Context 不应成为一个持续占屏的“Context 面板”。

默认情况下：

```text
Context = invisible input
```

只有当 Context 对用户理解当前结果有价值时，才提供轻量提示。

例如：

```text
📁 Documents
```

或者：

```text
Explorer · Documents
```

而不是显示完整内部：

```text
ContextSnapshot {
    hwnd...
    generation...
}
```

---

# 6. Context Change

当 Context 变化：

```text
Context generation N
       ↓
Context generation N+1
```

UI 不应该自行重新计算 Action。

应由 Core：

```text
ContextChanged
   ↓
re-resolve
   ↓
new ActionPresentation
```

UI 只更新：

```text
presentation
```

---

# 7. Command

Command 是用户真正选择的“能力入口”。

Result selection：

```text
One selected Command
```

Action Panel：

```text
Actions belonging to selected Command
```

UI 不应该把所有 Action 平铺到主 Result List。

默认层级：

```text
Result
  └── Actions
```

这样保持 Launcher 的认知层级：

> **先决定做什么，再决定怎么做。**

---

# 8. Action

Action Panel 保持 MVP3.1 已冻结的原则：

```text
Command
  ↓
ActionPanel
  ↓
ActionPresentation[]
```

UI 只知道：

```text
id
title
enabled
reason
shortcut
```

不解释：

```text
ActionKind
requires
capability
Effect
```

---

# 9. Primary Action

主操作继续由：

```text
first Ready action
```

决定。

UI 展示：

```text
Action title       Enter
```

但不自己推导：

```text
first action = primary
```

应该消费 Core 已解析的 presentation / primary identity。

---

# 10. Action Shortcut

Shortcut UX：

```text
Ctrl+Shift+C
```

直接显示在 Action Row。

快捷键的用户认知：

> “这个动作可以直接调用。”

而不是：

> “这个快捷键绑定了某个 OS API。”

执行仍然：

```text
shortcut
 → selected command
 → action_id
 → execute_action_by_id()
```

---

# 11. Confirmation

Confirmation 不应设计成新的页面。

建议采用 Launcher 内的 transient state：

```text
Normal Action UI
      ↓
Confirm Pending
```

例如：

```text
Delete 3 files?

[Enter] Confirm
[Esc] Cancel
```

状态栏/ActionPanel 内即可完成。

---

# 12. Confirmation 的视觉层级

推荐：

```text
Action title
Description

⚠ Confirmation required

[Enter] Confirm
[Esc] Cancel
```

不需要：

```text
Modal Window
Second Window
Native MessageBox
```

除非某个 OS Effect 在未来明确要求系统级 confirmation。

Launcher 内部 confirmation 应保持同窗口架构。

---

# 13. Confirmation 的关键 UX 语义

第一次：

```text
Enter
```

不会执行 Effect。

而进入：

```text
ConfirmationRequired
```

第二次：

```text
Enter
```

才确认。

但：

```text
confirmed=true
```

不是持久状态。

对于 Workflow：

```text
ConfirmationRequired
   ↓
Paused
```

UI 必须明确表现：

```text
Waiting for your confirmation
```

而不是：

```text
Running...
```

---

# 14. Workflow UI

这是当前 UI 架构中新出现的主要区域。

v0.1 不需要“Workflow IDE”。

Workflow 运行时只需要：

```text
Run status
Current step
Progress
Pause / confirmation
Failure
Completion
```

---

# 15. Workflow Presentation

推荐最小模型：

```text
Organize Downloads

✓ Scan files
✓ Classify files
● Move files
○ Generate report

Running step 3 of 4
```

这里：

```text
✓ complete
● current
○ pending
⚠ failed
⏸ paused
```

属于纯 Presentation。

UI 不负责判断 Step 状态。

---

# 16. Workflow Failure

不要只显示：

```text
Workflow failed
```

应显示：

```text
Move files
⚠ Permission denied

[Enter] Details
[Esc] Close
```

如果 Policy 决定：

```text
Retry
```

则显示：

```text
Retrying...
Attempt 2 of 2
```

但 UI 不自己决定 Retry。

---

# 17. Workflow Failure Presentation

建议分三级：

### Level 1 — Inline

```text
⚠ Plugin unavailable
```

### Level 2 — Detail

```text
Step: Compress PDF
Reason: Plugin unavailable
Attempt: 1 / 2
```

### Level 3 — Diagnostic

只有用户明确请求时显示：

```text
Plugin: ...
Execution: e-103
Failure class: PluginUnavailable
```

内部 diagnostics 不应该污染默认 Launcher UI。

---

# 18. Runtime Status

推荐定义统一状态栏，而不是每个子系统自行显示状态。

可以有：

```text
● Ready
⌛ Running
⏸ Waiting
⚠ Failed
✓ Done
```

底层映射：

```text
Workflow
Plugin
AI
Search
```

都可以提供自己的状态，但 UI 应该有统一 presentation vocabulary。

---

# 19. Plugin Runtime Status

插件启动/执行不建议默认显示：

```text
Starting plugin...
PID...
RPC...
```

用户真正需要知道的是：

```text
Searching...
Running...
Unavailable
Failed
```

只有诊断 UI 才显示 Runtime 细节。

---

# 20. AI Proposal

AI 不应在 UI 上形成第二套“AI Action UI”。

推荐：

```text
You can:
  Copy this value
  Open terminal here
  ...
```

这些仍然是：

```text
Command / Action
```

而不是：

```text
AI Button
```

---

# 21. AI Proposal Presentation

如果明确需要区分来源，可以轻量标记：

```text
✨ Suggested
```

例如：

```text
✨ Copy result
   Ctrl+Shift+C
```

但是：

```text
AI suggested
```

只是来源提示，不意味着：

```text
AI-authorized
AI-trusted
AI-executable
```

最终还是正常 Action。

---

# 22. AI Confirmation

AI 建议危险 Action 时：

```text
AI Proposal
   ↓
Normal Action UI
   ↓
ConfirmationRequired
```

不应该：

```text
AI
 ↓
special AI confirmation
```

仍然只走既有 Confirmation lifecycle。

---

# 23. Search → AI

建议不要让默认搜索框变成：

```text
[Ask AI anything...]
```

而保持：

```text
Search / Command
```

AI 可以在无法直接匹配或用户明确进入 AI mode 时参与。

例如：

```text
Search:
compress these PDFs
```

AI：

```text
→ proposes Workflow / Actions
```

但输出仍然进入：

```text
ActionProposal
```

而非直接显示成“AI execution result”。

---

# 24. Action / Workflow / AI 的 UI 层级

最终建议：

```text
Launcher
│
├── Search
│
├── Results
│
├── ActionPanel
│
├── Confirmation
│
└── Workflow Runtime View
      │
      ├── Steps
      ├── Current status
      ├── Failure
      └── Confirmation
```

AI 没有独立一级导航。

---

# 25. Empty State

Empty search：

```text
No results
```

不应该马上：

```text
Ask AI?
```

可以提供弱提示：

```text
No results

Try another query
```

未来 AI activation 可作为 secondary affordance。

避免 AI 侵占 Launcher 的核心 Command Discovery 模型。

---

# 26. Keyboard Model

整体键盘状态：

```text
Main
 │
 ├─ ↑/↓ → result selection
 │
 ├─ Enter → primary action
 │
 ├─ Ctrl+↓ → ActionPanel
 │
 └─ Esc → close launcher
          │
          ▼
      ActionPanel
          │
          ├─ ↑/↓ → action selection
          ├─ Enter → execute
          └─ Esc → main
```

Workflow：

```text
Paused(ConfirmationRequired)
          │
          ├─ Enter → confirm / resume
          └─ Esc → keep paused / close UI
```

重要：

> Esc 关闭 UI 不等于取消已提交 Effect。

---

# 27. Mouse Model

Mouse 可以支持：

```text
Click result
Click action
Click confirmation
```

但不能让 mouse path 形成另一套业务执行路径。

所有入口：

```text
Keyboard
Mouse
Shortcut
Future Voice
AI
MCP
```

最终都必须指向同一个 stable ID execution path。

---

# 28. Loading / Progress

Launcher 不应使用全屏 blocking spinner。

推荐：

```text
Query
  ↓
incremental result update
```

Workflow：

```text
Running
Step 2 / 5
```

Plugin：

```text
Running...
```

这样符合 Launcher 的低延迟定位。

---

# 29. Error UX

错误不是一个统一“红色错误页面”。

按严重程度分层：

```text
Recoverable
  ↓
inline status

Actionable
  ↓
actionable message

Workflow failure
  ↓
step-level error

Runtime failure
  ↓
diagnostic details

Fatal launcher failure
  ↓
system-level recovery
```

---

# 30. Context-aware Error

如果：

```text
StaleContext
```

默认不要显示：

```text
Error: stale context
```

而应该：

```text
Action updated
```

或者静默 refresh。

只有最终无法执行时才显示用户可理解的错误。

`FailureClass` 属于内部分类，不应直接暴露为默认用户文案。

---

# 31. CapabilityDenied UX

推荐：

```text
Open Terminal Here
⚠ Requires shell.execute
```

与 MVP3.1 保持一致。

但 UI 不能告诉用户：

```text
Grant permission
```

除非未来真正实现 Capability management UI。

目前：

```text
Denied
```

就是：

```text
Denied
```

不能形成不存在的设置入口。

---

# 32. PluginUnavailable UX

推荐：

```text
Compress PDF
⚠ Plugin unavailable
```

如果后台正在 bounded retry：

```text
Retrying plugin...
```

Retry 次数是 Runtime 状态，不由 UI 控制。

---

# 33. Plugin Business Error UX

Plugin：

```text
ActionFailed
```

应该表现为业务错误：

```text
Compress PDF
⚠ Could not compress the selected file
```

而不是：

```text
Plugin crashed
```

除非实际 failure class 是：

```text
PluginCrashed / ProtocolViolation
```

UI 文案必须遵循 Failure Classifier 的最终结果。

---

# 34. AI Runtime Error

AI Planner 本身失败时，不要污染 Action failure semantics。

例如：

```text
AI unavailable
```

应该是：

```text
Producer unavailable
```

而不是：

```text
Action failed
```

因为：

```text
AI planning
```

发生在：

```text
ActionProposal
```

之前。

---

# 35. Workflow Runtime 与 Launcher Popup 的关系

不建议 Workflow 永远占据主 Launcher Popup。

默认：

```text
Start Workflow
 ↓
Launcher closes / minimizes
 ↓
Workflow runs in background
```

需要用户介入时：

```text
ConfirmationRequired
 ↓
Launcher reopens
```

或者恢复到相应 transient surface。

这样 Launcher 仍然是瞬时工具，而不是常驻 Workflow Dashboard。

---

# 36. Workflow History

v0.1 不需要完整历史中心。

但可以保留：

```text
Recent Workflows
```

作为未来功能。

当前只需要：

```text
Current Run
```

以及完成后的：

```text
✓ Completed
```

即可。

---

# 37. Persistence 对 UI 的影响

因为当前只冻结：

```text
WorkflowRun serializable
```

而没有冻结：

```text
resumable after crash
```

所以 UI 不应该设计：

```text
Restore interrupted workflow automatically
```

这种 UX 承诺。

否则 UI 会反过来迫使 Runtime 实现 crash recovery。

---

# 38. Recommended Main Layout

主 Launcher 建议继续保持非常简单：

```text
┌─────────────────────────────────────────────┐
│  🔎  Search...                              │
├─────────────────────────────────────────────┤
│  ◎ Application / Command              Enter │
│    description                              │
│                                             │
│  ◎ Application / Command                   │
│    description                              │
│                                             │
│  ◎ File / Recent                            │
│    path                                     │
├─────────────────────────────────────────────┤
│  Context: Documents              Ctrl+↓ Actions │
└─────────────────────────────────────────────┘
```

不建议现在加入：

```text
Sidebar
Dashboard
Permanent toolbar
Large status cards
AI chat panel
Workflow tree sidebar
```

这些都会削弱 Launcher 的瞬时属性。

---

# 39. Action Panel

沿用 MVP3.1：

```text
┌─────────────────────────────────────────────┐
│  Copy result                         Enter  │
│  Insert result                      Ctrl+I │
│  Paste at cursor                            │
│  Open history                               │
│                                             │
│  ⚠ Execute command   requires shell.execute│
└─────────────────────────────────────────────┘
```

其中：

```text
disabled
```

仍然可见但不可选。

---

# 40. Workflow Runtime Surface

当需要展示 Workflow：

```text
┌─────────────────────────────────────────────┐
│ Organize Downloads                          │
├─────────────────────────────────────────────┤
│                                             │
│ ✓ Scan files                                │
│ ✓ Classify files                            │
│ ● Move files                                │
│ ○ Generate report                           │
│                                             │
│ Running · 3 / 4                             │
└─────────────────────────────────────────────┘
```

确认：

```text
┌─────────────────────────────────────────────┐
│ Organize Downloads                          │
├─────────────────────────────────────────────┤
│ ⏸ Confirmation required                     │
│                                             │
│ Move 27 files?                              │
│                                             │
│ Enter  Confirm      Esc  Keep paused        │
└─────────────────────────────────────────────┘
```

# 41. State-to-UI Mapping

| Core State           | UI Presentation           |
| -------------------- | ------------------------- |
| Searching            | subtle progress           |
| No Results           | empty state               |
| Command Selected     | highlighted row           |
| Action Panel         | secondary surface         |
| Ready                | normal                    |
| Disabled             | dim + reason              |
| ConfirmationRequired | confirmation state        |
| Executing            | executing/progress        |
| Success              | close / success feedback  |
| StaleContext         | refresh/re-resolve        |
| CapabilityDenied     | actionable disabled/error |
| PluginUnavailable    | unavailable/retrying      |
| BusinessError        | user-readable failure     |
| ProtocolViolation    | runtime error             |
| Workflow Running     | step progress             |
| Workflow Paused      | paused + reason           |
| Workflow Failed      | step error                |
| Workflow Complete    | success                   |

---

# 42. Core-to-UI Boundary

推荐正式冻结：

```text
Core
   ↓
Presentation Model
   ↓
Slint
```

而不是：

```text
Core
   ↓
Slint directly
```

Presentation Model 应继续成为：

```text
CommandPresentation
ActionPresentation
WorkflowPresentation
RuntimeStatusPresentation
```

未来可以：

```text
ActionPresentation
WorkflowStepPresentation
ProposalPresentation
```

但都不暴露 Core internals。

---

# 43. Stable IDs

UI 对象引用全部使用：

```text
command_id
action_id
step_id
workflow_run_id
```

禁止：

```text
row_index
position
visible_index
text matching
```

例如：

```text
execute-action(
    command_id,
    action_id
)
```

以及：

```text
resume-workflow(
    workflow_run_id
)
```

---

# 44. Accessibility

因为 Launcher 是键盘第一的产品，Accessibility 不只是视觉问题。

至少保证：

```text
logical focus
selected state
disabled state
confirmation state
status state
```

可以由辅助技术理解。

不要只通过：

```text
opacity
color
```

表达状态。

---

# 45. Performance UX Constraints

UI 不应该为了丰富状态而增加常驻资源。

特别是：

```text
Search
ActionPanel
Workflow status
AI proposal
```

都应该复用当前窗口与现有组件。

禁止：

```text
第二窗口
embedded browser
per-plugin UI process
per-action popup process
```

MVP3.1 已经冻结了同窗口 ActionPanel，这一原则应继续延伸。

---

# 46. Visual Complexity Budget

建议设一个产品级约束：

> Launcher 默认视图中，同时出现的主信息层级不超过三个。

即：

```text
1. Search
2. Results
3. Context / Action affordance
```

Workflow / Confirmation 属于 transient mode，不与主 Result UI 永久叠加。

这有助于维持“Launcher”而不是“Dashboard”。

---

# 47. UI Mode Model

最终建议主 UI 只有：

```text
Main
Action
Confirmation
Workflow
```

而不是大量 modal：

```text
Main
Search
Context
Action
Shortcut
Confirmation
Plugin
AI
Workflow
Error
...
```

其中：

```text
AI
Plugin
Context
```

是内容来源/状态，而不是 UI mode。

---

# 48. AI 不应该拥有独立 UI Mode

这是未来最容易发生产品漂移的地方。

不建议：

```text
Ctrl+Space
 ↓
Launcher
 ↓
AI Chat Mode
```

至少 v0.x 不应该默认如此。

AI 应该首先表现为：

```text
Command / Action / Proposal
```

而不是 ChatGPT-like 面板。

只有未来确定自然语言任务需要连续多轮交互时，再考虑独立 AI Surface。

---

# 49. MCP 不需要独立 UI

MCP 是 Adapter：

```text
MCP
 ↓
ActionProposal
```

因此 UI：

```text
不需要 MCP tab
不需要 MCP panel
不需要 MCP runtime page
```

用户看到的仍然是普通 Command/Action。

---

# 50. Workflow 是否需要独立 UI？

需要，但只需要：

> **Runtime Surface**

而不是：

> **Workflow Builder**

MVP4.1：

```text
Workflow Runner UI ✅
Workflow Builder ❌
```

Workflow Definition 的编辑器应该属于明显更后的产品能力。

---

```text
                         Launcher
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
           Search         Context       Runtime
              │             │             │
              ▼             │        ┌────┴────┐
           Results          │        ▼         ▼
              │             │     Workflow   Status
              ▼             │
          Command           │
              │             │
         ┌────┴────┐        │
         ▼         ▼        │
      Primary   ActionPanel │
                  │         │
                  ▼         │

```

# 54. Critical UX Invariants

建议新增 UI invariants：

```text
UI-INV-001
UI MUST select commands/actions using stable IDs.

UI-INV-002
UI MUST NOT resolve ActionDescriptor or capability semantics.

UI-INV-003
UI MUST NOT invoke Effect executors directly.

UI-INV-004
Confirmation UI MUST NOT persist authorization state.

UI-INV-005
Workflow UI MUST represent runtime state, not execute workflow logic.

UI-INV-006
AI proposals MUST render as normal Action-capable results.

UI-INV-007
MCP-originated capabilities MUST not require a separate UI execution path.

UI-INV-008
Context changes MUST be consumed through Core-provided Presentation updates.

UI-INV-009
Failure presentation MUST consume classified runtime state rather than infer failure class.

UI-INV-010
Closing the UI MUST NOT implicitly cancel an already submitted Effect.
```

```text

  ↓

  ↓

  ↓
Action
  ↓
Confirmation
  ↓
Workflow
  ↓
AI Proposal
  ↓

```

而且整个生命周期仍然只有一个执行方向：

```text
Producer
   ↓
Action / Proposal
   ↓
Resolver
   ↓
ActionEngine
   ↓
Effect
```

因此 UI 不应该再继续向 Core 增加特殊入口。
