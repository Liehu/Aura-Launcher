# Aura Launcher P2.6 开发设计规范

## Workflow 2.0

**状态：DRAFT v0.1**

**基线：P2.5 Search Intelligence 1.0**

**工作目录：**

```text
demo2/native-launcher/
```

---

# 1. P2.6 定位

P2.6 是：

> **Workflow 2.0：从“线性 Action 编排器”升级为“可验证 DAG + Durable Run + Human Approval + Visual Editor”的本地工作流引擎。**

P2.6 不负责 AI Agent。

最终架构：

```text
Trigger
   ↓
Workflow Definition
   ↓
Graph Validation
   ↓
Execution Planner
   ↓
Durable Workflow Run
   ↓
┌───────────────┐
│ DAG Scheduler │
└───────┬───────┘
        │
   ┌────┼──────────┐
   ↓    ↓          ↓
 Step  Step       Step
   │    │          │
   └────┼──────────┘
        ↓
 ActionResolver
        ↓
 launcher-action
        ↓
 Effect
```

Human Approval 和 Recovery 都位于 Workflow Runtime 层，而不是 Action Authority 层。

---

# 2. P2.6 核心目标

## 2.1 DAG

支持：

```text
A
├── B
└── C
    ↓
    D
```

即：

- 节点
- 边
- entry
- terminal
- branch
- join

---

# 3. 条件

支持 deterministic condition：

```text
if variable == true
if file_count > 10
if step.output.status == "ok"
```

Condition：

```text
DATA / CONTROL FLOW
```

不是：

```text
AUTHORITY
```

条件永远不能授权 Action。

---

# 4. Variables

Workflow 2.0 引入 Run-scoped variables：

```text
WorkflowRun.variables
```

变量来源：

- Step input
- Step output
- Trigger input
- Static workflow value

禁止：

- Action Engine 直接修改 workflow variables
- Provider 修改 global variables
- 插件进程直接访问 Run state

---

# 5. DAG Execution

必须支持：

```text
Sequential
Parallel
Branch
Join
```

## Parallel

例如：

```text
A
├── B
├── C
└── D
   ↓
   E
```

B/C/D 可以并发执行。

但：

> 并行执行不得让 Action Authority 出现多个旁路。

每个 Action invocation 仍然必须：

```text
Resolve
→ Validate
→ Execute
```

---

# 6. DAG Scheduler

Scheduler 负责：

```text
ready node detection
dependency tracking
parallel scheduling
join detection
failure propagation
cancellation
checkpoint
```

Scheduler 不负责：

```text
Action authorization
Plugin capability
Filesystem mutation
```

---

# 7. Workflow Definition

建议冻结：

```rust
pub struct WorkflowDefinition {
    pub id: WorkflowId,
    pub version: u64,
    pub name: String,
    pub entry_node: NodeId,
    pub nodes: Vec<WorkflowNode>,
    pub edges: Vec<WorkflowEdge>,
    pub variables: VariableSchema,
    pub failure_policy: WorkflowFailurePolicy,
}
```

---

# 8. Workflow Node

建议：

```rust
pub struct WorkflowNode {
    pub node_id: NodeId,
    pub action: WorkflowAction,
    pub input: Value,
    pub condition: Option<ConditionExpr>,
    pub retry_policy: RetryPolicy,
    pub approval_policy: Option<ApprovalPolicy>,
}
```

---

# 9. Workflow Edge

```rust
pub struct WorkflowEdge {
    pub from: NodeId,
    pub to: NodeId,
    pub condition: Option<ConditionExpr>,
}
```

要求：

- source 存在
- target 存在
- 不允许 dangling edge
- 无非法 cycle
- entry 唯一

---

# 10. DAG Validation

Workflow 保存/执行前必须：

```text
schema validation
→ identity validation
→ graph validation
→ expression validation
→ action reference validation
```

至少检查：

- duplicate NodeId
- missing NodeId
- dangling Edge
- multiple entry
- unreachable node
- cycle
- invalid join
- invalid condition
- invalid variable reference

---

# 11. Cycle Policy

P2.6 第一版：

> **DAG only，不允许 arbitrary loop。**

即：

```text
A → B → C
```

允许。

```text
A → B → C → A
```

拒绝。

未来 Workflow 2.1/3.x 再定义 loop/repeat contract。

这样可以显著降低 Durable Scheduler 的状态空间。

---

# 12. Action Model

当前 Workflow v0.1 的核心原则继续保留：

```text
Definition
≠
Run
≠
ResolvedAction
≠
Effect
```

Workflow Definition 保存：

```text
ActionReference
```

而不是：

```text
ResolvedAction
```

当前冻结契约已经明确：

- Definition 不保存 ResolvedAction
- Run 不保存 executable Effect
- 每次 execution 前重新 resolve
- Workflow 没有 Capability Authority。

P2.6 不得推翻这些规则。

---

# 13. Reference Resolution

仍然：

```text
Session Result
    ↓ miss
Fresh Provider Discovery
    ↓ miss
CommandNotFound
```

ReferenceResolver 与 ActionResolver 分离。

```text
ReferenceResolver
= 找到 Action

ActionResolver
= 当前是否允许执行
```

---

# 14. Execution Semantics

保持：

```text
at-least-once
```

不承诺 exactly-once。

Retry：

```text
same step
+
new execution_id
```

---

# 15. Durable Execution

P2.6 正式增加：

```text
WorkflowRun persistence
StepRun persistence
checkpoint
recovery
resume
```

目标：

> Core/Launcher 重启以后，Workflow Run 状态不会因为进程退出而整体丢失。

---

# 16. Durable State Machine

Run：

```text
Created
↓
Queued
↓
Running
├── Paused
├── Recovering
├── Cancelled
├── Failed
└── Succeeded
```

Step：

```text
Pending
↓
Ready
↓
Resolving
↓
Resolved
↓
WaitingApproval
↓
Executing
↓
Completed
```

失败路径：

```text
Failed
├── Retry
├── Skip
├── ReResolve
└── Stop
```

---

# 17. Checkpoint

Checkpoint 必须记录：

```text
workflow_run_id
definition_id
definition_version
node states
step attempts
variables
pending approvals
last execution_id
last committed transition
```

但：

> Checkpoint 不得保存可直接执行的 ResolvedAction。

---

# 18. Recovery

恢复流程：

```text
load persisted run
        ↓
validate definition/version
        ↓
restore graph state
        ↓
inspect last checkpoint
        ↓
classify incomplete node
        ↓
re-resolve
        ↓
continue
```

禁止：

```text
Executing
→ assume Effect never happened
→ blind retry
```

原因是原有 Workflow 契约明确规定：

```text
at-least-once
Timeout != Effect did not happen
```



因此 recovery 必须先根据 execution/checkpoint 状态裁决，而不是盲目重复。

---

# 19. Human Approval

P2.6 正式将：

```text
ConfirmationRequired
```

升级为通用：

```text
HumanApproval
```

支持：

- Approval
- Reject
- Cancel
- Expire

---

# 20. Approval Model

```rust
pub struct ApprovalRequest {
    pub approval_id: ApprovalId,
    pub workflow_run_id: WorkflowRunId,
    pub node_id: NodeId,
    pub reason: String,
    pub requested_at: u64,
    pub expires_at: Option<u64>,
}
```

Approval 是：

```text
external event
```

而不是：

```text
persisted authorization
```

不能持久化：

```text
confirmed = true
```

---

# 21. Approval Security

Resume 必须验证：

```text
workflow_run_id
approval_id
originating session
node_id
current generation
```

Approval 不得跨 Run 重放。

必须防：

```text
replay
duplicate approve
stale approval
wrong run
wrong node
```

---

# 22. Trigger Framework

P2.6 建立统一 Trigger Framework：

```text
Hotkey
Plugin
AI
Schedule
Manual
```

统一：

```rust
pub trait WorkflowTrigger {
    fn trigger(&self) -> Result<WorkflowRunRequest, TriggerError>;
}
```

Trigger 只创建：

```text
WorkflowRunRequest
```

不能直接执行 Action。

---

# 23. Queue

P2.6 增加 Durable Run Queue：

```text
Trigger
 ↓
Queue
 ↓
Scheduler
 ↓
Run
```

Queue 必须：

- bounded
- durable
- recoverable
- deduplicable

---

# 24. Concurrency

Workflow 层必须限制：

```text
max active runs
max nodes per run
max parallel nodes
max retry attempts
max queue depth
```

所有限制必须 configurable + bounded。

---

# 25. Visual Editor

P2.6 首次加入 Workflow Visual Editor。

目标：

```text
Canvas
 ├── Start
 ├── Action Node
 ├── Condition
 ├── Parallel Branch
 ├── Join
 ├── Approval
 └── End
```

Editor 的模型不是运行时模型本身。

架构：

```text
Visual Graph
 ↓
WorkflowDefinition
 ↓
Graph Validator
 ↓
Runtime
```

禁止：

```text
UI canvas
→ direct execute()
```

---

# 26. Visual Editor 功能

第一版：

- 创建 Node
- 删除 Node
- 移动 Node
- 创建 Edge
- 删除 Edge
- 配置 Action
- 配置 input
- 配置 condition
- 配置 retry
- 配置 approval
- 校验
- 保存
- Load
- Export
- Import

暂不需要：

- collaborative editing
- cloud
- multiplayer
- marketplace

---

# 27. Editor Undo/Redo

Editor state 必须具备：

```text
undo
redo
dirty state
save
discard
```

Undo/Redo 是 UI state，不应污染 Workflow Run state。

---

# 28. Versioning

Definition 版本与 Run 解耦：

```text
Definition v1
Run-001
```

即使随后：

```text
Definition v2
```

Run-001 仍然执行 v1。

禁止运行中的 Run 隐式切换到新 Definition。

---

# 29. Workflow Migration

P2.6 第一版：

> 不允许自动修改正在运行的旧 Definition。

允许：

```text
v1 → v2
```

作为显式新 Definition 创建。

后续专门定义 Workflow Migration Contract。
