这版 **MVP4.0 我认为已经把前面讨论的核心矛盾解决了**：`plugin.*` 可以开放扩展，而 Host 仍然保持唯一执行闸门。

更重要的是，你现在的设计已经具备进入 **MVP4.1 Workflow** 的基础。不过在继续扩展之前，我建议把几个边界正式钉死。

## 1. 当前 MVP4.0 的架构已经成立

现在实际形成的是：

```text
Plugin
  │
  │ ActionDescriptor
  ▼
resolve_descriptor_for(own_plugin)
  │
  │ ResolvedAction
  ▼
ActionEngine
  │
  │ validate / policy / context
  ▼
Effect::PluginInvoked
  │
  ▼
Core::execute_plugin_action()
  │
  ▼
PluginBroker
  │
  ▼
execute_action RPC
  │
  ▼
Plugin Process
```

其中：

```text
Plugin
```

拥有的是**业务能力**，

而：

```text
ActionResolver
ActionEngine
PluginBroker
```

分别拥有：

```text
是否允许
是否执行
怎么把 Effect 交给插件
```

这三个层次没有混在一起。

特别是你修掉的：

> 插件业务失败不能 kill 插件进程

这个非常重要。否则 Plugin RPC 会被错误地建模成：

```text
RPC error = plugin broken
```

而正确模型是：

```text
Plugin Process
   │
   ├── protocol failure → kill
   ├── timeout           → kill
   ├── malformed frame   → kill
   │
   └── business failure  → EffectFailed
                           process survives
```

这个边界应该继续保留到以后所有 Runtime。

---

# 2. 现在最值得确认的是：`Effect::PluginInvoked` 的抽象层级

这里是我唯一建议你在正式继续 MVP4.1 前再检查一次的地方。

如果现在是类似：

```rust
enum Effect {
    Copy(...),
    Paste(...),
    Open(...),
    Execute(...),
    PluginInvoked {
        plugin_id: String,
        action_id: String,
        input: Value,
    },
}
```

那么目前没问题。

但**不要继续沿着这个方向把所有插件 Effect 再塞进 enum**：

```rust
PluginPdfCompress
PluginPdfMerge
PluginOcr
PluginGitCommit
PluginTranslate
...
```

正确的长期形态应该逐渐变成：

```rust
Effect {
    effect_type: EffectType,
    input: Value,
    target: EffectTarget,
    context: ExecutionContext,
}
```

其中：

```text
system.*
plugin.*
```

是开放/半开放的 namespace。

而：

```text
PluginInvoked
```

可以继续作为当前 Rust 内部的一个**执行域/路由分类**，但不要让它成为插件业务能力的枚举。

换句话说：

```text
Effect
  └── domain = plugin
        ├── effect_type = plugin.com.example.foo.echo
        ├── effect_type = plugin.com.example.foo.compress
        └── effect_type = plugin.com.example.foo.translate
```

而不是：

```text
Effect
  ├── PluginEcho
  ├── PluginCompress
  └── PluginTranslate
```

这样才能真正兑现你现在 ADR-0014 中：

> `plugin.*` 成为扩展 Effect Domain。

---

# 3. `resolve_descriptor_for()` 的身份绑定设计是对的，但有一个细节值得永久写进测试

你现在采用：

```text
own
own.
```

匹配：

```text
plugin.<id>.*
```

这个比简单的：

```text
starts_with(plugin_id)
```

安全得多。

例如：

```text
own = com.example.calc
```

允许：

```text
com.example.calc.echo
```

以及：

```text
com.example.calc.v2.echo
```

但必须拒绝：

```text
com.example.calculator.echo
```

建议把这个边界直接做成一个纯函数，例如：

```text
owns_plugin_namespace(owner, target)
```

并加入：

```text
exact owner
owner + "."
same prefix without dot
short prefix
case variant
empty id
```

测试。

这属于安全边界，值得单独守住。

---

# 4. `plugin.invoke` 的设计也基本正确

你现在是：

```text
declared requires[]
        +
implicit plugin.invoke
        ↓
Resolver
```

这意味着：

```text
plugin.foo.bar
```

永远不能通过：

```json
{
  "requires": []
}
```

变成无权限 Action。

同时又没有把：

```text
plugin.foo.bar
```

本身变成 capability。

这是正确的二维分离：

```text
Effect Type
    =
“我要做什么”

Capability
    =
“我可以使用什么权限”
```

建议继续保持这个原则。

---

# 5. `execute_action` 的协议边界已经足够支持未来 Workflow

现在：

```json
{
  "execution_id": "e-12",
  "action_id": "echo",
  "input": {},
  "context_generation": 42
}
```

已经有三个非常重要的性质：

```text
execution_id
    → 执行实例身份

action_id
    → 插件内部 Action 身份

context_generation
    → 执行时的上下文版本
```

以后 Workflow 只需要在上层增加：

```text
workflow_run_id
step_id
```

而**不要污染 `execution_id` 的语义**。

最终可以是：

```text
workflow_run_id
       │
       ▼
    step_id
       │
       ▼
 execution_id
       │
       ▼
 Plugin / System Effect
```

这样日志和失败恢复都会比较清晰。

---

# 6. 这里建议给 `execution_id` 再增加一个生命周期语义

当前你定义了：

```text
e-<seq>
```

建议正式规定：

> `execution_id` 标识一次 Effect execution attempt，而不是一次用户 Action。

例如：

```text
一次用户按 Enter
    ↓
ActionExecution #1
    ↓
Effect #1
```

如果以后 Workflow 中：

```text
Action
  ↓
EffectPlan
  ├── Effect #1
  ├── Effect #2
  └── Effect #3
```

不要让三个 Effect 共用同一个 execution_id。

可以有：

```text
action_execution_id
effect_execution_id
```

或者更简单：

```text
execution_id = 一次最终 Effect execution
```

而由上层 `ActionInvocation` 保存自己的 ID。

现在不一定要实现，但要把语义写下来。

---

# 7. Context Generation 现在已经能支撑 Workflow，但不要把它变成“事务锁”

这一点很重要。

现在：

```text
context_generation
```

解决的是：

> **这个 Action 是否还是针对我看到的那个 Context？**

它不应该被扩展成：

> Context generation 相同，就保证所有外部世界状态仍然一致。

例如：

```text
generation = 42
```

并不意味着：

```text
文件一定存在
窗口一定还存在
网络一定在线
插件状态一定没变化
```

所以未来应该区分：

```text
Context validity
Execution preconditions
Effect failure
```

也就是：

```text
generation check
        ↓
precondition validation
        ↓
actual Effect
```

这样不会把 `ContextGeneration` 设计得过重。

---

# 8. MVP4.1 Workflow 最好不要立即引入新的 Effect 类型

你的 ADR-0014 已经写得很好：

> Workflow 仅编排 ActionInvocation 序列。

我建议严格贯彻。

不要：

```text
workflow.execute
workflow.loop
workflow.branch
workflow.parallel
```

全部做成 Effect。

Workflow 是：

```text
Orchestrator
```

不是：

```text
Effect Domain
```

# 9. Workflow 最核心的对象应该只有三个

我建议 MVP4.1 先控制在：

```text
WorkflowDefinition
WorkflowRun
ActionInvocation
```

例如：

```text
WorkflowDefinition
    │
    ▼
WorkflowRun
    │
    ├── ActionInvocation #1
    ├── ActionInvocation #2
    └── ActionInvocation #3
```

而：

```text
ActionInvocation
```

最终仍然：

```text
ActionResolver
    ↓
ResolvedAction
    ↓
ActionEngine
```

这样 Workflow 完全复用你现在的基础设施。

---

# 10. Workflow 最好不要保存 `ResolvedAction`

这是一个很容易踩的坑。

不要：

```text
Workflow
  ↓
保存 ResolvedAction
  ↓
过几秒再执行
```

因为：

```text
Context
Capabilities
Plugin availability
Confirmation policy
```

都可能变化。

应该保存：

```text
ActionReference / ActionProposal
```

然后执行时：

```text
ActionInvocation
      ↓
Resolve again
      ↓
ResolvedAction
      ↓
ActionEngine
```

这与你现在 MVP3.2 的 stale-context 思路完全一致。

---

# 11. AI 会因此变得非常简单

未来 AI 不需要特殊 Effect API。

它只产生：

```text
ActionProposal
```

例如：

```json
{
  "command_id": "calculator",
  "action_id": "echo",
  "input": {
    "text": "hello"
  }
}
```

然后：

```text
AI
 ↓
Proposal
 ↓
Resolver
 ↓
Context / Capability / Confirmation
 ↓
ActionEngine
```

因此 AI 不需要知道：

```text
PluginBroker
SendInput
Clipboard
Process
RPC
```

这正是现在架构最大的收益之一。

---

# 12. MCP 也会因此只是一个翻译层

MCP：

```text
Tool
```

翻译成：

```text
ActionProposal
```

即可。

例如：

```text
MCP Tool:
compress_pdf
```

转成：

```text
provider = mcp.xxx
command = pdf
action = compress
```

然后仍然：

```text
Resolver
   ↓
ActionEngine
```

MCP 本身没有执行权限。

# 14. 因此我建议 MVP4.1 不要先做“复杂 Workflow”

第一版应该只验证：

```text
ActionInvocation[]
```

例如：

```text
Step 1:
plugin.com.example.calculator.plus.echo

Step 2:
system.copy

Step 3:
plugin.com.example.calculator.plus.echo
```

要求：

```text
Step 1 → Resolver → Engine
Step 2 → Resolver → Engine
Step 3 → Resolver → Engine
```

而不是 Workflow 自己直接执行。

这样一旦 MVP4.1 CAT 能证明：

> **Workflow 只是 ActionInvocation 编排器**

整个后续 AI/MCP 路线就会非常稳。

# 15. 当前我建议新增一个非常关键的 invariant

你现在已经有：

```text
INV-044 ~ INV-048
```

下一阶段我会特别增加：

```text
INV-049

Workflow MUST persist Action references/proposals,
not trusted ResolvedAction or executable Effect objects.
```

以及：

```text
INV-050

Every Workflow ActionInvocation MUST be re-resolved
before execution against current capability/policy/context state.
```

这两条可以防止 Workflow 把 Resolver 绕掉。

## 最终判断

**MVP4.0 现在可以关账。**

而且这次比 MVP3.1 更重要：你实际上已经验证了前面那条核心架构假设：

```text
“统一 ActionEngine”
        ≠
“Host 必须知道所有插件能力”
```

真正统一的是：

```text
Identity
Authorization
Context
Confirmation
Execution lifecycle
Error semantics
```

真正开放的是：

```text
Effect Type
Plugin business semantics
Plugin implementation
```

这就是比较理想的插件运行时边界。

下一阶段 **MVP4.1 Workflow** 最值得冻结的不是 UI，而是 `WorkflowDefinition / WorkflowRun / ActionInvocation / failure policy / re-resolution` 五个对象和它们的状态机；只要这里设计正确，AI 和 MCP 基本都会变成上层适配问题，而不会再侵入 Core。
