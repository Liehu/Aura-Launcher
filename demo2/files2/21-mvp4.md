这一步的核心不是“把 `plugin.*` 做出来”，而是要防止系统在 MVP4 以后出现 **两套执行体系**：

```text
当前正确体系
Command
  ↓
ActionResolver
  ↓
ResolvedAction
  ↓
ActionEngine
  ↓
Effect
```

然后某一天插件、Workflow、AI、MCP 各自偷偷发展成：

```text
Plugin → 自己执行
Workflow → 自己执行
AI → 自己调用工具
MCP → 自己发 Effect
```

那样现在 MVP3.0~3.2 建立的边界基本会被重新架空。

我建议把后续架构冻结成一句总原则：

> **所有“想做什么”的参与者都是 Action Producer；所有“实际做什么”的行为都必须经过 ActionResolver 与 ActionEngine。**

---

# 1. 先把四类对象彻底分开

未来系统里其实存在四种完全不同的东西：

| 对象      | 本质               | 例子                         |
| ------- | ---------------- | -------------------------- |
| Context | 当前世界状态           | Explorer 当前目录、选中文件、前台窗口    |
| Command | 用户可发现的能力入口       | `calculator.copy`          |
| Action  | Command 的一个可执行变体 | `copy`, `history`, `paste` |
| Effect  | 最终副作用            | Clipboard、Shell、Plugin RPC |

而 Plugin / Workflow / AI / MCP 都不应该成为第五种“执行对象”。

它们只是**能力提供者 / Action Producer**。

---

# 2. Plugin-owned `plugin.*` 应该怎样接

现在 `plugin.*` 已经在契约里被定义，但 MVP3.x 明确不执行。

我建议 MVP4 不要直接让：

```text
plugin.foo.bar
```

进入 `ActionEngine` 后就“动态 RPC 一下”。

应该明确分成两层：

```text
Action Type
plugin.foo.bar
      ↓
ActionResolver
      ↓
ResolvedPluginAction
      ↓
ActionEngine
      ↓
PluginBroker
      ↓
Plugin Process
```

所以：

> `PluginBroker` 是一种 Effect Executor，而不是绕过 ActionEngine 的执行入口。

---

# 3. Plugin Action 的真正生命周期

推荐：

```text
Plugin manifest
      │
      ▼
Command / ActionDescriptor
      │
      ▼
Host assigns provider_id
      │
      ▼
ActionResolver
      │
      ├─ capability
      ├─ context
      ├─ confirmation
      ├─ action type
      └─ validity
      │
      ▼
ResolvedAction
      │
      ▼
ActionEngine
      │
      ▼
PluginEffect
      │
      ▼
PluginBroker
      │
      ▼
Plugin RPC
      │
      ▼
Plugin Process
```

这里有个非常重要的方向：

**插件不是“拥有 ActionEngine”。**

插件只拥有：

```text
plugin effect implementation
```

而：

```text
authorization
confirmation
context eligibility
execution identity
timeout
cancellation
audit
```

都由 Host 控制。

---

# 4. `plugin.*` 不应该允许插件自己决定 provider identity

这一点延续你现在的规则。

插件可以声明：

```json
{
  "type": "plugin.foo.export",
  "input": {
    "format": "pdf"
  }
}
```

但最终系统内部：

```text
provider_id = Host assigned
command_id  = provider_id + ":" + command.id
action_id   = declared action.id
```

AI、Workflow、MCP 甚至远程请求都不能说：

```text
provider_id = "trusted-system"
```

然后借此冒充另一个 Provider。

---

# 5. Plugin Action RPC 应该与 Query RPC 分离

当前 Plugin Contract 主要是：

```text
initialize
query
shutdown
```

未来千万不要：

```text
query
↓
顺便执行 action
```

建议新增独立 RPC：

```text
initialize
query
execute_action
shutdown
```

并且拥有不同的 ID：

```text
query_id
execution_id
```

例如：

```json
{
  "jsonrpc": "2.0",
  "id": 17,
  "method": "execute_action",
  "params": {
    "execution_id": "e-0042",
    "action_id": "export",
    "input": {
      "format": "pdf"
    },
    "context": {
      "generation": 19
    }
  }
}
```

这里 `execution_id` 与 `query_id` 必须完全分离。

否则以后：

```text
用户重新搜索
→ query-42
→ query-43
```

和：

```text
正在执行
→ execution-7
```

互相污染，会很快变成状态管理灾难。

---

# 6. Plugin RPC 的输入应该是什么

这里我反而建议**不要直接把整个 `ContextSnapshot` 原样交给 Plugin**。

更合理：

```text
ResolvedPluginAction
        │
        ├── action input
        ├── permitted context fields
        ├── context generation
        └── execution metadata
```

Plugin 得到的是：

```text
ExecutionContext
```

而不是 Host 内部的：

```text
ContextSnapshot
```

因为 ContextSnapshot 是 Core domain model，未来很可能继续变化。

例如：

```json
{
  "context": {
    "generation": 19,
    "location": {
      "path": "C:\\Users\\A\\Documents"
    }
  }
}
```

而不是直接暴露：

```rust
ContextSnapshot {
    foreground_hwnd,
    shell_window,
    selection,
    ...
}
```

---

# 7. Context 的正确位置

未来应该形成：

```text
                Context
                   │
         ┌─────────┼─────────┐
         ↓         ↓         ↓
      Search    Resolver   Workflow
                   │
                   ↓
              Action
                   │
                   ↓
              ActionEngine
```

而不是：

```text
ActionPanel → Context
Plugin      → Context
AI          → Context
MCP         → Context
```

即：

> **Context 是 Core 的共享输入，不应该成为各层自己监听、自己解释的状态。**

---

# 8. Context Generation 还需要升级

你现在 MVP3.2 已经有：

```text
context_gen
results_gen
```

这一设计很有价值。

进入 Workflow / AI / MCP 后，我建议把它发展成：

```text
ContextSnapshot {
    generation
    timestamp
    source
    ...
}
```

然后每一个可执行计划都绑定：

```text
context_generation
```

例如 AI 给出：

```text
Open Terminal Here
```

实际上系统内部应该是：

```text
Plan
 └─ ActionRef
      ├─ command_id
      ├─ action_id
      └─ context_generation = 21
```

执行的时候：

```text
current_generation == 21
```

才允许继续。

否则：

```text
STALE_CONTEXT
```

要求重新解析。

---

# 9. 这会直接解决 AI 的一个大坑

假设：

```text
20:01:01
AI:
“我帮你打开当前项目目录的终端”

20:01:03
用户切换到另一个 Explorer

20:01:04
AI 之前生成的计划执行
```

如果 AI 可以直接调用：

```text
shell.execute
```

就会对错误目录执行。

而正确链路应该是：

```text
AI
 ↓
Action Proposal
 ↓
ActionResolver
 ↓
Context generation check
 ↓
Confirmation policy
 ↓
ActionEngine
 ↓
Effect
```

所以 **AI 不应该拥有 Effect 权限**。

AI 只拥有：

```text
Plan / Propose Action
```

这个能力。

---

# 10. Workflow 应该怎么接

Workflow 很容易变成系统里的“超级执行器”。

建议从第一天就禁止：

```text
Workflow
 ├─ shell.execute()
 ├─ clipboard.write()
 ├─ plugin.call()
 └─ http.request()
```

而是：

```text
Workflow
   ↓
Action Plan
   ↓
ActionResolver
   ↓
ResolvedAction[]
   ↓
ActionEngine
   ↓
Effects
```

例如：

```text
Workflow: “整理下载目录”

Step 1
  find files

Step 2
  CommandRef: classify-file

Step 3
  CommandRef: move-file

Step 4
  CommandRef: archive-file
```

Workflow 本身不执行 `move-file`。

它只是产生：

```text
ActionInvocation
```

然后交给 ActionEngine。

---

# 11. Workflow 应该成为“计划执行器”，而不是 Effect 执行器

我建议建立三个对象：

```text
WorkflowDefinition
WorkflowRun
ActionInvocation
```

结构：

```text
WorkflowDefinition
       │
       ▼
    WorkflowRun
       │
       ├── ActionInvocation
       ├── ActionInvocation
       └── ActionInvocation
                 │
                 ▼
            ActionEngine
```

这样：

```text
Workflow
AI
MCP
```

其实可以共享同一个：

```text
ActionInvocation
```

---

# 12. AI 应该更像 Planner

未来 AI 层我建议严格分成：

```text
AI Planner
      ↓
Action Proposal
      ↓
Policy / Resolver
      ↓
ActionEngine
```

例如 AI 输出：

```json
{
  "intent": "open_project_terminal",
  "candidate_actions": [
    {
      "command_id": "terminal",
      "action_id": "open_here"
    }
  ]
}
```

而不是：

```json
{
  "tool": "shell.execute",
  "command": "cmd.exe /k cd ..."
}
```

后者等于 AI 自带 Effect 系统。

---

# 13. MCP 应该也只是 Adapter

MCP 最容易破坏当前架构。

因为典型 MCP 模型是：

```text
Model
  ↓
Tool
  ↓
Tool Execution
```

但你的架构应该把它翻译成：

```text
MCP Server
   ↓
MCP Adapter
   ↓
Command / Action Proposal
   ↓
ActionResolver
   ↓
ActionEngine
```

也就是说：

> MCP Tool 不应该成为 Launcher 的第二个 Effect API。

---

# 14. 最终应该形成一个统一的 Producer → Resolver → Engine

我建议把 MVP4+ 的总架构定成：

```text
                  ┌──────────────┐
                  │ Native UI    │
                  └──────┬───────┘
                         │
                  ┌──────▼───────┐
                  │ Plugin Query │
                  └──────┬───────┘
                         │
                  ┌──────▼───────┐
                  │ Workflow     │
                  └──────┬───────┘
                         │
                  ┌──────▼───────┐
                  │ AI Planner    │
                  └──────┬───────┘
                         │
                  ┌──────▼───────┐
                  │ MCP Adapter   │
                  └──────┬───────┘
                         │
                         ▼
                Command / Action Proposal
                         │
                         ▼
                ┌─────────────────┐
                │ ActionResolver  │
                │                 │
                │ identity        │
                │ capability      │
                │ context         │
                │ confirmation    │
                │ applicability   │
                └────────┬────────┘
                         │
                         ▼
                  ResolvedAction
                         │
                         ▼
                ┌─────────────────┐
                │  ActionEngine   │
                └────────┬────────┘
                         │
             ┌───────────┼───────────┐
             ↓           ↓           ↓
        SystemEffect PluginEffect WorkflowEffect
             │           │
             │           ▼
             │       PluginBroker
             │           │
             ▼           ▼
           OS APIs    Plugin Process
```

这里最关键的是：

**下面只有一个 Effect 出口。**

---

# 15. Workflow Effect 甚至可以不作为新的 Effect Domain

我倾向于不增加：

```text
workflow.*
```

这样的 Effect Type。

Workflow 本身只是**编排多个 Action**。

例如：

```text
Workflow
  ↓
ActionInvocation #1
  ↓
ActionEngine
  ↓
ActionInvocation #2
  ↓
ActionEngine
```

这样可以避免：

```text
system.*
plugin.*
workflow.*
ai.*
mcp.*
```

最后变成五种执行机制。

---

# 16. `plugin.*` 应该成为唯一真正新增的 Effect Domain

未来可以形成：

```text
system.*
    Host-owned

plugin.<id>.*
    Plugin-owned

workflow
    orchestration only

ai
    proposal only

mcp
    adapter / proposal only
```

这非常干净。

---

# 17. Plugin Action 与 Capability 的关系

这里建议再进一步。

现在：

```text
requires[]
```

描述 Action 所需能力。

未来：

```text
plugin.foo.export
```

可能需要：

```text
plugin.invoke
store.read
filesystem.write
network.connect
```

但不能因为是 Plugin Action 就默认拥有：

```text
plugin.invoke = granted
```

正确流程：

```text
Action.requires
      ↓
Manifest.capabilities
      ↓
GrantedCapabilities
      ↓
ActionResolver
      ↓
Ready / Disabled
```

继续沿用你现在的能力模型。

---

# 18. Plugin Action 最好再有一个 Plugin Capability

我建议以后增加：

```text
plugin.invoke
```

作为 **Host → Plugin Effect** 的基础能力。

但不要直接用：

```text
plugin.<id>.*
```

作为 capability。

也就是说：

```text
Action:
plugin.foo.export

Capability:
plugin.invoke
```

然后 Host 再检查：

```text
action provider == target plugin
```

避免插件获得：

```text
plugin.bar.*
```

这类跨插件调用能力。

进一步可以演化成：

```text
plugin.invoke.self
plugin.invoke.other
```

但 MVP4 不需要这么复杂。

---

# 19. Confirmation 与 Plugin Action 会天然结合

例如：

```text
plugin.foo.delete
```

Resolver：

```text
requires = ["plugin.invoke"]
confirmation = "confirm"
```

变成：

```text
Ready + ConfirmationRequired
```

UI：

```text
Delete archive?

[Enter] Confirm
[Esc] Cancel
```

然后：

```text
Confirm
 ↓
ActionEngine
 ↓
PluginBroker
 ↓
execute_action
```

所以 Confirmation 不需要特殊支持 Plugin。

这正是目前 MVP3.2 设计正确的地方。

---

# 20. Action 生命周期最终可以统一成这个状态机

```text
Declared
   │
   ▼
Resolved
   │
   ├───────────────► Hidden
   │
   ├───────────────► Disabled
   │
   ▼
Eligible
   │
   ├─ stale context ─────► Re-resolve
   │
   ├─ confirmation ──────► ConfirmPending
   │                           │
   │                           ▼
   │                        Confirmed
   │                           │
   └───────────────────────────┘
               │
               ▼
          Executing
               │
        ┌──────┼──────┐
        ▼      ▼      ▼
     Success Failed Timeout
```

Plugin 只是：

```text
Executing
   ↓
PluginBroker
```

AI / Workflow / MCP 不需要进入这个状态机。

---

# 21. AI / MCP 产生的 Action 应该叫 Proposal，而不是 ResolvedAction

这是我比较建议你冻结的命名边界：

```text
Command
ActionDescriptor
ActionProposal
ResolvedAction
ActionInvocation
Effect
```

语义分别是：

| 类型               | 谁产生             | 是否可信  |
| ---------------- | --------------- | ----- |
| ActionDescriptor | Provider/Plugin | 不可信   |
| ActionProposal   | AI/Workflow/MCP | 不可信   |
| ResolvedAction   | Core Resolver   | 可信    |
| ActionInvocation | Core            | 可信    |
| Effect           | ActionEngine    | 实际副作用 |

于是：

```text
AI → ActionProposal
Plugin → ActionDescriptor
Workflow → ActionProposal
MCP → ActionProposal
```

最终都：

```text
               ┌──────────────┐
               │   Resolver   │
               └──────┬───────┘
                      ▼
               ResolvedAction
                      │
                      ▼
                ActionEngine
```

这会非常稳定。

---

# 22. 一个非常重要的规则：Proposal 不能携带已授权状态

例如 AI 不允许说：

```json
{
  "action": "shell.execute",
  "authorized": true,
  "confirmed": true
}
```

Resolver 必须忽略这些字段。

同样 Workflow/MCP/Plugin 都不能说：

```text
requires = []
```

就代表“不需要权限”。

权限必须由：

```text
Manifest
Policy
GrantedCapabilities
```

决定。

# 23. 关于 AI 的“工具调用”问题

以后 AI 很可能需要：

```text
搜索文件
查询当前 Context
执行某个 Plugin Command
```

这里建议区分：

### Read-only Tools

例如：

```text
context.read
search.query
plugin.query
```

可以进入：

```text
AI Tool Gateway
```

但仍然受 Host policy 管控。

### Mutating Tools

例如：

```text
system.execute
plugin.foo.delete
system.paste
```

必须转换：

```text
ToolCall
   ↓
ActionProposal
   ↓
ActionResolver
   ↓
Confirmation
   ↓
ActionEngine
```

这样 AI 不存在所谓：

```text
“tool execution bypass”
```

# 24. MCP 的最终位置

因此建议未来把 MCP 明确定位为：

```text
MCP Adapter
```

而不是：

```text
MCP Runtime
```

Adapter 负责：

```text
MCP Tool
   ↓
Launcher Command / Action
```

以及：

```text
Launcher Command / Action
   ↓
MCP exposed capability
```

如果以后要让 Launcher 作为 MCP Server，对外暴露能力，也应该暴露：

```text
Command / Action
```

而不是暴露：

```text
ActionEngine::execute(...)
```

# 25. 这样可以自然形成“双向 MCP”

未来甚至可以：

```text
外部 MCP
   ↓
MCP Adapter
   ↓
Action Proposal
   ↓
Resolver
   ↓
ActionEngine
```

同时：

```text
Launcher
   ↓
Command/Action Registry
   ↓
MCP Server Adapter
   ↓
External AI Agent
```

两边仍然不会破坏 Core。


# 27. 我建议现在新增的核心 ADR

在 MVP4 开工前，最好冻结一个比 ADR-0013 更上层的：

## ADR-0014 — Unified Action Execution Architecture

核心原则建议直接写成：

> **All externally produced commands, action descriptors, action proposals, workflow steps, AI tool calls, and MCP tool calls MUST pass through Core Action Resolution before execution. ActionEngine is the sole mutation/effect execution gateway.**

再加六个 invariants：

```text
INV-046
Plugin-owned Actions MUST execute through ActionEngine.

INV-047
PluginBroker MUST NOT be an independent Effect execution gateway.

INV-048
Workflow MUST orchestrate ActionInvocations, not execute Effects directly.

INV-049
AI/MCP MUST produce proposals or adapters, never bypass ActionResolver.

INV-050
Context-bound ActionInvocations MUST carry a context generation/version.

INV-051
Externally supplied authorization/confirmation state MUST NOT be trusted.
```

# 28. 最终架构边界

如果把整个项目未来的核心思想压缩成一张图，我认为应该冻结成：

```text
                 ┌───────────────────────────────┐
                 │           Producers           │
                 │                               │
                 │ UI / Plugin / Workflow / AI  │
                 │ MCP / Hotkey / Shortcut      │
                 └──────────────┬────────────────┘
                                │
                  Command / Proposal / Descriptor
                                │
                                ▼
                    ┌────────────────────┐
                    │  ActionResolver    │
                    │                    │
                    │ identity           │
                    │ capability         │
                    │ context            │
                    │ confirmation       │
                    │ policy             │
                    │ applicability      │
                    └──────────┬─────────┘
                               │
                         ResolvedAction
                               │
                               ▼
                    ┌────────────────────┐
                    │    ActionEngine    │
                    │                    │
                    │ validation         │
                    │ execution          │
                    │ result             │
                    └──────────┬─────────┘
                               │
               ┌───────────────┼────────────────┐
               ▼               ▼                ▼
         System Effects   PluginBroker      Future Effects
               │               │
               ▼               ▼
             OS APIs        Plugin Process
```

**Context 则横切 Resolver，而不是横切所有执行者：**

```text
Context
   │
   ├── Search
   ├── Resolver
   ├── Workflow
   └── AI Planner
```

但真正执行时，还是必须回到：

```text
Context-aware ResolvedAction
              ↓
         ActionEngine
```

---

## 我认为这套边界最值得冻结的一句话

> **Producer 可以提出“做什么”，Resolver 决定“现在是否允许做”，ActionEngine 决定“如何产生 Effect”；任何上层系统都不得绕过后两者。**

这样设计后，`plugin.*`、Workflow、AI、MCP 并不是四套能力，而只是四种不同的 **Action Producer / Adapter**。这会使你现在 MVP3.0~3.2 的工作真正成为整个系统后续扩展的“骨架”，而不是一个只对 Native UI 有效的局部设计。

下一步最适合直接进入 **ADR-0014 + MVP4.0 Plugin-owned Action RPC v0.1** 的冻结，重点把 `execute_action` RPC、`PluginBroker`、`PluginEffect`、execution_id、timeout/crash、context envelope、capability/confirmation 和插件端 SDK API 一次定义完整。
