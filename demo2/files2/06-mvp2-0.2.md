看这版 **MVP2 的 benchmark 设计**，我认为已经比上一版成熟很多了。现在已经从“测几个数字”进入了“建立性能工程体系”的阶段。

而且从你给出的数据口径看，我会把评价分成两部分：

> **测试设计：已经基本合格，可以作为 v0.2 的正式性能规范。**
> **指标定义：还有几个关键地方需要修正，否则后面 Agent 很容易把不同含义的内存/延迟数字混在一起。**

下面我按“必须改 / 建议改 / 可以以后再做”来评。

# 2. 但有一个必须立即修正的指标定义

你写：

> Commit = `Process.PagedMemorySize64`

这个定义不准确。

`PagedMemorySize64` 表示的是**进程分页内存大小**，不能直接等同于 Windows 的 Process Commit。

所以文档这里建议改掉：

```text
Commit
```

不要再写：

```text
Process.PagedMemorySize64
```

否则以后你在性能报告里可能出现：

```text
Private Bytes
Commit
Paged Memory
```

三个名称看起来不同，实际上底层又不完全对应，Agent 也很容易误用。

我建议 MVP2 直接采用：

```text
Private Bytes    ← 主预算指标
Working Set      ← 用户看到的即时 RAM 参考
Commit Size      ← 单独定义采集方式
Peak Private     ← 峰值
```

如果暂时不想引入 ETW/Performance Counter，可以干脆：

> **v0.2 暂时取消 Commit 作为正式 benchmark 指标。**

宁可少一个，也不要定义错。

# 3. 还有一个非常重要的问题：`Hotkey → Popup` 和 `Warm start popup` 实际上现在混了两个概念

你定义：

```text
Hotkey → Popup
RegisterHotKey event → ui.show() return
```

同时：

```text
Warm start popup
Ctrl+Space → first pixel
```

这两个绝对不能共用同一个 benchmark 名字。

因为：

### A. Application latency

```text
hotkey event
    ↓
ui.show()
```

测的是：

> **应用内部响应速度**

### B. User perceived latency

```text
physical key press
    ↓
Windows hotkey dispatch
    ↓
event loop
    ↓
UI state update
    ↓
render
    ↓
first visible frame
```

测的是：

> **用户真正感知到的响应速度**

两者差异可能非常大。

建议直接拆：

```text
T1: Hotkey Dispatch → Show Request
T2: Show Request → First Frame
T3: Physical Hotkey → First Frame
```

最终：

```text
User Visible Latency
= T1 + T2 + OS scheduling overhead
```

这样以后优化才知道到底慢在哪里。

# 4. `ui.show() 返回` 不能作为最终 UX 指标

这是目前 benchmark 里我最想改的一点。

你现在：

```text
Hotkey
    ↓
ui.show()
    ↓
return
```

只能证明：

> show 调用返回得很快。

不能证明：

> 用户已经看到 Launcher。

因为 UI framework 中：

```text
show()
```

可能只是：

```text
enqueue state change
```

真正绘制发生在：

```text
event loop
render
present
```

所以最终应该有：

```text
First Frame / Present
```

这个指标。

# 5. 不要把“P99 不做门禁”固定死

你的理由是合理的：

> 100 samples 时 P99 本身抖动比较大。

但我建议稍微修改规范。

目前：

```text
P50/P95 → gate
P99 → observation
```

可以保留。

但是再增加：

```text
Max
```

作为辅助指标。

例如：

```text
P50    0.4 ms
P95    1.2 ms
P99    2.1 ms
MAX   18.3 ms
```

这样你就能发现：

> “平均性能非常漂亮，但偶尔会卡一下。”

对于 Launcher：

**tail latency 比平均 latency 更重要。**

尤其：

```text
Hotkey
Search
Plugin
```

用户对偶发 100ms/200ms 卡顿非常敏感。

# 8. 你的 soak 规则建议升级成“趋势检测”

现在：

> 前后差 ≤ 基线 +20%

这对于最初版本够用，但其实有一个问题：

```text
start = 12 MB
end = 14 MB
```

可以通过。

但中间如果：

```text
12
30
80
120
300
14
```

也可以通过。

而实际上可能存在非常严重的瞬时峰值。

所以 soak 应该记录：

```text
initial
min
median
p95
peak
final
slope
```

特别是：

```text
memory slope
```

例如：

```text
Memory = 12.6 + 0.002MB × operation
```

这个趋势就值得警惕。

# 9. `Plugin Host Private = 0` 的定义稍微调整

你写：

> 空闲期必须为 0，即无插件常驻。

这个作为：

```text
"Plugin Host Process Count = 0"
```

更准确。

因为：

```text
process doesn't exist
```

和：

```text
process exists but reports 0 MB
```

不是一回事。

建议 benchmark 输出：

```text
plugin_process_count = 0
plugin_host_private_bytes = 0
```

甚至：

```text
plugin_process_peak_count
plugin_spawn_count
plugin_kill_count
orphan_process_count
```

这样很漂亮。

特别是以后做 Python/Node：

```text
plugin.exe
python.exe
node.exe
```

时可以验证：

> 插件退出以后是不是整个 process tree 都干净了。

# 12. 最重要的一条：把 benchmark 从“性能测试”升级成“性能契约”

你现在：

```text

```

已经有很好的基础。

下一步我建议 baseline 不只存数字，而是：

```json
{
  "version": 1,
  "environment": {
    "os": "...",
    "cpu": "...",
    "ram": "...",
    "build": "release",
    "commit": "..."
  },

    "files": 210000,

    "idle_private_bytes": 13212000
```

```text

+
硬件
+

数据规模
```

否则 baseline 会慢慢失去意义。

# 13. 对 Agentic Coding，再补一个非常重要的规则

你现在的 Agent Completion 已经要求：

```text
Summary
Changed files
Tests run
Benchmark / memory impact
Architecture impact
Known risks
```



我建议进一步要求：

```text
Performance Impact
```

每次 Agent 修改代码都明确写：

```text
Performance Impact:
  Memory: unchanged
  Startup: unchanged
  Search: -2.3%
  IPC: +0.1ms

Benchmark:
  before: ...
  after: ...
  delta: ...
```

对于没有 benchmark 的任务：

```text
Performance Impact: N/A
Reason: no performance-sensitive path touched
```

这会极大提升长期 Agentic Coding 的可控性。
