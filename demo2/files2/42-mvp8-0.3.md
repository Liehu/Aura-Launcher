# MVP4.3 Phase 8 — Workflow Integration

Phase 8 建议正式定义为：

> **让 MCP Tool 成为普通 `WorkflowAction::Reference` 的一种可解析目标，完整复用现有 ReferenceResolver → ActionResolver → ActionEngine → EffectExecutorRegistry 链路。**

本阶段不新增 MCP 专属 Workflow API，不修改 Workflow 生命周期语义。

---

## 1. Phase 8 架构目标

最终链路必须是：

```text
WorkflowDefinition
      │
      ▼
WorkflowRun
      │
      ▼
WorkflowStep
      │
      ▼
WorkflowAction::Reference
      │
      ▼
ReferenceResolver
      │
      ├── current popup results
      │
      └── fresh provider discovery("")
              │
              ▼
        mcp:calc / evaluate / invoke
              │
              ▼
        ActionResolver
              │
              ▼
        ResolvedAction
              │
              ▼
        ActionEngine
              │
              ▼
 Effect("plugin.mcp.invoke")
              │
              ▼
       ExecutorRegistry
              │
              ▼
         McpExecutor
              │
              ▼
         MCP Server
```

最重要的是：

```text
WorkflowRunner
    X → McpProvider
    X → McpExecutor
    X → MCP transport
```

Workflow 只知道：

```text
ActionReference
```

---

# 2. 不新增任何 MCP Workflow 类型

不要出现：

```rust
WorkflowAction::Mcp(...)
WorkflowStep::Mcp(...)
McpWorkflowStep
McpToolReference
```

继续使用已有：

```rust
WorkflowAction::Reference(ActionReference)
```

例如：

```rust
ActionReference {
    provider_id: "mcp:calc",
    command_id: "evaluate",
    action_id: "invoke",
}
```

这样 MCP 与：

```text
apps.*
plugin.*
system.*
mcp.*
```

在 Workflow 看来完全是同一种 Action Reference。

---

# 3. ReferenceResolver 不需要 MCP 特判

这点应作为 Phase 8 的核心 Gate。

现有逻辑：

```text
ReferenceResolver
    │
    ├── Current Popup Session Results
    │
    └── Fresh Provider Query("")
```

继续保持。

例如：

```text
Workflow Reference:

provider_id = mcp:calc
command_id  = evaluate
action_id   = invoke
```

Resolver：

```text
Current Popup Results
        │
        └── found → use current route

        │ not found
        ▼

Fresh Provider Query("")
        │
        ▼
McpProvider
        │
        ▼
Catalog
        │
        ▼
exact identity match
```

然后再交给 `ActionResolver`。

**不要写：**

```rust
if reference.provider_id.starts_with("mcp:") {
    ...
}
```

这会让 Workflow 开始理解具体 Provider 类型。

---

# 4. Phase 8 正式解决 DISCOVERY-TODO-001

此前：

```text
Workflow
  ↓
ReferenceResolver
  ↓
Provider.search("")
```

插件侧曾经是 TODO。

MCP Phase 4 已经实现：

```text
McpProvider.search("")
```

因此 Phase 8 首先验证：

```text
Workflow Reference
    ↓
Fresh Provider Discovery
    ↓
MCP Tool
```

这意味着 `DISCOVERY-TODO-001` 的 MCP 部分从：

```text
MCP Provider supports empty query
```

提升为：

```text
MCP Provider
    +
ReferenceResolver
    +
Workflow
```

形成真正可执行闭环。

---

# 5. Current Popup Result 优先级继续保持

例如用户当前搜索：

```text
evaluate
```

得到：

```text
mcp:calc / evaluate / invoke
```

随后触发 Workflow。

Resolver：

```text
Step Reference
    ↓
Current Popup Session
    ↓
Exact route match
```

成功后不应该再无条件重新 discover。

只有当前 Session 中找不到，才：

```text
Fresh Provider Query("")
```

这保持你之前冻结的 R1 语义：

```text
Current Popup Session Results
        ↓
Fresh Provider Query
        ↓
CommandNotFound
```

---

# 6. Fresh Discovery 的实现边界

`ReferenceResolver` 只需要调用既有 Provider 接口：

```rust
provider.search("", &context)
```

它不应该：

```text
调用 McpTransport
读取 MCP Catalog
调用 McpExecutor
解析 MCP Tool
```

所以：

```text
ReferenceResolver
      │
      ▼
Provider abstraction
      │
      ├── Built-in Provider
      ├── Plugin Provider
      └── McpProvider
```

这是 Phase 8 最重要的拓扑验证之一。

---

# 7. ActionResolver 仍然是最终 eligibility authority

Workflow resolve 到：

```text
mcp:calc / evaluate / invoke
```

以后必须：

```text
ActionDescriptor
      │
      ▼
ActionResolver
```

而不是：

```text
ReferenceResolver
      ↓
“找到了 MCP Tool”
      ↓
直接执行
```

因此：

```text
Discovery success
    ≠
Execution permission
```

例如：

```text
MCP Tool exists
mcp.invoke denied
```

结果：

```text
Reference resolution
    = found

Action resolution
    = Disabled / CapabilityDenied
```

最终 Workflow 根据既有 Failure Class 处理。

---

# 8. Workflow 不感知 `mcp.invoke`

Workflow 看到的只是：

```text
ActionResolution
```

因此：

```text
MCP Tool exists
but mcp.invoke denied
```

统一进入：

```text
CapabilityDenied
```

而不是：

```text
McpPermissionDenied
```

这样保持整个 Workflow failure matrix 不变：

| Error             | Workflow     |
| ----------------- | ------------ |
| CapabilityDenied  | Stop         |
| InvalidInput      | Stop / Skip  |
| StaleContext      | ReResolve    |
| Timeout           | Retry        |
| BusinessError     | Stop         |
| ProtocolViolation | Stop         |
| PluginUnavailable | Retry → Stop |
| CommandNotFound   | Stop         |

Phase 8 **不应该新增 `McpFailure` / `McpUnavailable` 之类的 Workflow error class**。

---

# 9. Context Generation

MCP Workflow 也必须继续使用：

```text
resolved_context_generation
```

流程：

```text
resolve
  ↓
generation = G1
  ↓
precondition
  ↓
execute
```

如果：

```text
context generation changed
```

则：

```text
StaleContext
    ↓
ReResolve
```

即使 MCP Tool 本身不使用 folder context，也不能建立另一套 MCP 特殊逻辑。

---

# 10. MCP Tool 的 context 需求

Phase 8 不建议给 MCP 自动添加：

```text
requires_context
```

默认：

```text
requires_context = none
```

未来某个 MCP Tool 如果需要 Launcher Context：

```text
folder
selection
location
```

这是 Action Descriptor / capability/context contract 的问题，而不是 Workflow-MCP integration 问题。

因此：

```text
MCP metadata
    X
    ↓
自动产生 requires_context
```

仍然禁止。

---

# 11. Workflow execution

成功 resolve 后：

```text
WorkflowRunner
    ↓
ActionInvocation
    ↓
ActionResolver
    ↓
ActionEngine.execute(...)
```

然后：

```text
ActionEngine
    ↓
Effect {
    effect_type: "plugin.mcp.invoke"
}
```

最后：

```text
ExecutorRegistry
    ↓
McpExecutor
```

Workflow 完全不知道后面发生的是 MCP。

---

# 12. `execution_id` 语义

Workflow：

```text
workflow_run_id
    ↓
step_id
    ↓
attempt
    ↓
execution_id
```

例如：

```text
workflow-run-17
    step=fetch
        attempt=1
            execution_id=e-42
```

MCP Executor 收到：

```text
e-42
```

仅用于 correlation。

如果超时：

```text
attempt=1
execution_id=e-42
```

retry：

```text
attempt=2
execution_id=e-43
```

严禁：

```text
retry same execution_id
```

这与现有 Workflow Contract 完全一致。

---

# 13. Timeout 语义尤其需要测试

MCP stdio timeout：

```text
tools/call
    ↓
timeout
```

转换：

```text
McpError::Timeout
    ↓
FailureClass::Timeout
```

Workflow：

```text
Timeout
    ↓
Retry policy
```

第二次执行：

```text
new Mcp process
new execution_id
new attempt
```

最终：

```text
at-least-once
```

不能错误地假设：

```text
timeout = remote definitely did not execute
```

---

# 14. MCP BusinessError

例如：

```text
Tool call
    ↓
MCP server
    ↓
isError=true
```

Phase 6 已定义：

```text
BusinessError
```

Phase 8 中直接进入：

```text
Workflow FailureAction
```

默认：

```text
Stop
```

如果以后：

```text
step.failure_policy = Retry
```

那么才 Retry。

Workflow 不需要知道：

```text
isError
```

它只知道：

```text
BusinessError
```

---

# 15. CommandNotFound

下面三种情况最终应该统一：

```text
MCP server 已删除
MCP tool 已删除
MCP tool 不再出现在 fresh catalog
```

Resolver：

```text
Fresh Provider Query("")
        ↓
no exact route
        ↓
CommandNotFound
```

Workflow：

```text
CommandNotFound
    ↓
Stop
```

不能继续：

```text
旧 ActionDescriptor
    ↓
直接执行
```

这正是 Reference 持久化而不是 ResolvedAction 持久化的价值。

---

# 16. MCP Tool 被替换

这是一个非常值得新增的测试。

初始：

```text
mcp:calc / evaluate / invoke
```

Workflow 保存：

```text
Reference
```

之后 server：

```text
evaluate
    ↓
removed
```

然后新增：

```text
calculate
```

重新执行 Workflow：

```text
ReferenceResolver
    ↓
fresh catalog
    ↓
evaluate not found
    ↓
CommandNotFound
```

**不得模糊匹配 `calculate`。**

Reference identity 必须 exact：

```text
(provider_id, command_id, action_id)
```

# 17. MCP Tool Input 不应该在 Workflow Definition 中保存 metadata

Workflow：

```rust
WorkflowStep {
    action: Reference(...),
    input: json!(...)
}
```

仍然保持：

```text
WorkflowStep.input
    = authoritative runtime input
```

不要：

```text
WorkflowStep
    ├── action.input
    └── step.input
```

否则会重新引入之前 A1 发现的 double source 问题。

MCP 场景应该：

```text
WorkflowStep
    │
    ├── Reference
    │      provider
    │      command
    │      action
    │
    └── input
          server_id
          tool_name
          arguments
```

Resolver 得到：

```text
ActionDescriptor
```

然后：

```text
Step.input
```

覆盖/提供 execution input。

---

# 18. `server_id` 一致性

Phase 7 已经存在：

```text
provider_id = mcp:calc
input.server_id = calc
```

必须一致。

Workflow 不能构造：

```text
Reference:
    provider = mcp:calc

input:
    server_id = jira
```

最终：

```text
Effect validation
    ↓
reject
```

建议 Phase 8 再加一层测试：

```text
MCP-WF-006
```

确保 Workflow 永远不能利用 `Step.input` 做 cross-server confused deputy。

---

# 19. Confirmation

MCP Workflow 不需要新的确认状态。

如果 ActionResolver 返回：

```text
ConfirmationRequired
```

还是已有：

```text
WorkflowRun
    ↓
Paused(ConfirmationRequired)
```

之后：

```text
resume
   ↓
originating UI session
   ↓
re-resolve
   ↓
execute
```

尤其：

```text
confirmed=true
```

不持久化。

这条对 MCP 特别重要，因为某些 MCP Tool 可能是：

```text
create_issue
delete_file
send_message
deploy
```

但其风险判断仍由 Launcher 本地 policy 决定。

## Phase 8 的最终验收标准

最重要的不是“Workflow 能调用 MCP”。

而是下面这句话必须成立：

> **从 `WorkflowRunner` 的角度看，MCP 与 Plugin、Built-in、System Action 没有特殊执行路径；差异只存在于 Provider discovery 和最终 Effect Executor。**

达到这一点，MVP4.3 的核心架构就已经基本闭合。下一阶段 Phase 9 才需要处理 **AI Planner → MCP ActionProposal**，而那一阶段理论上应该比 Phase 8 更简单，因为 AI Planner 已经在 MVP4.2 中把 Proposal → Workflow 的通路建立好了。
