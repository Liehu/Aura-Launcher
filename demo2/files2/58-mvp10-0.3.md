# P1-C：Workflow v0.2 — Variables / Conditions / Branching

P1-C 正式进入实施定义。

本阶段的核心不是把 Workflow 做成“通用脚本语言”，而是在 **Workflow v0.1 的线性、step-scoped 执行模型**上，增加有限的数据流和控制流：

```text
v0.1
Workflow
  Step → Step → Step

v0.2
Workflow
  Variable
      ↓
  Condition
      ↓
  Branch
   ↙   ↘
 Step   Step
   \   /
    ↓
  Step
```

同时继续保持此前最重要的架构边界：

```text
Workflow
    只负责：
    数据编排 + 控制流 + 状态

ReferenceResolver
    负责：
    “这个逻辑引用现在解析成什么 Action”

ActionResolver
    负责：
    “这个 Action 当前是否允许执行”

ActionEngine
    负责：
    “真正产生 Effect”

RuntimeManager
    负责：
    “runtime 生命周期”
```

因此：

> **Workflow v0.2 增加控制能力，但不获得新的执行授权能力。**

---

# 1. P1-C 冻结目标

P1-C 只增加四件事情：

```text
1. Variables
2. Expression / Condition
3. Branching
4. Step Output → Variable
```

最终 Workflow 可以表达：

```text
读取输入
  ↓
执行 Action A
  ↓
保存输出
  ↓
判断 condition
  ├── true  → Action B
  └── false → Action C
  ↓
继续
```

但暂不提供：

```text
❌ loop
❌ while
❌ for-each
❌ recursion
❌ parallel
❌ subworkflow
❌ dynamic code
❌ arbitrary expression language
❌ user-defined functions
```

---

# 2. v0.1 → v0.2 原则

v0.1 已经冻结：

```text
WorkflowStep
    action
    input
    failure_policy
```

v0.2 不推翻它。

建议扩展成：

```rust
pub struct WorkflowStep {
    pub step_id: StepId,

    pub action: WorkflowAction,

    pub input: WorkflowInput,

    pub output: Option<WorkflowOutputBinding>,

    pub condition: Option<Condition>,

    pub on_success: StepTransition,

    pub on_failure: StepTransition,

    pub failure_policy: FailurePolicy,
}
```

但是这里要特别注意：

> **控制流不能直接绕过现有 failure semantics。**

`on_failure` 不是替代 `FailurePolicy`，而是在 failure 被分类后决定是否可以继续走某条显式路径。

---

# 3. Workflow v0.2 Object Model

建议冻结为：

```text
WorkflowDefinition
├── id
├── version
├── name
├── inputs
├── variables
├── steps
└── entry_step
```

运行态：

```text
WorkflowRun
├── workflow_run_id
├── definition_id
├── definition_version
├── status
├── current_step
├── variables
└── steps
```

其中：

```text
WorkflowDefinition
    = immutable plan

WorkflowRun
    = mutable execution state
```

---

# 4. Variable 模型

不要把变量设计成任意 JSON document + script。

建议 v0.2 保持一个严格的值域：

```rust
pub enum Value {
    Null,
    Bool(bool),
    Number(f64),
    String(String),
    Array(Vec<Value>),
    Object(BTreeMap<String, Value>),
}
```

但 **Workflow v0.2 的表达式只允许读取有限 Value 类型**。

推荐：

```text
Null
Bool
Number
String
Array
Object
```

暂不支持：

```text
Binary
DateTime
Regex object
Handle
Process
Action
Effect
Runtime
Capability
```

这些对象不能进入 Workflow variable。

---

# 5. Variable Namespace

必须避免变量覆盖系统身份字段。

建议变量分为：

```text
workflow.*
step.*
input.*
var.*
```

用户可定义变量统一位于：

```text
var.<name>
```

例如：

```text
var.file
var.result
var.exit_code
var.should_continue
```

而系统只读上下文：

```text
workflow.id
workflow.run_id
step.id
step.status
step.attempt
```

禁止用户写：

```text
workflow.run_id
step.status
step.execution_id
```

---

# 6. Execution Identity 绝不能成为普通 Variable

尤其禁止：

```text
var.execution_id
```

或者通过变量把它重新绑定为：

```text
input.execution_id
```

Workflow 可以**观察** execution metadata，但不能使用变量改变 execution identity。

因此：

```text
ExecutionId
    ↓
diagnostic/read-only metadata
```

而不是：

```text
Variable
    ↓
ExecutionId authority
```

这继承已有：

```text
INV-AUTH-005
```

---

# 7. Variable 生命周期

变量应该属于 `WorkflowRun`：

```text
WorkflowDefinition
    ↓
WorkflowRun
    ↓
variables
```

而不是全局存储。

生命周期：

```text
Run started
    ↓
initialize declared variables
    ↓
Step 1
    ↓
write output
    ↓
Step 2 reads
    ↓
Step 3 writes
```

Run 结束：

```text
Completed / Failed / Cancelled
    ↓
variables become historical run state
```

不自动传播到下一个 WorkflowRun。

---

# 8. Definition Variables 与 Runtime Variables

建议定义两个概念：

```text
VariableDeclaration
VariableState
```

例如：

```rust
pub struct VariableDeclaration {
    pub name: String,
    pub value_type: ValueType,
    pub default: Option<Value>,
    pub mutable: bool,
}
```

v0.2 可以只支持：

```text
mutable = true
```

但建议保留字段，为以后增加只读输入做准备。

更重要的是：

> **VariableDeclaration 是 schema，不是 runtime value。**

---

# 9. Workflow Inputs

v0.2 可以正式增加 Workflow 输入：

```rust
pub struct WorkflowInput {
    pub name: String,
    pub value_type: ValueType,
    pub required: bool,
    pub default: Option<Value>,
}
```

调用：

```text
Workflow
  inputs:
    source_dir: string
    compression_level: number
```

Run 创建：

```text
source_dir = "D:\\Downloads"
compression_level = 9
```

映射进入：

```text
input.source_dir
input.compression_level
```

---

# 10. Variable Resolution

统一变量读取：

```text
resolve(expression)
```

优先级建议固定：

```text
input.*
var.*
step.*
workflow.*
```

但不要允许同名 shadowing。

因此：

```text
var.x
input.x
```

是不同 namespace。

禁止：

```text
x
```

这种裸变量形式。

---

# 11. Expression 不做通用编程语言

这是 P1-C 最容易失控的地方。

不要引入：

```text
JavaScript
Lua
Rhai
CEL full runtime
Python
embedded scripting
```

也不要让 AI 生成任意代码。

建议实现一个非常小的：

```text
WorkflowExpr v0.1
```

只支持：

```text
literal
variable reference
comparison
boolean operators
null check
string predicates
```

---

# 12. Expression Grammar

建议冻结成类似：

```text
expr
  := literal
   | reference
   | comparison
   | logical

comparison
  := expr == expr
   | expr != expr
   | expr < expr
   | expr <= expr
   | expr > expr
   | expr >= expr
   | expr contains expr
   | expr starts_with expr
   | expr ends_with expr
   | expr exists

logical
  := not expr
   | expr and expr
   | expr or expr
```

括号：

```text
(
    ...
)
```

允许。

---

# 13. Type Rules

必须显式类型检查。

例如：

```text
"10" == 10
```

不要自动转换成：

```text
true
```

应该：

```text
TypeMismatch
```

同样：

```text
"abc" > 10
```

应该拒绝。

这样可以避免 AI / 用户配置产生隐蔽行为。

---

# 14. Numeric Comparison

统一：

```text
Number
```

不支持：

```text
int
uint
float
decimal
```

多种 Workflow numeric runtime type。

但是 JSON 解析时：

```text
10
10.0
```

都映射到 Number。

---

# 15. Condition

建议：

```rust
pub struct Condition {
    pub expression: Expr,
    pub on_error: ConditionErrorPolicy,
}
```

`ConditionErrorPolicy` v0.2 只允许：

```rust
ConditionErrorPolicy::{
    FailWorkflow,
}
```

暂不允许：

```text
treat-as-false
treat-as-true
fallback
retry
```

原因很简单：

> Condition evaluation error 不应被悄悄吞掉。

---

# 16. Branching

最简单且最稳定的模型是：

```rust
pub enum StepTransition {
    Next,
    Goto(StepId),
    End,
}
```

例如：

```text
Step A
  condition
     true  → B
     false → C
```

可以表达成：

```rust
pub struct ConditionalTransition {
    pub condition: Condition,
    pub on_true: StepId,
    pub on_false: StepId,
}
```

但我更建议在 definition 层统一使用：

```rust
pub enum Transition {
    Next,
    Goto(StepId),
    End,
}
```

然后让 Step 的条件控制两个 transition。

---

# 17. 推荐 WorkflowStep 最终结构

P1-C 建议冻结：

```rust
pub struct WorkflowStep {
    pub step_id: StepId,

    pub condition: Option<Condition>,

    pub action: Option<WorkflowAction>,

    pub input: WorkflowInput,

    pub output: Option<WorkflowOutputBinding>,

    pub success: Transition,

    pub failure: Transition,

    pub failure_policy: FailurePolicy,
}
```

这里 `action: Option` 是故意的。

因为：

```text Step
 ├── Condition-only
 └── Action step
```

可以同时存在。

例如：

```text
check_should_compress
    condition only
        ↓
    compress
```

---

# 18. 更重要的限制：禁止隐式 Branch

不要出现：

```text
某个 Action 返回 false
→ Runner 自动选择 false branch
```

必须明确声明：

```text
Condition
    ↓
Transition
```

Action business result 只是：

```text
step output
```

如果要根据它判断：

```text
Action
 ↓
output.result
 ↓
next Condition
```

这样更清晰，也不会把每个 Action 都强行解释成控制流 primitive。

---

# 19. Output Binding

v0.1 没有正式输出变量。

P1-C 增加：

```rust
pub struct WorkflowOutputBinding {
    pub target: VariablePath,
    pub source: OutputPath,
}
```

例如：

```text
Action result
    ↓
var.compress_result
```

---

# 20. Action Output 模型

这里不要让 Workflow 直接理解 Effect。

推荐 ActionEngine 最终提供一个有限的 execution result：

```rust
pub struct ActionResult {
    pub status: ActionResultStatus,
    pub value: Option<Value>,
}
```

例如：

```text
status = Success
value = {
    "count": 12,
    "path": "..."
}
```

Workflow 只看到：

```text
StepResult.value
```

不看到：

```text
Effect
PluginBroker
McpExecutor
RuntimeId
ProcessSession
```

---

# 21. Output 绑定示例

```text
Action:
    calculate-size

Result:
{
    "bytes": 1024,
    "files": 8
}
```

绑定：

```text
var.total_bytes = output.bytes
var.file_count  = output.files
```

下一步：

```text
Condition:
var.total_bytes > 1000000
```

---

# 22. Output 不存在

例如：

```text
output.bytes
```

但 Action 没有：

```text
bytes
```

那么应该是：

```text
OutputPathNotFound
```

而不是：

```text
null
```

尤其不能：

```text
missing → null → comparison false
```

否则会制造大量隐蔽 branch bug。

---

# 23. Step Result 状态

建议 v0.2 扩展：

```rust
pub enum StepStatus {
    Pending,
    Running,
    Paused,
    Succeeded,
    Failed,
    Skipped,
}
```

新增：

```text
Skipped
```

用于条件不满足导致某些 branch path 不执行时。

---

# 24. Branch 与 Skip 的区别

例如：

```text
A
├── true  → B
└── false → C
```

不是：

```text
B skipped
C skipped
```

而是：

```text
B executed
C never selected
```

运行记录可以：

```text
B = Skipped
C = Succeeded
```

但需要明确原因：

```text
reason = BranchNotSelected
```

否则 UI 很难解释。

---

# 25. 推荐增加 SkipReason

```rust
pub enum SkipReason {
    BranchNotSelected,
    ConditionFalse,
    UpstreamFailure,
}
```

P1-C 实际只需要：

```text
BranchNotSelected
ConditionFalse
```

`UpstreamFailure` 可以为以后 failure graph 保留。

---

# 26. Workflow 控制流模型

建议最终限制为：

```text
Directed Graph
```

但不是 DAG 保证。

原因是：

```text
A → B
A → C
B → D
C → D
```

完全需要。

但是：

```text
A → B → A
```

会形成 loop。

因为本阶段明确：

> **不做 loops。**

所以 Definition Validator 必须检测：

```text
cycle
```

并拒绝。

---

# 27. 为什么不直接做 DAG

如果强制 DAG，理论上更简单。

但 Workflow 的终态实际上已经有：

```text
goto
branch
```

未来 Agent/Workflow v0.3 很可能需要循环。

所以当前更合理的是：

```text
Graph
+
Cycle Validator
```

而不是把 DAG 写进 domain contract。

---

# 28. Branch Validation

Workflow Definition 在加载/保存时必须静态验证：

```text
entry_step exists
every StepId unique
every Goto target exists
no cycles
all variable references syntactically valid
all output bindings reference possible output locations
```

然后才能进入 Runner。

---

# 29. 死节点检测

例如：

```text
A → B

C → End
```

但是 `C` 没有任何入口。

应该：

```text
UnreachableStep(C)
```

这是 DefinitionInvalid。

不要运行时才发现。

---

# 30. Termination

v0.2 每个合法 workflow 必须能够到达：

```text
End
```

因此做 CFG 分析：

```text
entry
 ↓
reachable graph
 ↓
all terminal paths → End
```

否则：

```text
A → B
B → B
```

已经被 cycle validator 捕获。

---

# 31. Failure Policy 与 Branch 的关系

保持已有语义：

```text
CapabilityDenied → Stop
InvalidInput → Stop / Skip
StaleContext → ReResolve
Timeout → Retry
BusinessError → Stop
ProtocolViolation → Stop
PluginUnavailable → Retry
CommandNotFound → Stop
ConfirmationRequired → Pause
```

P1-C 不允许把这些分类重新定义。

---

# 32. Failure Branch

可以允许：

```text
failure → ErrorHandler
```

但只能在 failure policy 最终允许 continuation 时使用。

例如：

```text
InvalidInput
    policy = Skip
    failure = Cleanup
```

而：

```text
CapabilityDenied
    policy = Stop
```

即便配置了：

```text
failure = Cleanup
```

也不能执行。

这非常重要：

> **Transition 不能覆盖 FailurePolicy。**

---

# 33. Failure Transition 优先级

冻结规则：

```text
Action execution
      ↓
Failure classification
      ↓
FailurePolicy
      ↓
if policy permits continuation
      ↓
Failure Transition
```

而不是：

```text
failure
 ↓
goto
 ↓
bypass policy
```

---

# 34. Confirmation + Branch

确认仍然属于 ActionEngine 生命周期。

例如：

```text
Step A
 ↓
Condition true
 ↓
Dangerous Action
 ↓
ConfirmationRequired
```

Workflow 必须：

```text
Paused
```

之后用户确认：

```text
Resume
 ↓
re-resolve
 ↓
execute
```

不能：

```text
var.confirmed = true
```

然后让 Workflow 自己绕过 Confirmation。

---

# 35. Context Generation

v0.1 已经有：

```text
resolved_context_generation
```

P1-C 不允许把它变成 Variable authority。

可以：

```text
step.context_generation
```

用于 diagnostic。

但是：

```text
var.context_generation = 17
```

不能强行让 Resolver 接受这个 generation。

Resolver 必须继续自行验证当前 context。

---

# 36. Reference Binding + Variables

这是 P1-C 另一个容易产生权限问题的位置。

例如：

```text
Reference:
mcp:calc / calculate

input:
{
    "expression": "${var.expression}"
}
```

这是允许的。

但：

```text
server_id = "${var.server_id}"
tool_name = "${var.tool_name}"
```

不建议允许。

原因是此前已经发现过：

> **Tool substitution vulnerability。**

因此 P1-C 必须延续：

```text
Identity fields
    server_id
    tool_name
    provider_id
    command_id
    action_id
```

必须由：

```text
WorkflowAction / ActionReference
```

静态绑定。

Variable 只能注入：

```text
ordinary action input
```

---

# 37. Identity Binding Invariant

新增：

```text
INV-WORKFLOW-IDENTITY-001

Workflow variables must never alter the canonical identity of
a referenced Action.

ProviderId / CommandId / ActionId and protocol identity fields
are definition-bound, not runtime-variable-bound.
```

这会延续之前的：

```text
generic identity_mismatch
```

防护。

---

# 38. Variable Injection 位置

推荐只允许：

```text
WorkflowStep.input
```

例如：

```json
{
  "path": "${var.source}",
  "level": "${var.level}"
}
```

而不允许：

```text
WorkflowAction.provider_id
WorkflowAction.command_id
WorkflowAction.action_id
WorkflowAction.action_type
```

---

# 39. Template Syntax

建议不要允许任意字符串脚本。

统一：

```text
${var.name}
${input.name}
${step.current.output.value}
```

对于整个字段：

```text
"${var.count}"
```

可以恢复原始 Number。

对于字符串拼接：

```text
"backup-${var.date}"
```

得到 String。

---

# 40. Template 类型规则

例如：

```text
path = "backup-${var.name}"
```

合法。

但是：

```text
retry_count = "3"
```

目标类型 Number 时：

```text
TypeMismatch
```

不要隐式 `parse number`。

如果需要：

```text
to_number()
```

属于未来 expression function，不放在 v0.2。

---

# 41. Condition 与 Template 必须分开

不要：

```text
condition = "${var.a > 3}"
```

而是：

```rust
Condition::Comparison(...)
```

即：

```text
Template
    → string/input construction

Expr
    → typed boolean evaluation
```

两个 parser 不混。

---

# 42. Workflow Run Persistence

P1-A 只完成 runtime persistence。

P1-C 开始需要：

```text
WorkflowRun
variables
current_step
step states
```

但是本阶段仍然不需要做：

```text
durable queue
crash-consistent checkpoint
machine restart resume
```

推荐先把状态模型建起来：

```text
in-memory first
```

持久化实现留给独立的 Workflow persistence phase。

这样可以防止：

```text
Workflow semantics
+
SQLite
+
recovery
```

三个问题一次混在一起。

---

# 43. Resume 语义

现有 v0.1 Confirmation Pause：

```text
Paused
```

P1-C 只扩展：

```text
Paused
    ↓
same WorkflowRun
    ↓
resume current step
```

但恢复时：

```text
current action
```

仍然必须：

```text
re-resolve
```

不能复用旧：

```text
ResolvedAction
```

---

# 44. WorkflowRunner 新职责

v0.2 Runner 扩展：

```text
WorkflowRunner
 ├── evaluate condition
 ├── resolve template
 ├── resolve reference
 ├── invoke ActionEngine
 ├── capture output
 ├── update variables
 ├── choose transition
 └── update run state
```

依然禁止：

```text
WorkflowRunner
 ├── Effect
 ├── McpExecutor
 ├── PluginBroker
 ├── Capability grant
 └── ActionResolver implementation
```

---

# 45. 推荐增加独立组件

不要把 expression 解析塞进 Runner。

推荐：

```text
WorkflowRunner
    │
    ├── TemplateResolver
    │
    ├── ConditionEvaluator
    │
    ├── VariableStore
    │
    └── ReferenceResolver
```

因此：

```text
Workflow
    = orchestration

TemplateResolver
    = input materialization

ConditionEvaluator
    = pure evaluation

VariableStore
    = run state
```

---

# 46. ConditionEvaluator 必须 Pure

强制：

```text
ConditionEvaluator
    only Value → Result
```

不得：

```text
filesystem
network
process
MCP
plugin
clock
environment variable
```

尤其禁止：

```text
condition:
file_exists("C:\\...")
```

否则 condition 本身就成为 Effect gateway。

---

# 47. 时间也不应偷偷读取

不要支持：

```text
now()
random()
env()
hostname()
```

P1-C。

如果未来需要时间，应该作为：

```text
WorkflowInput
```

或者显式 Context Data。

这样测试才能 deterministic。

---

# 48. VariableStore API

建议：

```rust
pub trait VariableStore {
    fn get(&self, path: &VariablePath) -> Result<&Value, VariableError>;

    fn set(
        &mut self,
        path: &VariablePath,
        value: Value,
    ) -> Result<(), VariableError>;

    fn snapshot(&self) -> VariableSnapshot;
}
```

但：

```text
WorkflowInput
workflow.*
step.*
```

不能通过 `set()` 修改。

---

# 49. Transaction Semantics

一个 Step 内部：

```text
template resolve
↓
condition
↓
reference resolve
↓
action execution
↓
output binding
↓
variable mutation
↓
transition
```

建议：

> **只有 Action 成功并且 OutputBinding 成功后，变量 mutation 才提交。**

例如：

```text
Action succeeded
Output binding failed
```

则：

```text
Step = Failed
new variable values = NOT committed
```

不能产生半提交状态。

```text

    ↓
```

## P1-C 冻结原则

最后把本阶段最重要的边界压缩成 6 条：

```text
1. Variable 是数据，不是权限。

2. Condition 是纯计算，不是 Effect。

3. Branch 是控制流，不是执行授权。

4. Variable 可以填充 Action input，但不能改变 Action identity。

5. FailurePolicy 优先于 FailureTransition，branch 不能绕过安全语义。

6. WorkflowRunner 永远只能通过 ReferenceResolver → ActionResolver → ActionEngine
   进入真实执行路径。
```

**P1-C 的工程目标就是让 Workflow 从“线性 Action 编排器”升级成“有限状态控制流引擎”，但仍然没有任何独立 Effect 权限。**
