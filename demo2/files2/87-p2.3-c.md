# P2.3-C — Reliability / Recovery Closure

进入这一批后，重点从 P2.3-B 的“**正常产品链路能完整跑通**”转为：

> **当组件崩溃、超时、数据损坏、升级中断、进程异常退出时，Launcher 是否能够以确定、可恢复、无重复执行、无静默数据损失的方式继续工作。**

本批次**不新增用户功能**。只允许修复可靠性、恢复性、一致性和数据安全相关问题。

# 2. C1 — Failure Taxonomy

第一步先冻结失败分类。

不能出现大量：

```text
Other
Unknown
GenericError
```

最终建议统一到：

```text
FailureClass
├─ InvalidInput
├─ CapabilityDenied
├─ ConfirmationRequired
├─ CommandNotFound
├─ ProviderUnavailable
├─ PluginUnavailable
├─ PluginCrashed
├─ PluginProtocolViolation
├─ McpUnavailable
├─ McpTimeout
├─ McpProcessCrashed
├─ McpProtocolViolation
├─ IndexFailure
├─ PersistenceFailure
├─ ConfigurationFailure
├─ MigrationFailure
├─ StartupFailure
├─ ProcessCrashed
└─ InternalFailure
```

同时区分：

```text
Business failure
Protocol failure
Infrastructure failure
Data integrity failure
```

### 核心原则

```text
Failure
  ↓
Classification
  ↓
Policy
  ↓
Retry / Stop / Recover / Quarantine / Rebuild
```

不能：

```text
Failure
  ↓
catch
  ↓
ignore
```

# 3. C2 — Launcher Process Crash Recovery

验证整个 Launcher 进程被强制终止之后：

```text
Launcher
   ↓
Crash
   ↓
Next Startup
   ↓
startup_state
   ↓
Recovery Decision
```

必须验证：

### 正常关闭

```text
healthy
→ shutdown
→ next startup
→ normal
```

### 异常退出

```text
starting
→ process killed
→ next startup
→ failure_count++
```

### 连续失败

例如：

```text
failure_count = 1
failure_count = 2
failure_count = 3
```

达到阈值后：

```text
RecoveryRequired
```

不得继续：

```text
normal startup
```

而绕过 Recovery decision。

# 4. C3 — Plugin Crash / Restart / Quarantine

已有：

```text
PluginBroker
PluginHost
Runtime
failure threshold
quarantine
```

现在需要产品级验证。

## Scenario 1：单次 Crash

```text
Plugin
 ↓
Crash
 ↓
Execution fails
 ↓
Runtime cleanup
 ↓
next invocation
 ↓
new runtime/process
```

不得 replay 上一次 execution。

---

## Scenario 2：Repeated Crash

```text
E1 → crash
E2 → crash
E3 → crash
```

达到：

```text
threshold = 3
```

之后：

```text
Plugin = Quarantined
```

必须满足：

```text
search candidates = 0
execution = rejected
```

---

## Scenario 3：Business Error

```text
plugin returns business failure
```

不得错误累计成：

```text
crash/protocol failure
```

并确认既有 failure counter reset 行为没有被破坏。

例如：

```text

 ↓

```

```text

```

* root 恢复后可重新扫描；
* generation 行为有定义。

这一项你之前已经明确是 P2.1-B 的 deferred area，现在应该在 Recovery Closure 中确认**产品最终行为**。


# 10. C8 — Workflow Failure / Resume Semantics

重点不是增加 Durable Workflow。

当前 Workflow 仍保持：

```text
in-memory orchestration
```

但必须验证异常行为。

---

## Action Failure

```text
Step1 success
Step2 fail
```

根据：

```text
failure_policy
```

产生：

```text
Retry
Skip
Stop
```

---

## Retry

必须：

```text
attempt 1 → ExecutionId E1
attempt 2 → ExecutionId E2
```

并保证：

```text
E1 ≠ E2
```

---

## ConfirmationRequired

```text
Step
 ↓
ConfirmationRequired
 ↓
Paused
```

而不是：

```text
automatic retry
```

恢复时：

```text
re-resolve
```

然后再决定是否执行。

# 11. C9 — Execution Replay Prevention

这是 P2.3-C 的**最高优先级之一**。

定义：

> Recovery never implies replay.

必须测试：

### Launcher crash after dispatch

```text
E1
 ↓
Effect dispatched
 ↓
Launcher crashes
```

重启以后：

```text
E1
```

不得自动再次执行。

---

### Plugin crash after execution

```text
E1
 ↓
plugin may have completed side effect
 ↓
transport/process crash
```

不能根据：

```text
“没有收到成功响应”
```

自动产生：

```text
E2
```

除非上层明确发起新的 Retry。

---

### MCP timeout

同理：

```text
E1 timeout
```

不代表：

```text
E1 failed before server execution
```

所以不能自动 replay。

这一条应该明确写入 1.0 安全/可靠性不变量：

```text
INV-RECOVERY-001
Recovery MUST NOT replay a previously dispatched execution.
```

# 13. C11 — Process / Resource Leak Soak

这一项很重要，因为 Launcher 是常驻软件。

建立：

```text
30 min
60 min
4 hour
```

至少一个自动化 soak profile。

循环：

```text
open popup
search
close popup
launch application
execute plugin
execute MCP
index changes
icon loading
workflow
```

观察：

```text
process count
thread count
handle count
RSS
private bytes
IPC sessions
plugin runtimes
MCP processes
file descriptors / Windows handles
```

重点不是绝对数值，而是：

```text
monotonic growth = 0
```

```text

1 → 1 → 1 → 1

Plugin runtime:
0 → 1 → 0 → 1 → 0
```

而不能：

```text
1 → 2 → 3 → 4 → ...
```

# 16. 新增 Recovery Invariants

在已有：

```text
INV-AUTH
INV-RUNTIME
INV-MCP-SESSION
INV-CONTEXT
```

之上新增：

### INV-RECOVERY-001

Recovery 不得自动 replay 已 dispatch 的 execution。

### INV-RECOVERY-002

失败事务不得递增对应 committed Generation。

### INV-RECOVERY-003

可重建数据不得采用不可恢复的数据删除策略。

### INV-RECOVERY-004

用户持久数据损坏时不得无提示静默清空。

### INV-RECOVERY-005

失败进程退出后不得留下失控的 child process/runtime。

### INV-RECOVERY-006

Repeated failure 必须最终进入 bounded state，而不能无限 retry。

# 19. P2.3-C 完成后的状态

整个 P2.3 就会形成：

```text
                    P2.3
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
      P2.3-A        P2.3-B        P2.3-C
   Architecture     Product       Reliability
     Frozen         Verified       Verified
        ✅             ✅             ✅
                                      │
                                      ▼
                                   P2.3-D
                              Performance /
                              Memory Closure
```

其中 **P2.3-C 的核心验收标准可以浓缩成一句话：**

> **任何失败都必须有边界、有分类、有确定的后续状态；恢复不能制造第二次执行，数据损坏不能静默变成数据丢失。**

完成 C 后，Launcher 才开始具备真正意义上的**长期运行产品**特征。下一批 P2.3-D 就可以放心把重点转向 Release 性能、内存、Soak 与正式基线，而不是一边测性能一边担心后台 Runtime/Process 在泄漏。
