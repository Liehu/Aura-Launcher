# P2.3-H — Release Engineering & CI

进入 **P2.3-H**。

这一批是整个 1.0 发布链的工程化收口。前面的 A～G 已经分别验证了架构、E2E、可靠性、性能、安全、UI 和安装升级；H 的任务是把这些验证**统一编排成一个不可绕过、可重复执行的 Release Pipeline**。

核心目标：

> **任何一个 1.0 Release Artifact，都必须能够证明它通过了同一套完整 Gate；本地“手工验证过”不再算 Release 条件。**

# 2. H1 — Release Pipeline Contract

先冻结一条唯一 Release Pipeline：

```text
Source
  ↓
Format / Static Check
  ↓
Compile
  ↓
Unit Test
  ↓
Integration Test
  ↓
E2E
  ↓
Security
  ↓
Performance
  ↓
Memory / Soak
  ↓
UI / VR
  ↓
Package
  ↓
Install
  ↓
Upgrade
  ↓
Recovery
  ↓
Artifact Verification
  ↓
Release Candidate
```

禁止：

```text
“CI 没跑完，但本地测试过了”
```

作为正式 Release 条件。

---

# 3. Release Pipeline 必须有唯一入口

建议冻结：

```text
scripts/release/
├─ release.ps1
├─ release.toml
├─ verify.ps1
└─ manifest.ps1
```

或者对应 Rust/CI 实现，但必须有：

```text
one canonical release command
```

例如：

```powershell
.\scripts\release\release.ps1 -Profile 1.0-rc
```

内部统一调用：

```text
build
test
verify
package
```

不能：

```text
script-a
script-b
manual-c
```

各自做一部分然后靠人记忆组合。

---

# 4. H2 — Workspace Build Matrix

当前 workspace 不是单 crate 项目，因此要同时覆盖：

```text
library crates
application
bench
example/test apps
```

至少：

```text
cargo check --workspace
cargo test --workspace
cargo build --release -p launcher-app
```

并继续保留：

```text
zero warnings
```

作为发布 Gate。

---

# 5. Release Profile

明确：

```text
Debug
Dev
Release
Release Candidate
```

其中真正 Release：

```text
Cargo profile = release
```

不要出现：

```text
Debug benchmark
+
Release package
```

却把两者混称为同一性能基线。

# 6. H3 — Static / Unit / Integration Gate

建立统一 Gate：

```text
G1 Formatting
G2 Compilation
G3 Warnings
G4 Unit Test
G5 Integration Test
G6 Topology
```

### G1

```text
cargo fmt --check
```

### G2

```text
cargo check --workspace
cargo build --workspace
```

### G3

必须：

```text
warnings = 0
```

### G4

```text
cargo test --workspace
```

### G5

跨 crate：

```text
integration tests
```

### G6

重新验证：

```text
crate boundary
dependency rules
```

# 7. H4 — E2E / Golden Path Gate

直接纳入 P2.3-B：

```text
E2E-001 ... E2E-020
```

正式规定：

```text
Golden E2E = mandatory
```

任何：

```text
skip
quarantine
xfail
```

都不能进入正式 Release。

若测试确实存在平台依赖，必须明确：

```text
required
optional
platform-specific
```

而不是临时跳过。

---

# 8. H5 — Security Gate

直接接入 P2.3-E：

```text
security-source-scan
security invariants
adversarial E2E
resource limits
dependency audit
```

硬规则：

```text
security blocker > release blocker
```

也就是安全 Gate 一项失败，Release 立即失败。

---

# 9. H6 — Performance Gate

使用 P2.3-D 最终 baseline：

```text
benchmarks/release-baseline.json
benchmarks/thresholds.json
```

测试：

```text
startup
popup
search
cache
index
icon
```

结果：

```text
PASS
WARN
FAIL
```

## 关键区别

### WARN

允许开发继续。

### FAIL

禁止生成 RC。

不要把所有性能问题都直接设成失败，否则很快会因为运行环境噪声导致 CI 不稳定。

---

# 10. H7 — Memory / Soak Gate

短测试：

```text
10~30 min
```

正式 RC：

```text
long-run soak
```

至少检测：

```text
memory slope
handle slope
thread slope
process count
runtime count
```

条件：

```text
unexpected monotonic growth = FAIL
```

---

# 11. H8 — UI / Visual Regression Gate

直接使用已有：

```text
VR-001 ... VR-020
```

继续保持：

```text
--require-baseline
```

正式 Release：

```text
missing baseline = FAIL
```

禁止：

```text
missing baseline
→ generate new baseline automatically
→ test passes
```

否则 Visual Regression 很容易退化成：

> “当前画面和当前画面一样”。

# 12. UI Baseline 管理

baseline 目录建议冻结：

```text

├─ baseline/
│  ├─ vr-001.bmp
│  ├─ ...
│  └─ vr-020.bmp
├─ expected/
└─ diff/
```

```text

```

```text

```

方便定位。

# 14. H10 — Artifact Reproducibility

目标不是追求严格 bit-for-bit reproducible build，而是先做到：

> **同一个源码版本产生的 Release，内容、版本、依赖和构建信息可追溯。**

至少记录：

```text
commit SHA
branch/tag
version
Rust toolchain
Windows SDK
Cargo.lock hash
build profile
build timestamp
package version
```

---

# 15. Build Manifest

每一个 artifact 生成：

```text
launcher-1.0.0-rc1.manifest.json
```

例如：

```json
{
  "product": "launcher",
  "version": "1.0.0-rc1",
  "commit": "...",
  "toolchain": "...",
  "profile": "release",
  "cargo_lock_sha256": "...",
  "package_sha256": "..."
}
```

这个文件本身也进入 Release Artifact。

---

# 16. H11 — Package Integrity / Signing

最终发布包必须验证：

```text
artifact
 ↓
hash
 ↓
signature
 ↓
metadata
 ↓
verification
```

至少：

```text
SHA-256
```

并验证：

```text
signature valid
publisher valid
version matches
artifact matches manifest
```

如果最终采用 MSIX，则正式 Release Gate 应直接验证 MSIX 包，而不是只验证裸 exe。

# 17. H12 — Version / Metadata Management

Launcher 的版本不能散落在：

```text
Cargo.toml
package script
installer
UI
```

然后人工保持一致。

建议定义：

```text
VERSION = canonical source
```

然后生成：

```text
Cargo package version
installer version
MSIX version
UI About
release manifest
```

必须检查：

```text
all versions match
```

# 18. Semantic Versioning

1.0 阶段建议：

```text
1.0.0-alpha.N
1.0.0-beta.N
1.0.0-rc.N
1.0.0
```

禁止发布：

```text
1.0.0
```

但内部仍存在明显：

```text
experimental / incomplete
```

的核心能力。

# 19. H13 — Release Manifest

正式 Release 必须产生：

```text
release-manifest.json
```

包括：

```text
product version
commit
build environment
test result
security result
benchmark result
package hashes
signature
migration schema versions
plugin SDK version
MCP profile
```

这样以后拿到：

```text
Launcher 1.0.0
```

可以回答：

> “这个二进制当时到底通过了哪些测试？”

而不是只能看 Git history。

---

# 20. H14 — CI Failure Policy

必须明确：

### Hard Failure

```text
compile failure
warnings
unit failure
E2E failure
security failure
missing VR baseline
package failure
migration failure
signature failure
```

直接：

```text
STOP
```

### Flaky Retry

只允许：

```text
performance noise
network download transient
external dependency unavailable
```

而且：

```text
retry <= 1
```

不能：

```text
test fails
→ retry 10
→ eventually passes
→ green
```

否则会掩盖真实故障。

---

# 21. Test Result Classification

测试结束后必须产生：

```text
PASS
FAIL
BLOCKED
SKIPPED
```

其中 Release Gate：

```text
SKIPPED
```

不能等价：

```text
PASS
```

只有明确：

```text
not applicable for this target
```

才允许不执行。

---

# 22. H15 — CI Environment Isolation

测试不能依赖开发者机器状态。

必须隔离：

```text
HOME
APPDATA
LOCALAPPDATA
TEMP
PLUGIN_ROOT
MCP_ROOT
E2E_DATA_ROOT
```

E2E 要使用独立 fixture。

特别是：

```text
real user's plugins
real user's history
real user's favorites
```

全部禁止进入 Release Test。

---

# 23. Windows Matrix

由于 Launcher 是 Windows-first，Release Pipeline 至少区分：

```text
Windows 10
Windows 11
```

以及：

```text
x64
```

如果 1.0 暂不支持 ARM64，则明确：

```text
ARM64 = unsupported
```

而不是让 CI 默认通过然后产生未声明行为。

# 29. Gate 与测试类型关系

```text
                 Release
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
    Correctness              Quality
        │                       │
    G01-G05                G06-G12
```

不要把：

```text
unit test
```

当成整个产品质量的代表。

---

# 30. H17 — Release Engineering Closure

最终必须回答 10 个问题：

```text
1. 能否从 commit 自动构建？
2. 能否自动执行全部 Gate？
3. 任一 Gate failure 是否阻止 Release？
4. 是否能够验证 Release package？
5. 是否能够验证 Installer？
6. 是否能够验证 Upgrade？
7. 是否能够生成完整 evidence？
8. 是否能够定位具体 commit/toolchain？
9. 是否能够复现同一测试环境？
10. 是否能够明确得到“这个版本为什么可以发布”？
```

全部：

```text
YES
```

才算 H 完成。

# 32. 本批次的第一实施顺序

不要一上来写完整 `release.yml`。

依次做：

```text
H1 Release Pipeline Contract
        ↓
H2 Workspace Build Matrix
        ↓
H3 Static / Unit / Integration
        ↓
H4 E2E
        ↓
H5 Security
        ↓
H6 Performance
        ↓
H7 Memory
        ↓
H8 Visual
        ↓
H9 Installer
        ↓
H10-H13 Evidence / Manifest
        ↓
H16 RC Pipeline
```

原因是：

> CI 只负责**编排已经定义好的验证能力**，不应该反过来决定产品契约。

完成 H 后：

```text id="zgw0wp"
P2.3-A Architecture       ✅
P2.3-B Product E2E         ✅
P2.3-C Reliability        ✅
P2.3-D Performance        ✅

                    │

          Release Candidate
```

此时 H 的核心成果不是某一个 CI YAML，而是建立这条**不可绕过的生产链**：

```text
Commit
  ↓
Build
  ↓
Test
  ↓
Security
  ↓
Performance
  ↓
UI
  ↓
Installer
  ↓
Upgrade
  ↓
Recovery
  ↓
Package
  ↓
Verify
  ↓
Evidence
  ↓
RC
```

而且：

> **Release Artifact 与 Release Evidence 必须一一对应。**

也就是说，拿到 `Launcher 1.0.0-rc1` 时，能够反查它对应的 commit、toolchain、测试结果、性能结果、安全结果、安装升级结果和最终 hash。

完成 P2.3-H 后，就只剩 **P2.3-I — Release Candidate**。I 应该是一个非常小的批次：**冻结、打包、全量执行 Gate、修复阻断缺陷、重新出 RC；禁止再开发新功能。**
