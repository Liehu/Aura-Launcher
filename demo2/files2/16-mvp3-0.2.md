# 一、ActionResolver 这一刀是正确的，而且建议正式成为核心边界

你现在：

```text
ActionDescriptor
    ↓
ActionResolver
    ↓
ResolvedAction
    ↓
ActionEngine
    ↓
Effect
```

这是这轮最重要的结果。

之前最危险的模型是：

```text
Plugin
   ↓
ActionDescriptor
   ↓
ActionEngine
```

因为意味着 Action Engine 必须同时承担：

```text
validation
permission
context
type dispatch
input parsing
effect execution
```

最终必然变成一个巨型组件。

现在拆成：

```text
Untrusted
    ↓
Resolver
    ↓
Trusted
```

就形成了明确的 trust boundary。

我建议把它升级成一个非常强的 invariant：

```text
INV-033

ActionEngine MUST accept only ResolvedAction.
Raw ActionDescriptor MUST NEVER reach ActionEngine.
```

这条以后对 AI/MCP 尤其重要。

因为未来：

```text
AI
 ↓
generates ActionDescriptor
 ↓
ActionResolver
```

AI 也属于不可信输入来源。

# 二、`system.*` / `plugin.*` 的划分正确，但我建议现在就把 `plugin.*` 定义为“future execution domain”

你现在：

```text
system.*
    Host-owned Effect

plugin.<id>.*
    Plugin-owned Effect
```

概念上没问题。

但因为：

> `plugin.*` RPC 还没有实现

所以建议 Contract 里把它明确标成：

```text
Defined Namespace
≠
Supported Execution
```

即：

```text
plugin.<id>.*
    namespace reserved
    execution unavailable in v0.1
```

否则有人看到：

```text
type = plugin.foo.bar
```

可能认为这是当前可执行能力。

更严格一点：

```text
v0.1:
system.*      supported
plugin.*      reserved / unsupported
```

未知或 unsupported：

```text
secondary → Hidden
primary → Disabled
```

这也正好与你已有规则统一。

# 三、`requires ⊆ Manifest.capabilities` 应该进入“硬验证”，不是只写文档

这是非常正确的设计：

```text
Action.requires ⊆ Manifest.capabilities
```

但这里有一个很容易踩的坑：

### 不要在 Host 侧做“自动补权限”

错误：

```text
Manifest:
[]

Action:
requires = ["clipboard.write"]

Host:
“插件既然需要，那就临时申请”
```

正确：

```text
Manifest:
[]

Action:
requires = ["clipboard.write"]

            ↓

INVALID / UNSATISFIABLE
```

即：

```text
Manifest capabilities
        ↓
Upper Bound
```

Action 只能在这个集合内声明需求。

建议正式写：

```text
Capability monotonicity:
Action MUST NOT increase the plugin's declared authority.
```

这是安全模型中很有价值的一条。

# 五、这里有个细节：`CapabilityDenied` 不一定等于“UI 置灰”

你目前：

```text
声明但未授予
→ Action 呈现置灰/DENY
```

这个产品行为需要稍微弱化成：

```text
Execution state = Denied
Presentation = Host policy
```

原因很简单。

未来不同来源可能有不同 UX：

```text

    disabled + reason

Search result:
    hidden

AI:
    rejected

    branch failure
```

所以 Contract 应该冻结的是：

```text

```

而不是强行冻结：

```text

```

否则未来 UI Schema / AI UI 会被 Action Contract 绑住。

# 六、`unknown secondary → Hidden` 这个决定很好，我建议推广成“Action-level fault containment”

现在：

```text

    ↓

```

非常合理。

建议再补一个总原则：

```text
Malformed Action MUST have the smallest possible blast radius.
```

也就是：

```text

    ↓
Action-level failure
```

不要：

```text

    ↓

```

```text

```

才：

```text

```

这样以后插件大量返回 action 时会稳定很多。

# 十、`score ∈ [0,1]` 是合理的，但不要把 `0` 同时定义成“无效”和“最低分”

本身也是一个合法的最低 hint。
