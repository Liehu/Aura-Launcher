应该**现在开始，但不要现在开始实现“完整插件系统”**。

你现在的 MVP2.1 已经把 `Context → Command → Action` 真正跑通，而且插件的外部进程边界已经存在、JSON-RPC 协议也已经有了。这个时点非常适合进入：

> **Plugin Architecture / SDK Design Freeze 评审阶段**

而不是继续往后拖到 Python / Node / WASM 真要接入时再设计。

原因是插件一旦进入真实开发，很多现在还能随时调整的东西会迅速变成兼容性负担：Manifest、Command Schema、Action Schema、IPC、错误模型、生命周期、Capability、版本兼容、UI 扩展方式。你当前架构已经规定外部插件采用 stdio JSON-RPC，而且插件结果经过 Host 校验、100 条上限和 timeout/crash 隔离。

## 我建议现在做的是“插件规范”，但分两层

不要一次写成：

```text
Python SDK
Node SDK
WASM SDK
Native SDK
Marketplace
签名
自动更新
```

应该先冻结：

```text
Plugin Contract v0.1
        ↓
Plugin SDK Architecture v0.1
        ↓
External Process Plugin MVP
```

然后语言 SDK 都只是这个 Contract 的实现。

# 一、为什么现在就是最佳时间

你已经同时具备了三个条件。

### 条件 1：Plugin Boundary 已真实存在

当前架构已经是：

```text
Core
  ↓
Plugin Host
  ↓
External Process
  ↓
stdio JSON-RPC
```

而且已经验证：

```text
normal
slow
crash
malformed
flood
spawn-soak
```

等异常条件不会拖垮 Core。

这意味着 Plugin Contract 已经不再是纸上谈兵。

### 条件 2：Command / Action 模型已经存在

插件最终不是控制 UI，而是产生：

```text
Command
  ↓
Action
```

这为后面的插件设计提供了非常好的基础。

### 条件 3：你已经经历一次真实架构 bug

这次 MVP2.1 出现：

```text
UI last_results
```

与实际 command state 不一致。

这恰好说明现在设计插件 API 是合适的。

否则很容易出现：

```text
Plugin result
↓
UI 自己解释
↓
UI 自己保存
↓
Plugin action 又有另外一份状态
```

最终越来越乱。

你现在已经有一个非常好的起点。

# 四、尤其不要照搬 uTools 的 UI 插件模式

uTools 的开发体验确实很好：`plugin.json` 描述 `main`、`logo`、`preload`、`features` 等，开发者可以从配置文件开始接入插件。([u-tools.cn][2])

但它的执行模型高度依赖：

```text
HTML
+
Electron
+
preload
+
Node
```

官方文档也明确说明 preload 可以直接使用 Node API 和 Electron 渲染进程 API。([u-tools.cn][3])

我们应该：

> **抄 Manifest / Feature 声明方式，不抄 HTML/Preload 运行模型。**

所以最终变成：

```text
plugin.json
    ↓
feature declaration
    ↓
Native Command
```

而不是：

```text
plugin.json
    ↓
index.html
    ↓
WebView
```

# 五、Raycast 的东西值得重点研究

尤其是：

```text
Extension
  ↓
Command
  ↓
UI
  ↓
Action
```

以及：

```text
Command
  ├── title
  ├── subtitle
  ├── icon
  ├── keywords
  ├── arguments
  ├── actions
  └── preferences
```

这和你现在的：

```text
Provider
→ Command
→ Action
```

天然兼容。

所以我建议最终 Plugin API 不暴露：

```text
show_popup()
set_window_size()
set_html()
```

这些东西。

而暴露：

```text
register_command()
return_result()
register_action()
request_capability()
open_panel()
```

让：

> **Plugin 声明意图，Host 决定呈现。**

这是你这个项目和 uTools 最大的架构差异。

# 六、Flow 的 JSON-RPC 可以直接作为第一版协议参考

Flow 的官方文档明确把 JSON-RPC 当成 Flow 与其他语言插件之间的本地 RPC，并通过统一 API 连接 Python / JavaScript / TypeScript 插件。([GitHub][1])

你当前已经采用：

```text
stdin
stdout
newline-delimited JSON-RPC
```

这个决定我建议暂时不改。

但我们应该在现有基础上补齐：

```text
request_id
plugin_id
protocol_version
api_version
method
params
result
error
```

例如：

```json
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "query",
  "params": {
    "query": "term",
    "context": {}
  }
}
```

返回：

```json
{
  "jsonrpc": "2.0",
  "id": 42,
  "result": {
    "commands": []
  }
}
```

# 七、这里千万不要让 `query()` 成为万能 API

这是我认为插件设计最重要的地方之一。

很多旧 Launcher 的插件最终都会变成：

```text
query()
    ↓
return anything
```

然后慢慢演化出：

```text
query
query2
execute
callback
change_query
show
hide
...
```

我们最好一开始就拆：

```text
Plugin
├── Discovery
├── Query
├── Action
├── Context
├── Preview
├── Settings
└── Lifecycle
```

但并不是每个 Plugin 都必须实现全部能力。

定义：

```text
capabilities:
    query
    action
    preview
    context
    settings
```

这样就可以形成：

```text
Minimal Plugin
    query

Normal Plugin
    query + action

Context Plugin
    context + query

Preview Plugin
    query + preview

Workflow Plugin
    query + action + workflow
```

```text
 ↓
```

但先只做：

```text

```

采用：

```text
requested

```

三层。

例如：

```json

  "capabilities": [
    "network"
  ]
}
```

只是：

> requested


# 十三、再加一个非常重要的设计：Plugin 不应该直接执行 Effect

```text

 ↓
```

```text

MCP
Builtin Provider
```

```text
Action Engine
```

这会成为整个项目最大的架构收益之一。

## 一句话判断

**现在就是定义插件规范的最佳时间，但现在应该冻结的是“协议与架构”，不是“插件生态”。**

你的 MVP2.1 已经证明：

```text
Context → Command → Action
```

成立；

MVP2 已经证明：

```text
Provider → Plugin Host → External Process
```

成立。

所以现在把二者合起来，正好进入：

```text
              Plugin Contract
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       Context              Query
          │                   │
          └─────────┬─────────┘
                    ▼
                 Command
                    │
                    ▼
                  Action
                    │
                    ▼
                  Effect
```

**这时候做插件规范，刚好能避免未来 Python/Node/WASM/AI/MCP 各自长出一套 API。**
