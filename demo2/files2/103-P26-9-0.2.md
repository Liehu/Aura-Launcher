# 三、第二个问题：`SystemAuthorization` 最好绑定 Command，而不是只有“授权过”这一语义

你现在：

```text

    ↓
SystemAuthorization
    ↓
Adapter
```

方向正确。

但是建议明确：

```text
SystemAuthorization
{
    command_identity
    target_identity
    policy_decision
    approval_identity
    request_id
    expiration
}
```

至少要保证：

```text

        ≠
Command B
```

不能发生：

```text

        ↓

        ↓
```

最干净的方式其实是：


让 `auth` 本身携带完整的已解析 Effect。

```text

    ├── capability
    ├── target
    ├── normalized input

    ├── approval id
    └── execution metadata
```

Adapter 不需要再次接收：

```text
SystemCommand
```

这样边界会更加漂亮：

```text

  ↓
ActionEngine
  ↓
AuthorizedEffect
  ↓
Adapter
```

而不是：

```text

       +

       ↓
Adapter
```

# 九、目前 `retry_decision` 有一个语义值得再细化

当前矩阵：

```text
Succeeded → Forbidden
Unknown/Timeout → idempotent 才允许
Failed/Cancelled/Rejected → Allowed
```

整体没问题。

但是：

```text
Cancelled → Allowed
```

要小心。

因为：

```text
Cancelled
```

到底发生在哪个阶段？

### 情况 A

```text
NotStarted
→ Cancelled
```

当然可以 retry。

### 情况 B

```text
Executing
→ Cancel request
→ runtime doesn't confirm stop
→ Cancelled
```

这时实际 Effect 可能已经发生。

所以：

> `Cancelled` 不应该天然等价于“安全重试”。

应该由：

```text
CommandResult
+
EffectState
```

一起决定。

例如：

```text
Cancelled + NotStarted
    → retry allowed

Cancelled + Unknown
    → same semantics as Unknown

Cancelled + Completed
    → forbidden
```

这其实和你已经建立的：

```text
CommandResult
EffectState
```

模型完全一致。

所以建议把：

```text
retry_decision(result, idempotent)
```

升级为：

```text
retry_decision(
    result,
    effect_state,
    idempotency
)
```

这是一个很值得修的 **P1**。
