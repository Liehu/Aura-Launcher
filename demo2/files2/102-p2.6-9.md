# 四、第二个重要问题：P2.9 的 **Effect Authority 还可以再收紧**

你现在的设计是：

```text
SystemResolver
    ↓
SystemCommand
    ↓
launcher-action
    ↓
execute_system_command(&SystemCommand, confirmed)
```

而：

```text
execute_system_command()
```

是唯一实际进入 Win32 的地方。

这个方向正确。

但我建议这里再加一个非常硬的架构约束：

> **不能只保证“只有一个函数执行 Win32”，还必须保证“只有 ActionEngine 可以调用这个函数”。**

目前文档里仍然存在这种模型：

```text
execute_system_command(command, confirmed=true)
```

从 API 形态上看：

```text
confirmed=true
```

本身就是一个危险的 authority-like 参数。

因为理论上：

```rust
execute_system_command(&command, true)
```

就可以绕过上游 Policy。

即使当前项目没有这么调用，它在架构上还是一个潜在旁路。

### 我建议改成

不要让 adapter 暴露：

```rust
execute_system_command(command, confirmed)
```

而改成类似：

```text
ValidatedSystemEffect
```

只有经过：

```text
Resolver
→ Policy
→ Approval
→ ActionEngine
```

才能产生：

```text
AuthorizedSystemEffect
```

然后：

```text
WindowsAdapter.execute(AuthorizedSystemEffect)
```

这样：

```text
confirmed=true
```

甚至可以彻底消失。

架构变成：

```text
SystemCommand
      ↓
Validation
      ↓
Policy
      ↓
Approval
      ↓
AuthorizedSystemEffect
      ↓
WindowsAdapter
      ↓
Win32
```

这会比当前：

```text
SystemCommand + confirmed
```

安全得多。

# 五、第三个问题：Process Identity 的文档与实现记录存在风险

这是我比较建议你重点检查的地方。

P2.9 设计里你定义过：

```text
PID ≠ Process Identity
```

并且明确要求防 PID reuse。

但是 `149-p29-windows-adapter.md` 实际记录的是：

```text
Process:
    OpenProcess(PROCESS_TERMINATE)
    → TerminateProcess
```

以及：

```text
pid 过期 = 干净报错
```

这只能证明：

```text
PID 当前不存在
```

并不能完全证明：

```text
PID 对应的还是原来那个进程
```

真正危险的是：

```text
Resolve PID 1234
      ↓
old process exits
      ↓
new process obtains PID 1234
      ↓
TerminateProcess(1234)
```

这里：

```text
pid 仍然存在
```

所以不能靠：

```text
OpenProcess
```

判断目标没变。

### 建议

把 P2.9 的 ProcessTarget 真正升级成：

```text
ProcessIdentity {
    pid
    creation_identity
}
```

执行前：

```text
pid match
AND creation identity match
```

否则：

```text
StaleTarget
```

而不是继续执行。

这个我会列为 **P2.9 P1 级审计项**。

# 六、第四个问题：Workflow 的 Replan 语义有潜在重复 Effect

这个是我认为 **P2.6/P2.7 联动之后最大的一处架构风险**。

你现在 P2.7 Agent Loop 的 Replan 是：

```text
Step1
Step2 ← fail
     ↓
Replanning
     ↓
Planning
     ↓
Executing
     ↓
Whole Plan From Head
```

也就是文档明确记录：

> “全 plan 从头重执行一次”

对于：

```text
read
search
calculate
open
```

问题不大。

但是如果：

```text
Step1 = Delete file
Step2 = Send something
Step3 = Restart
```

而：

```text
Step2 failure
```

然后重跑：

```text
Step1
```

那么：

```text
Step1 Effect
```

有可能被执行两次。

即使 Step1 是：

```text
copy
move
rename
terminate
```

也存在问题。

---

## 建议

Agent Runtime 不应该简单地：

```text
re-run whole plan
```

而应该至少记录：

```text
StepExecutionState
```

例如：

```text
Pending
Executing
Succeeded
Failed
Unknown
```

然后 Replan 时：

```text
Succeeded
    → 不重复执行

Failed
    → 根据 retry policy 决定

Unknown
    → 高风险 Effect 不自动重试
```

更进一步，可以采用：

```text
Replan produces replacement suffix
```

而不是：

```text
Replan whole plan
```

即：

```text
Plan:

A → B → C → D

A = completed
B = completed
C = failed
```

重新规划：

```text
A ✓
B ✓
      ↓
    C'
      ↓
    D'
```

而不是：

```text
A
B
C'
D'
```

重新执行 A/B。

这和你的 P2.6 Durable Workflow 语义其实天然契合。
