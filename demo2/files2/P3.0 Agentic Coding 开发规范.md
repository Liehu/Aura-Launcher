# 3. 每批执行纪律（沿用 P2 惯例 + P3.0 增补）

1. **契约先行**：批次内第一个动作是实现锚点处的接口/类型定义 + 单测
   骨架；纯函数模块（fuzzy/retry 类）必须先有测试再有实现分支。
2. **小步提交**：每任务一个 commit；批尾一个 Gate commit（验收清单
   逐项勾选写入批次文档）。
3. **Gate 命令（每轮收尾，不可省）**：

```bash
cargo test --workspace          # 全绿
cargo build --workspace         # 零警告
python scripts/check_topology.py
LAUNCHER_SNAPSHOT_DIR=<fresh> ./target/debug/launcher-app   # B1 起重生成基线
```

4. **测试计数不再是完成度证据**：批次文档必须按 `P3.0 测试方案` 的
   维度矩阵报告覆盖（属性/边界/性能预算/E2E），测试数量只作附属信息。
5. **文档对齐**：批次完成 → `docs/phase/status.md` 状态更新 + 批次
   文档入 `docs/history/`（四态词汇）；HANDBOOK/README 只改索引行。
6. **红线检查点**（每个 Gate 必查）：UX-R1~R4 + UI 纯投影 + 三 Mode
   不变 + Motion ≤200ms。

# 4. 允许与禁止

**允许**：
- 新增纯函数模块与 provider（本阶段唯一新增 crate 内容）；
- launcher-ui 内新增组件文件 / Theme 调色板；
- launcher-config 新增字段（serde default，向后兼容）。

**禁止**：
- 修改六份 FROZEN 契约语义（富结果只出草案）；
- 在 UI 层新增任何解析/决策/IO；
- 绕过 Resolver → Engine 的任何执行捷径；
- 在 fuzzy/expr 路径引入 IO、网络、时钟、随机；
- 为动效引入后台线程或非声明式动画。

# 5. 评审与升级路径

- 每批 Gate 后：批次文档 + 验收清单提交评审（对照 `P3.0 验收标准`）；
- 评审结论分级沿用 P2.10 惯例：PASS / ACCEPTED WITH FOLLOW-UP /
  NOT ACCEPTED（Follow-up 项必须编号并归入下一批）；
- 设计变更（如 F01 评分权重、F04 设置项集合）须先改设计规范再改码。

# 6. Definition of Done（单任务级）

- 实现锚点处代码 + 单测（含边界）；
- `cargo test --workspace` 全绿、零警告、topology ok；
- 涉及 UI 的任务：暗/亮两套主题下目视检查 + 快照模式回归；
- 涉及性能预算的任务：预算数字写入批次文档（实测值）。
