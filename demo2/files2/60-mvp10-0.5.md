# P1-E：Visual Polish / Production UI

P1-E 进入。

这一阶段不再增加核心执行能力，而是把目前已经完成的：

```text
P0
Action / MCP / AI

P1-A
Runtime Persistence

P1-B
Protocol Session

P1-C
Workflow v0.2

P1-D
Agent Runtime
```

统一收敛成**可长期使用的生产级 UI/UX**。

核心原则：

> **P1-E 只改变“怎么呈现、怎么操作、怎么诊断”，不改变“谁有权执行什么”。**

因此 P1-E 不应反向修改 `ActionResolver`、`ActionEngine`、Workflow/Agent semantics。

---

# 1. P1-E 目标

已有 Visual Design v0.1 已经完成：

```text
Main
Action
Workflow
Confirmation
Diagnostics
Visual Regression
```

P1-E 的目标不是重做这些基础组件，而是做第二轮产品化：

```text
信息层级
状态反馈
键盘交互
Agent / Workflow / MCP runtime 可视化
大信息量压缩
错误恢复
可访问性
动画与状态过渡
视觉一致性
性能
```

最终达到：

```text
Developer UI
        ↓
Product UI
```

---

# 2. P1-E 非目标

明确不做：

```text
❌ 新增执行权限
❌ 修改 ActionResolver
❌ 修改 ActionEngine
❌ 修改 Effect
❌ 修改 Workflow semantics
❌ 修改 Agent authority
❌ 修改 MCP protocol
❌ 修改 Runtime lifecycle
❌ 引入 WebView
❌ 引入 Electron / CEF
❌ 引入 CSS engine
❌ 引入复杂 animation framework
```

继续：

```text
Rust + Slint
software renderer
```

---

# 3. UI 最重要的结构

P1-E 后建议把整个 UI 理解为三层：

```text
┌──────────────────────────────────────┐
│ Presentation                         │
│ Main / Action / Workflow / Agent     │
├──────────────────────────────────────┤
│ UI State                             │
│ Selection / Focus / Loading / Error  │
├──────────────────────────────────────┤
│ Core View Model                      │
│ Command / Action / Run / Diagnostic  │
└──────────────────────────────────────┘
```

严格禁止：

```text
UI
 ↓
Core internals
```

直接暴露：

```text
Effect
RuntimeManager
McpExecutor
PluginBroker
Capability
```

---

# 4. 顶层 Mode 保持不变

不要增加：

```text
AgentMode
McpMode
RuntimeMode
```

现有：

```text
Main
Action
Workflow
```

继续作为顶层导航状态。

Agent/Workflow/MCP 都属于：

```text
content/state
```

而不是：

```text
top-level navigation mode
```

---

# 5. Main Mode

Main 负责：

```text
Search
Discovery
Launch
AI entry
Recent
```

推荐视觉结构：

```text
┌─────────────────────────────────────┐
│ 🔎 Search / Command                 │
├─────────────────────────────────────┤
│                                     │
│ Result                              │
│ Result                              │
│ Result                              │
│                                     │
├─────────────────────────────────────┤
│ Enter  Open      Ctrl↓ Actions      │
└─────────────────────────────────────┘
```

但是底部 hint 必须根据实际状态动态变化。

不要固定显示所有 shortcuts。

---

# 6. Empty State

空状态不能只有：

```text
No Results
```

建议根据场景区分：

```text
No query
→ Start typing...

No results
→ No matching commands

No provider
→ No providers available

Provider unavailable
→ Provider temporarily unavailable
```

不能将：

```text
ProviderUnavailable
```

渲染成：

```text
No Results
```

否则用户会误判索引/搜索失败。

---

# 7. Result Row

每行统一：

```text
Icon
Title
Subtitle
Provider badge
Optional shortcut
```

例如：

```text
┌──────────────────────────────────────┐
│ ◉ Compress PDF                       │
│   Tools · Archive                    │
└──────────────────────────────────────┘
```

不要把所有 metadata 同时显示。

视觉优先级：

```text
Title
   ↓
Subtitle
   ↓
provider / metadata
```

---

# 8. Selected Result

选中状态必须明显，但不能过度高亮。

结构：

```text
Normal
──────
Selected
██████
```

推荐：

```text
selected row
 ├── leading accent
 ├── stronger title
 └── visible shortcut
```

仍然由：

```text
Core
```

提供：

```text
is_selected
```

而不是 UI 猜测。

---

# 9. Action Panel

Action Panel 仍然从：

```text
Ctrl + Down
```

进入。

建议改成：

```text
┌─────────────────────────────────────┐
│ ← Compress PDF                     │
├─────────────────────────────────────┤
│ ✓ Compress                          │
│ ✓ Preview                           │
│ ⛔ Delete                            │
│ ─────────────────────────────────── │
│ disabled explanation                │
└─────────────────────────────────────┘
```

重点是：

> **Disabled Action 必须告诉用户为什么不可用。**

---

# 10. Action State Visual Taxonomy

完整区分：

```text
Ready
Disabled
Hidden
Invalid
ConfirmationRequired
Executing
Succeeded
Failed
```

其中：

```text
Hidden
```

不显示。

```text
Invalid
```

通常不显示给普通用户，但 diagnostics 可展开。

```text
Disabled
```

显示，并提供 reason。

---

# 11. Disabled Reason

推荐统一文案映射：

```text
CapabilityDenied
    → Not permitted

MissingContext
    → Requires a folder

StaleContext
    → Context changed

InvalidInput
    → Input is invalid

Unavailable
    → Temporarily unavailable

ConfirmationRequired
    → Confirmation required
```

不要直接展示：

```text
CapabilityDenied
FailureClass::ProtocolViolation
```

这些是 diagnostics vocabulary，不是普通 UI vocabulary。

---

# 12. Confirmation UI

延续既有 Confirmation child state。

P1-E 增强信息层级：

```text
Action
Input
Reason
Risk indicator
Confirm / Cancel
```

例如：

```text
Delete 12 files?

Action
Delete files

Target
D:\Downloads

12 files will be permanently removed.

[Cancel]     [Confirm]
```

但：

> UI 不负责计算风险，也不能自行改变 ConfirmationRequired 状态。

---

# 13. Confirmation 防替换

必须继续维护：

```text
Confirmation
    ↓
same logical action
    ↓
fresh resolve
    ↓
execute
```

视觉上可以显示：

```text
Action changed while waiting
```

如果 re-resolve 后 identity 不一致，应直接拒绝执行，而不是更新 UI 后继续。

---

# 14. Workflow UI

P1-E 第一个重要新增部分是 Workflow。

建议不要把 Workflow 显示成传统复杂 DAG 编辑器。

v0.2 主要是：

```text
Run view
```

例如：

```text
Workflow: Organize Downloads

● Scan files              Succeeded
● Classify                 Succeeded
● Move files               Running
○ Verify                   Pending
○ Finish                   Pending
```

---

# 15. Workflow Step 状态

视觉：

```text
Pending
○

Running
◐

Succeeded
✓

Skipped
–

Failed
!

Paused
Ⅱ
```

但不要只靠颜色。

每个状态必须同时通过：

```text
icon
text
layout
```

区分。

这是可访问性要求。

---

# 16. Branch Visualization

P1-C 新增 branching。

UI 不需要画复杂 graph。

可以显示：

```text
Check file count

Condition
file_count > 100

✓ true
    → Compress

✗ false
    → Finish
```

当前 branch：

```text
Current path
```

其他路径：

```text
Not selected
```

这样比完整 DAG 更节省空间。

---

# 17. Workflow Failure

失败 step：

```text
● Move files
  Failed

  Reason:
  Capability denied

  Attempt:
  1 / 1
```

展开：

```text
Failure Details
Execution ID
Failure Class
Action
Provider
```

仍然遵守既有三级 diagnostics：

```text
Level 1
message + severity

Level 2
step / reason / attempt

Level 3
execution_id / failure_class
```

---

# 18. Agent UI

Agent 不创建：

```text
Agent Mode
```

建议作为 Workflow-style runtime panel。

例如：

```text
Agent: Organize Downloads

Goal
Organize large files

Turn 3 / 8

Observe        ✓
Plan           ✓
Execute        ◐
Replan         ○
```

下面：

```text
Recent actions
✓ Scan files
✓ Inspect results
◐ Move files
```

---

# 19. Agent Decision Display

不要展示模型 chain-of-thought。

应该展示：

```text
Plan summary
Proposal
Result
Next step
```

例如：

```text
Plan

1. Scan the selected folder
2. Group files by size
3. Move files larger than 1 GB

Proposed action
Scan folder
```

而不是：

```text
Thought:
I should...
Maybe...
Let's reason...
```

---

# 20. Agent Proposal UI

每个 Proposal 显示：

```text
Provider
Command
Action
Input summary
Status
```

例如：

```text
MCP · Calculator

calculate

expression = 123 * 456

Ready
```

注意：

```text
Proposal
```

不是：

```text
Authorized Action
```

UI 不应该暗示 Agent 已经“获准”。

---

# 21. Agent Replan

需要一个明确但简洁的状态：

```text
Execution failed
↓
Replanning…
```

之后：

```text
New observation
↓
New proposal
```

不要显示成：

```text
Retrying…
```

因为：

```text
Retry
≠
Replan
```

这是核心语义差异。

---

# 22. Agent Budget UI

建议顶部很轻量显示：

```text
Turn 3 / 8
Executions 5 / 16
```

接近限制时：

```text
Turn 7 / 8
```

显示 warning。

达到：

```text
Budget exhausted
```

进入 terminal state。

---

# 23. Agent Confirmation

Agent 请求危险 Action：

```text
Agent proposes:

Delete 12 files

[Review]
```

进入现有 Confirmation，而不是创建：

```text
AgentConfirmationMode
```

这样整个产品只有一套 confirmation semantics。

---

# 24. MCP / Runtime Visualization

用户不应该直接面对：

```text
RuntimeId
ProcessSession
McpSessionId
```

普通 UI 只需要：



# 25. Persistent Runtime 状态

可以提供轻量状态：

```text
MCP Calculator
● Connected
```

hover/details：

```text
Persistent runtime
Idle
Last used 8s ago
```

但是：

> **Persistent 不应该视觉上等同“更高权限”。**

不要使用：

```text

```

等词。

# 26. Session Reconnect

当：

```text
Runtime alive
Session invalid
```

显示：

```text
Reconnecting…
```

而：

```text
Runtime dead
```

显示：

```text
Starting…
```

这正好对应 P1-A/P1-B 两层状态。

# 28. Diagnostics 三层保持

### Level 1

普通用户：

```text
Something went wrong
```

### Level 2

开发/高级用户：

```text
Step failed
Reason
Attempt
```

### Level 3

诊断：

```text
Execution ID
Failure Class
Runtime
Session
Protocol
```

不要把 Level 3 默认暴露。

# 29. 键盘系统

P1-E 要把整个 UI 收敛成：

```text
Enter
Up / Down
Ctrl+Down
Esc
```

再补充：

```text
Ctrl+R
Ctrl+D
Ctrl+L
```

等诊断/辅助快捷键。

但所有 shortcut 必须：

```text
context-aware
```

不能全局硬编码。

---

# 30. Keyboard Focus Model

建议定义明确：

```rust id="focus"
pub enum FocusTarget {
    Search,
    Results,
    Actions,
    Confirmation,
    Workflow,
    Diagnostics,
}
```

禁止 UI 内部散落：

```text
bool focused
```

否则 Agent/Workflow 状态增加后很容易出现焦点错乱。

---

# 31. Esc 语义继续冻结

```text
Main
    Esc → close

Action
    Esc → Main

Confirmation
    Esc → Action

Workflow/Agent detail
    Esc → previous level
```

但：

```text
Running
```

不能因为普通 Esc 自动停止 Effect。

需要明确：

```text
Esc
→ close panel

Cancel
→ cancel run
```

这两个概念必须分开。

---

# 32. Loading

不要用无限旋转动画作为唯一状态。

显示：

```text
Searching…
Connecting…
Starting…
Planning…
Executing…
Reconnecting…
```

同时保留静态 fallback。

---

# 33. Animation

Slint 软件渲染环境下，动画必须克制。

只建议：

```text
150–200ms
```

用于：

```text
panel enter
selection highlight
status transition
```

不要：

```text
blur
heavy shadow animation
continuous pulse
large-scale transform
```

尤其不要让后台 Agent running 产生持续刷新 UI 的高频动画。

---

# 34. Refresh Budget

P1-E 应建立 UI update policy：

```text
User interaction
    → immediate

State transition
    → immediate

Progress
    → coalesced

Diagnostic logs
    → batched
```

不要：

```text
every runtime event
→ full UI rebuild
```

---

# 35. State Diff

建议 ViewModel 更新采用：

```text
old state
   ↓
diff
   ↓
minimal property update
```

而不是：

```text
AgentEvent
 ↓
recreate all components
```

这对于：

```text
Workflow
Agent
Diagnostics
```

都非常重要。

---

# 36. Large Workflow

几十个 step：

```text
50+
```

不能把整个 run 全部渲染到屏幕。

推荐：

```text
virtualized step list
```

或者至少：

```text
windowed rendering
```

但 MVP 级别暂时可以：

```text
max visible logical rows
```

进行裁剪。

---

# 37. Large Diagnostics

日志必须：

```text
bounded
paginated/windowed
```

不能：

```text
10 MB logs → Slint text component
```

---

# 38. Accessibility

P1-E 应加入：

```text
Keyboard-only
Focus visibility
Text contrast
No color-only status
Minimum hit target
Readable error messages
Screen-reader friendly semantic labels
```

其中你的产品本身就是 keyboard-first，因此：

> **任何核心功能都不能要求 mouse。**


# 42. Window Geometry

Launcher 类型应用需要重点处理：

```text
show
hide
reopen
screen change
DPI change
```

建议保存：

```text
last preferred placement
```

但不要让窗口配置直接进入核心 domain。

---

# 43. Multi-monitor

至少保证：

```text
current cursor monitor
```

或者：

```text
active foreground monitor
```

作为 popup placement 来源。

避免：

```text
launcher appears on monitor 1
when keyboard action occurred on monitor 3
```

---

# 44. Popup Placement

主窗口：

```text
center / cursor-aware
```

Action panel：

```text
same anchor
```

Confirmation：

```text
same visual context
```

不要切到另一块屏幕。

---

# 45. Error Presentation

错误必须分层：

```text
Recoverable
Actionable
Terminal
Internal
```

例如：

```text
MCP reconnecting
```

不是 error。

而：

```text
ProtocolViolation
```

才是 error。

用户不应该看到大量红色。

---

# 46. Toast

可以使用，但限制范围。

Toast 适合：

```text
Copied
Saved
Completed
Disconnected
```

不适合：

```text
Confirmation
Security denial
Workflow failure requiring action
```

这些需要进入对应 UI state。

---

# 47. Status Bar

建议 Main 底部：

```text
Ready
3 providers
```

MCP/Agent running 时：

```text

```

避免显示：

```text

```

# 48. Background Runtime Indicator

Persistent MCP：

```text
● 2 background services
```

这样既满足可观察性，又不会让 Runtime implementation details 污染普通 UI。

# 55. Performance Gate

P1-E 应正式加入：

```text
Startup
Popup show
Search response
Selection movement
Action panel open
Workflow transition
Agent state update
```

目标不是绝对微秒数字，而是：

```text
no perceptible lag
```

同时重点避免：

```text
LLM/network
blocking UI thread
```

# 56. UI Memory

你的产品定位本身强调 native / low-memory。

因此 P1-E 必须测：

```text
Cold startup RSS
Idle RSS
Main active RSS
Workflow active RSS
Agent active RSS
Diagnostics active RSS
```

同时检查：

```text
open/close popup 1000x
Action panel 1000x
Workflow panel 100x
Agent run 100x
```

是否：

```text
memory grows continuously
```

---

# 57. Event Leak Test

尤其：

```text
AgentRuntime
WorkflowRunner
RuntimeManager
```

都有 event subscriptions。

必须验证：

```text
open panel
close panel
reopen
```

不会造成：

```text
duplicate listeners
duplicate updates
```

例如：

```text
1 event
→ 1 UI update
```

而不是：

```text
1 event
→ 17 handlers
```

---

# 58. P1-E UI Architecture Guard

增加源码 guard：

```text id="guard"
launcher-ui
    ✗ launcher-mcp
    ✗ launcher-plugin-host
    ✗ launcher-runtime
    ✗ launcher-ai internals
```

UI 只能依赖：

```text
ViewModel / DTO / Commands
```

不能：

```text
use McpExecutor
use RuntimeManager
use ActionEngine internals
```

# 59. ViewModel Boundary

建议：

```text
Core
 ↓
UiSnapshot
 ↓
launcher-ui
```

例如：

```rust
pub struct UiSnapshot {
    pub mode: UiMode,
    pub results: Vec<ResultItem>,
    pub actions: Vec<ActionItem>,
    pub workflow: Option<WorkflowView>,
    pub agent: Option<AgentView>,
    pub diagnostics: Option<DiagnosticsView>,
}
```

# 79. P1-E 完成标准

P1-E 并不是“UI 更漂亮”就完成。

真正的完成标准是：

```text
功能状态
   ↓
Core semantic state
   ↓
ViewModel
   ↓
consistent UI presentation
   ↓
keyboard operation
   ↓
diagnostic visibility
```

整个链条没有第二套语义。

特别是：

```text
Agent
Workflow
MCP Session
Persistent Runtime
Confirmation
Failure
```

全部必须能够在 UI 中解释清楚，但**UI 不得因此获得任何额外权限**。

# 80. P1 总结

到 P1-E 完成后，整个 P1 的演进关系会非常清晰：

```text
P1-A
“进程是否继续存在？”
        ↓
Runtime persistence

P1-B
“进程上的协议会话是否仍然有效？”
        ↓
Protocol session persistence

P1-C
“确定性的工作流下一步走哪里？”
        ↓
Variables / Conditions / Branching

P1-D
“模型下一步建议做什么？”
        ↓
Bounded Agent Runtime

P1-E
“把以上状态安全、统一、可观察地呈现给用户”
        ↓
Production UI
```

最终仍然只允许这一条真正的执行路径：

```text
                    WHAT
                     │
          Workflow / Agent / User
                     │
                     ▼
              ActionProposal
                     │
                   RESOLVE
                     ▼
              ActionResolver
                     │
                 AUTHORIZE
                     ▼
               ActionEngine
                     │
                  EFFECT
                     ▼
             Executor / Runtime
```

**P1-E 不应该改变这条链，只应该把这条链的状态完整地呈现出来。**

这样 P1 就可以作为一个完整的产品能力闭环冻结：

> **Runtime 持久化 → Protocol Session → Workflow 控制流 → Agent 决策循环 → Production UI。**
