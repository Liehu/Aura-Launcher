# MVP4.4 P0-C — MCP Auth Foundation

P0-C 的边界继续保持非常窄：

> **只为 `StreamableHttpTransport` 增加认证能力和凭据安全边界，不改变 `McpExecutor`、`ActionEngine`、Workflow、AI、ActionProposal，也不让 Auth 模块获得 execution authority。**

当前 MCP `2026-07-28` 的授权修订重点包括：授权服务器返回并由客户端校验 `iss`、凭据与签发者绑定、DCR 正式转向 deprecated、CIMD 成为推荐注册方式，以及 OIDC/PKCE/refresh 等授权流程更加明确。([Model Context Protocol Blog][1])

因此 P0-C 最终架构应是：

```text
                    McpExecutor
                         │
                  McpTransport
                         │
              ┌──────────┴──────────┐
              │                     │
           stdio                  HTTP
              │                     │
      ProcessSession       StreamableHttpTransport
                                      │
                                 AuthProvider
                                      │
                              Credential Store
                                      │
                                 HTTP Request
```

而不是：

```text
McpExecutor
    ↓
Auth
    ↓
ActionEngine            ❌
```

### 本阶段实现

```text
✅ HTTP 401/403 auth boundary
✅ OAuth authorization-code + PKCE foundation
✅ Protected Resource Metadata
✅ Authorization Server Metadata discovery
✅ issuer validation
✅ credential ↔ issuer binding
✅ token storage interface
✅ Windows credential-store implementation
✅ token expiry
✅ refresh foundation
✅ CIMD foundation
✅ explicit legacy DCR compatibility
✅ auth-aware HTTP request
```

### 本阶段不实现

```text
❌ Action/Workflow auth semantics
❌ MCP capability grants
❌ Agent authority
❌ AI auth decision
❌ MCP tool-specific permission
❌ Task auth
❌ MCP Apps auth
❌ custom identity provider protocol
❌ embedding OAuth secrets in config.toml
```

# 2. 新 crate / module

我建议**不要新增 `launcher-auth` crate**。

Auth 是 MCP Transport 的协议能力，不应该成为 Launcher 全局身份系统。

保持：

```text
launcher-mcp/
├── auth/
│   ├── mod.rs
│   ├── types.rs
│   ├── discovery.rs
│   ├── oauth.rs
│   ├── pkce.rs
│   ├── credential.rs
│   ├── storage.rs
│   ├── cimd.rs
│   └── policy.rs
│
└── transport/
    └── streamable_http.rs
```

依赖仍：

```text
launcher-mcp
    ↓
auth
```

而：

```text
launcher-domain
launcher-action
launcher-workflow
launcher-core
launcher-ai
```

全部不知道 OAuth。

# 3. Auth 的职责边界

`AuthProvider` 只负责：

```text
401
 ↓
discover authorization metadata
 ↓
obtain credential
 ↓
attach Authorization header
 ↓
refresh when expired
```

不负责：

```text
Capability
Confirmation
Action resolution
Workflow
Effect
```

核心原则：

```text
Authentication
    ≠
Authorization inside Launcher
```

更准确：

```text
OAuth
    = “我是谁 / 我能否访问这个 HTTP resource server”

Launcher Capability
    = “Launcher 是否允许这个 Action”
```

两个 authorization domains 必须分开。

# 4. 两层 Authorization

P0-C 后实际上存在：

```text
                 Action Execution
                       │
            ┌──────────┴──────────┐
            │                     │
       Launcher Policy        Remote MCP Auth
            │                     │
     mcp.invoke allowed?     access token valid?
            │                     │
            └──────────┬──────────┘
                       │
                     Effect
```

必须满足：

```text
Remote auth success
    ≠
Launcher capability grant
```

例如：

```text
OAuth token valid
+
mcp.invoke denied
```

最终仍然：

```text
CapabilityDenied
0 executor calls
```

反过来也一样：

```text
mcp.invoke allowed
+
HTTP 401
```

只能：

```text
AuthenticationRequired
```

不能变成 capability denial。

# 5. Credential Model

建议：

```rust
struct Credential {
    access_token: SecretString,
    refresh_token: Option<SecretString>,
    issuer: Url,
    client_id: String,
    expires_at: Option<SystemTime>,
    scopes: Vec<String>,
}
```

其中最重要：

```text

```

必须是绑定字段。

2026-07-28 明确要求客户端把凭据绑定到签发它的 issuer，不能跨 authorization server 重用凭据。([Model Context Protocol Blog][1])

# 6. Credential Identity

不要把：

```text
server_id
```

当作 credential identity。

一个 MCP Server：

```text
mcp:github
```

可能未来迁移到新的 Authorization Server。

所以：

```text
credential key
    =
resource/server identity
+
issuer
+
client_id
```

建议内部 key：

```text
CredentialKey {
    server_id,
    resource_origin,
    issuer,
    client_id,
}
```

而不是：

```text
CredentialKey = server_id
```

# 10. Protected Resource Metadata

Auth discovery 建议优先支持：

```text
/.well-known/oauth-protected-resource
```

获取：

```text
resource
authorization_servers
scopes_supported
```

并建立：

```text
ProtectedResourceMetadata
```

需要注意：

> metadata 是服务器声明的数据，不是 authority。

尤其：

```text
authorization_servers
```

只能作为 discovery input，之后仍必须做 issuer validation。

# 12. Issuer Validation

这是 P0-C 的 **S0/S1 级安全点**。

授权服务器返回：

```text
iss = https://auth.example.com
```

必须验证：

```text
discovered issuer
==
returned issuer
```

否则拒绝。

MCP 2026-07-28 明确要求客户端验证 OAuth authorization response 中的 `iss`，用于防止 authorization-server mix-up attack。([Model Context Protocol Blog][1])

错误：

```text
discovered issuer:
https://auth.example.com

callback iss:
https://evil.example.com
```

结果：

```text
Protocol/Auth Error
NO token exchange
NO credential storage
```

# 14. Credential Issuer Binding

例如已有：

```text

```

```text

```

```text

```

```text

      ↓
```

```text
      +
```

```text

```

除非某个兼容 server 明确强制，否则默认只：

```text

```

# 18. CIMD

2026-07-28 已正式把 **Client ID Metadata Documents (CIMD)** 作为 DCR 的替代方向，并将 DCR 标记为 deprecated；DCR 仍可用于 backward compatibility。([Model Context Protocol Blog][1])

因此 P0-C 建议：

```text

├── CIMD preferred
└── DCR compatibility
```

```toml

```

不要：

```toml
client_id = ...
client_secret = ...
```

长期凭据。

但必须明确：

```text
requires_auth
    = discovery metadata
```

不是：

```text
authorized = true
```

甚至我建议 v0.2 初版**不把 `requires_auth` 暴露给 AI Planner**，避免模型把它错误理解为权限状态。

# 49. 一个重要的新不变量

### `INV-AUTH-007`

> **A valid remote credential does not grant Launcher execution authority.**

### `INV-AUTH-008`

> **Launcher execution authority does not grant MCP credentials.**

这两条建立双向隔离：

```text
MCP OAuth
    X→ Launcher capability

Launcher capability
    X→ OAuth credential
```

# 52. P0-C 的真正成功标准

不是：

> “MCP 支持 OAuth”。

而是：

```text
OAuth
   ↓
只解决 Remote MCP authentication
```

同时：

```text
ActionResolver
   ↓
继续决定 Launcher capability

ActionEngine
   ↓
继续决定 Effect

Workflow
   ↓
继续决定 retry / pause / re-resolve

AI
   ↓
继续只产生 Proposal
```

因此最终依然满足：

```text
DATA
 ↓
PROPOSAL
 ↓
AUTHORITY WALL
 ↓
Resolver
 ↓
Engine
 ↓
Effect
 ↓
Authenticated MCP Transport
```

**Auth 位于 Effect 执行链的最底层 transport boundary，而不是 authority wall 上方。**

还有一个现实兼容性约束需要保留：当前 MCP 官方 `2026-07-28` 已把 CIMD 作为 DCR 的长期替代方向，同时仍允许 DCR 作为兼容路径；官方 SDK 目前也以 opt-in 方式提供这些 auth hardening，而不是把所有旧版本协议自动视为现代 auth。([Model Context Protocol Blog][1])

因此 P0-C 建议的正式顺序是：

```text
P0-C.1  Auth types / CredentialStore
    ↓
P0-C.2  Protected Resource + AS discovery
    ↓
P0-C.3  issuer validation + credential binding
    ↓
P0-C.4  PKCE + loopback OAuth
    ↓
P0-C.5  CIMD + DCR fallback
    ↓
P0-C.6  token / refresh
    ↓
P0-C.7  StreamableHttpTransport integration
    ↓
P0-C.8  security / secret / mix-up matrix
    ↓
P0-C.9  real authenticated MCP E2E
    ↓
P0-C.10 regression gate
```

这一步完成后，**P0-D LLM Planner** 就可以在一个同时支持本地 stdio、远程 HTTP、匿名 HTTP、OAuth HTTP 的统一 MCP capability substrate 上继续，而 Planner 本身仍然完全不需要知道认证是如何发生的。
