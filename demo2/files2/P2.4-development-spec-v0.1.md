## 0. 文档目的

P2.4 不是继续堆积用户功能的普通开发批次，而是 **Launcher 2.x 的 Foundation Closure**。

本批次只处理 1.0 已存在但尚未达到长期平台化要求的基础能力：

```text
Application Catalog
File Index Maintenance
Plugin Registry / Recovery
Plugin SDK / CLI
Plugin Development Diagnostics

        ↓

2.x Search / Workflow / AI / Platform
```

P2.4 **禁止提前实现**：Search Intent、Personal Ranking、Agent Productization、Workflow DAG、Marketplace、Cloud Sync 等 P2.5+ 能力。

### 0.1 主要依据

本规范基于：

- `demo2/files2/01-design-spec-v0.1.md`
- `demo2/files2/02-agentic-coding-development-spec-v0.1.md`
- `demo2/files2/03-test-plan-v0.1.md`
- `docs/P2.3-A-ARCHITECTURE-BASELINE.md`
- `docs/P2-CROSS-CUTTING-CONTRACTS.md`
- `docs/P2.3-C-RELIABILITY.md`
- `docs/KNOWN-ISSUES.md`
- Post-1.0 Roadmap

原始设计要求保持 Provider / Action / Indexer / Plugin 的职责边界，并要求 Agentic Coding 遵守 Inspect → Plan → Implement → Test → Review → Report 流程。当前仓库 AGENTS.md 同时要求所有公共 API 有测试、性能敏感变更必须 benchmark、并禁止绕过既有契约。

# 1. P2.4 目标与完成定义

## 1.1 主目标

P2.4 完成后必须满足：

```text
1. Application Catalog 可持续维护
2. File Index 可 self-healing
3. Plugin lifecycle state 可安全恢复
4. 第三方开发者可从 SDK/CLI 完成插件生命周期
5. 插件开发故障可诊断
6. 所有新增能力不破坏 1.0 Authority / Generation / Identity 契约
7. 所有能力拥有自动化 Gate
```

## 1.2 非目标

P2.4 不做：

```text
- Query Intent
- AI Query Understanding
- Personal Ranking
- Ranking Explainability
- Search Contract v2 的完整重构
- Workflow Editor
- DAG / Parallel / Join
- Durable Workflow
- Agent Productization
- Plugin Marketplace
- Cloud Sync
- Multi-device
- Enterprise
```

## 1.3 完成状态模型

继续使用：

| 状态 | 含义 |
|---|---|
| Closed | 能力、测试、Gate、文档全部完成 |
| Core Slice | 核心能力已经工作，但仍存在明确生命周期/体验缺口 |
| Experimental | 技术验证，不作为正式产品承诺 |
| Planned | 已批准但未实现 |
| Deferred | 明确推迟 |
| Rejected | 明确不做 |

P2.4 每个 Batch 必须在验收表中给出最终状态，不允许以“代码已写”作为完成条件。

# 2. Architecture Guard

P2.4 不改变以下已冻结架构：

```text
Producer
    ↓
ActionProposal / ActionDescriptor
    ↓
ActionResolver
    ↓
launcher-action::validate()
    ↓
launcher-action::execute()
    ↓
Effect
```

Search / Cache / Favorites / Context / Icon 只有信号权；Plugin / MCP / AI metadata 永远是 DATA，不能获得 authority。Authority、Generation、Identity、Lifecycle 的横向契约继续由 `P2-CROSS-CUTTING-CONTRACTS.md` 统一登记。 

### 2.1 Architecture Red Lines

任何 P2.4 Agent 不得：

- 通过重新实现 Provider 绕过现有 Core。
- 在 `launcher-domain` 引入 OS / IO。
- 在 UI 线程执行文件扫描、插件等待、数据库大操作。
- 让 Plugin SDK 依赖 `launcher-plugin-host` / `launcher-core` 私有类型。
- 在上层复制 runtime dispatch。
- 直接执行 Effect。
- 修改 Plugin / Command / Action v0.1 契约而不增加 ADR。
- 用时间戳代替 Generation。
- 将 RuntimeId、ExecutionId、ProtocolSessionId 混用。
- 添加无界缓存。

当前 AGENTS.md 已明确：插件协议修改必须通过 Canonical Reference Plugin + Contract Test Kit；runtime dispatch 只能位于 `launcher-plugin-host::runtime::resolve_launch`；公共 API、并发与性能敏感修改均须有相应测试/说明。

# 4. P2.4-A — Persistent Application Catalog 2.0

## 4.1 当前基线

1.0 已经存在多源 application discovery，并已将聚合结果写入 `catalog.db`；`CatalogStore` 已具备 generation 与原子 reconcile。当前仍属于 persistence layer，尚未完全成为长期 authoritative Search source。 

因此 P2.4-A 的任务不是重写 Discovery，而是完成：

```text
Discovery
  ↓
ApplicationCatalogCoordinator
  ↓
Persistent Catalog
  ↓
CatalogProvider
  ↓
Search
```

## 4.2 Discovery Source

必须支持并保持源隔离：

```text
Start Menu
Registry / Uninstall
Packaged / AUMID
App Paths
Configured Portable Roots
```

每个 source 必须产出统一中间结构：

```rust
ApplicationObservation {
    source_id,
    source_kind,
    identity_hint,
    display_name,
    launch_target,
    package_identity,
    aumid,
    app_path,
    icon_identity,
    metadata,
    observed_at,
}
```

> 注意：这是设计模型，不得直接把 `ApplicationObservation` 当作可执行 Action。

## 4.3 Canonical Application Identity

P2.4-A 必须冻结 Application Identity v1：

```text
Win32 executable
    → normalized executable path

Packaged App
    → package identity + AUMID

Portable App
    → normalized executable path

Unknown
    → source-qualified identity
```

要求：

1. 同一 application 多 source 必须归并。
2. source metadata 不得被丢弃。
3. identity 解析必须是纯函数。
4. identity 不依赖当前磁盘读取结果。
5. identity 不得包含 version 作为主 key。

现有 Search Identity v1 已采用 normalized target path 归并 File / Folder / Application，同时把 command/plugin identity 保持为 `(provider_id, id)`。P2.4-A 应延续这一原则，而不是另起一套 identity 规则。 

## 4.4 Catalog Record

建议冻结：

```text
application
├── identity_key          PK
├── kind
├── display_name
├── normalized_target
├── package_family
├── aumid
├── version
├── publisher
├── icon_identity
├── status
├── first_seen_at
├── last_seen_at
├── updated_at
└── generation
```

source 独立：

```text
application_source
├── application_id
├── source_kind
├── source_key
├── observed_name
├── observed_target
├── metadata_json
└── last_seen_at
```

禁止把所有来源数据压缩进一行 JSON 后失去可查询身份关系。

## 4.5 Lifecycle

状态：

```text
Discovered
  ↓
Validated
  ↓
Active
  ├── Stale
  ├── Broken
  └── Removed
```

规则：

- `Stale` ≠ `Removed`。
- 一次 source 暂时失败不得立即删除 application。
- 所有 source 消失后才进入 Removed candidate。
- 连续恢复后可以从 Stale → Active。
- Broken 表示 identity 尚在，但 launch target 不可用。

## 4.6 Reconciliation

采用：

```text
Observe source snapshots
        ↓
Normalize
        ↓
Resolve identity
        ↓
Compute diff
        ↓
Atomic transaction
        ↓
Commit
        ↓
CatalogGeneration + 1
```

失败：

```text
no commit
no generation bump
no partial visibility
```

## 4.7 Search Integration

P2.4-A 结束时必须有：

```text
CatalogProvider
```

它直接读取持久 Catalog snapshot，不在每次 query 时重新扫描 Start Menu / Registry。

查询只允许：

```text
Catalog snapshot
  ↓
Query
  ↓
Command projection
```

而 Discovery 运行于 reconcile lifecycle。

## 4.8 Gate

必须增加：

```text
CAT-001 same exe across sources → one identity
CAT-002 packaged AUMID stable
CAT-003 portable app identity
CAT-004 stale is not removed
CAT-005 broken launch target
CAT-006 source disappears / returns
CAT-007 atomic reconcile
CAT-008 generation only after commit
CAT-009 catalog provider does not rescan source
CAT-010 catalog corruption recovery
CAT-011 source metadata preserved
CAT-012 deterministic ordering
```

性能：

```text
catalog query P95 <= existing app-search budget
reconcile N=2,000 applications within defined baseline
startup must not block on discovery reconciliation
```

# 5. P2.4-B — Advanced Index Maintenance 2.0

## 5.1 当前基线

Index 已经存在 incremental batch、watcher、DirtyRoot、有界队列、recovery rescan 与 IndexGeneration；可靠性批次也已经覆盖 corrupt DB recovery。 

P2.4-B 的目标是把它从“具备增量能力”提升到：

> **长期运行的 self-healing filesystem index**。

## 5.2 Root State

每个 watched root 维护：

```text
RootState
├── configured
├── present
├── watching
├── dirty
├── recovering
├── unavailable
├── last_scan
├── last_event
├── last_error
├── indexed_count
└── generation
```

## 5.3 Root Lifecycle

```text
Configured
  ↓
Present
  ↓
Watching
  ├── Dirty
  │    ↓
  │  Reconcile
  │    ↓
  │  Watching
  │
  └── Missing
       ↓
   Unavailable
       ↓
   Reappeared
       ↓
    Reconcile
       ↓
    Watching
```

要求：

> Root 暂时消失不能触发全盘 rebuild。

## 5.4 Watcher Recovery

当 `ReadDirectoryChangesW` / watcher 发生：

```text
overflow
invalid handle
access denied
unexpected close
root rename/replacement
```

必须：

```text
Event
 ↓
classify
 ↓
DirtyRoot
 ↓
bounded rescan
 ↓
commit
 ↓
clear dirty
```

绝不允许：

```text
Watcher failure
 ↓
DELETE all index
 ↓
full rebuild
```

除非进入明确的 manual/full-rebuild recovery mode。

## 5.5 Event Semantics

继续冻结：

```text
filesystem event = hint
filesystem stat = truth
```

所有 mutation 必须经过：

```text
Event
 ↓
resolve candidate
 ↓
re-stat
 ↓
VerifiedChange
 ↓
apply_batch
```

## 5.6 Generation Cutover

严格：

```text
Before commit: G
After commit : G+1
Failure      : G
```

一次 batch 只能有一次 generation bump。

## 5.7 Maintenance

增加：

```text
periodic health check
index statistics
orphan detection
stale root report
queue depth metrics
last successful reconciliation
```

## 5.8 Compaction

P2.4 不做激进 SQLite VACUUM 自动化。

只允许：

```text
size threshold
fragmentation threshold
idle-only maintenance
```

并必须 benchmark。

默认关闭自动 VACUUM；需要通过显式 maintenance policy 开启。

## 5.9 Gate

必须新增：

```text
IDX-001 watcher overflow → dirty root
IDX-002 dirty root → bounded rescan
IDX-003 root disappears
IDX-004 root reappears
IDX-005 watcher re-registration
IDX-006 reparse point not followed
IDX-007 event/stats mismatch recovery
IDX-008 generation atomicity
IDX-009 search remains queryable during maintenance
IDX-010 long-running watcher stability
IDX-011 queue bound
IDX-012 index statistics consistency
IDX-013 crash during reconcile
IDX-014 restart after watcher failure
```

Soak：

```text
>= 30 min
filesystem mutation workload
watcher disconnect/reconnect
multiple roots
no monotonically increasing queue/memory/handle count
```

# 6. P2.4-C — Plugin Control Plane 2.0

## 6.1 当前基线

Plugin Registry 已经支持 enabled/quarantined/failure persistence、backup、corrupt-file quarantine/restore 与 capability records。 

因此 P2.4-C 不重新设计 Registry，而是正式冻结：

```text
Plugin Identity
Plugin Installation Revision
Lifecycle State
Trust State
Capability Decision
Recovery Policy
```

## 6.2 Plugin State Model

建议拆成：

```text
PluginRecord
├── plugin_id
├── instance_id
├── version
├── api_version
├── runtime_type
├── status
├── trust_state
├── installed_at
├── updated_at
└── last_health
```

状态：

```text
Unknown
Discovered
Validated
Disabled
Ready
Quarantined
Broken
```

其中：

```text
status ≠ trust_state
```

例如：

```text
Trusted + Disabled
Trusted + Quarantined
Unknown + Disabled
Known + Broken
```

## 6.3 Trust Model

P2.4 不实现 Marketplace 签名体系，但必须把 trust state 数据模型冻结：

```text
Unknown
Known
Trusted
Rejected
```

任何 trust 状态都不能直接绕过 ActionResolver。

## 6.4 Capability Decision

Manifest：

```text
requested capabilities
```

Registry：

```text
requested
approved
rejected
unset
```

默认：

```text
unset = denied
```

Manifest 不能自行把 `unset` 变为 approved。

## 6.5 Recovery Policy

恢复优先级：

```text
1. last known good database
2. backup
3. quarantined corrupt artifact
4. clean rebuild
```

安全策略：

> 任何无法确认旧安全决策的恢复，都不得自动提升插件权限。

这点需要优先于“启动一定成功”。

## 6.6 Failure Window

Quarantine 不应只依赖无限累计计数。P2.4 应冻结：

```text
failure_count
failure_window
cooldown
quarantine_threshold
manual_clear
```

例如：

```text
3 protocol failures / 10 min
→ quarantine
```

业务错误不进入 protocol failure count。

## 6.7 Plugin Diagnostics Snapshot

每次 Plugin failure 应能够生成：

```text
PluginDiagnostic
├── plugin_id
├── instance_id
├── execution_id (when execution exists)
├── runtime_id
├── protocol_session_id
├── method
├── elapsed_ms
├── failure_class
├── exit_code
├── stderr_tail
├── frame_size
├── output_count
├── capability_state
└── timestamp
```

必须 bounded。

## 6.8 Gate

```text
PLG-001 disable survives restart
PLG-002 quarantine survives restart
PLG-003 capability deny survives restart
PLG-004 corrupt registry restores security state
PLG-005 backup itself is never treated as authority
PLG-006 repeated protocol failure quarantines
PLG-007 business failure does not quarantine
PLG-008 quarantine blocks discovery
PLG-009 quarantine blocks execution
PLG-010 manual re-enable does not grant capability
PLG-011 unknown plugin defaults safe
PLG-012 diagnostic snapshot bounded
```

# 7. P2.4-D — Plugin SDK / CLI

## 7.1 目标

从：

```text
“Host 可以运行插件”
```

升级为：

```text
“第三方可以独立开发、验证、打包、安装插件”
```

Roadmap 已将 SDK / CLI 定义为 P2.4 高优先级能力。 

## 7.2 SDK 层级

### Rust

```text
launcher-plugin-api
```

只暴露：

```text
Manifest
Request
Response
Command
Action descriptor
serve()
```

### Python

```text
plugins/python/launcher_plugin.py
```

只暴露稳定 plugin-facing API。

不得暴露：

```text
launcher-plugin-host
launcher-core
launcher-runtime
```

## 7.3 CLI

建议命令：

```text
launcher-plugin init <id>
launcher-plugin validate
launcher-plugin build
launcher-plugin package
launcher-plugin install <package>
launcher-plugin uninstall <id>
launcher-plugin run
launcher-plugin inspect <package|manifest>
launcher-plugin logs
```

## 7.4 Project Layout

标准 Rust：

```text
my-plugin/
├── plugin.json
├── Cargo.toml
├── src/
│   └── main.rs
├── tests/
│   └── contract.rs
├── README.md
└── dist/
```

Python：

```text
my-plugin/
├── plugin.json
├── main.py
├── requirements.txt
├── tests/
└── README.md
```

## 7.5 Validate

`validate` 必须做：

```text
manifest schema
id syntax
api_version
runtime type
executable/script existence
capability syntax
timeout range
idle timeout
package layout
```

不得在 validate 阶段执行插件代码。

## 7.6 Build

Build 只负责生成可运行 artifact。

不得隐式 install。

## 7.7 Package

建议生成：

```text
<plugin-id>-<version>.nlplugin
```

P2.4 可以使用 zip container，但必须冻结 manifest 与 package layout。

## 7.8 Install

Install pipeline：

```text
Input
 ↓
Validate
 ↓
Stage
 ↓
Conflict check
 ↓
Activate
 ↓
Health check
 ↓
Registry update
```

失败：

```text
rollback
```

安装过程不得直接修改 active plugin tree 后再失败退出。

## 7.9 Run

开发态运行必须支持：

```text
launcher-plugin run
```

语义：

- stdout 只用于 protocol frame。
- diagnostics 进入 stderr / log sink。
- 支持环境变量注入。
- 支持指定 launcher executable。
- 支持 test query。

## 7.10 Contract Test

CLI 初始化项目必须能自动生成：

```text
contract test template
```

并支持：

```text
launcher-plugin validate
launcher-plugin test-contract
```

最终必须通过已有 Plugin Contract Test Kit。

```text
spawn
```

```text
timestamp

method
```

# 9. P2.4 Cross-cutting Contracts

## 9.1 ID

P2.4 新增 ID 前必须登记到 `P2-CROSS-CUTTING-CONTRACTS.md`。

允许新增：

```text
CatalogEntryId
ApplicationObservationId
PluginDiagnosticId
PackageArtifactId
```

禁止：

```text
将 CatalogGeneration 当 ID
将 RuntimeId 当 PluginInstanceId
将 ExecutionId 当 DiagnosticId
```

## 9.2 Generation

P2.4 新增：

```text
CatalogGeneration
RootMaintenanceGeneration (仅在确有需要时)
```

但必须明确：

```text
Generation = committed data version
```

## 9.3 Cache

所有新 cache 必须定义：

```text
key
max entries
max bytes
TTL / invalidation
owning generation
```

默认：

```text
unbounded = prohibited
```

## 9.4 Authority

P2.4 所有 CLI、catalog、diagnostics 都只能操作：

```text
data / lifecycle / diagnostics
```

不能创建：

```text
authority
capability grant
confirmed effect
```

# 10. Data Model Changes

```text
catalog.db
├── catalog_meta
├── application
├── application_source
└── catalog_events (bounded diagnostics / optional)

index.db
├── files
├── index_meta
├── history
├── index_roots
└── maintenance_stats

plugins.db
├── plugins
├── plugin_instances
├── plugin_capabilities
├── plugin_trust
├── plugin_diagnostics
└── plugin_meta
```

所有 schema 修改必须：

```text
migration
 ↓
backward compatibility decision
 ↓
test
 ↓
corruption recovery test
```

不得直接 `DROP TABLE` 后依赖重建掩盖 migration 错误。
