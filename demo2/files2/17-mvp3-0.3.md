# **MVP3.0：通过，Command/Action Contract v0.1 正式冻结**

而且这次与前面的 Plugin Protocol Freeze 不同——现在已经完成了从**协议层**到**领域执行层**的第一次闭环：

```text
Plugin
  │
  ▼
Command
  │
  ├── Context eligibility
  │
  └── ActionDescriptor
           │
           ▼
     ActionResolver
           │
      ┌────┴────┐
      ▼         ▼
   Hidden    Disabled
                │
             Ready
                │
                ▼
        ResolvedAction
                │
                ▼
          ActionEngine
                │
                ▼
              Effect
```

这套结构现在已经值得作为后续 AI / Workflow / MCP 的共同基础，而不是临时 MVP 模型。



你在 ADR-0011 里把这个作为 INV-033 固化，是正确的。

# 6. Capability monotonicity 现在也真正落到了执行边界

你现在形成的是：

```text
Manifest
    ↓
Requested capability upper bound
    ↓
Action.requires
    ↓
must be subset
    ↓
Granted
    ↓
Enforced
```

即：

```text
Action.requires ⊆ Manifest.capabilities
```

这个非常重要。

它意味着 Action 无权扩大插件权限。

以后 AI 生成：

```text
requires:
    shell.execute
```

也是一样：

```text
Resolver
    ↓
capability check
```

而不会因为“AI 说需要”就临时提升权限。

# 7. `requires_context` 与 Capability 的正交性也已经正确

现在：

```text id="qod5yy"
requires_context
    = eligibility
```

而：

```text id="z9h3s2"
requires
    = permission
```

这两个概念不要再合并。

例如：

```text
Open Terminal Here

    folder

    shell.execute
```

实际就是：

```text
当前有 folder？
    ↓
Yes

插件有 shell.execute？
    ↓
Yes

用户授权？
    ↓
Yes

→ Ready
```

而不是把这些条件塞进一个 permission system。

这个结构以后做 Context-aware AI Action 会非常有价值。

# 10. 另一个要明确的边界：Action Resolution 是一次性的，还是执行时重新 resolve？

这个问题现在最好写进契约。

例如：

```text
t0:
Command generated
```

```text
t1:
ActionResolver
```

```text
t2:
Action Panel displayed
```

```text
t3:
Enter
```

如果 capability / context 在 t2→t3 发生变化：

```text
Explorer changed
User revoked permission
Clipboard state changed
```

应该：

### 推荐模型

```text
displayed action
    ↓
ResolvedAction
```

但真正 Effect 执行前：

```text
ActionEngine
    ↓
final safety validation
```

或者明确：

> `ResolvedAction` 已经包含执行所需的全部不可变条件，ActionEngine 不再重新解释 Descriptor。

我更倾向：

```text
Descriptor
   ↓
Resolve at execution boundary
   ↓
ResolvedAction
   ↓
Execute immediately
```

而 UI 只保存：

```text
command_id
action_id
```

到 Enter 时重新 resolve。

这样不会出现：

```text
UI 显示 5 秒后
Context 已变
Action 仍拿旧 Context 执行
```

这个和你之前 `ContextSnapshot` 的 Session 生命周期正好相关。

## 结论

**MVP3.0 和两份 v0.1 Contract 可以正式冻结。**

你这次没有把未来的 UI Schema、`plugin.*` RPC、Workflow、AI、MCP 提前塞进来，而是把真正必须稳定的几个东西冻结：

```text
Command Identity
Action Identity
Action Type
Provider Authority
Capability Monotonicity
Context Eligibility
Action Resolution
ResolvedAction
Effect Boundary
```

这正是正确的冻结粒度。

现在最有价值的下一步不是继续设计协议，而是做：

```text
MVP3.1
Native Action Panel
        ↓
calculator-plus E2E
        ↓
Command/Action Contract Test Kit
        ↓
真实用户交互验证
```

**等 Native Action UI 跑通以后，再决定 UI Schema 是否真的有必要；等真实插件出现复杂 Action 后，再决定 `plugin.*` RPC 是否值得进入 v0.1.x。**

这样你的架构演进会一直保持“用真实需求推动抽象”，而不是为了预想中的 AI/Workflow/插件生态提前把协议做复杂。
