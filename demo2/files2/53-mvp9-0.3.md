# MVP4.4 P0-A — RuntimeSupervisor

进入 P0-A。这里建议把它定义成一次**外部进程运行时基础设施重构**，而不是新功能开发。

核心验收保持不变：

> PluginBroker 和 McpExecutor 共享进程生命周期基础设施，但不共享协议语义、授权语义或执行权限。

---

## 1. P0-A 冻结目标

```text
PluginBroker ─────┐
                  │
McpExecutor ──────┤
                  ▼
          launcher-runtime
                  │
          ProcessSupervisor
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
      Spawn       I/O      Reap/Kill
        │         │         │
        └─────────┼─────────┘
                  ▼
              OS Process
```

P0-A 完成后：

```text
PluginBroker
    = Plugin protocol + plugin lifecycle policy

McpExecutor
    = MCP protocol + MCP execution policy

launcher-runtime
    = external process mechanics
```

---

# 2. 第一原则：Runtime 不获得 Authority

`launcher-runtime` 不能知道：

```text
ActionProposal
ActionResolver
ActionEngine
Effect
Capability
Confirmation
Workflow
MCP
Plugin
```

它只能处理：

```text
LaunchSpec
RuntimeHandle
RuntimeId
stdin/stdout/stderr
timeout
process lifecycle
```

因此：

```text
ActionEngine
    ↓
Effect
    ↓
Executor
    ↓
launcher-runtime
```

而不是：

```text
launcher-runtime
    ↓
决定这个 process 是否允许执行
```

| `error.rs`      | runtime-level errors                 |
| `lib.rs`        | public API                           |

# 4. 核心类型

建议先冻结这几个，不要继续扩大。

```rust
pub struct RuntimeId(String);

pub struct LaunchSpec {
    pub program: PathBuf,
    pub args: Vec<OsString>,
    pub env: Vec<(OsString, OsString)>,
    pub working_dir: Option<PathBuf>,
}

pub struct RuntimeLimits {
    pub startup_timeout: Duration,
    pub io_timeout: Duration,
    pub shutdown_grace: Duration,
    pub max_stdout_bytes: usize,
    pub max_stderr_bytes: usize,
}

pub struct RuntimeHandle {
    pub id: RuntimeId,
}
```

# 5. RuntimeId 与 ExecutionId

必须继续分开：

```text
RuntimeId
    = 一个实际运行实例

ExecutionId
    = 一次 Effect execution attempt
```

例如：

```text
Runtime r-10
    ├── execution e-100
    ├── execution e-101
    └── execution e-102
```

Ephemeral：

```text
r-11 → e-103 → stopped
r-12 → e-104 → stopped
```

不要让 RuntimeSupervisor 生成：

```text
e-xxx
```

### `execution_id` owner

仍然是：

```text
caller / execution orchestrator
```

Runtime 只能接收 correlation metadata，不能铸造新的 execution ID。

这可以直接成为：

```text
RT-SEC-001
```

---

# 6. Lifecycle

统一为：

```text
Created
   ↓
Starting
   ↓
Running
   ↓
Stopping
   ↓
Stopped
```

异常：

```text
Running
   ↓
Crashed
   ↓
Stopped
```

建议不要加入：

```text
Authorized
Confirmed
ExecutingAction
McpReady
PluginReady
```

这些都不是 Runtime concern。

---

# 7. LaunchSpec 是最重要的安全边界之一

建议：

```rust
pub struct LaunchSpec {
    pub program: PathBuf,
    pub args: Vec<OsString>,
    pub env: Vec<(OsString, OsString)>,
    pub working_dir: Option<PathBuf>,
}
```

注意：

### 不要

```rust
pub struct LaunchSpec {
    pub capability: Capability,
    pub effect: Effect,
    pub provider_id: ProviderId,
}
```

这样会把 authority 混进基础设施。

---

# 8. Environment 策略

当前 P0-A 不建议设计复杂环境继承策略。

默认：

```text
inherit environment
```

但要允许 executor 显式覆盖：

```text
env
```

未来如果需要：

```text
clear_env
safe_env
credential_env
```

再增加。

特别不要由 RuntimeSupervisor 自动注入：

```text
PATH
TOKEN
AUTHORIZATION
MCP_SECRET
```

---

# 9. Windows Job Object

你现有的：

```text
CREATE_SUSPENDED
        ↓
AssignProcessToJobObject
        ↓
ResumeThread
```

正式迁移到：

```text
launcher-runtime::windows
```

启动流程：

```text
CreateProcess(CREATE_SUSPENDED)
        ↓
CreateJobObject
        ↓
AssignProcessToJobObject
        ↓
ResumeThread
```

关键是：

> **从 Runtime 第一个时刻开始就进入 Job Object。**

不要：

```text
CreateProcess
    ↓
child starts
    ↓
later assign Job
```

否则存在 process tree 在加入 Job 之前脱离控制的窗口。

---

# 10. Job Object cleanup

停止：

```text
RuntimeHandle
    ↓
TerminateJobObject
    ↓
Wait
    ↓
reap
```

不能只：

```text
child.kill()
```

因为：

```text
root process
   └── child
       └── grandchild
```

可能继续存在。

---

# 11. IO 模型

建议 Runtime 层只提供：

```text
stdin
stdout
stderr
```

不解析：

```text
JSON
JSON-RPC
NDJSON
MCP
Plugin protocol
```

结构：

```text
                    Runtime
                       │
              ┌────────┼────────┐
              ▼        ▼        ▼
            stdin    stdout    stderr
              │        │        │
          bytes      bytes    diagnostics
```

协议解析留在：

```text
McpTransport
PluginHost/Broker
```

---

# 12. 为什么不要 Runtime 直接提供 NDJSON Reader

不要：

```rust
RuntimeHandle::read_json_line()
```

因为这样 Runtime 就开始理解：

```text
protocol framing
```

以后：

```text
MCP
Plugin
future protocol
```

都会反向依赖。

应该提供：

```rust
read_stdout_chunk()
```

或：

```rust
take_stdout(...)
```

由上层决定 framing。

---

# 13. Bounded IO

P0-A 要特别强调：

```text
bounded ≠ read all then reject
```

必须：

```text
OS pipe
   ↓
bounded reader
   ↓
limit
```

例如：

```text
max_stdout_bytes = 256 KiB
```

超过：

```text
RuntimeError::OutputLimitExceeded
```

而不是先：

```text
malloc 100 MB
```

再判断超限。

这与 Phase 10 已修复的 MCP oversized frame 问题保持同一个底层安全原则。

---

# 14. stdout 与 stderr 必须独立限流

例如：

```text
stdout = 256 KB limit
stderr = 64 KB limit
```

不要共享一个总 buffer：

```text
stdout + stderr = 320 KB
```

因为 stderr 只是 diagnostics，却可以被恶意 server 用来挤占 protocol channel 的 buffer。

---

# 15. stderr Policy

Runtime 应支持：

```text
stderr → bounded diagnostics stream
```

但：

```text
stderr
```

不应该：

```text
UI raw render
AI instruction
Action input
Effect input
```

仍然只是 diagnostics。

---

# 16. Timeout 分层

至少区分：

```text
startup_timeout
io_timeout
shutdown_grace
```

例如：

```text
startup = 2s
io = 5s
shutdown grace = 200ms
```

但具体默认值继续由项目现有合同决定，不要在 P0-A 擅自改变 MCP/Plugin 当前行为。

关键是 Runtime 只报告：

```text
StartupTimeout
IoTimeout
ShutdownTimeout
```

然后上层转换：

```text
McpError
PluginError
FailureClass
```

---

# 17. Shutdown 状态机

建议：

```text
Running
  │
  │ graceful shutdown
  ▼
Stopping
  │
  ├── exited
  │     ↓
  │   Stopped
  │
  └── grace expired
        ↓
      kill job
        ↓
      wait
        ↓
      Stopped
```

不能：

```text
Esc
 ↓
kill process
```

由 UI 决定。

UI 根本不应该接触 RuntimeHandle。

---

# 18. Crash detection

Runtime 应保留：

```rust
pub struct ExitStatus {
    pub code: Option<i32>,
    pub signal: Option<i32>,
}
```

Windows 可能没有 Unix signal 语义，因此不要强制设计成 Unix-only：

```rust
signal: Option<i32>
```

甚至可以更通用：

```rust
pub enum ProcessTermination {
    Exited { code: i32 },
    Terminated,
    Killed,
    Unknown,
}
```

但不要把：

```text
BusinessError
ProtocolViolation
```

放进 Runtime termination type。

---

# 19. Process startup failures

例如：

```text
program not found
permission denied
working directory invalid
```

Runtime：

```text
SpawnFailed
```

上层：

```text
McpExecutor
    ↓
McpError
    ↓
PluginUnavailable
```

不要 Runtime 自己直接返回：

```text
FailureClass::PluginUnavailable
```

否则 Runtime 又开始知道业务语义。

---

# 20. PluginBroker 迁移

迁移前：

```text
PluginBroker
├── std::process::Command
├── Job Object
├── reader thread
├── shutdown
└── timeout
```

迁移后：

```text
PluginBroker
├── Plugin protocol
├── query_id
├── execution_id
├── contract validation
└── RuntimeHandle
```

即：

```text
PluginBroker
    ↓
launcher-runtime
```

---

# 21. McpExecutor 迁移

迁移前：

```text
McpExecutor
├── spawn
├── initialize
├── tools/list
├── tools/call
└── shutdown
```

迁移后：

```text
McpExecutor
├── MCP lifecycle semantics
├── protocol profile
├── tools/call
├── error mapping
└── RuntimeHandle
```

也就是说：

```text
McpExecutor
    ↓
McpTransport
    ↓
launcher-runtime
```

---

# 22. 不要把 `McpTransport` 删除

RuntimeSupervisor 出现以后：

```text
McpTransport
```

仍然有意义。

关系：

```text
McpExecutor
     ↓
McpTransport
     ↓
Runtime
```

而不是：

```text
McpExecutor
     ↓
Runtime
```

否则 Transport abstraction 被错误地吞掉。

---

# 23. Persistent Runtime API

为 P0-A 预留，但不强制实现：

```rust
spawn()
send()
shutdown()
```

而不是：

```rust
run_once()
```

这样以后：

```text
Persistent MCP
Persistent Plugin
```

不需要重新改 Runtime API。

---

# 24. Runtime Registry

可以有：

```rust
RuntimeRegistry
```

但它只管理：

```text
RuntimeId → RuntimeHandle
```

不要：

```text
RuntimeId → Capability
RuntimeId → Provider
RuntimeId → Workflow
```

否则又开始变成 execution manager。


# 29. Topology 预期

新增：

```text
launcher-runtime
```

之后可能变成：

```text
16 crates
8 apps
```

如果这是你的当前 workspace 结构，那么 topology fixture 应同步更新。

推荐依赖：

```text
launcher-runtime
       ↑
 ┌─────┴─────┐
Plugin      MCP
```

而：

```text
launcher-runtime
    X → launcher-mcp
    X → launcher-plugin-host
    X → workflow
    X → action
```

这是非常关键的 DAG 方向。

# 30. Migration Strategy

不要一次删除旧实现。

采用：

```text
Step 1
新增 launcher-runtime

Step 2
PluginBroker 接入 Runtime

Step 3
所有 Plugin tests 全绿

Step 4
McpExecutor 接入 Runtime

Step 5
所有 MCP tests 全绿

Step 6
删除重复 process lifecycle

Step 7
topology + architecture guard

Step 8
performance baseline

Step 9
release-gate
```

这样任何回归都容易定位。

# P0-A 成功后的直接效果

最终：

```text id="p0a-final"
                  ActionEngine
                       │
                     Effect
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
    PluginBroker              McpExecutor
          │                         │
   Plugin Protocol            MCP Protocol
          │                         │
          └───────────┬─────────────┘
                      ▼
              launcher-runtime
                      │
                ProcessSupervisor
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
        Spawn         IO       Reap/Kill
          │           │           │
          └───────────┼───────────┘
                      ▼
                  OS Process
```

这一步完成后，**P0-B Streamable HTTP 就不应该再碰进程生命周期模型**；HTTP MCP 可以直接复用 MCP Executor 的上层语义，只新增 HTTP Transport。P0-C Auth 再挂在 HTTP Transport 前面。

### P0 主线因此保持：

```text
P0-A Runtime Foundation
        ↓
P0-B Streamable HTTP
        ↓
P0-C MCP Auth
        ↓
P0-D LLM Planner
```

P0-A 是这条链中唯一明显的横向基础设施重构，因此完成后应重新跑一次完整 Release-style regression，而不是只跑新增 Runtime tests。
