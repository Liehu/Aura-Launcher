# 但是这里有一个新的架构问题开始出现了

随着 Python SDK 加入，Plugin Runtime 已经从：

```text
runtime.type = process
```

变成：

```text
runtime.type = process
runtime.type = python
```

这其实意味着：

# `runtime` 已经开始成为一个真正的抽象层

所以从现在开始，强烈建议**不要在 `launcher-plugin-host` 里继续堆**：

```rust
match runtime_type {
    Process => ...
    Python => ...
    Node => ...
    Wasm => ...
}
```

如果继续这么写：

```text
v0.1:
Process
Python

v0.2:
Node
WASM

v0.3:
Lua
PowerShell
...
```

最后会变成一个巨型 `match`。

---

# 我建议现在就冻结 `RuntimeProvider` 抽象

不用立刻实现更多 Runtime。

只需要架构上形成：

```text
PluginHost
    │
    ▼
RuntimeResolver
    │
    ├── ProcessRuntime
    ├── PythonRuntime
    ├── NodeRuntime       [future]
    └── WasmRuntime       [future]
```

概念上：

```rust
trait PluginRuntime {
    fn spawn(&self, manifest: &Manifest) -> Result<RuntimeHandle>;
}
```

然后：

```text
ProcessRuntime
    → executable

PythonRuntime
    → python interpreter + script

NodeRuntime
    → node + script

WasmRuntime
    → wasm runtime
```

这样：

> **Plugin Contract 不关心运行时。**

你目前 Python 的：

```text
config
↓
environment
↓
```

所以建议抽象：

```text
Runtime Discovery

├── system discovery
└── unavailable
```

最终：

```text
Plugin

Runtime Type

Runtime Resolver

```

这样 Python 只是第一个实现。

# 第三个问题：`runtime.type = python` 最好明确它描述的是“Host Strategy”

也就是：

```text
python
```

不是说：

> 插件是 Python。

而是：

> Host 使用 Python Runtime Strategy 启动它。

这一点未来很重要。

因为以后可能：

```text
runtime.type = process
```

启动：

```text
custom-plugin-host.exe
```

里面又是 Python。

或者：

```text
runtime.type = python
```

直接：

```text
python.exe plugin.py
```

两者语义不同。

建议文档明确：

```text
runtime.type
=
Host launch strategy
```

而不是：

```text
Programming language
```

---

# 第四个问题：现在已经可以定义 Plugin “作者 API”与“Host API”的严格边界

目前：

```text
plugin-api
```

很好。

建议从现在开始严格区分：

```text
Plugin Author API
    ↓
Plugin SDK
```

和：

```text
Host API
    ↓
Plugin Host internal
```

插件开发者绝不能依赖：

```text
launcher-plugin-host
launcher-core
launcher-context
launcher-action
```

的内部类型。

只能：

```text
launcher-plugin-api
```

否则以后 SDK/API 会重新被 Host implementation 绑架。

这条建议我认为非常重要。

# 第六个问题：`store` 现在继续不做是正确的

你之前明确：

> reference-stateful plugin 暂缓，因为 Host 还没有 Store。

我赞成继续保持。

现在插件模型应该保持：

```text

 ↓
pure-ish result
```

等 `store.read/write` 真正有后端以后，再验证：

```text

```

否则现在做一个假的 store 反而会提前冻结错误 API。



因为你现在刚刚完成：


```text

```

否则容易出现：

```text

```

反过来绑架：


# 第八个问题：Python 的 `LAUNCHER_PYTHON` 很适合作为临时 MVP 方案，但以后最好增加 Runtime diagnostics

例如插件启动失败时，不应该只看到：

```text
plugin empty result
```

日志最好明确：

```text
plugin: calculator
runtime: python
resolved_executable:
    C:\Python312\python.exe
resolution_source:
    config.toml

failure:
    executable not found
```

因为以后用户安装：

```text
Python 3.12
Python 3.13
Anaconda
uv
pyenv
```

调试问题会非常多。

所以以后可以有：

```text
launcher plugins doctor
```

例如：

```text
Python runtime:
  source: config
  path: C:\...\python.exe
  version: 3.12.9
  status: OK
```

这个属于 Developer UX，不必进入 v0.1 Contract。

## 我的建议：这里正式停一下协议开发

你现在已经连续完成：

```text
MVP
 → MVP2
 → MVP2.1
 → Plugin Contract
 → Rust SDK
 → Python SDK
```

再继续不断扩协议，很容易陷入“设计越来越漂亮，但实际产品越来越晚”的陷阱。

**现在最有价值的实验已经从“插件协议是否成立”变成“一个第三方开发者是否能非常舒服地开发插件”。**

所以我下一阶段会把重点转成：

```text
Developer Experience
        +
Command / Action / UI
        +
Real plugin development
```

等这部分跑通，再决定 Node / WASM / MCP / AI 的最终形态。

尤其 **UI Schema + Action Contract**，我认为是现在最值得设计的一刀：它决定了你的插件最终到底只是“给 Launcher 提供搜索结果”，还是能够真正成为 **Raycast + uTools + Flow + Listary 能力的统一扩展模型**。
