# P2.1-B Incremental Index Engine 专门批次

本批次建议正式冻结为：

> **P2.1-B — Incremental Index Engine v0.1**
> 目标：在不阻塞交互式 Search 的前提下，实现 Windows 文件系统变化的**监听、限流、合并、增量解析、单写入、溢出恢复、代际管理与最终一致性**。

本批次只处理 **File Index**。
Application Identity、MSIX/UWP、Portable App、Icon Cache、Query Cache、Context Ranking、Favorites、Search Explain 均不进入本批次。

---

# 1. 批次边界冻结

## 1.1 本批次解决的问题

```text
Windows File System
       │
       ▼
ReadDirectoryChangesW
       │
       ▼
WindowsWatcher
       │
       ▼
Bounded Event Queue
       │
       ▼
Coalescer
       │
       ▼
IndexCoordinator
       │
       ├──── Normal Change ────► Re-stat / Re-read filesystem
       │                              │
       │                              ▼
       │                        IncrementalWriter
       │                              │
       │                              ▼
       │                           SQLite
       │
       └──── Overflow ─────────► DirtyRoot
                                      │
                                      ▼
                               OverflowRecovery
                                      │
                                      ▼
                               Bounded Rescan
```

核心原则：

> **Watcher Event 不是事实，Filesystem State 才是事实。**

例如收到：

```text
MODIFIED C:\Work\a.txt
```

不能直接假设：

```text
a.txt 一定存在
size 一定发生变化
mtime 一定发生变化
```

而应该重新执行：

```text
stat(C:\Work\a.txt)
```

然后根据真实 filesystem state 决定：

```text
Present → Upsert
Missing → Delete
```

# 3. 核心不变量

建议正式冻结：

## INV-INDEX-001 — Bounded Event Queue

Watcher 到 Coordinator 的事件队列必须有硬容量上限。

```text
Watcher → BoundedQueue
```

禁止：

```rust
VecDeque::new()
```

无限增长。

发生压力时：

```text
Queue Full
    ↓
mark affected root dirty
    ↓
discard redundant events
```

而不是继续堆积。

---

## INV-INDEX-002 — Overflow Never Means Full-Disk Rebuild

Watcher overflow：

```text
ERROR_NOTIFY_ENUM_DIR
```

或等价 overflow 条件，只能导致：

```text
DirtyRoot
```

而不是：

```text
rebuild_all()
```

例如：

```text
C:\Users\A\Documents
```

发生 overflow：

```text
DIRTY:
C:\Users\A\Documents
```

然后：

```text
bounded subtree rescan
```

---

## INV-INDEX-003 — Reparse Point Not Followed

默认：

```text
symlink     → 不跟随
junction    → 不跟随
mount point → 不跟随
```

否则：

```text
C:\A\B → C:\A
```

可能形成：

```text
infinite / overlapping traversal
```

第一版只索引：

```text
directory entry itself
```

不递归进入 reparse target。

---

# 4. INV-INDEX-004 — Watcher Event Is Only a Hint

所有事件最终必须通过 filesystem re-stat 重新确认。

例如：

```text
Created
Modified
Deleted
Renamed
```

统一进入：

```text
ChangeIntent
```

而不是直接操作数据库。

---

# 5. INV-INDEX-005 — Single Writer

SQLite Index 在增量维护时：

> **始终只有一个逻辑 Writer。**

禁止：

```text
Watcher ─────► SQLite
Provider ────► SQLite
Rebuild ─────► SQLite
Coordinator ─► SQLite
```

正确模型：

```text
Watcher ───────┐
               │
Rebuild ───────┤
               ▼
        IndexCoordinator
               │
               ▼
       IncrementalWriter
               │
               ▼
             SQLite
```

这样可以把：

```text
事务
generation
dirty state
failure recovery
```

统一起来。

---

# 6. INV-INDEX-006 — Queryable During Maintenance

后台更新过程中：

```text
Search
```

不得被锁死。

也就是说：

```text
Incremental Update
        │
        ▼
SQLite WAL
        │
        ├── Writer transaction
        │
        └── Reader ──► Search
```

仍然允许：

```text
SELECT ...
```

交互搜索不应该等待整个 subtree rescan 完成。

---

# 7. INV-INDEX-007 — Generation Only Advances After Commit

Generation 不在操作开始时增加。

错误：

```text
start batch
generation += 1
write...
```

正确：

```text
begin transaction
    mutations
commit
    ↓
generation += 1
```

因此：

```text
failed batch
```

不会产生新的可见 generation。

---

# 8. INV-INDEX-008 — Generation Is Batch-Level

不应该：

```text
event 1 → generation 101
event 2 → generation 102
event 3 → generation 103
```

而应该：

```text
events:
  a
  b
  c
  d

coalesce
    ↓

transaction
    ↓

generation:
100 → 101
```

因此 generation 表示：

> **Index 的一个成功提交版本。**

不是 filesystem event counter。

# 9. 文件系统变化模型

建议在 `launcher-domain` 定义最基础的数据模型。

```rust
pub enum FileChangeKind {
    Created,
    Modified,
    Deleted,
    Renamed,
}

pub struct FileChange {
    pub kind: FileChangeKind,
    pub path: SearchPath,
    pub old_path: Option<SearchPath>,
}
```

但这里有一个重要限制：

## 不让 Watcher 产生“最终语义”

Watcher 可以产生：

```text
Created
Modified
Deleted
Renamed
```

但不能产生：

```text
FileUpsert
FileDelete
DirectoryExists
```

这些是 Coordinator 经过 filesystem verification 后才能得到的结果。

---

# 10. Rename 模型

Windows watcher 会提供：

```text
RENAMED_OLD_NAME
RENAMED_NEW_NAME
```

Coordinator 合并为：

```rust
FileChange {
    kind: Renamed,
    old_path,
    path,
}
```

但数据库层不要盲目执行：

```sql
UPDATE path
SET path = new_path
WHERE path = old_path;
```

第一版更稳妥：

```text
re-stat old_path
re-stat new_path
```

然后：

```text
old missing
new exists
```

最终：

```text
delete old
upsert new
```

原因是 watcher 事件在真实 filesystem state 面前不是权威。

---

# 11. Coalescer

这是 P2.1-B 的关键组件。

例如短时间产生：

```text
Created a.txt
Modified a.txt
Modified a.txt
Modified a.txt
Renamed a.txt → b.txt
Modified b.txt
```

不应该执行 6 次数据库操作。

Coalescer 最终压缩为：

```text
a.txt → Deleted
b.txt → Upsert
```

---

# 12. Coalescing 规则

建议：

```text
Created + Modified
    → Created

Created + Deleted
    → Remove

Modified + Modified
    → Modified

Modified + Deleted
    → Deleted

Deleted + Created
    → Modified / Re-evaluate

Rename(old,new) + Modified(new)
    → Rename(old,new)

Rename(old,new) + Delete(new)
    → Delete(old)

Rename(old,new) + Rename(new,x)
    → Rename(old,x)
```

不过不要把这些规则散布成大量 `match`。

建议独立：

```rust
Coalescer
```

并定义：

```rust
Coalescer::push(event)
Coalescer::drain()
```

让它成为纯函数式/可单测组件。

---

# 13. Path Normalization

Coalescing 前必须执行：

```text
normalize_path_identity()
```

因此：

```text
C:\Foo\Bar
c:/foo/bar
C:\FOO\BAR\
```

统一为 canonical lexical identity。

现有 P2.1-A 已经冻结：

```text
launcher_domain::normalize_path_identity
```

P2.1-B 直接复用，不重新定义第二套路径规范。

# 14. Dirty Root

Watcher overflow 时不要保留海量事件。

例如：

```text
Queue:
99,999 events
```

发生：

```text
overflow
```

转换成：

```text
DirtyRoot {
    root: C:\Users\A\Documents
}
```

---

# 15. Dirty Root 合并

必须支持：

```text
C:\A
C:\A\B
C:\A\B\C
```

自动压缩：

```text
C:\A
```

因为：

```text
rescan(C:\A)
```

已经覆盖全部子目录。

反过来：

```text
C:\A\B
C:\A\C
```

不能合并成：

```text
C:\A
```

否则扩大恢复范围。

因此需要：

```text
DirtyRootSet
```

具备：

```rust
insert(path)
remove(path)
contains_or_parent(path)
drain()
```

# 16. Overflow Recovery

恢复模型：

```text
Watcher Overflow
       │
       ▼
DirtyRootSet
       │
       ▼
Coordinator
       │
       ▼
bounded subtree enumeration
       │
       ▼
filesystem snapshot
       │
       ▼
diff against index
       │
       ▼
IncrementalWriter
```

关键：

> **Recovery 也是 Incremental Index，而不是偷偷执行 Full Rebuild。**

---

# 17. Subtree Rescan

建议算法：

```text
scan(root)
    │
    ├── enumerate root children
    │
    ├── enumerate subdirectories
    │
    └── emit observed entries
```

每个 subtree 使用：

```text
bounded traversal
```

限制：

```text
max entries / batch
max transaction size
max pending work
```

不要：

```text
scan 2 million files
→ collect into Vec
→ one enormous transaction
```

而应：

```text
scan
  ↓
batch 1
  ↓
commit

scan
  ↓
batch 2
  ↓
commit
```

---

# 18. 删除检测

这是 incremental index 最容易做错的部分。

Watcher：

```text
DELETE
```

非常简单：

```text
DELETE FROM files WHERE path = ?
```

但是 overflow recovery 不一样。

例如索引里：

```text
A.txt
B.txt
C.txt
```

实际 filesystem：

```text
A.txt
C.txt
```

Rescan 必须发现：

```text
B.txt missing
```

因此 recovery 需要：

```text
Filesystem subtree
        vs
Index subtree
```

进行 bounded diff。

---

# 19. 推荐的 Recovery 算法

不要先把整个 filesystem subtree 全塞进内存。

而采用：

```text
database subtree cursor
             │
filesystem enumeration
             │
             ▼
        merge iterator
```

第一版如果实现复杂度过高，也可以接受：

```text
bounded HashSet<Path>
```

但必须有硬预算。

例如：

```text
max_recovery_entries
```

超过后：

```text
继续分批
```

不能无界分配。

# 24. Rebuild + Watcher 并行

这是本批次必须解决的 race。

场景：

```text
06:00 startup

rebuild started
```

期间：

```text
06:01 a.txt created
06:01 b.txt modified
06:02 c.txt deleted
```

不能简单：

```text
rebuild ignores watcher
```

否则最终 index 会丢状态。

正确流程：

```text
Startup
 │
 ├── start watcher
 │
 └── start rebuild
        │
        ├── watcher keeps collecting
        │
        └── rebuild creates baseline
                    │
                    ▼
               rebuild commit
                    │
                    ▼
              replay pending
                    │
                    ▼
                coalesce
                    │
                    ▼
              incremental apply
```

因此：

> **Watcher 在 Rebuild 期间不能停止。**

# 25. Rebuild 与事件的边界

需要定义：

```text
RebuildCutover
```

可以简单实现为：

```text
event sequence
```

例如：

```text
watcher_seq = 100

rebuild begins
cutover = 100
```

Rebuild 完成后：

```text
replay events seq > 100
```

这样可以避免：

```text
漏事件
```

# 26. 一个更稳妥的模型

Watcher 内部事件：

```rust
pub struct IndexedEvent {
    pub sequence: u64,
    pub change: FileChange,
}
```

要求：

```text

```

注意：

> sequence 不是 Index Generation。

两者必须明确区分：

| ID                  | 意义                        |
| ------------------- | ------------------------- |
| watcher sequence    | filesystem event ordering |

| execution_id        | action execution          |
| runtime_id          | process runtime           |
| protocol_session_id | MCP protocol session      |

这与你前面已经冻结的 ID 分层原则一致。

# 29. Incremental Decision

最终流程：

```text
FileChange
     │
     ▼
normalize
     │
     ▼
coalesce
     │
     ▼
re-stat
     │
     ├── Missing ─────► Delete
     │
     └── Exists ──────► Observe
                             │
                             ▼

```

```text

```

```text

```

# 33. Startup Recovery

启动时检查：

```text
previous health
pending dirty roots
```

如果上次：

```text
Degraded
Updating
Rebuilding
```

则不能假设 index 已完整。

启动：

```text
load metadata
    │
    ├── Ready
    │      ↓
    │   watch normally
    │
    └── degraded/interrupted
           ↓
       schedule recovery
```

---

# 34. Crash Safety

核心保证：

```text
transaction committed
    → visible

transaction not committed
    → invisible
```

所以 crash 后：

```text
SQLite
```

仍然可以作为最后一个一致 committed generation。

---

# 35. Queue Overflow 策略

推荐：

```text
queue capacity = configurable hard limit
```

例如：

```text
4096
```

不是让用户配置到：

```text
10 million
```

配置项应该有上下限：

```text
min <= event_queue_capacity <= max
```

Overflow：

```text
event queue full
       │
       ▼
mark containing root dirty
       │
       ▼
coalesce away redundant events
```

---

# 36. Dirty Root 的优先级

Coordinator 应优先：

```text
dirty root recovery
```

但不能完全饿死正常 interactive changes。

建议调度：

```text
Normal changes
    ↓
bounded batches

Recovery
    ↓
bounded batches

Normal changes
    ↓
...
```

不要：

```text
Recovery 2M files
    ↓
block everything for 30 seconds
```

---

# 37. Backpressure

整个链路最好形成：

```text
ReadDirectoryChangesW
       │
       ▼
bounded queue
       │
       ▼
coalescer
       │
       ▼
bounded coordinator
       │
       ▼
bounded writer batch
```

每层都有上限。

因此不会出现：

```text
Filesystem burst
       ↓
RAM unlimited growth
```

# 47. Eventual Consistency Definition

这一批次必须给“最终一致”一个严格定义。

定义：

> 当 `IndexCoordinator` 进入 quiescent 状态，且不存在 pending watcher events、pending coalesced events、dirty roots、running writer transaction 后，Index 内容必须与当时 filesystem 的 normalized state 一致。

即：

```text
pending_events == 0
dirty_roots == 0
writer_idle == true
watcher stable
```

之后：

```text
normalize(filesystem)
        ==
normalize(index)
```

# 64. P2.1-B 的最终架构

最终应冻结为：

```text
                   ┌─────────────────────┐
                   │    Windows FS       │
                   └──────────┬──────────┘
                              │
                    ReadDirectoryChangesW
                              │
                              ▼
                   ┌─────────────────────┐
                   │  WindowsWatcher     │
                   └──────────┬──────────┘
                              │
                              ▼
                   ┌─────────────────────┐
                   │  Bounded EventQueue │
                   └──────────┬──────────┘
                              │
                              ▼
                   ┌─────────────────────┐
                   │     Coalescer       │
                   └──────────┬──────────┘
                              │
                    ┌─────────┴─────────┐
                    │                   │
                 normal              overflow
                    │                   │
                    ▼                   ▼
              Verification        DirtyRootSet
                    │                   │
                    │             bounded scan
                    │                   │
                    └─────────┬─────────┘
                              ▼
                    VerifiedChange
                              │
                              ▼
                    ┌───────────────────┐
                    │  IndexCoordinator │
                    └─────────┬─────────┘
                              │
                              ▼
                    ┌───────────────────┐
                    │ IncrementalWriter │
                    └─────────┬─────────┘
                              │
                         transaction
                              │
                              ▼
                         SQLite Index
                              │
                         generation N+1
                              │
                              ▼
                      Search / Providers
```

这里最重要的边界其实只有三个：

```text
Watcher:
    “发生了什么变化？”

Coordinator:
    “应该如何处理这些变化？”

Writer:
    “把已经验证的事实提交进 Index。”
```

而整个 P2.1-B 的一致性闭环是：

```text
Filesystem
   ↓
Events
   ↓
Coalescing
   ↓
Filesystem re-stat
   ↓
VerifiedChange
   ↓
Single Writer
   ↓
Committed Generation
   ↓
Index
```

最终：

```text
EVENTUAL CONSISTENCY
=
QUIESCENT(FILESYSTEM EVENTS)
    ⇒
INDEX == NORMALIZED FILESYSTEM STATE
```

这可以作为 **P2.1-B Incremental Index Engine v0.1 的冻结总契约**。
