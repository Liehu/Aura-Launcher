# P2.1-D — Application Discovery 2.0

这一批的目标不是简单地“再增加几个 App Provider”，而是把 **Windows Application Catalog** 正式建立起来。

核心原则保持不变：

> **Discovery Source 负责发现；ApplicationIdentityResolver 负责归并身份；Catalog 负责形成统一 ApplicationEntry；SearchCoordinator 只消费统一结果，不知道来源。**

Windows 的打包应用与传统 Win32 应用在身份模型上确实不同：MSIX/APPX Package Identity 有 Package Name、Version、Architecture、ResourceId、Publisher 等字段，而 Package Family Name 又是一个稳定的、版本无关的身份维度；一个 Package 还可以包含多个 Application。([Microsoft Learn][1])

# 5. Application Identity v2

第一版可以正式定义：

```rust
pub enum ApplicationIdentityV2 {
    Win32 {
        executable: NormalizedPath,
    },

    Packaged {
        package_family: PackageFamilyName,
        application_id: String,
    },

    Portable {
        executable: NormalizedPath,
    },
}
```

这里有一个非常重要的设计：

## Portable 不应该只是 Win32 的另一个 source

Portable 应用本质上仍然是 Win32 executable。

所以：

```text
Portable
```

是：

```text
discovery classification
```

而不是完全不同的 launch identity。

因此实际 identity 可以最终归一为：

```text
Portable → Win32(executable)
```

同时保留：

```text
source = Portable
```

---

# 6. 为什么 Packaged 使用 Package Family + Application Id

微软的 Package Identity 明确区分：

```text
Package Full Name
Package Family Name
Package Identity
```

Package Full Name 包含版本、架构等，而 Package Family Name 由 Package Name + PublisherId 构成，因此更适合作为跨版本稳定身份的一部分。([Microsoft Learn][1])

而 `<Application Id>` 是**包内唯一**的 application identifier，不是全局唯一，因此：

```text
PackageFamilyName + ApplicationId
```

比单独：

```text
ApplicationId
```

安全得多。([Microsoft Learn][2])

因此：

```text
Microsoft.WindowsNotepad_8wekyb3d8bbwe
+
App
```

才能作为一个 packaged application identity。

---

# 7. Package 与 Application 必须分离

一个 package 可以包含多个：

```xml
<Applications>
    <Application .../>
    <Application .../>
</Applications>
```

微软文档明确指出 `<Applications>` 表示 package 所包含的一个或多个 app。([Microsoft Learn][3])

所以模型不能设计成：

```text
Package = Application
```

必须：

```text
Package
 ├─ Application A
 ├─ Application B
 └─ Application C
```

数据库也应对应：

```text
package
application_entry
```

而不是一个表把两者混在一起。

# 8. Package Model

建议：

```rust
pub struct PackageIdentity {
    pub name: String,
    pub publisher_id: String,
    pub family_name: String,

    pub version: PackageVersion,
    pub architecture: PackageArchitecture,
    pub resource_id: Option<String>,
}
```

注意：

```text
family_name
```

可以直接从 Windows Package API 得到/派生，而不是自己解析字符串。

微软文档也说明 Package Full Name 是由五部分组成，Package Family Name 则由 Name + PublisherId 构成。([Microsoft Learn][1])

# 9. Package Discovery

Windows 可以通过 `PackageManager.FindPackagesForUser` 获取当前用户安装的 package；空 SID 时表示当前用户。([Microsoft Learn][4])

因此：

```text
PackagedAppProvider
        │
        ▼
PackageManager
        │
        ▼
Package
        │
        ▼
Package.Manifest
        │
        ▼
Applications[]
        │
        ▼
ApplicationEntry[]
```

不要扫描：

```text
C:\Program Files\WindowsApps
```

来猜应用。

Windows package API 才是权威来源。

---

# 10. Manifest 是 Packaged App 的主要 metadata source

Package manifest 包含：

```text
identity
dependencies
capabilities
extensibility points
```

并且安装后 manifest 存在于 package directory。([Microsoft Learn][5])

`Application` 元素可以提供：

```text
Id
Executable
EntryPoint
StartPage
```

这些信息用于描述 application 及其激活方式。([Microsoft Learn][6])

因此 PackagedAppProvider 主要流程应该是：

```text
Package
 ↓
Package identity
 ↓
Package manifest
 ↓
Applications
 ↓
Application metadata
```

# 11. LaunchTarget

这是一个需要重点抽象的地方。

建议：

```rust
pub enum LaunchTarget {
    Win32Exe {
        executable: NormalizedPath,
        arguments: Vec<String>,
    },

    ShellLink {
        shortcut: NormalizedPath,
    },

    PackagedApplication {
        package_family: PackageFamilyName,
        application_id: String,
    },

    ShellUri {
        uri: String,
    },
}
```

Application Catalog 只记录：

```text
“如何启动”
```

具体：

```text
CreateProcess
ShellExecute
AUMID activation
```

应该继续属于 Action / Windows Integration 层。

---

# 12. Catalog 不拥有执行权

因此：

```text
ApplicationEntry
```

只包含：

```text
LaunchTarget
```

而不包含：

```text
fn launch()
```

也不允许：

```text
ApplicationCatalog
    → ShellExecuteEx
```

真正执行仍：

```text
ApplicationEntry
    ↓
ActionDescriptor
    ↓
ActionResolver
    ↓
launcher-action::validate()
    ↓
launcher-action::execute()
```

# 13. Packaged App Launch

对于 packaged apps，不能简单假设：

```text
Executable → CreateProcess
```

因为 manifest 的 `Executable`、`EntryPoint`、runtime behavior 等组合决定其激活模型。微软的 manifest 文档也明确说明 Application 的 Executable / EntryPoint 与应用激活相关。([Microsoft Learn][6])

因此第一版：

```text
PackagedApplication
```

应该作为独立的 `LaunchTarget`。

# 14. Application User Model ID

另外建立：

```rust
pub struct ApplicationUserModelId(pub String);
```

用于：

```text
running process
shortcut
packaged application
shell integration
```

Windows 提供 `GetApplicationUserModelId` 获取某个进程的 AUMID。([Microsoft Learn][7])

因此未来运行中进程与 Catalog Entry 可以有：

```text
process AUMID
       ↓
ApplicationUserModelId
       ↓
Catalog identity
```

# 15. 不要拿 AUMID 当唯一 identity

AUMID 很重要，但不应该成为整个 Application Catalog 的唯一 canonical identity。

建议：

```text
Win32
    identity = normalized executable

Packaged
    identity = package family + application id
```

AUMID：

```text
activation / runtime correlation metadata
```

这样不会把 Catalog 与运行时 Shell identity 绑死。

# 18. Shell Link 是 Source Metadata

`.lnk` 本身不是 Application Identity。

例如：

```text
Chrome.lnk
Edge.lnk
Chrome Portable.lnk
```

都可能：

```text
target = chrome.exe
```

所以：

```text
shortcut_path
```

只能：

```text
discovery source
```

而 canonical identity 由：

```text
resolved target
```

决定。

这正好延续现有 P2.1-A 的设计。

微软的 Shell Link 文档也明确说明 shortcut 可以指向 Shell namespace 中的对象，并可通过 `IShellLink::GetPath` 获取关联路径。([Microsoft Learn][9])

# 23. Source Precedence

必须冻结：

```text
Metadata merge ≠ Identity resolution
```

例如：

```text
StartMenu:
    display_name = "Google Chrome"

Registry:
    display_name = "chrome.exe"
```

最终：

```text
display_name = "Google Chrome"
```

可以依据：

```text
StartMenu > Registry
```

但这是：

```text
metadata precedence
```

而不是：

```text
identity precedence
```

---

# 24. Recommended Metadata Precedence

建议：

```text
Packaged Manifest
    >
Start Menu Shortcut
    >
Registry
    >
Portable Heuristic
```

原因：

Package manifest 是 packaged app 的系统 metadata source；Start Menu shortcut 则通常拥有用户可见名称；Registry / Portable 更适合作为补充。

但是：

> 这里的 precedence 只用于 metadata merge，不用于决定“谁存在”。

建议：

```rust
pub enum ApplicationState {

    Unavailable,
    Stale,
    Broken,
```




因此：

```text

```

与：

```text

```

应该分开。

```text

```

例如：

```toml

    "D:\\Portable",
```

# 30. Portable Candidate Heuristic

第一版可以定义：

```text
PortableCandidate
```

条件：

```text
*.exe
+
parent directory looks application-like
+
not known system directory
+
not already discovered
```

例如：

```text
D:\Portable\7zip\7zFM.exe
```

可以成为：

```text
Portable
```

但：

```text
D:\Games\abc.exe
```

不能仅因为是 exe 就自动强制标为 Launcher Application。

---

# 31. Portable Root Policy

推荐：

```text
root
  ├── depth <= N
  ├── executable candidates
  └── exclusion rules
```

例如：

```text
Portable Root
    ├── app.exe
    ├── AppDir\
    │    └── app.exe
    └── nested...
```

Depth 必须有限制。

# 32. Portable 与 File Index 的关系

P2.1-B 已经有 File Index。

不要让 Portable Provider 自己重新扫描相同目录。

更合理的是：

```text
File Index
    ↓
candidate executable files
    ↓
PortableClassifier
    ↓
ApplicationSourceRecord
```

因此可以变成：

```text
File Index
      │
      ▼
Executable Candidates
      │
      ▼
PortableClassifier
```

这样减少重复 I/O。

---

# 33. 但 Application Catalog 不依赖 File Index 可用

需要处理：

```text
startup
File Index rebuilding
```

Application Catalog 仍应能从：

```text
Start Menu
Registry
PackageManager
```

独立构建。

Portable 可以：

```text
pending
```

等 File Index ready。

# 34. Catalog Generation

与 File Index 类似，Application Catalog 应独立拥有：

```rust
pub struct ApplicationCatalogGeneration(pub u64);
```

不要复用：

```text

```

原因：

```text

```

是两个不同数据集。

---

# 35. 为什么不能共享 Generation

例如：

```text

    generation = 500

    generation = 21
```

这完全合理。

因为：

```text

```

不一定意味着：

```text

```

反之：

```text

```

也不一定意味着：

```text

```

发生同等语义变化。

# 43. Package Version 更新

假设：

```text
v1 → v2
```

Package Full Name 会变化，因为它包含 version；Package Family Name 保持版本无关维度。([Microsoft Learn][1])

因此：

```text
ApplicationIdentityV2
```

不要使用：

```text
PackageFullName
```

作为长期 canonical identity。

可以同时记录：

```text
family_name
full_name
version
```

其中：

```text
family + app_id
```

用于 merge。

---

# 44. Multiple Package Versions

理论上 Catalog 可能遇到：

```text

    v1
    v2
```

但正常安装更新场景应该以当前有效 Package 为主。

Catalog 可以保留：

```text

```

而不是把历史版本都显示成应用。

# 51. Refresh 策略

不同 source 应使用不同 refresh 模型：

| Source         | Refresh                                 |
| -------------- | --------------------------------------- |
| Start Menu     | watcher + periodic reconciliation       |
| Registry       | startup + targeted refresh              |
| PackageManager | startup + package change reconciliation |
| Portable       | configured roots + File Index changes   |

不要求每个 source 都实现 Windows watcher。

# 87. 本批次新增核心不变量

建议正式加入：

### `INV-APP-001`

Application discovery sources must never be exposed directly to SearchCoordinator.

### `INV-APP-002`

Equivalent discovery records resolve to one canonical ApplicationIdentity.

### `INV-APP-003`

Application identity resolution is deterministic and side-effect free.

### `INV-APP-004`

Package identity uses package-family + application-id semantics; PackageFullName/version is metadata, not canonical long-lived identity. ([Microsoft Learn][1])

### `INV-APP-005`

Package/Application are separate entities.

### `INV-APP-006`

Portable discovery is restricted to configured roots and bounded traversal.

### `INV-APP-007`

Source failure does not invalidate healthy catalog entries.

### `INV-APP-008`

Application Catalog has a single logical writer.

### `INV-APP-009`

Catalog generation changes only after successful commit.

### `INV-APP-010`

Catalog metadata never grants execution authority.
