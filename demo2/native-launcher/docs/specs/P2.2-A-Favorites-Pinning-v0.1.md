# P2.2-A — Favorites / Pinning v0.1

## 1. 批次目标

P2.2-A 为 Launcher 1.0 建立正式的 Favorites / Pinning 用户状态系统。

本批次必须解决：

1. Favorite / Pin 的数据模型；
2. 与 `SearchIdentity` 的稳定绑定；
3. 用户状态在 Application/File source 变化后的重新解析；
4. Favorite 对 Search Ranking 的影响；
5. Main Mode 中 Favorites 区域的交互；
6. SQLite 持久化；
7. Add / Remove / Reorder 的 Action 权限边界；
8. stale / unavailable / deleted identity 的处理；
9. 与现有 SearchCoordinator、Application Catalog、File Index 的集成；
10. 完整测试及 10 个 Acceptance Gates。

本批次不实现：

- Query Cache；
- Context-aware Ranking；
- ML/AI Ranking；
- Plugin Management；
- Marketplace；
- Cloud Sync；
- Favorite Folder；
- Favorite Group；
- Favorite Workflow；
- 跨设备同步。

# 2. 核心设计原则

## 2.1 Favorite 是用户显式意图

```text
Recent
    = system observed behavior

Favorite
    = explicit user preference

Pin
    = explicit placement preference
```

三者不得使用同一个数据库字段表达。

---

## 2.2 Favorite 绑定 Semantic Identity

禁止：

```text
favorite(provider_id, provider_item_id)
```

必须：

```text
favorite(search_identity)
```

例如：

```text
StartMenu / Chrome.lnk
Registry   / chrome.exe
```

最终：

```text
SearchIdentity::Application(...)
```

Favorite 绑定的是后者。

---

## 2.3 Favorite 不保存可执行 Action

Favorite 不得持有：

```text
ResolvedAction
ExecutionId
Effect
ActionResult
RuntimeId
ProtocolSessionId
```

Favorite 只保存：

```text
semantic identity
```

以及必要的用户状态。

真正使用 Favorite 时：

```text
Favorite
    ↓
Live Catalog Resolution
    ↓
SearchResult
    ↓
ActionDescriptor
    ↓
ActionResolver
    ↓
launcher-action::validate()
    ↓
launcher-action::execute()
```

---

## 2.4 Pin 不等于另一个 Identity

一个 application：

```text
Chrome
```

只有一个：

```text
SearchIdentity
```

Pin 是它的 UI placement state。

因此：

```text
ApplicationIdentity
      │
      ├── Favorite state
      └── Pin state
```

而不是：

```text
PinnedChrome
FavoriteChrome
```

两个不同对象。

---

# 3. User State 数据模型

建议最终统一模型：

```rust
pub struct UserItemState {
    pub identity: SearchIdentity,
    pub favorite: Option<FavoriteState>,
    pub pin: Option<PinState>,
}
```

其中：

```rust
pub struct FavoriteState {
    pub created_at: Timestamp,
    pub updated_at: Timestamp,
}

pub struct PinState {
    pub location: PinLocation,
    pub order: u32,
    pub created_at: Timestamp,
    pub updated_at: Timestamp,
}
```

但数据库层不必强制合成一张表。

推荐：

```text
favorite
pin
```

两个独立关系。

---

# 4. Favorite 数据模型

正式冻结：

```rust
pub struct Favorite {
    pub identity: SearchIdentity,
    pub created_at: Timestamp,
}
```

v0.1 不提供：

```text
title_override
note
description
group
color
icon_override
```

不要提前把 Favorite 做成书签管理器。

---

# 5. Pin 数据模型

正式冻结：

```rust
pub struct Pin {
    pub identity: SearchIdentity,
    pub location: PinLocation,
    pub order: u32,
    pub created_at: Timestamp,
    pub updated_at: Timestamp,
}
```

v0.1：

```rust
pub enum PinLocation {
    MainFavorites,
}
```

也就是说，第一版只允许：

```text
Main → Favorites section
```

不实现：

```text
Sidebar
Toolbar
ContextMenu
Folder
Category
```

---

# 6. Favorite 与 Pin 的关系

建议允许三个状态：

| Favorite | Pin | 语义 |
|---|---|---|
| No | No | 普通项目 |
| Yes | No | Favorite |
| Yes | Yes | Favorite + pinned |
| No | Yes | **v0.1 禁止** |

也就是说：

> Pin 默认建立在 Favorite 之上。

因此：

```text
Pin
```

操作可以隐式：

```text
Pin → ensure Favorite
```

但是：

```text
Unfavorite
```

必须先解除 Pin 或拒绝操作。

---

# 7. 为什么不允许 Pin-only

否则会出现：

```text
Pinned
but not Favorite
```

UI 和数据语义会变复杂：

```text
Home item
Favorite list
Ranking boost
```

三套状态开始组合。

v0.1 简化为：

```text
Favorite
  └── Pin
```

也就是：

```text
Pin ⊆ Favorite
```

这是一个明确的产品约束。

---

# 8. Unfavorite 行为

如果：

```text
Favorite = true
Pin = true
```

执行：

```text
Unfavorite
```

不得留下：

```text
Pin = true
```

统一：

```text
Unfavorite
    ↓
remove Favorite
    ↓
remove Pin
```

整个操作必须是一个事务。

---

# 9. Unpin 行为

```text
Unpin
```

只：

```text
Pin → removed
Favorite → preserved
```

因此：

```text
Pinned Favorite
      ↓
Unpin
      ↓
Favorite
```

---

# 10. Pin Reorder

Pin 的 order 是：

```text
u32
```

不要让 UI 自己决定持久化位置。

例如：

```text
A order 0
B order 1
C order 2
```

拖动：

```text
C → first
```

最终：

```text
C order 0
A order 1
B order 2
```

Database 中应保持：

```text
unique(location, order)
```

或者通过事务重新编号。

---

# 11. Order 不承担 Identity

不要：

```text
favorite_id = order
```

也不要让：

```text
order
```

影响：

```text
identity
```

Identity 永远独立。

---

# 12. SearchIdentity 绑定

Favorite 对 `SearchIdentity` 做 canonical serialization：

```rust
pub struct IdentityKey(pub String);
```

推荐：

```text
Favorite
    identity_key = canonical(SearchIdentity)
```

例如：

```text
win32:path:c:\program files\google\chrome\application\chrome.exe
```

或者：

```text
packaged:microsoft.foo_abc123:main
```

具体 serialization 必须复用 P2.1-D 的 canonical identity，不得在 Favorites 模块重新实现。

---

# 13. Identity 不允许使用 display name

错误：

```text
favorite("Chrome")
```

可能出现：

```text
Chrome Stable
Chrome Beta
Chrome Dev
```

正确：

```text
favorite(
    ApplicationIdentity(...)
)
```

---

# 14. Identity 不允许使用 provider item id

错误：

```text
favorite("start-menu", "chrome.lnk")
```

因为：

```text
shortcut renamed
shortcut relocated
source removed
```

都会导致 Favorite 失联。

正确：

```text
favorite(ApplicationIdentity::Win32(...))
```

---

# 15. Favorite 的 Resolution

Favorite 保存 identity：

```text
Favorite
    ↓
IdentityResolver / Catalog lookup
    ↓
Live ApplicationEntry
```

如果找到：

```text
Available
```

正常显示。

如果 identity 存在但 source 暂时不可用：

```text
Unavailable
```

仍可以显示，但不可执行。

如果所有 source 都不再存在：

```text
Stale
```

---

# 16. Stale Favorite

默认不要立即删除。

例如：

```text
D:\Portable\Foo\foo.exe
```

移动硬盘后：

```text
Favorite
    identity = Win32(D:\Portable\Foo\foo.exe)
    state = Stale
```

等重新出现：

```text
identity returns
    ↓
Favorite automatically resolves
```

---

# 17. 为什么不自动删除 Stale Favorite

因为：

```text
U盘拔出
网络盘暂时断开
Portable disk unavailable
```

都可能产生暂时 unavailable。

所以：

> “当前不可解析” ≠ “用户不再喜欢”。

---

# 18. Stale 永久清理

v0.1 不自动删除 stale Favorite。

可以提供：

```text
Remove Favorite
```

由用户显式删除。

后续再考虑：

```text
stale > 90 days
```

之类的 cleanup policy。

本批次不做。

---

# 19. File / Folder Favorite

P2.2-A 应支持：

```text
File
Folder
Application
```

因为 Launcher 不应该把 Favorite 系统设计成只属于 Application。

例如：

```text
Favorite:
C:\Projects\Launcher

Favorite:
C:\Notes\todo.md
```

都合法。

---

# 20. File Favorite

File Identity v1：

```text
normalized absolute path
```

所以：

```text
C:\A\file.txt
```

对应：

```text
FileIdentity(path)
```

当文件移动：

```text
C:\A\file.txt
→
C:\B\file.txt
```

v0.1 **不能自动推断成同一个 FileIdentity**。

因此 Favorite 会进入 stale。

这是有意的。

---

# 21. 不在本批次实现 File Identity v2

不要为了 Favorite 而提前引入：

```text
FILE_ID_128
volume serial
USN
NTFS file id
```

这些属于：

```text
File Identity v2
```

单独解决。

---

# 22. Folder Favorite

Folder Favorite 同样使用：

```text
FileIdentity
```

但：

```rust
SearchResultKind::Folder
```

区分。

---

# 23. Favorite Source Resolution

Favorite 本身不记录：

```text
StartMenu
Registry
Portable
```

因为 source 可能变化。

正确：

```text
Favorite
    ↓
identity
    ↓
current catalog/source resolution
```

---

# 24. SearchCoordinator 集成

SearchCoordinator 不需要新的：

```text
FavoriteProvider
```

这是关键。

错误：

```text
SearchCoordinator
 ├─ ApplicationProvider
 ├─ FileProvider
 ├─ FavoriteProvider
```

这样 Favorite 会与普通 Search candidate 并列，导致重复。

正确：

```text
SearchCoordinator
 ├─ ApplicationSearchProvider
 ├─ FileSearchProvider
 ├─ RecentSearchProvider
 └─ ...
          │
          ▼
      Candidate Pool
          │
          ▼
      Favorite Signal
```

# 25. Favorite Ranking Signal

定义：

```rust
pub struct FavoriteSignals {
    pub is_favorite: bool,
    pub is_pinned: bool,
}
```

然后：

```text
score =
    relevance
  + provider_score
  + history
  + favorite
  + context
```

P2.2-A 只实现：

```text
favorite
pin
```

Context 留给 P2.2-C。


```text

```

仍然不能压过：



```text

        ↓

        ↓
Recent/Frequent
```

而不是普通 query 的完全相同 scoring。


# 35. UI 不直接调用 FavoriteService

错误：

```rust
on_click(|| favorites.add(identity));
```

```text

```

# 36. Favorite Actions

建议定义：

```text
system.favorite.add

```

其中：

```text

```

与现有 Action Descriptor 体系一致。

# 37. Action Authority

Favorite mutations 属于：

> Host-owned system actions.

因此：

```text
type =
system.favorite.*
```

不是：

```text
plugin.favorite.*
```

也不是：

```text
favorite.*
```

---

# 38. Action Input

Add：

```json
{
  "identity": "..."
}
```

Remove：

```json
{
  "identity": "..."
}
```

Pin：

```json
{
  "identity": "...",
  "location": "main_favorites"
}
```

Unpin：

```json
{
  "identity": "..."
}
```

Reorder：

```json
{
  "identity": "...",
  "location": "main_favorites",
  "order": 2
}
```

实际 serialization 应直接复用 canonical `SearchIdentity` schema。

---

# 39. Action Resolver Validation

例如：

```text
system.favorite.add
```

Resolver 至少验证：

```text
identity valid
identity currently resolvable
```

但这里需要区分：

### Add Favorite

要求 identity 当前可解析。

### Remove Favorite

即使当前 stale，也应该允许删除。

### Unpin

同理，即使 stale，也允许。

否则用户无法清理失效状态。

---

# 40. Pin Validation

Pin：

```text
identity must be Favorite
```

如果不是：

```text
Ready
```

可以：

```text
ActionResolver
    ↓
InvalidInput
```

或者产品层直接把：

```text
Pin
```

实现成：

```text
EnsureFavorite + Pin
```

对于 1.0，我更推荐后者：

```text
Pin
    transaction:
        create favorite if absent
        create pin
```

用户不需要理解 Pin 是 Favorite 的子状态。

---

# 41. Pin 原子性

必须是单事务：

```text
BEGIN
    INSERT favorite
    INSERT pin
COMMIT
```

不能：

```text
insert favorite
commit

insert pin
crash
```

否则会出现部分状态。

---

# 42. Unfavorite 原子性

同样：

```text
BEGIN
    DELETE pin
    DELETE favorite
COMMIT
```

---

# 43. Reorder 原子性

例如：

```text
A 0
B 1
C 2
```

C 移到 0：

```text
BEGIN

C = 0
A = 1
B = 2

COMMIT
```

不能在中途让 reader 看到：

```text
C = 0
A = 0
```

因此 UI 不直接改 order。

---

# 44. SQLite Schema

建议：

```sql
CREATE TABLE favorites (
    identity_key TEXT PRIMARY KEY,
    identity_json TEXT NOT NULL,
    created_at INTEGER NOT NULL
);
```

Pin：

```sql
CREATE TABLE pins (
    identity_key TEXT PRIMARY KEY,
    location TEXT NOT NULL,
    order_index INTEGER NOT NULL,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,

    FOREIGN KEY(identity_key)
        REFERENCES favorites(identity_key)
        ON DELETE CASCADE
);
```

这样数据库层直接表达：

```text
Pin ⊆ Favorite
```

---

# 45. Identity JSON

虽然：

```text
identity_key
```

是 lookup key，

仍建议保存：

```text
identity_json
```

原因：

```text
key = efficient lookup
json = reconstruct semantic identity
```

但必须保证：

```text
identity_json
→ canonical identity
→ same identity_key
```

启动时可以校验。

---

# 46. Identity Schema Version

建议：

```text
identity_version
```

例如：

```sql
identity_version INTEGER NOT NULL
```

因为未来：

```text
Application Identity v2
File Identity v2
```

可能改变 serialization。

---

# 47. Migration 原则

不能简单：

```text
old key != new key
→ delete favorite
```

应该：

```text
old identity
    ↓
migration / resolver
    ↓
new identity
```

如果无法迁移：

```text
stale
```

保留，而不是默默删除。

---

# 48. Favorite Repository

推荐：

```rust
pub trait FavoriteRepository {
    fn get(&self, identity: &SearchIdentity) -> Result<Option<Favorite>>;
    fn list(&self) -> Result<Vec<Favorite>>;
    fn add(&self, identity: &SearchIdentity) -> Result<()>;
    fn remove(&self, identity: &SearchIdentity) -> Result<()>;
}
```

Pin：

```rust
pub trait PinRepository {
    fn list(&self, location: PinLocation) -> Result<Vec<Pin>>;
    fn pin(&self, pin: Pin) -> Result<()>;
    fn unpin(&self, identity: &SearchIdentity) -> Result<()>;
    fn reorder(&self, identity: &SearchIdentity, order: u32) -> Result<()>;
}
```

---

# 49. Repository 不是 Action Engine

Repository 是：

```text
persistence implementation
```

不是：

```text
Effect gateway
```

所以：

```text
UI
  → Repository
```

仍然禁止。

正确：

```text
UI
  → Action
  → launcher-action
  → FavoriteService
  → Repository
```

---

# 50. FavoriteService

建议：

```rust
pub struct FavoriteService {
    favorites: FavoriteRepository,
    pins: PinRepository,
}
```

职责：

```text
favorite invariants
pin invariants
transactions
reorder
```

它不负责：

```text
Search ranking
UI
Action authorization
```

---

# 51. Service 与 Action Engine 的边界

非常明确：

```text
ActionEngine
    = authorization + Effect execution gateway

FavoriteService
    = domain operation implementation
```

链路：

```text
ActionResolver
      ↓
launcher-action::execute()
      ↓
system.favorite.add
      ↓
FavoriteService
      ↓
SQLite
```

不要反过来：

```text
FavoriteService
    → ActionEngine
```

否则出现循环权限依赖。

---

# 52. Favorite Mutation Effect

如果当前 Effect abstraction 需要记录：

```text
system.favorite.add
```

建议直接使用：

```text
Effect {
    effect_type = "system.favorite.add"
    input = {...}
}
```

不新增：

```rust
ActionKind::FavoriteAdd
```

仍然遵守现有：

> Effect type 是开放 namespace string。

---

# 53. Audit / History

Favorite mutation 可以写入 usage/history：

```text
favorite.add
favorite.remove
pin
unpin
```

但：

> Favorite mutation 不应该成为普通 Search usage。

否则：

```text
Ctrl+D
```

会被误认为用户“执行了该应用”。

所以：

```text
Search usage history
```

与：

```text
User preference audit
```

应分离。

---

# 54. Ranking History 边界

例如：

用户：

```text
Ctrl+D Chrome
```

然后搜索：

```text
chr
```

Favorite boost 可以提升 Chrome。

但不能：

```text
favorite mutation
→ execution_count++
```

否则 Usage Model 污染。

```text
正常执行 Chrome
```

这应该产生：

```text
Recent / usage event
```

但是：

```text
Add Favorite Chrome
```

不应该产生。

```text

    ↓
success event

    ↓
SearchCatalog / Main ViewModel
```

```text
UI optimistic update
    ↓
database failed
    ↓
UI remains wrong
```

即数据库事务成功以后再发布 UI state change。

Favorite resolution always resolves against current live Catalog/Index state.

Pin implies Favorite in v0.1.

### `INV-FAV-007`

Unfavorite atomically removes associated Pin.

### `INV-FAV-008`

Favorite mutations do not increment normal execution/usage counters.

### `INV-FAV-009`

Favorite identity serialization is deterministic.

### `INV-FAV-010`

No UI component directly mutates Favorite persistence.
