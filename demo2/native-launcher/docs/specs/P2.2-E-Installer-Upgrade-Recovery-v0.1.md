# P2.2-E — Windows Installer / Upgrade / Recovery v0.1

## 1. 批次目标

将 Launcher 本身纳入与 Plugin Management 相同的安全生命周期模型：

```text
Install
  ↓
Stage
  ↓
Validate
  ↓
Quiesce
  ↓
Activate
  ↓
Migrate
  ↓
Health Check
  ↓
Running
```

失败：

```text
Health Check Failed
  ↓
Rollback / Repair
  ↓
Restart
```

同时建立：

- Windows Installer；
- staged upgrade；
- atomic activation；
- single-instance coordination；
- crash recovery；
- data migration；
- interrupted upgrade recovery；
- rollback；
- repair；
- uninstall；
- release channel/version policy。

---

# 2. 产品交付策略

## 2.1 Primary Installer

正式发行包：

```text
Launcher_<version>_<arch>.msix
```

多架构场景：

```text
Launcher_<version>.msixbundle
```

MSIX bundle 可承载多个架构，Windows 选择适用的 package。

---

## 2.2 为什么采用 MSIX

MSIX 已经提供：

```text
Install
Uninstall
Upgrade
Downgrade
Package isolation
Package identity
Differential update
```

官方文档明确说明，MSIX 更新可以只处理发生变化的文件块，并支持同一 package family 内的版本更新。

因此本项目不再实现：

```text
custom executable copier
custom DLL replacement
custom MSI-like registry installer
```

---

# 3. 一个关键区分

MSIX 的：

```text
Package Deployment
```

与 Launcher 的：

```text
Product Upgrade Transaction
```

不是同一层。

最终：

```text
                  Launcher Upgrade

             ┌─────────────────────┐
             │ Product Coordinator │
             └──────────┬──────────┘
                        │
           ┌────────────┼────────────┐
           ▼            ▼            ▼
       Preflight     Data          Recovery
                      Migration
           │            │            │
           └────────────┼────────────┘
                        ▼
                  MSIX Deployment
                        │
                        ▼
                   New Package
```

Launcher 不重新实现 Windows package deployment。

---

# 4. 核心生命周期对象

建议：

```rust
pub struct UpgradeTransaction {
    pub transaction_id: UpgradeTransactionId,

    pub current_version: ProductVersion,
    pub target_version: ProductVersion,

    pub state: UpgradeState,

    pub started_at: Timestamp,
}
```

---

# 5. UpgradeState

```rust
pub enum UpgradeState {
    None,

    Staging,
    Validating,

    WaitingForExit,
    Activating,

    Migrating,
    HealthChecking,

    Completed,

    Failed,
    RollingBack,
    Recovered,
}
```

状态必须持久化，以便进程 crash 后判断：

```text
“上一次升级进行到哪里了？”
```

---

# 6. Upgrade Transaction ID

```rust
pub struct UpgradeTransactionId(pub String);
```

它必须独立于：

```text
ExecutionId
RuntimeId
ProtocolSessionId
SearchRequestId
```

例如：

```text
Upgrade U1
    Plugin Execution E1
    Runtime R1
```

完全不同的生命周期。

---

# 7. Version Identity

Launcher product version：

```rust
pub struct ProductVersion {
    pub major: u16,
    pub minor: u16,
    pub patch: u16,
}
```

不与：

```text
PluginVersion
ProtocolVersion
ManifestSchemaVersion
```

混用。

# 8. 安装模式

Launcher 1.0：

```text
Per-user installation
```

目标：

```text
用户无需 Administrator
```

但实际 Windows package 能否进行特定部署操作仍受 Windows package policy / package registration 条件限制；因此产品不能假设“所有安装场景绝对无需权限”。

MSIX 的 per-user 安装和 `Add-AppxPackage` 属于当前 Windows deployment 模型。

---

# 9. Package Identity

MSIX 安装后的 package identity：

```text
Package Family
Package Full Name
Application Identity
```

与内部：

```text
ProductVersion
```

分开。

Launcher 自己的 canonical product identity 固定：

```text
com.<vendor>.launcher
```

例如：

```text
Package Family Name
    = launcher package identity

ProductVersion
    = 1.0.0
```

---

# 10. Application Data 必须与 Binary 生命周期分离

核心原则：

```text
Package
    = immutable application payload

User State
    = mutable persistent state
```

用户状态包含：

```text
Config
Favorites
History
File Index
Application Catalog
Plugins
Plugin Data
Icon Cache
Search cache
Logs
```

这些都不能依赖：

```text
“当前版本的 executable 目录”
```

---

# 11. 推荐数据分类

```text
Persistent State
├── config
├── favorites
├── history
├── database
├── plugin policy
└── plugin data

Rebuildable State
├── File Index
├── Application Catalog
├── Icon Cache
└── Search Cache

Diagnostic State
└── Logs / Crash reports
```

这样升级失败时，可以明确决定：

```text
Preserve
Migrate
Rebuild
Discard
```

---

# 12. Data Contract

推荐：

```rust
pub struct DataSchemaVersion(pub u32);
```

数据库必须具有：

```text
schema_version
```

不要把：

```text
ApplicationVersion
```

直接当：

```text
DatabaseSchemaVersion
```

---

# 13. Migration

启动新版本：

```text
database schema N
```

目标：

```text
schema N+1
```

执行：

```text
Migration N → N+1
```

每个 migration 必须：

```text
deterministic
transactional
versioned
```

---

# 14. Migration 原则

禁止：

```text
“打开数据库以后发现旧结构，然后临时修修补补”
```

必须：

```text
Current Schema
    ↓
Migration Planner
    ↓
N → N+1
    ↓
N+1 → N+2
    ↓
...
    ↓
Current
```

---

# 15. Migration Transaction

单个 migration：

```text
BEGIN
    schema changes
    data transformation
    metadata update
COMMIT
```

失败：

```text
ROLLBACK
```

---

# 16. Migration Backup

对于 potentially destructive migration：

```text
database
    ↓
backup
    ↓
migration
```

Backup 必须：

```text
versioned
atomic
bounded
```

例如：

```text
backup/
    pre-migration-v12.db
```

不需要无限保留。

---

# 17. Migration Journal

建议：

```text
migration_journal
-------------------------
migration_id
from_version
to_version
started_at
completed_at
status
```

状态：

```text
Started
Completed
Failed
RolledBack
```

用于 crash recovery。

---

# 18. Upgrade Preflight

在真正激活新版本前：

```text
Preflight
```

检查：

```text
current installation valid
disk space sufficient
database readable
migration path exists
target version compatible
single-instance handoff possible
pending previous upgrade resolved
```

---

# 19. Preflight 不执行新版本业务代码

不要：

```text
download v2
→ launch v2 arbitrary setup code
→ “check一下”
```

Preflight 必须由：

```text
Installer / Update Coordinator
```

执行。

---

# 20. Staging

推荐 staging：

```text
Update Package
    ↓
local staging
    ↓
validate
```

至少检查：

```text
Package identity
Version
Architecture
Signature / package integrity
Manifest
```

然后交给：

```text
MSIX deployment
```

---

# 21. Atomic Activation

这里需要区分两个层次。

### Windows package activation

由 MSIX deployment engine 负责。

### Launcher product activation

由：

```text
UpgradeTransaction
```

负责状态切换：

```text
Pending
→ Active
```

不要自行替换：

```text
Launcher.exe
```

---

# 22. 为什么不自建 active.exe pointer

Plugin 可以使用：

```text
active_instance_id
```

因为 Plugin 是我们的普通用户态资源。

Launcher 本身则已经由 Windows package identity 管理版本。

所以 Launcher 不需要：

```text
Launcher\
    versions\
        1.0\
        1.1\
    active.json
```

作为自身 executable dispatch mechanism。

否则会重新制造：

```text
自更新 bootstrapper
```

及额外攻击面。

---

# 23. Handoff

Launcher 正在运行：

```text
Launcher v1
```

用户触发：

```text
Update to v2
```

流程：

```text
v1
 │
 ├── save runtime state
 ├── stop accepting new work
 ├── flush databases
 ├── stop plugins
 ├── unregister hotkey
 └── release single instance
          │
          ▼
     MSIX activation
          │
          ▼
       Launcher v2
```

---

# 24. SingleInstanceGuard

已有：

```text
CreateMutex
```

继续作为 Launcher 唯一实例机制。

关键生命周期：

```text
main
 ├── acquire mutex
 ├── initialize
 ├── run
 └── release mutex
```

Mutex handle 必须活到：

```text
main exit
```

不能再次出现此前的：

```text
guard dropped early
```

问题。

---

# 25. Update Handoff Protocol

v1 退出前写：

```text
update_handoff.json
```

建议：

```json
{
  "transaction_id": "U-123",
  "target_version": "1.1.0",
  "reason": "user_update",
  "started_at": "...",
  "resume": true
}
```

文件本身：

```text
temporary
atomic replace
```

---

# 26. 不保存敏感状态

handoff 不保存：

```text
clipboard
query content
plugin payload
credentials
tokens
```

只保存：

```text
upgrade metadata
```

---

# 27. Process Shutdown

正常更新：

```text
Stop accepting new work
        ↓
Finish safe transient operations
        ↓
Flush state
        ↓
Stop Plugin Runtime
        ↓
Stop MCP Runtime where applicable
        ↓
Release resources
        ↓
Exit
```

---

# 28. Action Execution During Upgrade

一旦：

```text
UpgradeState >= WaitingForExit
```

禁止新的：

```text
ActionEngine execution
```

即：

```text
new action
    → rejected / launcher shutting down
```

已经执行中的 Action：

```text
ExecutionId = E1
```

不应被粗暴 replay。

---

# 29. Workflow / Agent

同样：

```text
Upgrade start
```

必须阻止：

```text
new workflow run
new agent run
```

当前正在运行的：

```text
Workflow
Agent
```

v0.1 建议：

> Upgrade 必须等待其进入安全终止状态；不做跨版本恢复执行。

---

# 30. 为什么不恢复 Workflow / Agent

因为：

```text
Action
Plugin
Runtime
MCP
```

都可能在新版本发生：

```text
schema change
capability change
behavior change
```

因此：

```text
“恢复 UI 状态”
```

和：

```text
“继续执行之前任务”
```

必须彻底区分。

---

# 31. Upgrade Snapshot

退出前保存：

```rust
pub struct ShutdownSnapshot {
    pub last_index_generation: IndexGeneration,
    pub last_application_generation:
        ApplicationCatalogGeneration,

    pub user_state_generation:
        UserStateGeneration,
}
```

只是 diagnostics/recovery metadata。

---

# 32. File Index

正常升级：

```text
existing File Index
    → preserve
```

原因：

```text
rebuild
```

通常是昂贵操作。

升级后：

```text
Watcher reconnect
    ↓
incremental reconciliation
```

如 schema unchanged，不重建。

---

# 33. Application Catalog

同理：

```text
existing catalog
    → preserve
```

新版本：

```text
Application Discovery reconciliation
```

后台重新确认即可。

---

# 34. Query Cache

不要迁移。

直接：

```text
discard
```

因为它是：

```text
rebuildable transient state
```

升级后自然为空。

---

# 35. Icon Cache

默认：

```text
preserve
```

但是：

```text
extractor_version
```

发生变化：

```text
old cache
    → naturally invalid
```

不用整个删除。

---

# 36. Plugin State

升级 Launcher：

```text
Plugin Registry
    → preserve
```

但 Plugin runtime：

```text
stop
```

升级后：

```text
new Launcher
    → fresh RuntimeManager
```

---

# 37. Plugin Version vs Launcher Version

Launcher v1 → v2：

```text
Plugin binaries
```

默认不自动升级。

只有：

```text
Plugin Manager
```

自己的 update policy 才改变 plugin version。

---

# 38. Config Migration

配置：

```text
v1
```

升级：

```text
v2
```

执行：

```text
config migration
```

不得：

```text
delete config
```

除非：

```text
irrecoverably invalid
```

此时：

```text
backup old config
→ reset
```

---

# 39. Favorites Migration

Favorite schema 若没有改变：

```text
keep
```

如果 identity serialization 改变：

```text
old identity
    ↓
migration resolver
    ↓
new identity
```

无法转换：

```text
stale
```

而不是：

```text
delete
```

---

# 40. Database Migration Failure

如果：

```text
Launcher v2 startup
migration fails
```

不要进入正常运行。

状态：

```text
RecoveryRequired
```

进入：

```text
Recovery Mode
```

# 41. Recovery Mode

Recovery Mode 是一个非常小的产品模式，只允许：

```text
Repair
Rollback
Reset Rebuildable Data
Export Diagnostics
Uninstall
```

不允许：

```text
normal search
plugin execution
MCP execution
workflow
agent
```

---

# 42. Recovery Mode UI

建议极简：

```text
Launcher Recovery

The last update could not be completed.

Version:
1.1.0

Problem:
Database migration failed.

[ Repair ]
[ Restore Previous State ]
[ Rebuild Index ]
[ Export Diagnostics ]
[ Uninstall ]
```

不要进入完整 Launcher UI。

# 43. Health Check

新版本首次启动：

```text
HealthCheck
```

最小：

```text
process alive
config readable
database open
migration complete
single instance acquired
core services initialized
UI initialized
```

---

# 44. Health Check 不执行 Plugin Effects

新版本启动时：

```text
plugin runtime
```

默认不启动。

因此：

```text
Launcher core healthy
```

不依赖：

```text
Plugin healthy
```

---

# 45. Health Check Window

需要定义：

```text
StartupHealthState
```

例如：

```rust
pub enum StartupHealth {
    Starting,
    Healthy,
    Failed,
}
```

启动成功后：

```text
Healthy marker
```

原子写入：

```text
last_startup.ok
```

---

# 46. Crash During First Launch

流程：

```text
v2 activates
 ↓
v2 crashes
 ↓
no healthy marker
```

下一次启动：

```text
detect incomplete upgrade
```

进入：

```text
Recovery
```

如果失败次数超过：

```text
threshold
```

自动：

```text
rollback
```

---

# 47. Crash Threshold

建议：

```toml
[update.recovery]
max_failed_startups = 2
```

实际默认值应通过测试后冻结。

关键：

```text
bounded
```

而不是：

```text
retry forever
```

---

# 48. Upgrade State Journal

推荐：

```text
upgrade_state
--------------------------------
transaction_id
current_version
target_version
state
attempt
started_at
updated_at
last_error
```

这样：

```text
crash
```

之后还能恢复状态。

---

# 49. State Recovery

启动：

```text
read upgrade_state
```

如果：

```text
state = Completed
```

正常启动。

如果：

```text
state = Activating
state = Migrating
state = HealthChecking
```

说明：

```text
previous upgrade interrupted
```

进入 recovery decision。

---

# 50. Upgrade Decision Table

| 状态 | 启动行为 |
|---|---|
| None | Normal |
| Completed | Normal |
| Staging | Resume / discard |
| Validating | Validate again |
| WaitingForExit | recover handoff |
| Activating | inspect installed version |
| Migrating | migration recovery |
| HealthChecking | startup retry / rollback |
| Failed | Recovery |
| RollingBack | finish rollback |
| Recovered | Normal |

---

# 51. 不允许“猜状态”

例如：

```text
active_version = v2
upgrade_state = Activating
```

不能仅凭：

```text
v2 exists
```

就认为：

```text
Upgrade successful
```

必须：

```text
Health Check
```

确认。

---

# 52. Rollback

MSIX 当前支持同一 package family 的降级场景；App Installer 可以通过 `ForceUpdateFromAnyVersion` 允许高低版本切换。

因此 Launcher 自身 rollback 不需要自建 executable swapping。

产品层：

```text
rollback requested
    ↓
select previous package
    ↓
Windows package deployment
    ↓
health check
```

---

# 53. Rollback 的最大风险：Data Compatibility

Windows 文档明确提醒，MSIX downgrade 会保留 appdata，因此新版本写入的数据即使回到旧版本也仍然存在；如果新版本数据格式不向后兼容，直接 downgrade 可能产生问题。

因此：

> **Rollback 不是“把 executable 换回去”就结束。**

必须同时解决：

```text
Binary version
+
Data schema compatibility
```

---

# 54. Database Compatibility Policy

建议：

```rust
pub enum RollbackCompatibility {
    FullyCompatible,
    RequiresRestore,
    Unsupported,
}
```

如果：

```text
v2 database schema
```

无法被：

```text
v1
```

读取：

必须：

```text
restore pre-upgrade database
```

而不是让 v1 强行打开 v2 数据库。

---

# 55. Pre-Upgrade Snapshot

在可能 destructive migration 之前：

```text
State Snapshot
├── config
├── database
└── user-state metadata
```

不需要备份：

```text
File Index
Icon Cache
Search Cache
```

这些都可以重建。

---

# 56. Snapshot Strategy

建议：

```text
%LOCALAPPDATA%\Launcher\Backups\
    upgrade-<transaction-id>\
        config/
        launcher.db
        metadata.json
```

但具体路径应继续通过 Config/Known Folder 层获得，不在业务代码硬编码。

---

# 57. Snapshot Retention

默认：

```text
current
+
previous successful upgrade
```

即可。

例如：

```text
max_upgrade_backups = 2
```

具体容量政策后续 benchmark。

---

# 58. Recovery Priority

发生问题时：

```text
1. Repair
2. Restore compatible state
3. Rollback package
4. Rebuild derived state
5. Reset only as last resort
```

不能：

```text
Reset everything
```

作为第一反应。

---

# 59. Repair

Repair 目标：

```text
package valid
database valid
config valid
```

可以：

```text
re-register package
reconcile catalog
rebuild File Index
rebuild icon cache
```

但：

```text
Favorites
History
Plugin policy
```

不得默认删除。

---

# 60. Rebuildable State

恢复优先：

```text
Search Cache
Icon Cache
File Index
Application Catalog
```

因为：

```text
rebuildable
```

而不是直接恢复 backup。

---

# 61. File Index Recovery

如果数据库损坏：

```text
restore DB backup
```

如果只有：

```text
File Index tables
```

损坏：

可以：

```text
drop index
rebuild in background
```

而保留：

```text
Favorites
Config
History
```

---

# 62. Application Catalog Recovery

同理：

```text
drop catalog
reconcile sources
```

不影响：

```text
Favorite identity
```

---

# 63. Plugin Registry Recovery

Plugin Registry 不属于 rebuildable state。

必须优先：

```text
restore
```

因为它包含：

```text
enabled state
capability policy
active plugin version
quarantine state
```

这些都是用户/安全状态。

---

# 64. Upgrade Failure 与 Plugin State

升级 Launcher 失败：

```text
Launcher rollback
```

Plugin Registry：

```text
preserve
```

Plugin binary：

```text
preserve
```

除非：

```text
Launcher protocol incompatible
```

才标记：

```text
Plugin unavailable
```

而不是删除插件。

---

# 65. Single Instance During Rollback

正常：

```text
v2 process
```

必须完全退出后：

```text
v1 activation
```

不能同时：

```text
v2 Launcher
v1 Launcher
```

都认为自己是 primary instance。

Mutex 是最后门槛。

---

# 66. Second-instance Behavior

已有设计中：

```text
second instance
```

最终应该：

```text
IPC activate existing
```

但是 Update/Recovery 场景：

```text
existing instance = shutting down
```

必须：

```text
reject / defer
```

不能把正常 invocation 发给已经进入：

```text
WaitingForExit
```

的 process。

---

建议新增：

```rust
pub struct UpgradeCoordinator {
```

职责：

```text
check
```

# 91. Security Invariants

新增：

### `INV-UPDATE-001`

Launcher binaries are never self-overwritten in place.

### `INV-UPDATE-002`

Update activation is delegated to the OS package deployment layer.

### `INV-UPDATE-003`

Persistent user state is independent from executable version.

### `INV-UPDATE-004`

Interrupted upgrade state is detectable after crash.

### `INV-UPDATE-005`

New version is not considered successful until health check passes.

### `INV-UPDATE-006`

Failed startup recovery is bounded; no infinite restart loop.

### `INV-UPDATE-007`

Rollback must account for data schema compatibility.

### `INV-UPDATE-008`

A migration failure cannot silently discard user state.

### `INV-UPDATE-009`

Upgrade cannot resume or replay previous Action/Workflow/Agent execution.

### `INV-UPDATE-010`

Only one Launcher process may own the active instance during upgrade/recovery.

### `INV-UPDATE-011`

Recovery infrastructure cannot become an Effect gateway.

### `INV-UPDATE-012`

Update state and transaction IDs are separate from `ExecutionId`, `RuntimeId`, and `ProtocolSessionId`.
