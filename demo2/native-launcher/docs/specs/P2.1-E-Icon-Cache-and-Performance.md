# P2.1-E — Icon Cache + Application Visuals + Search Performance Baseline

这一批正式处理两个问题：

```text
Application Catalog
        │
        ├──► Icon Pipeline
        │
        └──► Search Performance Baseline
```

但两者保持严格隔离：

```text
Icon Pipeline
    = “如何快速得到应用视觉资源”

Performance Baseline
    = “如何证明 Launcher 足够快、稳定、低内存”
```

**不在本批次继续扩展 Application Discovery，也不实现 Query Cache。**

---

# 1. 本批次目标

最终形成：

```text
                     ApplicationEntry
                            │
                            ▼
                         IconKey
                            │
                            ▼
                     IconResolver
                            │
                    ┌───────┴────────┐
                    ▼                ▼
               Memory Cache      Disk Cache
                    │                │
                    └───────┬────────┘
                            ▼
                       Icon Bitmap
                            │
                            ▼
                            UI
```

并同时建立：

```text
SearchRequest
      │
      ▼
SearchCoordinator
      │
      ▼
Performance Instrumentation
      │
      ├── startup → first result
      ├── query latency
      ├── result publication latency
      ├── catalog/index maintenance impact
      ├── memory
      └── CPU
```

---

# 2. 为什么 Icon 必须独立成 Pipeline

Windows Shell 本身有 system image list，可以通过 `SHGetImageList` 获取不同规格的系统图像列表，例如 large/small/extra-large 等。([Microsoft Learn][1])

但 Launcher 不应该：

```text
SearchResult
    ↓
每次 render
    ↓
Shell API
    ↓
extract icon
```

因为这会把：

```text
COM / Shell / icon decoding / filesystem
```

全部塞进 UI 渲染链。

尤其搜索结果快速刷新时：

```text
query = "chr"
query = "chro"
query = "chrom"
query = "chrome"
```

很容易产生重复 icon extraction。

所以正式引入：

> **IconKey → Resolver → Cache → Bitmap**

---

# 3. Icon 核心模型

建议放在 `launcher-domain` 的轻量模型：

```rust
pub struct IconKey {
    pub identity: ApplicationIdentityV2,
    pub variant: IconVariant,
}
```

```rust
pub enum IconVariant {
    Small,
    Normal,
    Large,
}
```

但这里需要进一步明确：

> **Identity 不等于 Icon Cache Key。**

因为同一个 application：

```text
Chrome
```

可能有：

```text
16x16
24x24
32x32
48x48
```

甚至未来：

```text
Dark
Light
HighContrast
```

因此更完整的是：

```text
IconCacheKey
    = ApplicationIdentity
    + IconVariant
    + ThemeVariant
```

---

# 4. IconSource

Application Catalog 中只记录：

```rust
pub enum IconSource {
    PackageResource,
    Executable,
    Shortcut,
    Shell,
}
```

其中 Packaged Application 可以从 manifest visual metadata 得到 logo 资源。Windows 的 `uap:VisualElements` 明确定义了 `Square44x44Logo`、`Square150x150Logo` 等视觉资源字段。([Microsoft Learn][2])

注意：

> Catalog 记录“图标来自哪里”，Icon subsystem 决定“如何取”。

---

# 5. 不让 ApplicationEntry 持有 Bitmap

错误：

```rust
pub struct ApplicationEntry {
    pub icon: Vec<u8>,
}
```

这样 Application Catalog：

```text
1000 apps
```

很容易直接持有大量图像内存。

正确：

```rust
pub struct ApplicationEntry {
    pub icon_key: Option<IconKey>,
}
```

实际 bitmap：

```text
IconCache
```

单独管理。

# 6. IconResolver

建议：

```rust
pub trait IconResolver {
    fn resolve(
        &self,
        request: &IconRequest,
    ) -> Result<IconBitmap, IconError>;
}
```

Request：

```rust
pub struct IconRequest {
    pub key: IconKey,
    pub size: u32,
}
```

# 7. Icon Resolver Pipeline

```text
IconRequest
    │
    ▼

    │
    ├── hit ───────────► Bitmap

    └── miss
          │
          ▼
      DiskCache
          │

                ▼
```

# 8. Cache 层级

推荐：

```text
L1 = in-memory
L2 = disk
L3 = source extraction
```

即：

```text
L1
  ↓ miss
L2
  ↓ miss
L3
```

绝不能：

```text
L1 miss
    ↓
every time Shell extraction
```

---

# 9. Memory Cache

第一版使用：

```text
LRU
```

并设置硬预算：

```text
max_entries
max_bytes
```

因为：

```text
1000 icons × 32KB
```

与：

```text
1000 decoded 256x256 RGBA
```

完全不是一个数量级。

因此 cache 的主要限制应该是：

> **bytes，而不是 entry count。**

---

# 10. Icon Bitmap 格式

建议内部统一：

```rust
pub struct IconBitmap {
    pub width: u32,
    pub height: u32,
    pub rgba: Arc<[u8]>,
}
```

统一为 RGBA 可以让：

```text
Slint
```

最终消费时不需要理解：

```text
ICO
PNG
DIB
HICON
Shell image list
```

# 11. Windows HICON 不跨边界

不要把：

```text
HICON
HIMAGELIST
IShellItem
PIDL
```

放进：

```text
launcher-domain
launcher-search
launcher-ui
```

它们只能存在：

```text
launcher-providers / Windows integration
```

或专门的 icon implementation。

Shell image list 本质上是 Windows Shell 的图像资源体系，因此应留在 Windows adapter 层。([Microsoft Learn][1])

---

# 12. Icon Extraction Strategy

推荐按优先级：

```text
Packaged
    1. Manifest visual resource

Win32
    1. Shell / system icon
    2. Executable resource

Shortcut
    1. Shortcut-associated icon
    2. Resolved target

Fallback
    1. generic application icon
```

不要自己重新实现 Windows icon selection 算法。

---

# 13. Shortcut 与 Target Icon

例如：

```text
Chrome.lnk
    target = chrome.exe
```

应该优先：

```text
Shortcut metadata icon
```

还是：

```text
Target executable icon
```

这里建议保留 source preference：

```text
StartMenu shortcut
    → shortcut icon if explicitly provided

otherwise
    → target icon
```

否则有些 installer 自带 `.lnk` custom icon 会丢失。

---

# 14. Packaged Icon

Packaged App 不要假设：

```text
icon = executable icon
```

因为 manifest 的 visual elements 可以明确指定 logo 资源。Windows 文档也明确指出这些 logo 字段属于 Application 的视觉元数据。([Microsoft Learn][2])

因此：

```text
Package
  ↓
Manifest
  ↓
VisualElements
  ↓
IconSource::PackageResource
```

# 16. Icon Disk Cache


# 17. Disk Cache Key

不要：

```text
hash(display_name)
```

应该：

```text
hash(
    identity
    + icon_variant
    + extractor_version
)
```

即：

```text
IconCacheKey
```

---

# 18. 为什么必须有 Extractor Version

以后你修改：

```text
icon extraction
resize
background handling
alpha processing
```

旧 cache 可能继续被使用。

因此：

```text
extractor_version = 1
```

升级：

```text
extractor_version = 2
```

自然失效旧缓存。

无需：

```text
delete all cache on every startup
```

---

# 19. Icon Cache 文件格式

建议：

```text
PNG
```

原因不是因为速度最快，而是：

```text
transparent alpha
portable
debuggable
stable
```

同时：

```text
memory cache
```

始终存 decoded RGBA。

所以：

```text
disk = encoded
memory = decoded
```

---

# 20. Atomic Cache Write

必须：

```text
temp file
   ↓
flush
   ↓
rename
```

而不是：

```text
write final.png
```

否则 crash 可能留下：

```text
corrupted cache file
```

---

# 21. Broken Cache

读取失败：

```text
corrupt
truncated
invalid PNG
```

应：

```text
delete cache entry
↓
re-extract
```

不能：

```text
panic
```

# 22. Icon Request Dedup

非常重要。

如果 UI 同时请求：

```text
Chrome 32
Chrome 32
Chrome 32
```

不能启动：

```text
3 extraction tasks
```

需要：

```text
in-flight map
```

例如：

```text
IconKey
    │
    ▼
InFlightRequest
    │
    ├── Consumer A
    ├── Consumer B
    └── Consumer C
```

只做一次 extraction。

---

# 23. 这不是 Search Dedup

必须区分：

```text
SearchCandidate dedup
```

和：

```text
IconRequest dedup
```

前者：

```text
semantic identity
```

后者：

```text
same resource work
```

两个系统不要合并。

---

# 24. Icon Loading 不能阻塞 Search

搜索：

```text
ApplicationEntry
```

立即返回：

```text
icon_key
```

而不是：

```text
wait icon extraction
```

所以：

```text
SearchResult
    ↓
UI renders text immediately
    ↓
IconRequest async
    ↓
bitmap arrives
    ↓
UI refreshes icon
```

这是 Launcher 感知性能最重要的设计之一。

```text

```

只转换为：

Windows Shell 有 icon overlay 体系，例如 shortcut/link overlay、shared 等；这些 overlay 位于 Shell system image list。([Microsoft Learn][3])

但 Launcher 1.0 **不应该把 Shell overlays 直接纳入 Application Icon**。

例如：

```text

```

不是：

```text
Application semantic icon
```

否则：

```text

```

和：

```text
chrome.exe
```

会得到视觉不同但 semantic identity 相同的图标。

第一版只取：

> **base icon**

# 33. 性能指标

至少冻结以下：

| Metric          | 含义                    |
| --------------- | --------------------- |
| Cold startup    | 进程启动到可交互              |
| Warm startup    | 已有 catalog/index 到可交互 |
| TTF             | Query 开始到首批结果         |
| TTFR            | Query 开始到首个可用结果       |
| TTL             | Query 到最终结果           |
| P50             | 中位数                   |
| P95             | 尾延迟                   |
| Memory idle     | 空闲工作集                 |
| Memory search   | 搜索高峰工作集               |
| CPU search      | 搜索期间 CPU              |
| Catalog rebuild | 后台 catalog 重建耗时       |
| Icon cold       | 首次 icon 获取            |
| Icon warm       | cache hit             |

---

# 34. Startup 定义必须严格

不能笼统叫：

```text
startup = process start
```

建议分成：

```text
T0 = process created

T1 = configuration loaded

T2 = index/catalog opened

T3 = UI created

T4 = hotkey ready

T5 = launcher visible

T6 = first input accepted
```

其中用户最关心的是：

```text
T0 → T4
```

以及：

```text
T0 → T6
```

---

# 35. Search Latency 定义

例如：

```text
Tq0
user query submitted

Tq1
coordinator dispatch

Tq2
first candidate available

Tq3
first result published to UI

Tq4
all providers completed

Tq5
final sorted result published
```

因此：

```text
TTFR = Tq3 - Tq0
TTL  = Tq5 - Tq0
```

---

# 36. First Result 比 Final Result 更重要

Launcher 是交互产品。

例如：

```text
MCP provider = 500ms
File provider = 20ms
Application = 5ms
```

用户应该：

```text
5~20ms:
看到应用结果
```

而不是：

```text
500ms:
所有结果一起显示
```

因此 P2.1-C 已经设计 partial result，这里正式把：

```text
TTFR
```

作为核心指标。

# 46. Icon Cache Eviction

推荐：

```text
LRU + byte budget
```

当：

```text
current_bytes > budget
```

执行：

```text
evict until <= target
```

建议设置：

```text
target = 80~90% budget
```

避免反复：

```text
insert
evict
insert
evict
```

形成 thrashing。

实际比例通过 benchmark 定。

# 47. Disk Cache 不需要无限增长

Disk cache 需要：

```text

```

并支持：

```text
periodic cleanup
```

而不是每次启动扫描整个 cache。

# 48. Cache Cleanup

建议：

```text

    ↓

    ↓

```

不要启动阶段：

# 49. Icon Invalidation

以下变化应导致重新获取：

```text
Application identity changed
Extractor version changed
Source identity changed
```

对于 Win32：

```text
executable path
```

改变：

```text
old IconKey != new IconKey
```

自然失效。

---

# 50. Package Icon Invalidation

Packaged application：

```text
PackageFamily + AppId
```

identity 没变化，但：

```text
package version
```

可能变化。

因此 IconKey 最好包含一个：

```text
resource_version
```

或等价 source revision。

否则：

```text
app update
but icon unchanged in cache
```

可能产生旧图标。

建议：

```text
IconSourceRevision
```

纳入 cache key。

# 51. IconKey 最终模型

比较完整地建议：

```rust
pub struct IconKey {
```

其中：


# 56. Icon Cancellation

用户：

```text
query = "chr"
```

请求：

```text
100 icons
```

随后：

```text
query = "chrome"
```

旧 query 的尚未开始的 icon requests 应可以取消。

但注意：

> 已经进入共享 cache 的 extraction 不一定值得取消。

因此：

```text
consumer cancellation
```

与：

```text
underlying extraction cancellation
```

分开。

# 57. Search + Icon Pipeline

最终：

```text
Query
 │
 ▼
SearchCoordinator
 │
 ▼
SearchResult[]
 │
 ├──────────────► UI text immediately
 │
 └──────────────► IconService
                       │
                       ▼
                   cache/extract
                       │
                       ▼
                    UI update
```

这会让 Launcher 主观体验明显优于：

```text
Query
 ↓
```

# 69. 本批次新增不变量

## `INV-ICON-001`

Application Catalog never stores decoded icon bitmaps.

## `INV-ICON-002`

Icon resolution is asynchronous and cannot block SearchResult publication.

## `INV-ICON-003`

Same `IconCacheKey` has at most one active underlying extraction.

## `INV-ICON-004`

Icon memory usage is bounded by a hard byte budget.

## `INV-ICON-005`

Corrupt disk cache entries are recoverable without process failure.

## `INV-ICON-006`

Icon cache identity is based on semantic application identity, not display name.

## `INV-ICON-007`

Icon extraction implementation does not leak Windows resource handles into domain/search/UI.

## `INV-PERF-001`

Performance measurements are reproducible against a versioned dataset.

## `INV-PERF-002`

TTFR is measured independently from final search completion.

## `INV-PERF-003`

Background index/catalog maintenance must not become part of the interactive search critical path.

## `INV-PERF-004`

Performance budgets are derived from Release baselines, not debug measurements.

# 73. P2.1-E Acceptance Gate

建议冻结为 **10 Gate**：

| Gate | 验收条件                                                 |
| ---- | ---------------------------------------------------- |
| E1   | Application 返回 IconKey 而非 Bitmap                     |
| E2   | Win32 / Shortcut / Packaged icon resolver 正常         |
| E3   | Memory cache 命中/淘汰正确且有硬 byte budget                  |
| E4   | Disk cache 原子写入、损坏可恢复                                |
| E5   | 相同 IconKey 的并发请求只产生一次底层 extraction                   |
| E6   | Icon 加载不阻塞 SearchResult 首批发布                         |
| E7   | 125/150/200% DPI 下图标与 UI 布局稳定                        |
| E8   | Search Performance Dataset v1 可重复运行                  |
| E9   | Startup / TTFR / Memory baseline 建立并进入 CI            |
| E10  | Index + Catalog maintenance + Search + Icon 并发压力测试通过 |

其中真正的产品级验收是：

```text
User presses hotkey
       ↓
Launcher appears
       ↓
types "chrome"
       ↓
text result appears immediately
       ↓
icon arrives asynchronously
       ↓
File Index/Catalog may still be updating
       ↓
Search remains responsive
```

也就是说，P2.1 到这里形成了一个完整的数据与表现闭环：

```text
P2.1-B
File Index
        ↓
P2.1-C
SearchCoordinator
        ↓
P2.1-D
Application Catalog
        ↓
P2.1-E
Icon + Performance
```

此时 **P2.1 基础设施阶段基本可以关闭**。接下来就不应继续围绕“搜索基础设施”无限扩张，而应转向真正的 Launcher 1.0 产品能力：**Favorites / Pinning、Query Cache、Context-aware Ranking、插件生态管理，以及 Windows Installer / Upgrade / Recovery**。
