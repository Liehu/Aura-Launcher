# P2.1-C — Search Core & SearchCoordinator 专门批次

P2.1-B 已经把 **Index 的数据供应能力**补齐。下一步应该把 Search 本身冻结下来，而不是立刻做 MSIX/UWP 或图标。

当前架构实际上已经具备：

```text
Hotkey
  ↓
Query
  ↓
Providers
  ├─ Context
  ├─ Application
  ├─ Recent
  ├─ File/Folder
  ├─ MCP
  └─ Plugin
  ↓
Ranking
  ↓
Action
```

问题在于，这个链路还缺一个正式的：

> **SearchCoordinator：统一管理查询生命周期、Provider 并发、取消、超时、失败隔离、候选归一化与身份去重。**

因此 P2.1-C 建议专门解决这一层。

---

# 1. 本批次目标

冻结为：

> **P2.1-C — Search Core & SearchCoordinator v0.1**

最终结构：

```text
User Query
    │
    ▼
SearchCoordinator
    │
    ├── Query normalization
    ├── Query generation / sequence
    ├── Provider dispatch
    ├── Cancellation
    ├── Timeout isolation
    ├── Provider failure isolation
    ├── Candidate normalization
    ├── Semantic identity dedup
    ├── Ranking
    └── Result limiting
    │
    ▼
SearchResults
```

这一批次**不改变 Action 系统**。

Action 仍然维持：

```text
ActionResolver
      ↓
launcher-action::validate()
      ↓
launcher-action::execute()
```

不引入新的执行层。

# 2. P2.1-C 解决的核心问题

现在最需要解决的不是“能不能搜到”，而是：

### 查询生命周期

```text
q1: "chr"
q2: "chro"
q3: "chrom"
```

如果 q1 的 Provider 返回慢：

```text
q1 ────────────────► result
q2 ───────► result
q3 ───► result
```

绝不能让：

```text
q1
```

覆盖：

```text
q3
```

---

### Provider 隔离

```text
ApplicationProvider ─── OK
FileProvider        ─── OK
RecentProvider      ─── OK
McpProvider         ─── ERROR
PluginProvider      ─── OK
```

最终仍然应该得到：

```text
Application
File
Recent
Plugin
```

而不是：

```text
Search failed
```

---

### 结果身份

目前 P2.1-A 的 dedup：

```text
(provider_id, id)
```

只能避免**同一个 Provider 自己重复返回**。

但现在需要进一步：

```text
Start Menu Chrome.lnk
Registry chrome.exe
Recent chrome.exe
```

识别成同一个 semantic candidate。

这正是 P2.1-C 应该正式建立的：

> `SearchIdentity`

# 6. Provider Contract v1

这批次建议正式冻结 Provider：

```rust
pub trait SearchProvider: Send + Sync {

    fn capabilities(&self) -> ProviderCapabilities;

    fn search(
        &self,
        request: &SearchRequest,
        sink: &mut dyn SearchSink,
```

但这里有一个架构选择：

```text

```

而最终：

```text

```

```text

```

负责。

# 10. Cancellation

取消应该是：

```text
new query
   ↓
cancel old request
```

例如：

```text
q1
 ↓
q2
 ↓
q3
```

变成：

```text
q1 → Cancelled
q2 → Cancelled
q3 → Active
```

但必须注意：

> **Cancellation 是 Search 生命周期，不是 Action cancellation。**

不能复用：

```text
ExecutionId
```

也不要与：

```text
Workflow
Agent
Runtime
```

的生命周期混合。

# 11. Provider Timeout

每个 Provider 独立：

```text
Application     50ms
File           100ms
Recent          20ms
MCP            300ms
Plugin         300ms
```

这里只是模型示例，不作为最终冻结数值。

关键是：

```text
timeout(provider)
```

不等于：

```text
timeout(search)
```

例如：

```text
Application → OK
File → OK
MCP → timeout
Plugin → OK
```

最终：

```text
partial results
```

仍然有效。

这一步完成后，Launcher 的搜索链就形成比较清晰的三层：

```text
P2.1-B
Index Layer
    “系统里有什么？”

        ↓

P2.1-C
Search Layer
    “用户现在最可能要什么？”

        ↓

Action Layer
    “当前允许执行什么？”
```

其中最后一层继续严格由已经冻结的 **`launcher-action` = ActionEngine** 承担，不新增第二个 ActionEngine。
