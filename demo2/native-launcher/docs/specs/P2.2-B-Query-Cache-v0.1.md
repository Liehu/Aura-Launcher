> **状态**：IMPLEMENTED (core) — generation-aware Key（含 application/ranking）、LRU 双预算、TTL、final-only、stale 拒绝已落地；SingleFlight/partial-cache 明确不做（final-snapshot-only 语义）。见 docs/history/81-p22-batches-response.md 与 82-p22f-response.md。
>
> **本文件已定稿归档**（源：files2/Launcher 1.0 — P2.2-B Query Cache v0.1 技术设计规范.md）。

# P2.2-B — Query Cache v0.1

## 1. 批次目标

P2.2-B 为 Launcher 1.0 建立受严格一致性约束的 Query Cache。

本批次解决：

1. generation-aware cache key；
2. partial result 与 cache 的边界；
3. stale cache rejection；
4. bounded LRU；
5. memory budget；
6. Cache 与 SearchCoordinator 的并发语义；
7. Cache 与 query cancellation 的关系；
8. empty query / normal query 的缓存策略；
9. cache invalidation；
10. Search result snapshot 的可安全复用。

本批次不实现：

- Disk Query Cache；
- Persistent Query Cache；
- ML ranking cache；
- Result prefetch；
- Semantic / embedding cache；
- HTTP response cache；
- Action / Effect cache；
- Workflow cache；
- Plugin result persistent cache。

核心原则：

> **Query Cache 只缓存 Search Snapshot，不缓存任何可执行 authority。**

---

# 2. 核心问题

SearchCoordinator 当前支持：

```text
User Query
    ↓
Provider dispatch
    ↓
partial results
    ↓
merge
    ↓
ranking
    ↓
final results
```

Query Cache 加入后：

```text
                SearchCoordinator
                       │
                ┌──────┴──────┐
                │             │
             Cache Hit     Cache Miss
                │             │
                ▼             ▼
          Snapshot       Provider Search
                │             │
                │       partial results
                │             │
                │            merge
                │             │
                │           ranking
                │             │
                └──────┬──────┘
                       ▼
                  SearchResult
```

但必须明确：

> **Cache 不参与 Provider 调度，也不参与 Action 执行。**

---

# 3. Cache 的真正边界

缓存对象：

```text
SearchSnapshot
```

不缓存：

```text
ResolvedAction
Effect
ExecutionResult
ActionEngine state
Provider runtime
MCP session
Plugin runtime
```

所以：

```text
Cache
  → SearchResultSnapshot
  → UI
```

而：

```text
SearchResult
  → ActionDescriptor
  → ActionResolver
  → launcher-action
```

仍然重新验证。

---

# 4. Generation-aware 是硬约束

Search result 的有效性依赖多个数据域：

```text
File Index
Application Catalog
User State
Context
```

因此 Cache Key 至少包含：

```rust
pub struct SearchCacheKey {
    pub normalized_query: String,
    pub mode: SearchMode,

    pub file_generation: IndexGeneration,
    pub application_generation: ApplicationCatalogGeneration,
    pub user_state_generation: UserStateGeneration,
    pub context_generation: ContextGeneration,
}
```

---

# 5. 为什么必须多个 Generation

例如：

```text
query = "chrome"
file_generation = 100
app_generation = 20
user_state_generation = 5
context_generation = 8
```

如果 Favorite 改变：

```text
user_state_generation:
5 → 6
```

那么：

```text
old cache key ≠ new cache key
```

自然 miss。

不需要：

```text
scan all cached queries
```

逐个判断。

---

# 6. 不允许只使用一个 Global Generation

错误：

```text
global_generation++
```

任何状态变化都：

```text
invalidate entire search cache
```

这会导致：

```text
File Index update
    →
all application-only searches invalidated
```

过于粗糙。

当前必须至少保持：

```text
file_generation
application_generation
user_state_generation
context_generation
```

独立。

---

# 7. Context Generation

P2.2-C 尚未实现完整 Context Ranking，因此本批次只预留：

```rust
pub struct ContextGeneration(pub u64);
```

即使当前永远：

```text
0
```

也可以。

以后 Context 改变：

```text
generation++
```

Cache 自动失效。

---

# 8. SearchCacheKey 的 Query Normalization

Cache key 使用：

```text
normalized_query
```

而不是 UI 原始字符串。

例如：

```text
" Chrome "
"chrome"
"CHROME"
```

如果 P2.1-C 的 query normalization 已定义为等价，则：

```text
same normalized query
→ same cache key
```

但不要在 Cache 层重新定义 Query normalization。

必须复用 SearchCoordinator 的 canonical normalization。

---

# 9. SearchMode

Cache key 必须包含：

```rust
mode: SearchMode
```

因为：

```text
Empty
Normal
```

不是同一个查询语义。

例如：

```text
query = ""
mode = Empty
```

不能与：

```text
query = ""
mode = Normal
```

混用。

---

# 10. Context Snapshot 不直接进入 Key

不要：

```rust
context_json: String
```

因为这会使 Cache Key：

```text
huge
unstable
```

正确：

```text
ContextSnapshot
    ↓
ContextGeneration
```

Key 只存：

```text
context_generation
```

---

# 11. Cache Value

建议：

```rust
pub struct SearchCacheEntry {
    pub key: SearchCacheKey,

    pub snapshot: SearchSnapshot,

    pub created_at: Timestamp,
    pub last_accessed_at: Timestamp,

    pub size_bytes: usize,
}
```

---

# 12. SearchSnapshot

推荐：

```rust
pub struct SearchSnapshot {
    pub request_context: SearchSnapshotContext,
    pub results: Arc<[SearchResultSnapshot]>,
}
```

其中：

```rust
pub struct SearchResultSnapshot {
    pub identity: SearchIdentity,

    pub title: String,
    pub subtitle: Option<String>,

    pub kind: SearchResultKind,

    pub score: f32,

    pub source: SearchSource,

    pub icon: Option<IconKey>,

    pub actions: Arc<[ActionDescriptor]>,
}
```

注意：

> 这里缓存的是 ActionDescriptor，不是 ResolvedAction。

---

# 13. 为什么 ActionDescriptor 可以缓存

`ActionDescriptor` 是：

```text
description
```

不是：

```text
authorization result
```

例如：

```text
action:
system.application.open
```

仍需要：

```text
current resolver
```

重新判断：

```text
Ready
Disabled
Hidden
Invalid
```

因此：

```text
cached ActionDescriptor
≠
cached authority
```

---

# 14. 禁止缓存 ResolvedAction

绝对禁止：

```rust
pub struct SearchCacheEntry {
    pub resolved_action: ResolvedAction,
}
```

因为：

```text
cache created
     ↓
capability changes
     ↓
plugin unavailable
     ↓
runtime state changes
```

旧 ResolvedAction 可能已经失效。

---

# 15. 也不缓存 ExecutionId

Cache Entry 不得包含：

```text
ExecutionId
```

每一次真正 Action invocation：

```text
new ExecutionId
```

继续保持：

> each attempt has its own ExecutionId.

---

# 16. Partial Result 的核心问题

SearchCoordinator 支持：

```text
Provider A → 5ms
Provider B → 20ms
Provider C → 300ms
```

可能产生：

```text
Batch 1
Batch 2
Batch 3
```

那么：

> **partial result 是否进入 Cache？**

答案：

## 默认不进入最终 Query Cache。

只有：

```text
final, fully ranked snapshot
```

才可以写入 Cache。

---

# 17. 为什么不缓存 Partial Result

假设：

```text
Batch 1:
Chrome
```

随后：

```text
Batch 2:
Chrome
Edge
Firefox
```

如果缓存 Batch 1：

下一次 query：

```text
Cache hit
```

只能得到：

```text
Chrome
```

而不是完整结果。

这会把：

```text
partial state
```

错误地当成：

```text
search state
```

---

# 18. Partial Results 只存在于 Request Scope

定义：

```text
SearchRequestState
```

只属于：

```text
request_id
```

例如：

```text
Request 100
    Batch 1
    Batch 2
    Batch 3
    Final
```

其中：

```text
Batch 1/2
    = transient

Final
    = cacheable
```

---

# 19. 例外：可选 Prefix Cache

本批次不实现：

```text
partial cache
prefix cache
```

比如：

```text
"chr"
```

不能作为：

```text
"chrome"
```

的候选 cache。

否则会开始涉及：

```text
prefix semantics
ranking equivalence
provider freshness
```

属于另一个优化课题。

---

# 20. Cache Write Boundary

严格定义：

```text
Provider results
      ↓
merge
      ↓
dedup
      ↓
ranking
      ↓
limit
      ↓
FINAL SearchSnapshot
      ↓
Cache.put()
```

因此：

```text
partial batch
    ❌ cache

final snapshot
    ✅ cache
```

---

# 21. Final 的定义

只有同时满足：

```text
all required providers completed
OR
provider reached terminal failure/timeout
```

才可以：

```text
final_batch = true
```

例如：

```text
Application OK
File OK
Recent OK
MCP timeout
Plugin OK
```

这是一个：

```text
final SearchSnapshot
```

因为 MCP 已经进入 terminal timeout。

---

# 22. Cancellation

如果：

```text
q1
```

被：

```text
q2
```

supersede：

```text
q1 cancelled
```

那么 q1：

```text
❌ cannot write cache
```

即使 q1 后台某个 Provider 最后又返回结果，也不能：

```text
Cache.put(q1)
```

---

# 23. Cancelled Request 不污染 Cache

硬规则：

```text
request.status == Cancelled
    ⇒
no cache write
```

这是防止：

```text
old query
late provider result
cache pollution
```

的关键。

---

# 24. Timeouted Provider

如果：

```text
MCP timeout
```

但整个 Search Request 已经完成：

```text
final = true
```

是否缓存？

答案：

> **可以缓存 partial-provider state，但必须把它标记为 degraded final snapshot。**

因此：

```rust
pub enum SearchCompleteness {
    Complete,
    Degraded,
}
```

例如：

```text
Application OK
File OK
MCP Timeout
```

最终：

```text
SearchCompleteness::Degraded
```

---

# 25. Degraded Cache 是否允许 Hit

允许。

但 Cache Entry 必须携带：

```text
completeness = Degraded
```

下一次：

```text
cache hit
```

返回之前应检查：

```text
cache policy
```

第一版建议：

> **Degraded entry 可以短 TTL 使用，但不能像 Complete entry 一样长期存在。**

---

# 26. Degraded TTL

推荐：

```rust
pub struct CacheTTL {
    pub complete: Duration,
    pub degraded: Duration,
}
```

实际数字暂不冻结。

例如设计原则：

```text
Complete:
    longer TTL

Degraded:
    short TTL
```

原因：

```text
MCP / Plugin transient failure
```

不应该让 Launcher 长期重复展示：

```text
missing provider results
```

---

# 27. No Result Cache

No-result 可以缓存：

```text
query = "does-not-exist"
```

因为：

```text
empty result
```

本身是一个有效 snapshot。

但必须：

```text
short TTL
```

因为：

```text
new app installed
new file indexed
```

可能马上让结果发生变化。

---

# 28. Negative Cache

建议：

```rust
SearchCacheEntryKind::Negative
```

或者：

```text
results.len() == 0
```

但不要单独创建一套缓存系统。

统一：

```text
SearchSnapshot
```

即可。

TTL：

```text
short
```

---

# 29. Empty Query Cache

Empty Query 特殊。

当前：

```text
Pinned/Favorite
Recent/Frequent
```

都是动态数据。

虽然 generation 已经能保证：

```text
Favorite changes → user_state_generation
```

但 Recent usage 本身可能频繁变化。

所以：

> **Empty Query 可以缓存，但 TTL 应显著短于 Normal Query。**

或者：

```text
empty query
→ no cache
```

第一版我建议：

```text
Empty Query = cacheable
```

但：

```text
short TTL
```

因为 Empty Query 是 Launcher 打开后的第一屏。

---

# 30. Cache Hit 不直接完成 Search Lifecycle

即使命中：

```text
Cache hit
```

仍应该产生：

```text
SearchStarted
SearchResults
SearchCompleted
```

这样 UI/Diagnostics 无需知道：

```text
provider path
```

还是：

```text
cache path
```

---

# 31. Cache Hit 与 SearchRequestId

Cache entry 原来的：

```text
request_id
```

绝不能复用。

例如：

```text
cached request_id = 100
```

新 query：

```text
new request_id = 200
```

Cache hit 后：

```text
returned snapshot
    request_id = 200
```

否则违反 Query Supersession 语义。

---

# 32. Snapshot Generation

Cache snapshot 应保留：

```rust
pub struct SearchSnapshotContext {
    pub file_generation: IndexGeneration,
    pub application_generation: ApplicationCatalogGeneration,
    pub user_state_generation: UserStateGeneration,
    pub context_generation: ContextGeneration,
    pub completeness: SearchCompleteness,
}
```

因此 Debug 时可以知道：

```text
result belongs to which data state
```

---

# 33. Stale Cache Rejection

Cache lookup：

```text
get(key)
```

本身已经通过 generation key 避免大部分 stale。

但是仍然需要第二道保护：

```text
entry.snapshot.context == current generation tuple
```

必须一致。

即：

```text
key matches
AND
snapshot generation matches
```

才允许返回。

---

# 34. 为什么要双校验

防止：

```text
serialization bug
manual cache insertion
migration bug
test fixture error
future key change
```

造成：

```text
key says fresh
snapshot says old
```

最终：

```text
reject cache
```

而不是冒险使用。

---

# 35. Stale Cache Handling

发现 stale：

```text
Cache.get()
    ↓
generation mismatch
    ↓
remove entry
    ↓
miss
```

不要把 stale entry 返回给 SearchCoordinator。

---

# 36. LRU

缓存使用：

```text
LRU
```

按：

```text
last access
```

进行淘汰。

每次 hit：

```text
entry
    ↓
touch
    ↓
most-recently-used
```

---

# 37. 为什么不 LFU

Launcher query：

```text
chrome
code
calc
notepad
```

非常容易存在高频 query。

但 LFU 会长期保留：

```text
历史 query
```

即使用户最近已经不再使用。

LRU 更符合：

> **短时间内重复搜索的 locality。**

---

# 38. Two-level Budget

必须至少：

```text
max_entries
max_bytes
```

两个限制同时存在。

例如：

```text
1024 entries
32 MiB
```

只是结构示例，不是最终默认值。

---

# 39. Entry Size

不能只计算：

```text
sizeof(SearchCacheEntry)
```

因为：

```text
String
Vec
Arc
ActionDescriptor
subtitle
```

都有 heap allocation。

建议：

```rust
fn estimated_size_bytes(entry: &SearchCacheEntry) -> usize
```

统一计算：

```text
owned string bytes
result count
action count
metadata
```

---

# 40. Arc 不等于零成本

即使：

```rust
Arc<[SearchResultSnapshot]>
```

仍然要统计 cache 拥有的底层 allocation。

不能：

```text
size = size_of::<Arc<_>>()
```

否则会严重低估 cache memory。

---

# 41. Large Result Protection

单条 SearchSnapshot 如果：

```text
size_bytes > max_entry_bytes
```

则：

```text
do not cache
```

例如：

```text
huge plugin result
```

不能因为：

```text
global cache = 32 MB
```

就吃掉：

```text
31 MB
```

的单个 entry。

---

# 42. Cache Admission

建议：

```rust
pub enum CacheAdmission {
    Admit,
    RejectTooLarge,
    RejectNonCacheable,
}
```

这样：

```text
large result
degraded state
cancelled request
```

都可以明确处理。

---

# 43. Cache Mutation API

建议：

```rust
pub trait SearchCache {
    fn get(
        &mut self,
        key: &SearchCacheKey,
        current: &SearchCacheGeneration,
    ) -> Option<SearchSnapshot>;

    fn put(
        &mut self,
        key: SearchCacheKey,
        snapshot: SearchSnapshot,
    ) -> CacheAdmission;

    fn invalidate(&mut self, reason: InvalidationReason);

    fn stats(&self) -> CacheStats;
}
```

---

# 44. CacheStats

建议：

```rust
pub struct CacheStats {
    pub entries: usize,
    pub bytes: usize,

    pub hits: u64,
    pub misses: u64,

    pub stale_rejections: u64,
    pub evictions: u64,

    pub writes: u64,
    pub rejected_writes: u64,
}
```

---

# 45. Hit / Miss 定义

必须冻结：

### Hit

```text
key matches
+
generation matches
+
snapshot valid
```

### Miss

包括：

```text
not found
stale
invalid
```

但 diagnostics 最好进一步区分：

```rust
pub enum CacheMissReason {
    NotFound,
    Stale,
    Invalid,
    NonCacheable,
}
```

---

# 46. Cache 与 SearchCoordinator 并发

如果多个 query 同时请求：

```text
same key
```

例如：

```text
request 101
request 102
```

不应该导致：

```text
two identical provider searches
```

是否需要 SingleFlight？

本批次建议：

> **需要。**

---

# 47. SingleFlight

定义：

```text
same SearchCacheKey
        │
        ├── Request A
        ├── Request B
        └── Request C
                │
                ▼
          one underlying search
```

结果：

```text
one SearchSnapshot
```

然后：

```text
A ← snapshot
B ← snapshot
C ← snapshot
```

---

# 48. SingleFlight 与 RequestId

每个 request 仍然有自己的：

```text
SearchRequestId
```

所以：

```text
Request A = 100
Request B = 101
```

共享：

```text
CacheKey
```

但结果发布必须分别经过：

```text
latest request check
```

---

# 49. SingleFlight 与 Cancellation

关键问题：

```text
A starts
B joins
A cancels
```

不能：

```text
A cancellation
→ cancel underlying search
→ B broken
```

所以需要：

```text
subscriber count
```

只有：

```text
all subscribers cancelled
```

才可以取消底层 single-flight operation。

---

# 50. SingleFlight Model

```rust
struct InFlightSearch {
    key: SearchCacheKey,
    task_id: SearchTaskId,

    subscribers: usize,

    state: InFlightState,
}
```

---

# 51. InFlight State

```rust
enum InFlightState {
    Running,
    Completed(SearchSnapshot),
    Failed(SearchError),
}
```

Completed 后：

```text
publish
→ Cache.put
```

---

# 52. InFlight 不等于 Cache

必须保持：

```text
InFlight
    = active computation

Cache
    = completed reusable result
```

不能：

```text
store in-flight result inside LRU
```

---

# 53. Cache Hit 与 SingleFlight 顺序

建议：

```text
Search request
    │
    ▼
Cache lookup
    │
    ├── hit → return snapshot
    │
    └── miss
          │
          ▼
      SingleFlight lookup
          │
          ├── existing → join
          │
          └── none → start
```

不要反过来：

```text
SingleFlight first
    ↓
Cache
```

否则 cache hit 会无意义创建 task。

---

# 54. Cache Write Race

可能发生：

```text
Request A
  ↓
Search snapshot S1

Generation changes
  ↓
N → N+1

A finishes
```

此时：

```text
S1 generation = N
current = N+1
```

必须：

```text
do not cache
```

因为它已经成为 stale。

---

# 55. Critical Race

必须测试：

```text
Search starts at generation N
      ↓
Index changes to N+1
      ↓
Search finishes
      ↓
Search tries Cache.put
```

结果：

```text
Cache.put = rejected stale
```

而不是：

```text
cache old result
```

---

# 56. Cache Lookup Race

另一个场景：

```text
Cache.get(key)
    ↓
hit
```

同时：

```text
generation changes
```

在：

```text
snapshot → UI
```

之前。

因此 SearchCoordinator 仍需在发布前检查：

```text
request current?
generation still valid?
```

这和现有 Query Supersession 是同一个安全边界。

---

# 57. Final Publish Guard

任何 Search Snapshot 到 UI 前：

```text
request_id == current_request_id
```

且：

```text
snapshot generations == current generations
```

否则：

```text
discard
```

---

# 58. Cache 不负责 Publish

Cache：

```text
get
put
evict
```

但：

```text
UI publish
```

属于：

```text
SearchCoordinator
```

这样 Cache 不知道：

```text
UI
request supersession
```

---

# 59. Cache 不知道 Provider

Cache 禁止依赖：

```text
ApplicationProvider
FileProvider
MCPProvider
PluginProvider
```

它只处理：

```text
SearchCacheKey
SearchSnapshot
```

---

# 60. Cache 不知道 ActionResolver

Cache 禁止：

```text
ActionResolver
launcher-action
```

因为：

```text
Search Cache
    = pure result reuse
```

不是执行层。

---

# 61. Cache 不知道 Index internals

Cache 只使用：

```text
IndexGeneration
ApplicationCatalogGeneration
UserStateGeneration
ContextGeneration
```

而不是：

```text
SQLite connection
Index tables
Catalog DB
File watcher
```

# 67. TTL 与 Generation

Generation 是：

```text
correctness
```

TTL 是：

```text
freshness optimization
```

两者不能混淆。

即使：

```text
TTL = 10 minutes
```

只要：

```text
generation changed
```

必须立即失效。

反过来：

```text
generation unchanged
```

TTL 到期：

```text
cache miss
```

建议使用：

```text

```

而不是：

```text

```

进行 TTL 判断。

```text
not supported
```

所以没有必要担心：

```text

```



# 132. Cache Security Rule

新增：

### `INV-CACHE-001`

Cache stores Search Snapshots only.

### `INV-CACHE-002`

Cache never stores `ResolvedAction`, `Effect`, `ExecutionId`, runtime handles, or protocol sessions.

### `INV-CACHE-003`

A cache hit never bypasses ActionResolver/ActionEngine.

### `INV-CACHE-004`

Stale generation snapshots are never published.

### `INV-CACHE-005`

Cancelled/superseded requests cannot populate cache.

### `INV-CACHE-006`

Partial search batches are not cacheable.

### `INV-CACHE-007`

Cache memory usage is bounded.

### `INV-CACHE-008`

Cache failure never causes Search failure.

### `INV-CACHE-009`

SingleFlight cancellation is subscriber-aware.

### `INV-CACHE-010`

# 154. 最终架构原则

P2.2-B 完成后，系统中存在四种完全不同的状态：

```text
Index state
    “文件索引现在是什么版本？”

Catalog state
    “应用目录现在是什么版本？”

User state
    “用户偏好/使用行为现在是什么版本？”

Search cache state
    “对于上述状态组合，最近一次最终搜索结果是什么？”
```

因此 Query Cache 不需要主动知道：

```text
文件怎么变化
应用怎么发现
Favorite 怎么存
Context 怎么计算
```

它只需要知道：

```text
generation tuple
```
