# P2.3-D — Performance / Memory Closure

进入 **P2.3-D**。

这一批的定位与前面不同：P2.3-C 证明“出问题能恢复”，D 要证明：

> **在 Release 构建、真实数据规模和长期运行条件下，Launcher 仍满足启动、搜索、索引、内存和资源占用预算。**

本批次**不新增功能**，也不进行性能导向的大规模架构重构。发现性能问题时，优先做局部优化；只有违反既有架构契约的瓶颈才允许进入设计修正。

# 2. D1 — Performance Contract

先冻结指标定义，再测数值。

不要直接写：

```text
search < 10ms
```

而应先明确：

```text
用户操作
→ 测量起点
→ 测量终点
```

否则不同版本的 benchmark 不可比较。

# 21. D12 — Performance Regression Gate

以前性能主要是：

```text
report
```

现在必须变成：

```text
gate
```

建议基线文件：

```text
benchmarks/
├─ release-baseline.json
├─ dataset-small.json
├─ dataset-medium.json
└─ thresholds.json
```

Threshold 不建议一开始卡得过死。

例如：

```json
{
  "startup_p95_max_regression": 0.10,
  "search_p95_max_regression": 0.15,
  "memory_max_regression": 0.10
}
```

即：

```text
baseline + 10~15%
```

才 FAIL。

这样可以减少机器噪声导致的 flaky performance CI。

---

# 22. Baseline 与 Threshold 分离

必须区分：

```text
Baseline
```

和：

```text
Budget
```

### Baseline

当前已测：

```text
当前 Release
```

实际性能。

### Budget

产品允许的上限：

```text
Cold start ≤ X
Search p95 ≤ Y
Idle memory ≤ Z
```

因此：

```text
Baseline ≠ Budget
```

否则某一次性能已经很差，也可能因为“与自己一致”而永远 PASS。

# 27. P2.3-D 最终状态

完成后，P2.3 的状态会变成：

```text
P2.3-A
Architecture Frozen
        ✅
        ↓
P2.3-B
Product Flow Verified
        ✅
        ↓
P2.3-C
Reliability / Recovery Verified
        ✅
        ↓
P2.3-D
Performance / Memory Verified
        ✅
        ↓
P2.3-E
Security / Trust Boundary Closure
```

这里有一个顺序上的关键点：

**P2.3-D 不应该为了达到 benchmark 数字而提前改变 Action、Resolver、Runtime、MCP Session 等基础契约。**

正确关系是：

```text
Architecture Contract
        ↓
Correctness
        ↓
Reliability
        ↓
Performance optimization
```

而不是：

```text
Performance
 ↓
破坏边界
 ↓
重新补安全/一致性
```

## 本批次第一实施步骤

建议先只实施 **D1 + D2**：

```text
D1 Performance Contract
D2 Release Benchmark Harness
```

然后用**实际 Release 构建跑第一轮全量 benchmark**，得到第一版：

```text
Launcher 1.0 Candidate Baseline
```

再根据数据决定哪些项目需要优化、哪些直接冻结。

**不要先凭经验拍性能数字。** 这一批最重要的产物不是“某个测试跑了 3ms”，而是建立一个以后每次 Release 都能复现、比较、阻断回归的性能测量体系。
